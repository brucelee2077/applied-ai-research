## ⚠️ The one structural difference from the m03 pass — read this first

**m01 has no `source.md`.** Verified: `ls sessions/m01-shape-of-data/day-*/` returns
`lesson.html`, `experiment.py`, `log.md`, `expected_output.txt` — and no source. m01 predates
the V8/V9 source+donor compiler; it was emitted by the legacy `_lesson_gen.py` and has been
hand-edited since (the Coach Layer batches, `_shell_migrate.py`).

So **spec §4.2 rule 5 cannot apply here.** That rule says a widget "lands through the
deterministic compiler, not the authoring loop," and its own evidence line is scoped to the
modules that have sources: *"All five target lessons already have a `source.md` (verified: m03
5/5, m04 6/6)."* m01 was never in that set. There is no `compile_lesson.py` path to take.

**Consequence:** these three edits go straight into `lesson.html` by hand. That loses the two
protections the m03 pass leaned on — no gate inspects the edit, and there is no
recompile-to-byte-identical check to prove the diff is scoped. Rules 1–4 still apply in full.

**Replacement protection, since the compiler cannot provide it:**

1. **Diff scope, asserted numerically.** Each lesson gains exactly 3 lines and loses 0.
   `git diff --numstat` must read `3	0	<path>`. Any other number means the edit strayed.
2. **jsdom render, per lesson.** Load the page, assert 0 JS errors, assert 7 `.module-section`,
   assert `data-quest-id` unchanged, assert the checklist still builds 7 rows.
3. **Real-Python cross-check of every claim the widget prints** (Task 5). NumPy 2.4.6 is
   available; each widget's arithmetic is re-derived in Python and diffed against the
   widget's own JS, run under node. This is stronger than the m03 pass had.

## Three verified traps

Each was checked against the real tree, not assumed.

1. **The height-receiver already exists in all three lessons.** `grep -c viz-height` returns 1
   for each; the IIFE is the standard clamped `Math.min(Math.max(d.px,320),3200)` receiver, and
   `.build-embed` CSS is present at lines 207–212. **Do not add either.** Adding a second
   receiver would double-handle every message.
2. **`bcastFrame` / `bcastReload` are live dead references.** All three tails already run
   `document.getElementById('bcastReload')` and `getElementById('bcastFrame')` — currently
   null, so the reload button is a no-op. Give the new iframe those exact two ids and the
   reload button starts working **with zero script edits**. Renaming them instead would mean
   touching a `<script>` in three files for no gain.
3. **`_shelf_audit.py` check 3 flags any embedded-but-unlisted viz page.** The three new pages
   become embedded the moment the lessons are edited, so Task 4 (shelf rows) must land in the
   same pass, or the audit fails. Note the tree currently carries two untracked viz pages from a
   concurrent session (`dk-scaling-dial.html`, `sqrt-dk-knob.html`) — they are **not ours**, are
   embedded by nothing, and must stay out of `TOYS` and out of every commit.

## Phase A — three standalone viz pages

House pattern: copy the chrome from `sessions/viz/embedding-similarity.html` — the newest page,
and the only one authored as an inline-lesson companion, so it ships **zero nav links** (a
`../index.html` back-link inside a Toy Shelf panel loads the whole hub into a small iframe).
Structural precedent for build-once/mutate-attributes drawing: `sessions/viz/positional-collide.html`.

Every page must: be plain SVG with **no `<script src=`**; carry the `viz-height` sender IIFE
verbatim; keep Reader-A register (§5 language rules — no idiom, one idea per sentence); and
satisfy the §4.2 bar, rule 3 above all — **you can break it.**

Keep the Google Fonts `<link>` tags. All 25 existing pages have them; they 403 here and fall
through to the local stack via `var(--body)`. Consistency beats a micro-optimisation.

- [ ] **A1 — `sessions/viz/shape-reshaper.html`** — *day 01, shape and ndim*

  Day 01's stated goal is "read its `shape` and `ndim` out loud". 24 numbered values; three
  sliders `sr-a` / `sr-b` / `sr-c` (each 1–8). Live: product, shape tuple, ndim, and the
  read-out-loud sentence in the lesson's own words ("2 sentences, then 3 words, then 4 numbers
  per word").

  Three states, and the middle one is the real lesson:
  - product ≠ 24 → `ValueError: cannot reshape array of size 24 into shape (5,5)` — the loud break.
  - product = 24 but axis order changed → **legal, and silently different meaning.** Track where
    value 5 lands: under `(2,3,4)` it is sentence 0 / word 1 / feature 1; under `(4,3,2)` it is
    sentence 0 / word 2 / feature 1. Same 24 numbers, no error, different data. This is the
    "batch axis in the wrong place" bug the lesson's own staff-lens callout names.
  - matches `(2,3,4)` → `2 sentences, then 3 words, then 4 numbers per word ✓`

  Presets: `the batch we started with` (2/3/4) · `axes swapped — still legal` (4/3/2) ·
  `one flat row` (24/1/1) · `illegal — 5×5` (5/5/1).

- [ ] **A2 — `sessions/viz/slice-picker.html`** — *day 02, indexing and slicing*

  Uses the lesson's own arrays. Panel A: `x = [10 20 30 40]`, sliders `sp-start` (0–4),
  `sp-stop` (0–4), `sp-step` (1–3) plus a `sp-neg` "count backwards" checkbox. Panel B:
  `g = [[1 2 3],[4 5 6]]` with a row/column toggle and an index slider.

  Four breaks, all true Python semantics:
  - `start ≥ stop` with a forward step → `[] shape (0,)`. No crash, no numbers — an empty batch
    that fails much later.
  - `x[0:3]` misses `40` — the half-open rule the day's goal asks the learner to explain.
  - `x[1:3:-1]` → `[]`. The reversed-slice trap: a negative step with `start < stop` selects nothing.
  - index out of range → `IndexError: index 2 is out of bounds for axis 0 with size 2`.

  Plus the aliasing break, as a live toggle (not a submit button, so rule 1 holds): **write 999
  into the piece you grabbed.** A slice is a VIEW, so the source grid changes; a single index is
  a COPY, so it does not. This reproduces `expected_output.txt`'s
  `batch_view[0,0] = 999 -> data[0] is now [999 1 2 3]`.

- [ ] **A3 — `sessions/viz/seed-recipe.html`** — *day 06, seeds and PRNG*

  The lesson already hands us the recipe: `f(s) = (5·s + 3) mod 16`, and `experiment.py` asserts
  seed 1 → `[1, 8, 11, 10]`. Sliders: `sd-seed` (0–15), `sd-mul` (0–8), `sd-inc` (0–8); modulus
  fixed at 16 so the whole state space is visible. Draw 8 states as a stream, plus a detected
  **period**.

  Four breaks:
  - `mul = 4, inc = 3` → 1, 7, 15, 15, 15… **frozen**. Period 1.
  - `mul = 1, inc = 8` → 1, 9, 1, 9… **period 2**. A data loader that reshuffles the same two ways forever.
  - `mul = 0` → every draw identical after the first.
  - a **no seed** toggle: each re-roll starts somewhere new, so the stream changes every time —
    exactly Part 1 of `experiment.py`, and the reason an unseeded bug never comes back.

  Honesty line, required by §5's "where the analogy breaks down": NumPy's real generator is
  PCG64, not this. State plainly that the widget runs the lesson's hand recipe, not NumPy, so
  nobody hunts for these digits in `experiment.py` output.

  Arithmetic warning: a 32-bit LCG overflows JS's exact-integer range. With modulus 16 the
  products stay tiny, so plain `%` is exact here — but if the modulus is ever widened, switch to
  `Math.imul`.
