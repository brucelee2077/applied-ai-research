Training LLaMA 3 on TPUs
Combining the Parallelisms

This week you met four ways to split a training job across chips. But no single one is enough at scale. Real runs — like training an 8B or 70B LLaMA 3 model on a TPU pod — combine them. Today: how a real config blends data, tensor, and pipeline parallelism so no single resource is the sole bottleneck.

🎯 By the end, you'll be able to: name the four parallelisms and the bottleneck each one solves, read a real 8B and 70B parallelization plan, and explain why serious training always interleaves several of them at once.
1 · WHAT IS ITWhat does "combining the parallelisms" mean?✓
🧭
What this assumes: the four parallelisms from earlier days — data parallel / FSDP (w04-d01), tensor parallel (w02-d04), and pipeline parallel (w04-d03). Today we put them together. No new mechanism to learn — this is a case study.

The problem: one parallelism is never enough at scale

You know how to split a training job in several ways. Each one fixes one problem. But a real model — say an 8-billion or 70-billion parameter LLaMA 3 trained on a TPU pod — hits all the problems at once: it is too big to fit in one chip's memory, its matrix multiplies are too large for one chip to do quickly, and you want to push huge batches through for throughput.

So you can't pick one parallelism. You layer several of them together. That is what today is about.

Quick recap: the four tools

Before we combine them, here is the one-line reminder of each. If any feels unfamiliar, revisit that day's lesson.

  • Data parallel (DP) — copy the whole model onto many chips; give each a different slice of the batch. Fixes throughput: more examples per second.
  • FSDP (fully sharded data parallel) — like DP, but instead of copying the model, you shard (split up) the parameters and optimizer state across chips. Fixes memory: no single chip has to hold the whole model.
  • Tensor parallel (TP) — split one big matrix multiply across several chips, each doing part of the matmul. Fixes big-matmul latency: one huge layer done faster by many chips together.
  • Pipeline parallel (PP) — put different layers on different chips, like stations on an assembly line. Lets you fit a model too tall for one chip by spreading its depth.

The idea: assign each tool to the bottleneck it solves

A bottleneck is the one resource that runs out first and limits everything else. In training there are three big ones: memory (fitting the model), interconnect bandwidth (how fast chips talk), and compute (raw math speed). A good training config points each parallelism at a different bottleneck so none of them is left as the sole limit.

🔗
The training config is just the set of choices that says how many chips go to DP vs. TP vs. PP, and how the model is sharded. It is the plan that blends all four tools into one working job.
📚
Official docs (optional): How to Scale Your Model — Training LLaMA 3 on TPUs (Scaling Book, ch. 6)
2 · INTUITIONAn orchestra, not a soloist✓

Imagine a symphony orchestra. No single section plays the whole piece. Strings, brass, and percussion each cover part of the sound, and the conductor blends them so the music is full and balanced — no one section is overloaded while others sit idle.

🎻🎺🥁
Each parallelism = one section

DP/FSDP, tensor parallel, and pipeline parallel are like strings, brass, and percussion. Each covers a different part of the workload. Alone, none can carry the whole piece.

🎼🧑‍🎤
The config = the conductor

The training config blends the sections so no single resource — compute, memory, or interconnect bandwidth — is the sole bottleneck. Balance, not a soloist, is the goal.

In one line: real training uses several parallelisms at once, each aimed at a different bottleneck, blended by the config so the whole pod works in balance.

⚠️
Where the analogy breaks: an orchestra plays for beauty; a training config is tuned by hard numbers — chip memory in gigabytes, link bandwidth, and matmul sizes. The "right blend" is measured, not felt.

4 · HOW & WHYHow the four tools compose, and why you interleave them✓

The rules for blending them

  • FSDP shards for memory. Split parameters, gradients, and optimizer state across chips so no single chip must hold the whole model. This is usually the first thing you reach for when a model won't fit.
  • Tensor parallel wants the fastest links. TP chips talk to each other every layer, so put TP inside a node — the group of chips joined by the fastest interconnect (on a TPU pod, chips wired together with the highest bandwidth).
  • Pipeline parallel spreads across slower links. PP chips only pass data between layer stages, so its communication is lighter. Put PP across nodes, where links are slower but PP can tolerate it.
  • Data parallel sits on top for throughput. Once one full "model replica" is laid out (using FSDP + TP + PP), you copy that layout across more of the pod and feed each copy a different batch slice.
✅
A rough mental picture of a real plan:
TP within a node (fast links) → PP across nodes (fewer, lighter comms) → FSDP to shard memory → DP on top to raise throughput.

Why interleave instead of picking one

  • Each fixes a different bottleneck. FSDP → memory, TP → big-matmul latency, PP → fitting a huge model, DP → throughput. Use only one and a different bottleneck becomes the wall.
  • Match the tool to the hardware. Heavy-communication TP goes where links are fastest; lighter-communication PP goes where they are slower. This is why the layout follows the pod's topology.
  • Balance wins. The goal is that compute, memory, and interconnect bandwidth all run near their limit together — no one resource left as the sole bottleneck.
🔗
Causal chain: model too big + matmuls too large + want high throughput → no single split is enough → assign FSDP/TP/PP/DP each to its own bottleneck → layer them by how much each one has to communicate → a balanced pod that trains 8B and 70B models.
