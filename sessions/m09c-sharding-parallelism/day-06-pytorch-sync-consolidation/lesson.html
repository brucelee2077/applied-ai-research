The problem: two stacks, same ideas

Frontier labs do not pick one framework and stay there. Some teams write JAX, some write PyTorch, and many people move between both across their career. If you only ever learn the JAX words for these ideas, you will freeze the first time a PyTorch codebase uses different words for the exact same thing.

The good news: the underlying distributed-training ideas are framework-agnostic. Only the API vocabulary changes. There are four ideas, and you already know all four from Weeks 2–4:

  • Shard the batch across devices — Data Parallelism (DP). Every device holds a full copy of the model, but sees a different slice of the data.
  • Shard the weights themselves across devices — Fully Sharded Data Parallel (FSDP), also called ZeRO-3. No device holds the full model at once.
  • Shard within one layer's matmul — Tensor Parallelism (TP). One matrix multiply gets split across devices, and they talk to each other mid-layer.
  • Split different layers across different devices — Pipeline Parallelism (PP). Device 1 holds layers 1–8, device 2 holds layers 9–16, and activations flow between them like a factory line.

Enter picotron

picotron is a small reference implementation of exactly these four ideas in PyTorch, written by Hugging Face to be readable start to finish in one sitting — no framework magic hidden behind a giant library. Today you read it and draw a straight line from each of its primitives back to the JAX sharding concepts you already built by hand.

📦
Same four ideas, two spellings: jax.sharding.NamedSharding + PartitionSpec (JAX) vs. picotron's DP/FSDP/TP/PP wrapper classes (PyTorch).
You are not learning new distributed-training theory today — you are learning to recognize the same theory wearing a different outfit.

4The primitive mapping, and why memory math mattersHow & why

The mapping (JAX concept → picotron/PyTorch primitive)

  • Data Parallelism (DP) — JAX: replicate params across a mesh axis, shard the batch with PartitionSpec('data', None). picotron: DataParallel wrapper, gradients averaged across replicas.
  • FSDP / ZeRO-3 — JAX: shard the weight's leading axis with NamedSharding(mesh, PartitionSpec('data', None)) applied to the parameter, not just the batch. picotron: FSDP wrap policy, each device holds a shard of every layer's weights.
  • Tensor Parallelism (TP) — JAX: split a matmul's contracting or output axis with PartitionSpec(None, 'model') and let XLA insert the collective. picotron: TensorParallel column/row-parallel linear layers.
  • Pipeline Parallelism (PP) — JAX: assign layer ranges to mesh axis 'pipe' and hand off activations manually between stages. picotron: PipelineParallel stage split with micro-batches flowing through.
  • All-reduce (gradient averaging) — JAX: explicit jax.lax.pmean inside a pmap'd step. PyTorch: automatic, triggered by DDP's gradient-bucketing hook during .backward().
  • All-gather (reassembling a sharded weight) — JAX: explicit jax.lax.all_gather, or implicit whenever XLA needs a fully-replicated copy of a sharded array to run an op. picotron/PyTorch: FSDP automatically all-gathers each layer's weight shards right before that layer's forward/backward pass, then frees them again afterward.
✅
Same theory, two vocabularies: every picotron class name is doing exactly what a PartitionSpec + collective does in JAX — it's just packaged as an object instead of a spec you pass around.

Why the memory math matters

  • Weights, grads, optimizer state, and activations are four separate memory pools, and each scales differently with model size, batch size, and sequence length.
  • Adam's optimizer state is the trap. Adam keeps momentum and variance — roughly 2x extra copies of the parameters — even if the weights themselves are stored in bf16. Forgetting this multiplier is the single most common reason a training run runs out of memory when inference on the same model would have fit fine.
  • Knowing the four pools tells you which parallelism strategy to reach for. If weights alone don't fit one device: FSDP. If one layer's activations don't fit: TP. If the whole model plus optimizer state still doesn't fit even sharded: PP on top.
🔗
Causal chain: Weeks 2–4 built sharding primitives by hand → picotron shows the same primitives with PyTorch's object-oriented spelling → the memory calculator turns "how much does X cost" into one number you can check against a real device budget.
🪜
Math Ladder — the training-memory calculator
1 · In words: add up the four memory pools — weights, gradients, optimizer state, activations — and compare the total to your device budget to pick a parallelism strategy.
2 · The formula: total = weights + grads + opt_state + activations, where weights = N·bpp, grads = N·bpp, opt_state = N·bpp·(2 if Adam else 0), activations ≈ batch·seq·layers·hidden·bpp — N = params; bpp = bytes/param; hidden = num_heads·head_dim.
3 · Tiny numbers: 7B, bf16 (bpp=2), Adam → weights 14 + grads 14 + opt 28 ≈ 56 GB static; add activations (batch 8, seq 4096) ≈ 34 GB → ≈ 90 GB > 80 GB (one H100) → needs FSDP.
4 · Sanity check: opt_state should be 2× the weights for Adam, regardless of weight dtype. If your total ≈ weights alone, you forgot grads + optimizer state.

The staff lens — one silent failure, one trade-off

The mapping cuts both ways: what PyTorch does for you automatically, JAX makes you write by hand — and the hand-written version is where a quiet scaling bug hides.

⚠️
Failure mode (silent): summing gradients instead of averaging them. PyTorch's DDP averages gradients across replicas for you. The JAX equivalent is an explicit jax.lax.pmean inside the pmap'd step — and it is easy to write jax.lax.psum (sum) by mistake, or to forget the divide. Nothing crashes: shapes match and the loss still goes down, but with 8 replicas your gradients are now 8× too large, which is the same as silently running at 8× the learning rate. The run just trains unstably or converges worse, with no error to point at. A senior engineer checks in code review that the cross-replica gradient collective is a mean (or a sum divided by the replica count), and confirms a 1-device and an N-device run at the same global batch match early loss.
⚖️
Trade-off: memory saved vs. optimizer-state cost you cannot skip. The memory calculator makes one thing unavoidable: Adam keeps momentum and variance — roughly 2× extra copies of the parameters — so a model that fits for inference can still refuse to fit for training. You can trade that away (shard the optimizer state with FSDP, or use a lighter optimizer like SGD or 8-bit Adam) but each choice costs something — more communication, or slower/less stable convergence. In a design review the decision is which of the four memory pools (weights, gradients, optimizer state, activations) to attack first, because forgetting the optimizer-state multiplier is the single most common reason a training run runs out of memory.
🎤
Say this in an interview: "Distributed-training ideas are framework-agnostic — DP/FSDP/TP/PP are the same four in JAX and PyTorch; only the spelling changes (NamedSharding+PartitionSpec and jax.lax.pmean vs. picotron's wrapper classes and DDP bucketing). The memory calculator sums four pools — weights, grads, optimizer state, activations — against the device budget, and the trap is Adam's optimizer state: ~2× extra copies of the params regardless of weight dtype, so a 7B model that infers fine can OOM in training. The silent failure on the JAX side is writing psum instead of pmean — gradients come out N× too big, silently N× the learning rate."
