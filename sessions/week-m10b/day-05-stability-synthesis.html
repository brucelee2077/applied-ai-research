1 · WHAT IS ITOne checklist you run before you press start✓
🧭
What this assumes: you did Days 1–4 of this module. Today adds no new mechanism — it collects what you already know into one ordered list you can actually use.

Why a checklist at all

A big training run is expensive and slow. Once it starts, a mistake can waste days and a lot of money before you notice. A pre-flight stability checklist is a fixed list you go down before pressing start. It turns "I hope this run is set up right" into "I checked every item".

What goes on the list

The items come straight from this module. Set the learning-rate schedule (Day 3). Turn on the stabilizers (Day 2). Make sure checkpoints save often (Day 1). Confirm the hyperparameters were transferred with muP (Day 4). Set up spike detection so a problem is caught early (Day 1).

Two kinds of items: prevent and catch

Some items prevent trouble: warmup, gradient clipping, z-loss. Others catch trouble that slips through: a loss monitor that flags a spike, frequent checkpoints so you can roll back. A good list has both — you cannot prevent everything, so you must also be ready to recover.

The order matters

You go top to bottom, and you do not start until every item is ticked. This is exactly how a pilot works: no skipping, no "I'll check that later". The whole point is that the list is boring and complete, so a tired engineer at 2am still gets it right. Keep going 👇

2 · INTUITIONA pilot going through the pre-flight checklist✓
🧑‍✈️
The pilot

Before every flight, even experienced pilots read a checklist out loud: fuel, flaps, instruments, doors. They do not trust memory. The list is fixed and boring on purpose, so nothing is missed on a bad day. Starting a big training run works the same way.

📋
Each item = one lesson

Every line on the checklist is something that has gone wrong before. "Warmup set?" exists because a cold model spiked once. "Clipping on?" exists because a huge gradient exploded a run. The list is the memory of past crashes.

In one line: the stability checklist is a pilot's pre-flight list for training — a fixed, ordered set of checks you complete before starting, so no known failure catches you by surprise.

You have already learned every item. Today you just put them in order and practice running the list, so that setting up a real run becomes calm and routine instead of anxious guessing.

⚠️
Where the analogy breaks: a pilot's checklist is the same on every flight. A training checklist changes with the model — a small model may skip muP, a huge one must not. The habit of running a list transfers; the exact items depend on the run.

4 · MECHANISM & WHYThe checklist, and why it pays for itself✓

The checklist itself

Here is a compact pre-flight stability list. Each line names what it guards against and the day it came from.

✅
[ ] warmup + schedule set (cosine or WSD) # no wild first step — Day 3
[ ] gradient clipping on (global norm ≤ C) # cap every step — Day 2
[ ] z-loss / soft-cap on if logits drift # keep logits calm — Day 2
[ ] QK-norm on if attention explodes # safe attention — Day 2
[ ] checkpoints save often # able to roll back — Day 1
[ ] loss monitor + spike detection running # catch it early — Day 1
[ ] hyperparameters transferred via muP # right dials, cheaply — Day 4
[ ] LR ↔ batch size coupled correctly # step matches batch — Day 3

Step 1 — why the list pays off, in plain words

A checklist takes a few minutes. A spike you did not catch can waste days of compute. So even if the list only sometimes saves you, the saving is huge compared to the tiny cost of running it. You can put real numbers on this.

Step 2 — the formula

🧮
expected_waste = p_fail × cost_of_failure
# p_fail = chance the run fails, cost_of_failure = compute lost

Symbols: p_fail = the chance the run hits an uncaught spike. cost_of_failure = the compute you lose when it does. expected_waste = the two multiplied — the average cost you should expect. The checklist lowers p_fail and, through frequent checkpoints, lowers cost_of_failure too.

Step 3 — a worked example

🔢
without list: p_fail=0.30, cost=1000 → expected_waste = 0.30×1000 = 300
with list: p_fail=0.05, cost=100 → expected_waste = 0.05×100 = 5

list cost ≈ a few minutes ≈ 1
saving = 300 − 5 − 1 = 294 units on average

Without the list, you expect to waste 300 units on average. With it, the chance of failure drops (fewer spikes) and the cost of any failure drops too (frequent checkpoints mean a short roll-back). Expected waste falls to 5. The list itself costs about 1. You save around 294 — every run.

🔗
The big picture: this module took you from "my run spiked at 40k steps and I panicked" to "I recognize it, roll back, skip, and I set up guardrails so it rarely happens". The checklist is how a team makes that reliable across many runs and many engineers. That is what training stability really means.
