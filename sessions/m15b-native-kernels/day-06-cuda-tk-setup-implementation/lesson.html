1What is a GPU kernel, and what is ThunderKittens?What is it
🧭
What this assumes: you can read normal Python and C-style code, and you have seen tile programming from the JAX/Pallas side this week. No CUDA experience needed — we start from what a GPU is.

Start with what a GPU actually is

A GPU (graphics processing unit) runs thousands of tiny workers at the same time. Each worker is a thread. Threads are grouped into layers:

  • A warp = 32 threads that all run the same instruction at the same moment (in lockstep).
  • A thread block = several warps that share a small, very fast scratchpad called shared memory.
  • The grid = all the blocks in one launch.
  • A kernel = the function you write that runs on the GPU across this whole hierarchy.

Why writing a fast kernel by hand hurts

By hand you juggle raw thread indices, memory addresses, and hardware instructions like WGMMA (the Hopper matrix-multiply instruction) and TMA (Tensor Memory Accelerator — a hardware unit that copies tiles of memory in the background so compute and data movement overlap). Get one index wrong and you get garbage or a crash.

ThunderKittens: think in tiles, not threads

ThunderKittens (TK) is a small header-only C++/CUDA library from Stanford Hazy Research. It hides the pain behind one idea: the tile — a small fixed-size 2D block of numbers (the base is 16×16) that TK treats as a single value. Instead of "thread 137 loads element 4,092," you say "load this 16×16 tile, matrix-multiply it, exponentiate it, store it."

📦
Why 16×16? Because that is the shape the GPU's matrix-multiply hardware natively consumes, so tiles map straight onto the fast instructions — nothing is wasted.
Two tile homes: a register tile (rt, ultra-fast per-thread registers, warp-level) and a shared tile (st, block-level shared memory). Ops read like PyTorch but the destination comes first, assembly-style: mul(c,a,b), mma_AB(d,a,b,d), load/store, exp, sum.

The kernel you build: linear attention

Standard attention costs O(n²) in sequence length n because every token attends to every other token. Linear attention rewrites the math so cost grows linearly (O(n)): it keeps a running state matrix S that summarizes all past tokens; each new token updates S and reads from it. It is memory-bound and awkward — exactly why TK highlights it. The TK paper reports beating the strongest prior linear-attention kernel by 14×.

Why the strict toolchain?

TK is bleeding-edge. It needs CUDA 12.8+ (the toolkit with the NVIDIA compiler, libraries, and drivers) and g++-11 (a C++ compiler new enough for C++20 concepts — a language feature TK uses to type-check tiles at compile time). Wrong versions means it will not compile, so you pin them first.

📚
Official sources: ThunderKittens paper (arXiv 2410.20399) · TK GitHub repo · TK blog post · CUDA install guide (Linux) · CUDA docs
2A giant kitchen full of line cooksIntuition

Picture cooking in a huge industrial kitchen. Each thread is one line cook who can only do simple steps. A warp is a team of 32 cooks who must all do the exact same step at the exact same moment. A block is a station where 32-cook teams share one prep counter (shared memory). The whole kitchen is the grid.

🧑‍🍳📋
Raw CUDA = manage every cook by name

"Cook 7, pick up tomato 412." Exhausting and error-prone. One wrong number and the whole dish is ruined.

🍱➡️🔥
ThunderKittens = give tray-level orders

TK hands you standard prep trays — each holds a 16×16 grid of ingredients (a tile). You say "chop this tray," "combine these two trays." Trays are sized to fit the fastest machine (the matrix-multiply unit) exactly.

And the conveyor belt: TMA refills the next tray while the current one is being cooked, so the cooks never stand waiting for ingredients.

In one line: raw CUDA orders individual cooks; TK orders whole trays that already fit the machines, so almost no effort is wasted.

⚠️
Where the analogy breaks: real trays are passive, but a TK tile is tied to a specific hardware home (registers vs. shared memory) — order an op that doesn't match where the tile lives and the compiler refuses. Also, warp cooks cannot quietly go off-script; true lockstep has no kitchen equivalent where one cook can just pause.

4How TK maps onto the hardware, and why linear attention is fastHow & why

The rules of TK

  • You think in tiles, not threads. The base tile is 16×16 because that is what the tensor-core matrix unit consumes natively.
  • Every tile has a home: rt = register tile (per-thread registers, warp-level, tiny + fastest) or st = shared tile (block-level shared memory, bigger + shared across warps). Ops must match the tile's home or the compiler rejects them.
  • Ops are destination-first, assembly-style: mma_AB(d, a, b, d) = matrix multiply-accumulate into d; also load/store, exp, mul, reductions like sum.
  • TK organizes helpers at three hardware levels: warp (16×16 tiles + parallel ops), block (a template to overlap async TMA loads with compute across warps), and grid (helpers to hide launch/teardown cost).
✅
zero(S);   mma_AB(S, k_t, v, S);   mma_AB(out, q, S, out);
"Clear the state tile S, accumulate kᵀv into it, then read it back with q." That is one step of linear attention in three tile ops.

Why linear attention is O(n), not O(n²)

  • Standard attention builds the full n×n score matrix QKᵀ — every token sees every token, so cost grows with n².
  • Linear attention keeps a fixed-size state matrix S (shape d×d). Each token does two things: S += kᵢᵀ vᵢ (fold this token into the summary) and outᵢ = qᵢ · S (read the summary). No growing square, so cost grows with n.
  • It is memory-bound — lots of small updates, little raw math — which is exactly the case where clever tile + TMA overlap wins big.

Why the strict versions, not "close enough"

  • CUDA 12.8+ / -arch=sm_90a — TK targets Hopper (H100) instructions like WGMMA and TMA. An older arch flag runs the wrong instruction path or fails to compile.
  • g++-11 + C++20 — TK "runs on concepts," a C++20 feature it uses to type-check tiles at compile time. A pre-C++20 compiler cannot compile the tile types at all.
🔗
Causal chain: pin CUDA 12.8 + g++-11 → TK's C++20 tile types compile → write attention as 16×16 tile ops (mma_AB, exp, sum) → the block template overlaps TMA loads with compute → fast and correct, verified against PyTorch.

The staff lens — one silent failure, one trade-off

The whole kernel hinges on the state tile S being clean at the right moment, and on knowing what linear attention gives up for its O(n) cost.

⚠️
Failure mode (silent): forgetting to zero(S), so the state carries over. The state tile S is accumulated with mma_AB(S, kᵀ, v, S). If you skip the zero(S) at the start of a sequence — or reuse the same S buffer across batch items or across kernel launches without resetting it — S still holds leftover kᵀv from a previous sequence. The kernel runs, produces full-shaped output, and it looks reasonable, but every token has silently attended to tokens from an unrelated sequence. There is no crash; only a careful diff against the PyTorch reference exposes it. A senior engineer checks in code review that S is zeroed exactly once per sequence, before the first accumulation, and verifies with a two-sequence test that swapping the order of sequences does not change either result.
⚖️
Trade-off: linear attention buys O(n) cost by giving up exact softmax recall. Compressing all past tokens into a fixed d×d state S is what makes cost grow linearly and long contexts affordable. The price is that S is a lossy summary — it cannot represent an arbitrary token-to-token attention pattern the way the full n×n softmax matrix can, so tasks that need precise lookup of a specific earlier token (exact copying, retrieval) can lose quality. In a design review you decide whether the workload tolerates a summarized history, or whether the exact-but-quadratic softmax attention is worth its cost.

7Write a linear-attention TK kernel and verify itProduce

Today's artifact: a custom linear-attention CUDA kernel written in the ThunderKittens DSL, compiled natively, with a Python harness that checks it against a PyTorch baseline. This is a reproducible coding experiment — code, a run command, and a clear pass/fail result.

Acceptance criteria (all checkable)

  • nvcc --version reports CUDA 12.8+ and g++ --version reports 11.x (recorded in the README).
  • The reference kernels/gemm/bf16_h100 example compiles and runs via make && make run (proves the toolchain works before you write your own kernel).
  • make on your custom kernel completes with exit code 0 and no C++20/concepts errors.
  • python verify_linear_attn.py prints max abs diff below tolerance (e.g. < 1e-2 for bf16) vs the PyTorch linear-attention reference, and prints PASS.
  • The harness prints TK vs PyTorch timing; TK is faster (target: a multiple-× speedup on the naive loop reference).
  • The README records exact CUDA/g++/GPU versions, the run command, and the final diff + timing numbers.
