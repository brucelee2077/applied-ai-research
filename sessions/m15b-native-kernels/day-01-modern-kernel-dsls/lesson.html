Modern Kernel DSLs
(ThunderKittens)

People picture a GPU as one giant matrix multiplier. That mental model is wrong, and it makes GPU code slow. Today you flip it: a GPU is a swarm of tiny cores tuned for small 16×16 tiles. ThunderKittens (TK), a C++ library from Stanford, is built around that truth.

🎯 By the end, you'll be able to: say what a kernel DSL is, explain why tensor cores are ~16× faster and eat 16×16 tiles, and describe TK's three abstractions — tiles (warp), a producer-consumer template (block), and a persistent grid.
1 · WHAT IS ITWhat is a GPU kernel, a kernel DSL, and ThunderKittens?✓
🧭
What this assumes: you know what a GPU is (a chip with many cores). No prior kernel, CUDA, or C++ experience needed. Every term below is defined the first time it appears.

Start from the words

A GPU kernel is a small program that runs on the graphics card. The CPU launches it, and thousands of tiny cores run it at the same time. A kernel is how you tell the GPU to do one specific piece of math — for example, multiply two matrices.

You can write a kernel by hand in CUDA — NVIDIA's low-level language for the GPU. CUDA is powerful, but painful: you manage the memory, the threads, and the timing (synchronization) all by yourself. It is easy to get slow or wrong.

What is a "kernel DSL"?

A kernel DSL (domain-specific language) is a smaller, opinionated language or library built on top of CUDA. "Domain-specific" means it is made for one job — here, AI math. It hides the painful parts and shows you only the pieces that matter. Three well-known ones:

  • Triton (from OpenAI) — a Python-like compiler for kernels.
  • CUTLASS / CuTe (from NVIDIA) — a C++ template library.
  • ThunderKittens (TK) — a C++ library from Stanford's Hazy Research group. This is the one we study today.

The one big idea behind TK

People imagine a GPU as one enormous matrix multiplier. That picture is wrong, and it makes kernels slow. The truth: a modern GPU is a collection of many small cores. The fastest units on them are the tensor cores — special hardware blocks that finish a small matrix-multiply in one shot. Tensor cores are built to chew on tiles: small fixed-size blocks of a matrix, natively 16×16 numbers.

⚡
On A100 and H100 GPUs, tensor cores deliver about 16× the math throughput of the general-purpose units.
So the whole game is: keep the tensor cores fed with 16×16 tiles, and spend as little time as possible on everything else (memory loads, softmax, exp).

TK's three abstractions — one per hardware level

A GPU has a hierarchy: nested layers of parallelism. TK gives one tool per layer.

  • Warp level. A warp is a group of 32 threads that run in lockstep. TK's basic data structure is a tile living in registers (fastest, smallest on-chip memory) or shared memory (bigger, a step away). Over tiles you call PyTorch-like ops: load, mma (matrix-multiply-accumulate on tensor cores), exp, mul.
  • Block level. A thread block is a group of warps that share data fast. TK gives a producer-consumer template: some warps ("producers") only load the next tiles from slow memory while other warps ("consumers") crunch the current tiles on tensor cores. The load hides behind useful math.
  • Grid level. The grid is all the blocks launched at once. TK hides the cost of starting/ending blocks (pipeline bubbles) and reuses the L2 cache with a persistent grid.

One more word you'll meet: swizzling — a clever reordering of where tile elements sit in shared memory so the 32 memory banks (numbered 0–31) don't collide. TK does this reshuffling for you.

2 · INTUITIONA GPU is a restaurant kitchen, not one robot chef✓

Picture a giant restaurant kitchen. The tensor cores are specialist line cooks who are unbelievably fast at exactly one thing: turning a standard 16×16 tray of ingredients into a finished dish. They are ~16× faster than the general helpers who chop and stir. The kitchen runs fast only if those specialists never stand idle waiting for trays.

🤖❌
Wrong: one robot chef

If you think the GPU is a single machine you feed whole matrices to, you write slow kernels — the specialists sit half-idle and the trays pile up wrong.

👨‍🍳🍳
Right: a swarm of tile cooks

Many small cooks, each stamping 16×16 trays. Keep every specialist busy with trays and the kitchen hits peak speed. That is the TK mindset.

Where the food lives (memory): registers are the cutting board right in front of the cook — tiny, instant. Shared memory is the counter the whole station shares — bigger, one step away. L2 cache is the walk-in fridge. HBM (global memory) is the delivery truck in the parking lot — huge, but slow to fetch from.

TK's producer-consumer template is like assigning some staff to only run trays from the truck to the counter (producers) while the specialists keep cooking (consumers). The cooks never wait. Swizzling is arranging trays on the counter so two cooks never reach for the exact same shelf at the same instant.

⚠️
Where the analogy breaks: real cooks improvise and handle odd-sized orders. Tensor cores are rigidly fixed to their 16×16 tray shape — feed them anything that doesn't tile cleanly and they refuse or waste effort. Also, kitchen staff chat freely; GPU warps must synchronize with strict, explicit barriers or they corrupt each other's data.

4 · HOW & WHYThe three abstractions, and why they matter✓

The rules, level by level

  • Warp — tiles. A tile is a 16×16 (or a multiple) block of numbers. It lives in registers (~64KB, ~130 TB/s) or shared memory (~227KB, ~33 TB/s). You write PyTorch-like ops over tiles: load, mma, exp, mul, cumsum. The mma op is the one that runs on the fast tensor cores.
  • Block — producer/consumer. Producer warps only load the next tiles from slow memory into buffers. Consumer warps only compute (mma) on tensor cores. Because the load and the math run at the same time, the slow load hides behind useful work.
  • Grid — persistent. Launching and ending blocks costs time (a pipeline bubble). A persistent grid keeps blocks alive to hide those bubbles and to reuse the L2 cache across tiles.
✅
The one number that dominates: tensor cores are ~16× faster than general units.
So every design choice in TK — tiles, producer/consumer, persistent grid — exists to keep those tensor cores busy and hide everything else.

Why this is the whole game

  • Feed the fast units. If tensor cores idle even a little, you leave most of the chip's speed on the table. Tiling into 16×16 is what lets you feed them.
  • Hide the slow loads. Memory from HBM is far slower than compute. The producer-consumer overlap turns "load, then compute, then load" into "always computing."
  • One tool per level. Tiles (warp), producer-consumer (block), persistent grid (grid). Three abstractions map onto the three layers of the GPU — that is the entire ThunderKittens philosophy.
🔗
Causal chain: GPU is a swarm of cores → tensor cores are ~16× faster but only eat 16×16 tiles → tile the matrix and keep the tensor cores fed → overlap loads with producer/consumer → hide bubbles with a persistent grid → peak throughput.

The staff lens — one silent failure, one trade-off

The three abstractions only pay off if the tensor cores stay fed with clean 16×16 tiles — and the ways that quietly fails are exactly what a reviewer looks for.

⚠️
Failure mode (silent): the tensor cores never ran, but the answer is still right. Your kernel compiles, runs, and returns the correct matrix — yet the shapes did not tile cleanly into 16×16, so the work silently fell back to the slow general units (or masked off partial tiles). Nothing crashes; the numbers are correct; you just quietly lost the ~16× speedup and think TK "didn't help". A senior engineer checks in code review that the matmul dimensions are actual multiples of the tile size and that a profiler confirms the mma (tensor-core) path is the hot path — not exp, loads, or a scalar fallback.
⚖️
Trade-off: writing in tiles buys peak throughput but costs generality and portability. TK's tile-shaped model wins when your op is a big, regular, tensor-core-friendly matmul. You pay for it: your code is now tied to a specific tile size and hardware generation, and memory-bound or irregular ops (heavy exp/softmax, tiny or ragged shapes) get little from it while still carrying the complexity. In a design review the real question is whether the op is compute-bound enough to earn a hand-tiled kernel, or whether a simpler library call is the right call.
