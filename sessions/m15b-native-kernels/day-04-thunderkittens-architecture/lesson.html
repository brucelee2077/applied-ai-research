A quick refresher: the three physical levels of a GPU

A GPU chip is divided into Streaming Multiprocessors (SMs) — think of them as the chip's independent "workshops." Work is launched as a grid of thread blocks. Each thread block runs on one SM, and is split further into warps — groups of 32 threads that all execute the same instruction in lockstep. Each SM has a small pool of fast on-chip SRAM (shared memory, a few hundred KB), which is far faster than the GPU's big off-chip HBM (its "RAM", tens of GB). The entire game of writing a fast kernel is: keep data in SRAM/registers as long as possible, and overlap slow HBM transfers with fast compute so the chip is never sitting idle.

What is ThunderKittens?

ThunderKittens (TK) is a C++/CUDA embedded DSL — a mini programming language living inside CUDA C++ — built by Stanford's Hazy Research lab (Spector, Arora, Singhal, Fu, Christopher Ré; arXiv 2410.20399, Oct 2024). Its core claim: instead of hand-tuning every kernel with dozens of one-off tricks, you can get near-peak GPU speed from a small, fixed set of abstractions — as long as each one is shaped to match a real, physical level of the GPU.

Today's job: see the three abstractions as ONE system

This week you already met each piece separately:

  • Warp level: a 16×16 register tile — the exact shape a Tensor Core (the GPU's matrix-multiply hardware) consumes in one instruction.
  • Thread-block level: some warps load (via TMA), other warps compute — running at the same time, so memory latency hides behind math (Wednesday's overlap template).
  • Grid level: scheduling support that hides the cost of launching and tearing down thread blocks, so that cost doesn't sit as pure overhead.

Today's catch: these three aren't independent tricks. TK's real contribution is proving that one abstraction per hardware layer, used together, is enough to match or beat CuBLAS (NVIDIA's own hand-tuned matmul library) and FlashAttention-3 — while being dramatically shorter to write. The paper isn't a faster GEMM trick; it's a case for a small, composable toolkit that mirrors the hardware exactly.

Official sources (optional): ThunderKittens paper (arXiv 2410.20399) · ThunderKittens GitHub · Hazy Research blog: Quick TK
2A restaurant kitchen during dinner rushIntuition

Think of a GPU kernel like running a busy kitchen during dinner rush. Each part of the kitchen matches one level of the GPU.

🍽️
Tiles = standard prep trays

Every cook plates ingredients onto the exact same 16×16 tray size, so the grill (the Tensor Core) never pauses to figure out an odd-shaped plate. It just slides trays in and out at full speed.

🏃‍♂️🔥
Overlap = a dedicated runner

One runner only fetches ingredients from the walk-in fridge (HBM) while the cooks (compute warps) keep grilling. Runner and cooks never wait on each other — different jobs, same time.

In one line: the manager (grid scheduling) re-sets tables for the next seating while the last course of this seating is still being eaten, instead of shutting the kitchen down between seatings.

⚠️
Where the analogy breaks: in a real kitchen, the runner and cooks are separate people who can freely improvise. On a GPU, "the runner" and "the cooks" are actually just warps of the same thread block, on the same SM, sharing the same small counter space (SRAM). The overlap only works because TK carefully divides that shared space in advance — there's no free lunch.

4The three abstractions, and why they matter togetherHow & why

The three levels, matched one-to-one to hardware

  • Warp level — register tiles: TK's basic data type is a 16×16 chunk of a matrix living across a warp's 32 registers. Ops like add, mul, mma (matrix-multiply-accumulate), and transpose work on whole tiles, hiding register allocation and Tensor Core instruction selection.
  • Thread-block level — load/compute overlap: some warps are "load" warps (issue async TMA copies from HBM to SRAM); other warps are "compute" warps (run Tensor Core MMAs on tiles already in SRAM). They run at the same time, so the next tile's data is arriving while this tile's math still runs — this is Wednesday's Load-Store-Compute-Finish template, now seen as a reusable abstraction.
  • Grid level — scheduling: launching and tearing down thousands of thread blocks costs real time. TK provides grid-level scheduling support so launch/teardown for a whole wave of work overlaps with blocks that are already mid-execution, instead of sitting as pure overhead.
✅
One abstraction, one hardware layer, each. No layer is optional — a fast tile op with no overlap still stalls on memory; overlap with no tile abstraction still pays reshuffle costs; both with no grid scheduling still pay launch/teardown tax on every wave.

Why it's a real contribution, not a GEMM trick

  • Small and fixed — a handful of tile ops and two scheduling patterns, not dozens of kernel-specific tricks.
  • Composable — the three levels stack: warp tiles feed thread-block overlap, which runs inside grid-level scheduling, with no special-casing between layers.
  • Matches or beats hand-tuned code — the paper reports matching CuBLAS and FlashAttention-3 on GEMM/attention, and beating hand-written baselines by 8× (state-space models) and 14× (linear attention) — because those newer ops had rarely been carefully re-mapped onto all three layers by hand before.
🔗
Causal chain: tiles (Mon) → TMA async loads (Tue) → load/compute-warp overlap (Wed) → today: all three, plus grid scheduling, working as one system → near-peak throughput with far less code.

The staff lens — one silent failure, one trade-off

The whole point of TK is that the three layers only pay off together — using some but not all of them is the quiet way to leave most of the speedup on the table.

⚠️
Failure mode (silent): a partial stack that looks "optimized" but sits far below peak. You adopt TK's tile ops and get a correct, noticeably-faster kernel — but you skipped the load/compute overlap, or left blocks launching per output tile instead of using grid-level scheduling. Nothing errors, the numbers are right, and the kernel is faster than your old code, so it looks done. It is quietly stalling on memory or paying launch/teardown tax on every wave, running at maybe half of what all three layers together would reach. A senior engineer catches this in code review by asking for the achieved-vs-peak (MFU) number and a profile: correct-and-faster is not the same as near-peak, and each missing layer shows up as a specific stall the profiler names.
⚖️
Trade-off: a small fixed abstraction set buys composability and less code, at the cost of the last few percent. TK deliberately offers a handful of tile ops and two scheduling patterns instead of dozens of per-kernel tricks — that is why the three layers stack cleanly and a kernel is a few small functions. You give up the freedom to hand-tune one specific op past what the abstractions express, so a truly bespoke kernel can sometimes still edge out TK on that single op. In a design review the choice is reusable-and-near-peak-everywhere versus hand-tuned-and-maximal on one kernel you must then maintain forever.

7Simulate the overlap's timing win — no GPU neededProduce

Today's task (from the curriculum): ThunderKittens itself needs a CUDA-capable NVIDIA GPU (Hopper-class hardware, for the TMA), which this sandbox almost certainly does not have. Actual compilation is deferred to the weekend, once CUDA 12.8 is set up. Today's artifact is instead a simulation of the abstraction mapping: model the timing math from the playground's demo ②, in plain NumPy/JAX.

Acceptance criteria

  • File exists at sessions/m15b-native-kernels/day-04-thunderkittens-architecture/experiment.py.
  • Models a toy tiled-attention computation over 8 K/V tiles of shape 16×16, using plain NumPy or JAX arrays to stand in for register tiles.
  • Implements two loop versions: (a) no-overlap — load then compute sequentially, with sleep/timer stand-ins for the 200ns/100ns costs from demo ②; (b) overlapped — loads tile i+1 while "computing" tile i, matching walkthrough steps 8–12.
  • Running it prints/plots total simulated time for both versions across a sweep of tile counts (2, 4, 8, 16, 32), showing overlapped time < non-overlapped time for every count ≥ 2, with the gap widening as tile count grows — confirming overlapped converges toward max(load, compute) × N while non-overlapped stays at (load + compute) × N.
  • An assertion confirms the two versions produce matching output tile values — proving overlap changes when work happens, not what is computed.
  • A short docstring at the top states the real-hardware analogy being modeled (TMA async load warps vs. compute warps) and links back to today's sources.
