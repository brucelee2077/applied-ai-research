TPU Architecture
The Matrix Multiply Unit

A GPU is a big room of flexible workers. A TPU is a purpose-built assembly line for one job: multiplying matrices. Today you'll see the piece at its heart — the MXU — and understand why it powers so much modern AI training.

🎯 By the end, you'll be able to: say what an MXU and a systolic array are, explain how a TPU differs from a GPU's SMs, know why TPUs love bf16, and reason about why big-matmul workloads (like transformers) fit TPUs so well.
1 · WHAT IS ITWhat is a TPU, and how does it differ from a GPU?✓
🧭
What this assumes: you can read Python/NumPy and you know what a matrix multiply (matmul) is — rows times columns, summed. No chip or hardware background needed.

Two ways to build a chip that does AI math

Training and running a neural network is mostly one operation, done again and again: multiply two big matrices. Chip designers have two very different ways to make that fast.

First, some words we'll use a lot. Let's define each one right now:

  • A GPU (Graphics Processing Unit) is a chip packed with many small general-purpose engines called SMs (Streaming Multiprocessors). Each SM can run almost any kind of math. They are flexible workers.
  • A TPU (Tensor Processing Unit) is Google's chip, built for one job. Its heart is the MXU (Matrix Multiply Unit): a single hardware block whose whole purpose is to do one big matmul per pass.
  • The MXU is a systolic array: a grid of tiny cells, each of which multiplies two numbers and adds the result to a running total. Numbers flow through the grid step by step, and partial sums build up as they pass — like water pumping through pipes. ("Systolic" comes from the heart pumping in beats.)

The one-line difference

🏭
A GPU is a big room of flexible general workers — you can hand them any task.
A TPU is a purpose-built assembly line for matmul — less flexible, but for that one job it wins on speed and efficiency.

What they share: memory and bf16

Both chips pair their compute with fast memory. Right next to the compute there is a little on-chip memory, and further out there is HBM (High-Bandwidth Memory): stacked memory chips wired for very fast data movement. Compute is useless if you can't feed it data fast enough, so HBM matters as much as the math unit.

Both also love a number format called bf16 ("brain float 16"): a 16-bit floating-point number. Normal floats are 32 bits (fp32). bf16 uses half the bytes, so you can move and store twice as much per second and fit twice as much in memory — for a small loss of precision that neural nets usually tolerate well.

2 · INTUITIONAn assembly line vs. a room of workers✓

Picture a factory that has to multiply matrices all day. You can staff it two ways.

🧑‍🔧🧑‍🔧🧑‍🔧
GPU = a room of flexible workers

Many general-purpose workers (the SMs). Give them any task and they figure it out. Great when jobs vary — but for one repeated job, coordinating them wastes effort.

🏭➡️➡️➡️
TPU MXU = a purpose-built assembly line

Inputs stream in one end. Each station on the line multiplies and adds, passing partial sums along. For the single job of matmul, nothing sits idle — the whole line does one huge multiply per pass.

In one line: when the work is one op done a million times (big matmuls), the assembly line beats the flexible room. That is the TPU's bet.

⚠️
Where the analogy breaks: the MXU's cells don't pass a physical object down a belt. Numbers flow through the grid in a timed rhythm and each cell keeps a running sum — the "product" of the whole line is one finished matmul, not a row of separate items.

4 · HOW & WHYHow the MXU works, and why TPUs suit big matmuls✓

How the MXU does a matmul

  • The MXU is a grid of tiny cells. Each cell does one multiply-accumulate: take two numbers, multiply them, add the result to the sum it's already holding.
  • One matrix is loaded into the grid. The other matrix streams through, row by row, on a timed rhythm — staggered so each cell gets its inputs at the right beat.
  • As numbers pass, partial sums flow with them and grow. When a stream reaches the far edge of the grid, its running total is one finished entry of the output matrix.
  • Because the data keeps moving and every cell stays busy, one pass computes a whole block of the result — this is why it is so efficient for large matmuls.
✅
The grid does the work; you feed it. Once matrix data is loaded, the MXU chews through a big matmul with almost no idle cells and almost no extra instructions — that is the whole design goal.

Why this shape wins for AI

  • The workload matches the machine. Transformer training is dominated by big matrix multiplies (attention and feed-forward layers). A machine built for exactly that op runs it near peak efficiency.
  • bf16 doubles throughput. Half the bytes per number means the MXU and HBM move twice as much data per second, and twice as much fits in memory — with precision loss that training usually tolerates.
  • Fewer moving parts. A GPU's flexible SMs must be scheduled and fed with general instructions; the MXU's fixed dataflow avoids much of that overhead for its one job.
🔗
Causal chain: AI training is mostly big matmuls → build a chip whose core (the MXU / systolic array) does exactly that op → keep it fed with HBM and bf16 → get high, efficient throughput on the workloads that matter.

The staff lens — one silent failure, one trade-off

A TPU is fast only when the workload is the shape it was built for; feed it the wrong shape and it stays quietly slow with no error at all.

⚠️
Failure mode (silent): tiny matmuls that leave the MXU mostly empty. The MXU is a fixed grid — say 128×128 cells. If your matrix dimensions are much smaller than the grid (a small batch, a narrow layer, or a per-example loop), the extra cells sit idle but the pass still takes the same number of beats to drain. The code runs and gives correct answers, but you get a small fraction of peak throughput and no warning. In code review, a senior engineer checks that matmul dimensions (especially batch and the contracted dimension) are large multiples of the MXU tile size, and flags per-example or tiny-batch loops that starve the grid.
⚖️
Trade-off: fixed-function speed vs. flexibility. A GPU's general SMs run almost any code; the MXU only does one op — matrix multiply — extremely well. You gain near-peak efficiency and lower overhead on the matmul-heavy work that dominates transformer training, and you give up the freedom to run irregular, branchy, or non-matmul kernels efficiently. In a design review, this is the choice between a specialized accelerator that wins on your main workload and a general one that never falls off a cliff on the odd operation.
