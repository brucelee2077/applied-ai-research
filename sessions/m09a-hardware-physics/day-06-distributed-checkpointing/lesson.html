1What is activation checkpointing (remat)?What is it
🧭
What this assumes: Week 2's jax.grad and the sharded ViT from Days 1–5. You know that training needs a forward pass and a backward pass. No prior checkpointing experience needed.

The problem: the backward pass needs to remember everything

When you run a forward pass through a network, every layer produces an activation — the output tensor of that layer, sitting in memory. Normally JAX keeps all of them around, because the backward pass (the part that computes gradients) needs them: the gradient of layer 5 depends on the activation that layer 5 saw.

For a small MLP, that's fine. For a deep transformer with dozens of layers and huge batches, storing every activation from every layer can eat more memory than the weights themselves — and memory is exactly what you spent Day 5 measuring and worrying about.

The answer: throw activations away, recompute them later

Activation checkpointing (also called remat, short for "rematerialization") is a deliberate trade: instead of keeping every intermediate activation in memory, you throw some of them away right after using them in the forward pass. Then, during the backward pass, when you need one of those thrown-away activations, you just recompute it by re-running that piece of the forward pass.

📦
ckpt_fn = jax.checkpoint(fn)  →  only fn's inputs are saved; everything fn computes inside itself gets recomputed during the backward pass instead of stored.
You spend extra compute (re-running forward math) to buy back memory (fewer stored activations).

So what's today's catch?

Recomputing is real, extra work — real extra FLOPs on the accelerator, not a free lookup. You only want to wrap expensive, activation-heavy chunks of your model (like a whole transformer block), not tiny cheap functions. We'll cover why in the playground.

📚
Official docs (optional): JAX Gradient Checkpointing guide · jax.checkpoint API · The Ultrascale Playbook · How to Scale Your Model — Transformers · nanotron (reference distributed trainer)
😕
为什么这里容易卡住 · Why this trips people up: "扔掉再重算"听起来像在做无用功 —— 为什么故意多算一遍反而是好事？很多人想不通这笔账。In plain terms: recomputing sounds wasteful, so people can't see why deliberately doing extra forward work is a win — until they realize that memory, not compute, is often the binding constraint that decides whether the job fits at all.
2Cooking without a photo of every stepIntuition

Imagine cooking a recipe with twenty steps. You could take a photo after every single step, so if you ever need to check what you did three steps ago, you just look at the photo. Or you could skip most photos and, if you need to check step 14, just redo step 14 from what you had at step 10.

📸📸📸
No checkpointing = photo every step

Every activation from every layer stays in memory, ready whenever the backward pass needs it. Fast to "look up" later, but you're storing a LOT of photos.

🔁
jax.checkpoint = redo the step instead

You only keep the photo at a few checkpoints (layer boundaries). Need something from inside? Redo that piece of cooking. Fewer photos stored, more re-cooking done.

In one line: jax.checkpoint keeps only a function's inputs, and recomputes everything it did internally when the backward pass needs it — less memory, more compute.

直觉 / Intuition: 想象做菜时不给每一步都拍照，只在几个关键点拍 —— 需要中间某步时，就从最近的照片重做一遍。The technical point is that jax.checkpoint stores only a function's inputs and recomputes its internals during the backward pass — trading extra FLOPs for much lower peak activation memory.

⚠️
Where the analogy breaks: redoing a cooking step in real life is basically free (a few seconds). Recomputing a forward pass on an accelerator is genuinely expensive — real extra FLOPs, real extra time. It is not a free glance at a receipt; it is real, billed, extra work.

4The rules of remat, and this weekend's two jobsHow & why

Saturday: leave the simulator

All week you've sharded arrays across 4 simulated local devices on one machine (Day 4). That's great for learning the API, but it never tests real network links between physically separate accelerators. Saturday's job: provision an actual multi-GPU (or multi-host) setup — a cloud instance with real GPUs, or a documented plan if you don't have cloud access — and deploy this week's sharded ViT onto it for real.

Sunday: the rules of jax.checkpoint

  • jax.checkpoint(fn) (alias jax.remat(fn)) returns a new function. Only fn's inputs are saved for the backward pass; everything computed inside fn is recomputed instead of stored.
  • It is transparent to autodiff: jax.grad(loss_fn) still works exactly the same on top of it. You don't change your training loop at all.
  • The change to your code is one line: wrap the function, nothing else moves.
  • For a real stack of layers, pair it with jax.lax.scan so you don't unroll 20+ blocks in Python — scan applies the checkpointed block repeatedly and stays fast to trace and compile.
✅
block_ckpt = jax.checkpoint(block_fn)
One line. Everywhere you called block_fn(params, x), call block_ckpt(params, x) instead — same math, same gradients, less peak memory, more recompute.

⚠️ The gotcha: remat is not free, and not always a win

Remat only pays off when the wrapped region's inputs are cheap relative to its internal activations. A whole transformer block is a great target: its input is one activation tensor, but internally it computes attention scores, softmax outputs, MLP hidden states — many large tensors. Wrapping a tiny function (like a single add) is pure overhead: you save almost nothing and still pay the recompute cost.

⚠️
Rule of thumb: checkpoint expensive, activation-heavy blocks (transformer layers). Don't checkpoint cheap elementwise ops — there's nothing big to save, only recompute cost to pay.
🔗
Causal chain: Day 5 measured peak memory → activations dominate it in deep models → jax.checkpoint lets you trade FLOPs for memory → bigger batches or bigger models fit in the same hardware budget.
🪜
Math Ladder — the memory-for-compute trade of remat
1 · In words: normally you store every layer's activation; checkpointing stores only a few and recomputes the rest, spending extra forward work to shrink peak memory.
2 · The formula: naive stores O(L) activations; checkpoint every layer → store O(1), recompute each once. The sweet spot — checkpoint every √L layers — gives O(√L) memory for ≈ 1 extra forward pass. (L = number of layers.)
3 · Tiny numbers: L = 100. Naive: store 100 activations. Checkpoint every √100 = 10 layers → store ≈ √L ≈ 20, recompute one segment at a time → about one extra forward pass total.
4 · Sanity check: remat never changes the gradients — jax.grad(remat(f)) == jax.grad(f). If your loss or gradients shift after wrapping, something else broke, not remat.

The staff lens — one silent failure, one trade-off

Remat changes only where compute happens, never the answer — which is exactly why a badly placed jax.checkpoint hides as "training just got slower for no reason."

⚠️
Failure mode (silent): checkpointing cheap functions, so you pay recompute for almost no memory saved. jax.checkpoint is transparent to autodiff, so wrapping the wrong thing never changes the gradients or raises an error — the model still trains correctly. But if you wrap a cheap function (a single add, an activation, a thin layer) whose inputs are as big as its internals, you save almost no activation memory yet still re-run its forward math in the backward pass. Step time goes up and peak memory barely moves, with nothing to catch in a stack trace. In code review, a senior engineer checks that jax.checkpoint wraps expensive, activation-heavy regions (a whole transformer block), not tiny elementwise ops.
⚖️
Trade-off: less peak memory vs. extra FLOPs (and wall-clock time). Remat frees activation memory so you can fit a bigger batch or a bigger model on the same hardware — but the freed activations are recomputed in the backward pass, so you deliberately spend real extra compute and a slower step. In a design review, this is the choice you make when memory is the binding constraint: you accept a slower step to make the job fit at all, rather than shrinking the model or batch.
🎤
Say this in an interview: "Activation checkpointing trades compute for memory: instead of storing every layer's activation for the backward pass, you keep a few checkpoints and recompute the rest during backprop — checkpoint every √L layers and you get O(√L) memory for about one extra forward pass. It's a one-line jax.checkpoint wrap, transparent to autodiff. The nuance is the silent failure: wrap a cheap function whose inputs are as big as its internals and you pay recompute for almost no memory saved — step time rises, peak memory barely moves, nothing errors. So I checkpoint whole transformer blocks, not elementwise ops."
