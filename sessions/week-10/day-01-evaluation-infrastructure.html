Autoregressive Exact-Match Accuracy

Your training loop already reports a loss number. That number is lying to you about how good your model really is. 1 · WHAT IS ITTwo ways to grade a model, and why they disagree✓
🧭
What this assumes: you have a trained addition transformer from Week 9 (it takes "123+456=" and should output "579") and normal Python/pytest fluency. No prior eval-infrastructure experience needed.

The problem: your training loss has been lying to you

Every day this training run has printed a loss number that keeps going down. That number comes from teacher-forced loss: at every position, you feed the model the ground-truth previous digits — even the ones the model itself would have predicted wrong — and ask "how surprised are you by the next true digit?" For input "123+456=" and target "579", teacher forcing feeds the model the true "5", then the true "7", then the true "9" as history, no matter what the model's own guesses were. This is fast — one parallel forward pass — and it's exactly what your training loop's cross-entropy loss measures.

The answer: score it the way it will actually be used

Autoregressive (AR) generation is what happens at real inference time: the model predicts digit 1, that predicted digit (not the true one) gets appended to the input, then it predicts digit 2 conditioned on its own possibly-wrong digit 1, and so on. Exact-match accuracy means the whole generated string must equal the true sum, character for character — one wrong digit anywhere fails the entire example.

📦
Teacher-forced loss asks: "given the correct answer so far, do you agree with the next digit?"
AR exact-match asks: "starting from nothing but the problem, can you produce the whole correct answer yourself?"
Nobody hands a deployed model the correct answer while it's trying to produce that same answer. AR accuracy is the only metric that reflects real usage.

Why the gap exists: error compounding

Addition has carries. A wrong tens-digit early in generation shifts every digit after it, so one bad token can cascade into a totally wrong number — even though teacher-forced loss on that same example can look fine, because each position is still scored against the correct prefix, hiding the cascade. Published work on transformer arithmetic (Nogueira et al. 2021; Lee et al. 2023, "Teaching Arithmetic to Small Transformers") repeatedly shows models reaching near-zero teacher-forced loss while AR exact-match accuracy stays far below 100%, especially as digit length grows. Catching that gap is the whole point of today's build.

2 · INTUITIONGrading long division with vs. without the answer key✓

Imagine grading a student on long division problems, digit by digit.

📖
Teacher-forced = answer key on the page

You write every correct intermediate digit on the page already, and just ask "do you agree this next digit is right?" at each step. The student always looks like they understand, because you keep handing them the answer one line at a time.

✍️
Autoregressive = no answer key

You take the answer key away. The student writes digit 1 from their own work, then must use their own digit 1 to compute digit 2, and so on. Slip on digit 1, and every later digit inherits that mistake.

In one line: teacher-forced grading checks each step against the truth in isolation; autoregressive grading checks whether the whole chain, built entirely on the model's own prior steps, lands on the right final answer.

A driving-test version of the same idea: teacher-forcing is like resetting the car to the perfect position before each phase of a parallel-parking test and asking "would you have signaled here?" — always graded from a pristine state. Autoregressive grading is watching the whole park happen in one continuous attempt, mistakes and all.

⚠️
Where the analogy breaks: a human student who messes up digit 1 can often notice and self-correct using number sense. A transformer doing autoregressive decoding has no built-in "wait, that carry was wrong" instinct — it confidently keeps building on its own mistake unless training specifically taught it to recover. That's why the AR-vs-teacher-forced gap is a real, measurable phenomenon, not a theoretical nitpick.

4 · HOW & WHYThe pytest building blocks, and why this eval matters✓

The building blocks

  • pytest is Python's standard test framework. Functions named test_* are auto-discovered and run; each uses plain assert statements, and pytest rewrites them to give rich failure diffs.
  • @pytest.fixture — reusable setup code, shared across many tests. Today: load a trained checkpoint's params and apply_fn once, not once per test.
  • @pytest.mark.parametrize — runs the same test body once per input case, without duplicating code. Today: run the same accuracy test once per digit-length bucket (1, 2, 4, 8, 12, 16, 20 digits).
  • pytest-benchmark — a plugin adding a benchmark fixture that runs a callable many times, discards warmup, and reports calibrated min/mean/stddev timing. Today it's not about correctness — it answers "can I afford to run full AR eval after every N training steps?"
✅
@pytest.mark.parametrize("num_digits", [1, 2, 4, 8, 12, 16, 20])
One test function, run seven times — once per digit-length bucket — so you get seven separate accuracy numbers, not one blended average that hides length-generalization failure.

Why this matters for the capstone

  • The metric is the contract — every scaling-law curve for the rest of Phase 3 plots accuracy on the y-axis. If that accuracy number is measured the wrong way (teacher-forced instead of AR), every curve you fit is measuring the wrong thing.
  • The gap is diagnostic, not noise — a large teacher-forced-vs-AR gap at high digit counts tells you the model hasn't learned to generalize its carry logic, which is exactly the failure mode Chinchilla-style scaling work needs to see.
  • Speed is a real constraint — AR decoding is sequential (one token at a time), unlike the fully parallel teacher-forced forward pass, so you must know its wall-clock cost before deciding how often to run it during training.
🔗
Causal chain: teacher-forced loss hides error compounding → AR exact-match reveals it → pytest + parametrize turns that into one reliable, repeatable number per digit length → pytest-benchmark confirms you can afford to collect it often enough to fit a scaling law.

7 · PRODUCEBuild the strict AR-accuracy eval harness✓

Today's task (from the curriculum): finalize a pytest-based eval script that grades the addition transformer by strict digit-by-digit autoregressive generation accuracy, not teacher-forced loss — the contract every later scaling-law plot in Phase 3 depends on.

Acceptance criteria

  • A fixture that loads/builds a trained checkpoint and exposes params + apply_fn.
  • A fixture or helper that generates stratified digit-length evaluation batches (buckets: 1, 2, 4, 8, 12, 16, 20 digits).
  • A pure-JAX autoregressive_decode function whose every new digit prediction conditions on the model's own previously generated digits — never on the ground-truth targets. This is the one non-negotiable correctness property.
  • At least one @pytest.mark.parametrize-driven test asserting/reporting strict exact-match accuracy per digit-length bucket.
  • At least one retained teacher-forced-loss test, kept explicitly as a contrast baseline — not as the pass/fail gate.
