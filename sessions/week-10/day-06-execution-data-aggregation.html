Phase 2 · Week 10 · Day 6 (Weekend Lab)

Execution & Data Aggregation
Run the Matrix, Then Harvest It

Monday–Friday you squeezed hardware inefficiency out of one training run. This weekend you stop optimizing and start harvesting: Saturday you fire off the whole grid of training runs and keep them alive, Sunday you pull every run's final loss into one clean table. Today: how that pipeline works and why both halves matter.

🎯 By the end, you'll be able to: describe a run matrix as a list of run configs, wrap a training job in a checkpoint-and-resume retry loop, and turn a folder of per-run JSON results into a clean, NaN-free pandas table ready for next week's power-law fit.
1 · WHAT IS ITWhat is a run matrix, and what is data aggregation?✓
🧭
What this assumes: you already know how to write and run one JAX training loop (Weeks 1–9), and how JAX allocates device memory and caches JIT-compiled shapes. No prior pandas or MLOps experience needed.

The problem: one run is easy, sixty runs is a different job

All week you tuned one training run to be fast. But your Chinchilla-style scaling-law study does not need one run — it needs a whole grid of them: several model sizes N crossed with several data budgets D, maybe crossed with a couple of learning rates too. That grid of jobs is called a run matrix (also called a training-run grid or sweep): one row per job, one column per hyperparameter you are varying. Sweep 6 model sizes × 5 data budgets × 2 learning rates and you get 6×5×2 = 60 separate training runs.

Two new problems show up only at this scale, and neither is new math — both are new engineering discipline:

  • Saturday — execute the matrix. At 60 runs, some will crash: out-of-memory (OOM, when a job asks the accelerator for more memory than it has), a diverging loss, or a cloud instance getting preempted mid-run. You cannot afford to restart a whole 6-hour run from step 0 every time one of these happens.
  • Sunday — aggregate the results. Each finished run leaves behind one number you actually care about (its final loss) plus the metadata that produced it (N, D, maybe compute C = 6ND). Right now that is scattered across 60 separate files. You need it in one clean table.

The answer, part 1: checkpointing for resumability

Checkpointing for resumability means each run periodically writes its optimizer and model state to disk, so a crashed run restarts from its last saved point instead of from scratch. Pair that with memory-usage monitoring — watching the live number of bytes allocated on the accelerator — so you catch a memory leak or an OOM-prone config before it kills an instance and burns cloud budget.

The answer, part 2: pandas and the DataFrame

pandas is a Python library for tabular data — think of it as programmable spreadsheet software. Its core object is the DataFrame: a 2D table with named columns (like N, D, final_loss) and a row index, where each column is backed by a NumPy array so column math vectorizes just like NumPy. Aggregation means reading every run's raw JSON output into one row per run; cleaning means handling the ugly reality — some rows have NaN (Not a Number, logged when a run's loss diverges to infinity), some rows are exact duplicates from reruns, some columns arrive as strings that should be floats.

📦
records = [json.load(open(f)) for f in glob.glob("results/*.json")]
df = pd.DataFrame(records)  →  one row per run, columns run_id, N, D, final_loss.
This is the entire shape of Sunday's job: 60 scattered JSON files become 1 table.

So what's today's catch?

The catch is that "clean the data" is not optional busywork — it is where you decide, explicitly, what happened to every run that did not produce a clean number. Drop a NaN silently and you lose the chance to notice that every run at lr=1e-3 and the two largest N values diverged — which is itself a real finding, not noise.

In one line: Saturday turns 60 independent jobs into 60 completed jobs without losing hours of work to crashes; Sunday turns 60 scattered result cards into 1 table the whole class (next week's power-law fit) can read at once.

⚠️
Where the analogy breaks: student projects don't checkpoint themselves, and a knocked-over volcano doesn't silently write NaN on its result card — your training runs do exactly that when they diverge, and catching those silent NaN cases is most of Sunday's real work. Also, unlike independent fair stations, your runs share hardware (the accelerator/cloud instance), so one badly-behaved run can crash a neighbor sharing its memory — a coupling the gym doesn't have.

4 · HOW & WHYThe rules of execution and aggregation, and why they matter✓

The rules — Saturday

  • Finalize the run matrix before launching — do not add configs mid-execution. Each row is one job: run_id, N, D, lr.
  • Before starting any run, check for an existing checkpoint. If one exists, resume — never restart cold.
  • Save a checkpoint on a fixed step interval (e.g. every 500 steps). The interval bounds how much work a crash can lose.
  • Wrap every job in a retry loop: on exception (OOM, NaN loss, preemption), reload the last checkpoint and try again, up to a max retry count.
  • Watch device-memory usage live — a slow upward creep is a leak; a stable plateau is normal.
✅
state = load_checkpoint(path) if exists(path) else init_state(cfg)
"If this run has a saved checkpoint, resume from it. Otherwise start fresh." This one line is the difference between losing 5 minutes and losing 6 hours when a job crashes.

The rules — Sunday

  • glob.glob("results/*.json") to list every finished run's result file; confirm the count matches the planned matrix size.
  • Load each JSON with json.load, collect into a list of dicts, then pd.DataFrame(list_of_dicts) — one row per run.
  • df.isna().sum() tells you, per column, how many rows are missing a value — usually final_loss for a diverged run.
  • Decide and record a policy for divergent rows (drop vs. clip) — never drop silently.
  • Check df.duplicated(subset=["run_id"]) for reruns; keep the latest, drop the rest.
  • Convert the cleaned N, D, final_loss columns to NumPy arrays with .to_numpy() — next week's curve_fit needs raw arrays, not a DataFrame.

Why it matters

  • Compute is money and time — losing a 6-hour run to a 5-minute OOM, repeated across 60 runs, is the difference between finishing this weekend and blowing past it.
  • NaNs propagate silently — a single NaN in an array corrupts every downstream calculation that touches it, including a curve fit, without raising an error.
  • Dropped rows carry information — a run that diverged because its learning rate was too high for its model size is a different failure mode than a run that never finished. Recording which rows you dropped, and why, preserves that signal for interpreting next week's fit.

Causal chain: profiled step time + hardware efficiency (Mon–Fri) → you can now afford to run the full matrix → checkpointing keeps the matrix alive through crashes (Sat) → pandas turns 60 scattered files into 1 clean table (Sun) → next week's power-law fit consumes that table directly.

7 · PRODUCEExecute the matrix, then aggregate a fit-ready loss table✓

Today's task (from the curriculum) has two artifacts — one per day of the weekend.

Artifact 1 (Saturday) — the executed run matrix with survival evidence

Under experiments/week10_jax/, produce:

  • run_matrix.json (or .py config) — the finalized list of run configs (N, D, lr, run_id) actually executed.
  • results/<run_id>.json — one file per completed run, each with at least run_id, N, D, lr, final_loss, final_step, wall_clock_seconds.
  • logs/execution_log.md — a short operational log: how many runs crashed at least once, the crash cause (OOM / NaN loss / preemption), and confirmation each crashed run resumed from checkpoint rather than restarting cold.

Acceptance criteria: number of files in results/ equals the planned matrix size (no missing runs); execution_log.md states the peak device-memory usage observed and at least one crash-and-resume event (or explicitly states "zero crashes" if true); no run's final_loss is missing without an explanation in the log.

Artifact 2 (Sunday) — the cleaned, fit-ready loss table

Under experiments/week10_jax/, produce:

  • aggregate_results.py — globs results/*.json, loads into a pandas DataFrame, reports row count before/after cleaning, drops/flags NaNs and duplicate run_ids, and writes the final arrays.
  • reports/week10_loss_table.csv (or .npz) — the cleaned table with columns run_id, N, D, final_loss (and C = 6*N*D if compute is tracked), ready for next week's power-law fit.

Acceptance criteria: python experiments/week10_jax/aggregate_results.py runs end-to-end without error and prints a before/after row count that differs by exactly the number of dropped NaN/duplicate rows; the output file exists at experiments/week10_jax/reports/week10_loss_table.csv; every row has a finite, non-null final_loss; the array/column shapes for N, D, final_loss are equal and printed by the script.
