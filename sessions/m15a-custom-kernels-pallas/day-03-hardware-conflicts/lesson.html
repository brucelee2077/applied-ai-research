Hardware Conflicts
SRAM Bank Conflicts in Pallas Kernels

Your Pallas kernel from Mon/Tue can be correct and still be slow — for a reason that has nothing to do with FLOPs. Today: the hardware-level reason a kernel silently serializes its own warps, and the one-line fix (padding a stride) that a lot of production kernels rely on.

🎯 By the end, you'll be able to: compute a shared-memory bank index by hand, explain why a [32,32] tile causes a 32-way bank conflict, fix it by padding to [32,33], and read a profiler trace that shows the difference.
1 · WHAT IS ITWhat is a bank conflict, and why should you care?✓
🧭
What this assumes: you've written a Pallas kernel with a BlockSpec (Mon/Tue this week). No CUDA experience needed — we build every term from zero.

Two kinds of memory on a GPU

Every GPU has two very different places to keep numbers. The big one is HBM (off-chip DRAM) — it holds your whole tensors, but it is slow to reach. The small one is shared memory — an on-chip pool of SRAM, tens of KB up to about 228KB per chip on an H100, that is roughly 100x faster to touch than HBM.

A fast kernel's whole game is: copy a small tile from HBM into shared memory once, then reuse it from shared memory many times. This is exactly the manual memory management that Pallas lets you control with a BlockSpec, instead of leaving it to XLA.

Banks: shared memory is not one big box

To let many threads read at once, shared memory is physically split into banks — 32 of them on essentially every modern NVIDIA GPU, each 4 bytes wide. Which bank an address lands in is simple arithmetic:

📦
bank_index = (byte_address / 4) % 32
Each bank can serve exactly one memory request per clock cycle — no more.

A warp is a group of 32 threads that run the same instruction at the exact same moment. When a warp reads from shared memory, all 32 threads ask for their address in the same cycle.

The problem: a bank conflict

A bank conflict happens when two or more threads in the same warp, in the same instruction, want different addresses that land in the same bank. One bank can only answer one request per cycle, so the hardware splits the access into several sequential steps — roughly N cycles instead of 1 for an N-way conflict. (If two threads ask for the exact same address, that's free — a "broadcast," not a conflict.)

Why this happens in a compiled Pallas kernel

Pallas lets you write kernel logic in traceable Python — pallas_call, BlockSpec, grid, kernel body — which then compiles down to real memory instructions on GPU. The compiler lays your block out in shared memory using the strides you gave it. If your tile's inner dimension is exactly 32 elements of a 4-byte type (a very common shape, like a [32,32] float32 tile read column-wise), every thread in the warp can collide into one single bank — a 32-way conflict, about a 32x slowdown on that one instruction, even though your math is completely correct.

The fix: pad the stride

The decades-old CUDA fix is to pad the tile so its row length is no longer a multiple of 32 — allocate [32,33] instead of [32,32]. That one "ghost" column per row shifts every row by one bank, spreading the warp across all 32 banks instead of piling it onto one. You pay a tiny bit of wasted SRAM for up to a 32x win. This is the "modify the memory striding" step you'll do by hand today in a Pallas kernel.

2 · INTUITION32 teller windows, one tour group✓

Picture shared memory as a bank with exactly 32 teller windows — the 32 banks. A warp is a tour group of 32 people who all walk up at the exact same moment, each wanting to withdraw from their own account.

🏦❌
bank conflict = everyone picks window 7

Because of how their account numbers were assigned, all 32 people want window 7 specifically. Window 7 serves them one at a time while the other 31 windows sit empty. The whole group waits for 32 sequential transactions instead of 1 parallel one.

🏦✅
the fix = re-assign account numbers

Change the memory stride (like renumbering accounts) so the 32 people spread evenly across all 32 windows again. Everyone finishes in one round — the same withdrawal, just laid out differently.

In one line: a bank conflict is 32 threads piling onto one memory bank in the same cycle; padding the stride spreads them back out so each thread gets its own bank.

⚠️
Where the analogy breaks: real teller windows have no "broadcast" freebie. If two GPU threads want the exact same address in the same bank (not just the same bank), the hardware serves both in one cycle for free — like one teller instantly cloning a receipt for two people asking for the identical thing. A literal bank teller can't do that.

4 · HOW & WHYThe rules of bank conflicts, and why they matter✓

The rules

  • Shared memory has 32 banks, each 4 bytes wide. bank_index = (byte_address / 4) % 32.
  • A warp is 32 threads issuing one instruction together. Each needs its own bank in that cycle to avoid serialization.
  • If the tile's row stride is a multiple of 32 elements (e.g. exactly 32 float32s = 128 bytes), a column-wise access across rows collapses onto one bank — an N-way conflict costs roughly N cycles instead of 1.
  • Padding the stride to something not a multiple of 32 (e.g. 33) spreads the same access across all 32 banks — zero conflicts, same data, tiny SRAM cost.
✅
tile = scratch_shape((32, 33), jnp.float32) # pad, don't ever read column 32
"Allocate one extra ghost column per row so the row stride (33) is no longer a multiple of the bank count (32)." Same tile, conflict-free access.

Why it matters

  • Correctness is not enough — a bank-conflicted kernel gives the right numbers but wastes up to 32x on that one instruction, invisible unless you profile it.
  • It's a stride problem, not an algorithm problem — fixing it changes zero FLOPs and zero math, only the physical layout of the tile in shared memory.
  • It's the prerequisite mental model for the rest of Phase 4 — quantized kernels and long-context attention kernels all live or die by memory-access patterns, not FLOPs.
🔗
Causal chain: Pallas BlockSpec (Mon/Tue) → compiler picks a physical shared-memory layout from your strides → a stride that's a multiple of 32 → every thread in the warp collides on one bank → padding the stride breaks the collision → conflict-free, same result, faster.

The staff lens — one silent failure, one trade-off

A bank conflict only costs you speed. Its dangerous cousin — a missing barrier between writing shared memory and reading it back — costs you the answer, and neither one announces itself.

⚠️
Failure mode (silent): the missing barrier (data race). When threads write a tile into shared memory and then read each other's writes, every thread must reach a barrier (a sync point) before anyone reads, or a thread reads a slot its neighbor has not written yet. This is a data race: it does not crash, and it often produces the right answer on small inputs or one hardware queue, because the timing happens to line up. On a different chip, a larger tile, or a different day it returns quietly wrong numbers that you cannot reproduce. In code review, a senior engineer scans every "write shared memory, then read it across threads" pattern and checks there is a barrier between the write phase and the read phase — a green test run is not proof the sync is there.
⚖️
Trade-off: padding for speed vs. spending SRAM you may need. Padding the row stride from 32 to 33 removes the bank conflict for free in FLOPs — but it grows every tile by one ghost column, and SRAM is the scarcest resource on the chip. Spend those bytes on padding and you may be forced to shrink the tile, which lowers arithmetic intensity and can cost more than the conflict you removed. It is also purely a performance fix, not a correctness fix, so it is easy to over-invest in. In a design review, the question is whether this access pattern is hot enough to profile and justify the padding, or whether the SRAM is better spent on a bigger tile.
