1Kernels, memory tiers, MoE, and the fusion ideaWhat is it
🧭
What this assumes: you can write x @ w in JAX and you built an MoE layer in Week 12. No prior kernel-writing experience needed. We start from the word "kernel".

What is a kernel?

A kernel is one small program that runs on the accelerator (GPU or TPU) and does one chunk of math. When you write x @ w in JAX, the compiler quietly picks a pre-made kernel for you. You never see it.

Pallas is a JAX extension that lets you write your own kernel in Python. You decide exactly which slices of the big matrices get loaded from slow memory into fast on-chip memory, what math runs on them, and where the results get written back.

Two memory speeds matter

HBM (High Bandwidth Memory) is the large, slow, off-chip memory where your arrays live — gigabytes, but far away. SRAM (on TPU this is VMEM/registers) is tiny, on-chip, and roughly ~100× faster to reach.

Every kernel is really a story about moving data from HBM into SRAM, computing, and writing back. Reading and writing HBM is the expensive part.

What is MoE?

MoE (Mixture of Experts): instead of one big feed-forward network (FFN), the layer holds many small FFNs called experts. A router sends each token to just one or a few experts. Most experts are skipped per token — that is what "sparse" means. Each expert FFN has two matrices: an up-projection W_up that maps a token vector of size D (model dimension) up to a larger hidden size F (feature dimension, often F = 4·D), then an activation like GELU, then a down-projection W_down that maps F back to D.

The ragged matmul problem

After routing, expert 0 got maybe 30 tokens, expert 1 got 12, expert 2 got 51 — uneven ("ragged") group sizes that change every step. jax.lax.ragged_dot(lhs, rhs, group_sizes) is JAX's built-in primitive for exactly this: lhs is all tokens stacked (M, K), rhs is the stacked per-expert weights (G, K, N) for G experts, and group_sizes is an int array of length G saying how many consecutive rows of lhs belong to each expert. It does G independent matmuls in one call. It is great — but it is ONE matmul. An MoE FFN is TWO (up then down), so calling ragged_dot twice writes the giant (M, F) hidden activation all the way out to HBM and reads it back in.

The fusion idea

Write one Pallas kernel that, for each block of tokens, loads the token block and both expert weights into SRAM, computes h = act(x @ W_up) and y = h @ W_down while h never leaves the chip, and writes only the small (block, D) result to HBM. You skipped a full read+write of the (M, F) intermediate. When F > D, that intermediate is the biggest array in the whole layer, so skipping it saves the most memory traffic — which is exactly why the custom kernel outpaces two ragged_dot calls in that regime.

2The cook who stops carrying the giant trayIntuition

Picture a restaurant kitchen. HBM is the big walk-in freezer down the hall. SRAM is the small counter right next to the stove. Cooking is the matmul.

🚶‍♂️🍱🚶‍♂️
ragged_dot ×2 = two pointless trips

The cook walks to the freezer, grabs ingredients, prepares a HUGE tray (the size-F hidden activation), then carries that entire giant tray ALL the way back to the freezer to store it — only to walk back, haul it out again, and finish it into a small plate. Two trips carrying the biggest object in the kitchen.

🍳🍽️
fused kernel = keep the tray on the counter

The cook keeps the prepped tray right on the counter (in SRAM), finishes it there, and only carries the small finished plate to the freezer. One trip, and the big object never leaves the counter.

In one line: the bigger that middle tray is relative to the finished plate (F > D), the more walking you save — that is the whole benchmark claim.

⚠️
Where the analogy breaks: a real counter can usually hold a whole tray, but SRAM often cannot hold the entire size-F hidden activation at once. So you tile it — process a few columns of F at a time — and the accumulation is more careful than "just leave it on the counter." Also, on hardware you fight for parallel lanes and memory alignment, which the walking analogy ignores.

4The rules of a fused MoE kernel, and why it winsHow & why

The rules

  • A Pallas kernel is launched over a grid of blocks. Each grid instance handles one tile — for example one block of tokens (BM rows) for one expert. It loads only that tile from HBM into SRAM.
  • Inside the kernel you write the math on the tile, not the whole array. You compute h_block = act(x_block @ W_up) and then y_block = h_block @ W_down while h_block stays in SRAM the whole time.
  • group_sizes tells the kernel which weight slab each token block multiplies by. Its length is the number of experts G, and its entries must sum to M (the total number of routed token rows). No padding to a fixed size.
  • If the size-F hidden block does not fit in SRAM, you tile over F: process a few columns of F at a time and accumulate into y_block. The point is that h is still never written to HBM.
✅
Fused: h_block is born, used, and dies inside one pallas_call. Only the thin (BM, D) result y_block is written to HBM.
Two ragged_dot calls instead write the fat (M, F) hidden array out and read it back — that is the traffic we delete.

Why it wins (and when it doesn't)

  • Fusion cuts memory traffic, not FLOPs. The multiply count is the same. What you save is a read+write of the (M, F) intermediate through slow HBM.
  • The saving scales with the intermediate size. When F > D, the (M, F) hidden activation is bigger than the (M, D) output, so deleting its round-trip saves the most — that is why the win grows with F/D.
  • When F ≤ D, fusion can LOSE. The deleted intermediate is smaller than the output, so there is little traffic to save, and the hand-written kernel's launch/tiling overhead can make it slower than the vendor-tuned ragged_dot. Honest engineers scope the claim.
🔗
Causal chain: HBM is ~100× slower than SRAM → the (M, F) hidden activation is the biggest array when F > D → two ragged_dot calls round-trip it through HBM → a fused Pallas kernel keeps it on-chip → less HBM traffic → faster, provably, in the F > D regime.

The staff lens — one silent failure, one trade-off

The group_sizes array is where an MoE kernel goes quietly wrong, and fusing the kernel at all is a bet you should only make in one regime.

⚠️
Failure mode (silent): group_sizes that don't sum to M. group_sizes tells the kernel how many consecutive token rows each expert owns; its entries must total M, the number of routed rows. If a routing bug makes them sum to less than M, the tail rows are never assigned to any expert — those tokens silently get stale or zero output while every shape stays legal and nothing crashes. If they sum to more, the kernel reads past the token buffer. Either way the model still trains and the loss still moves; it just quietly ignores or corrupts a slice of tokens, which is nearly invisible in an average loss. In code review, a senior engineer asserts group_sizes.sum() == M right after routing and checks it stays true after any token dropping or capacity change — not just once at startup.
⚖️
Trade-off: fusion wins only when F > D. Fusing the up- and down-projections deletes the HBM round-trip of the fat (M, F) hidden activation — a real win when the hidden size F is larger than the model dimension D, because that intermediate is then the biggest array. But it cuts zero FLOPs, and when F ≤ D the deleted intermediate is smaller than the output, so there is little traffic to save and your hand-written kernel's launch and tiling overhead can make it slower than the vendor-tuned ragged_dot. In a design review, the honest move is to scope the claim to the F > D regime and benchmark against the library baseline before committing to owning the kernel.

7Write the fused MoE kernel and prove it beats ragged_dotProduce

Today's capstone task: hand-write a fused MoE up/down-projection Pallas kernel, plus a benchmark that proves it beats jax.lax.ragged_dot when F > D. This is a reproducible coding experiment — code, tests, run commands, results, and a short writeup.

Acceptance criteria

  • moe_fused_kernel.py defines a fused kernel via pallas_call that computes y = act(x @ W_up) @ W_down for grouped/ragged expert assignment, keeping the (block × F) hidden activation on-chip (never materialized to HBM).
  • A reference baseline in the same file computes the identical result using two jax.lax.ragged_dot calls (up, then down), both jit-compiled, compared apples-to-apples.
  • test_correctness.py asserts jnp.allclose(fused, ref, atol=2e-2, rtol=2e-2) (bf16 tolerance) across at least 2 random group_size distributions; exit code 0.
  • group_sizes handling is correct: entries sum to M, uneven groups tested (not all-equal), and a same-seed run is deterministic.
  • bench.py sweeps F for fixed D (at least F/D in {0.5, 1, 2, 4}), warms up + times both paths with block_until_ready(), and reports ms per call.
  • The printed result shows fused is FASTER than 2× ragged_dot for at least the F = 4D case, and the README states the measured speedup (e.g. ~1.4–1.5×) and hardware used.
  • The README states honestly where fusion does NOT win (F ≤ D) so the claim is scoped, not oversold.
⚠️
The trap: "proving" fusion wins without actually keeping the intermediate on-chip — e.g. computing h = x @ W_up as one full JAX op (which materializes (M, F) in HBM) then h @ W_down, and calling that "fused." That is just the baseline with extra steps. Also: without block_until_ready() you time async dispatch, not compute; and without a warm-up run the first call's JIT compile time counts as runtime. Both give fake speedups.
