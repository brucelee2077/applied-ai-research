Module 9b · Scale · Day 3

The Mixed-Precision
Recipe

You have the two ingredients: fast 16-bit formats and the loss-scaling safety net. Now you put them together into the recipe real training uses. The trick is to do the heavy, forgiving math (the big matrix multiplies) in fast 16-bit, but do the delicate, easy-to-break math (adding up long sums, normalizing, the optimizer) in exact fp32. Use the right tool for each job.

🎯 By the end, you'll be able to: describe the full mixed-precision loop (16-bit matmuls, fp32 accumulation, fp32 master weights), and name what must stay fp32 — layer-norm stats, softmax, and the optimizer state.
1 · WHAT IS ITFast math where it is safe, exact math where it is not✓
🧭
What this assumes: from Day 1 you know fp32, fp16, and bf16. From Day 2 you know fp32 master weights and loss scaling. Today we combine them into one loop and learn which parts of the model refuse to run in 16-bit.

The idea: not everything needs the same precision

Mixed precision means running most of the model in fast 16-bit, but keeping a few fragile parts in fp32. You do not have to pick one format for the whole model. You pick the cheapest format that is safe for each operation.

The big, forgiving jobs go to 16-bit

Most of the compute is in matrix multiplies (matmuls). These are heavy but forgiving: a small rounding error in one number barely changes the averaged result. So matmuls run in fp16 or bf16, which is where nearly all the speed and memory savings come from.

Add up the long sums in fp32

A matmul multiplies many pairs and adds them into one total. Doing that adding in 16-bit loses tiny contributions. So the hardware multiplies in 16-bit but accumulates in fp32 — the running sum is kept in full precision. You get 16-bit speed with fp32-quality totals.

Some parts stay fp32, always

A few operations break in 16-bit no matter what. Layer normalization statistics, the softmax, and the optimizer state all stay in fp32. These involve exponentials, long sums, or slowly changing tiny numbers — exactly what 16-bit is bad at. Keep going 👇

2 · INTUITIONRough-cut with the cheap tool, measure with the precise one✓
🪚
The rough cut

A carpenter cutting a big pile of boards uses a fast, cheap saw. It is not perfectly exact, but for bulk cutting that is fine — a hair off on each board does not matter. This is the matmul in 16-bit: heavy work, small errors that wash out.

📏
The precise measure

But for the final fit — where two pieces must line up exactly — the carpenter switches to a precise ruler and a careful hand. This is layer norm, softmax, and the optimizer in fp32: small, delicate steps that must be exact or the whole thing goes wrong.

In one line: mixed precision uses the fast tool for the bulk work (16-bit matmuls) and the precise tool for the few delicate steps (fp32 normalization, softmax, optimizer), getting both speed and correctness.

Accumulating in fp32 is like keeping a running total on a precise notepad even while cutting fast: each cut is rough, but you write the running sum down exactly, so the final tally does not drift.

⚠️
Where the analogy breaks: a carpenter chooses tools by hand, deliberately. In a real model the framework applies these format choices automatically for each operation — you turn mixed precision on, and it routes each op to the right precision without you picking tools one by one.

4 · MECHANISM & WHYWhy the accumulator must be fp32✓

Step 1 — in plain words

A matmul adds up many products into one total. If you keep the running total in a coarse format, each time you add a tiny product to an already-large sum, the tiny product can round away to nothing. Adding many small terms to a big total, one at a time, quietly loses them. Keeping the total in fp32 fixes this: the accumulator has enough digits to notice each small addition.

Step 2 — the formula

🧮
total = 0.0 # kept in fp32
for k in range(N):
  prod = a[k] × b[k] # inputs 16-bit, product 16-bit
  total = total + prod # add into the fp32 total
# output = total, then cast back to 16-bit for the next layer

Symbols: a[k], b[k] = the k-th pair of 16-bit inputs. prod = their product. total = the running sum, kept in fp32. N = how many terms are added (can be thousands in a big layer).

Step 3 — a worked example of drift

Say the big total is already 1024.0, and you keep adding a small product 0.03 many times. Compare a coarse 16-bit total to an fp32 total. (bf16 near 1024 has a gap of about 8, so 0.03 is far below it.)

🔢
total (bf16) = 1024.0
  1024.0 + 0.03 → rounds back to 1024.0 # 0.03 lost
  after 100 adds → still 1024.0 # all 100 lost!

total (fp32) = 1024.0
  1024.0 + 0.03 = 1024.03 # kept
  after 100 adds → 1027.0 # correct total

With a bf16 total, 0.03 is smaller than the gap near 1024, so each add rounds straight back to 1024.0 and all 100 contributions vanish. With an fp32 total, each add sticks, and after 100 adds you correctly reach about 1027.0. Same 16-bit inputs, but the accumulator's precision decides whether the sum is right.

What must stay fp32, and why

  • Matmul accumulation: long sums lose small terms in 16-bit, so the running total is fp32 (the drift shown above).
  • Layer-norm statistics: computing a mean and variance over many values is another long sum; done in 16-bit it is too noisy, so the stats are fp32.
  • Softmax: it exponentiates values that can be large, then divides; 16-bit can overflow or lose precision here, so it runs in fp32.
  • Optimizer state: Adam keeps slowly changing averages per weight; these are small and long-lived, so storing them in 16-bit would round tiny updates away — they stay fp32, like the master weights.
🔗
The big picture: mixed precision is a routing decision — heavy forgiving math to 16-bit, delicate sums and exponentials to fp32. With bf16 you often skip loss scaling entirely because its wide range keeps gradients safe. Tomorrow: fp8, where the same trade-offs get much sharper and the failure modes get real.
