Quantization Intro
(LLM.int8)

Tuesday's roofline math proved decoding is bottlenecked by bytes moved from HBM, not by compute. Today's lever: shrink the weights so there are fewer bytes to move. Storing each weight in 8 bits instead of 16 nearly doubles decode speed — for free.

🎯 By the end, you'll be able to: explain why post-training quantization (PTQ) beats the memory-bandwidth wall, run the FP16-vs-INT8 roofline math yourself, and see why naive INT8 breaks on outlier values — setting up Week 8's deeper dive into LLM.int8().
1 · WHAT IS ITWhat is quantization, and why does it exist?✓
🧭
What this assumes: Tuesday's roofline result — at batch size 1, decode time per token is roughly bytes_of_weights_read / HBM_bandwidth, and compute time barely matters. No prior quantization experience needed.

The word: weights, precision

A trained model stores millions or billions of learned numbers inside its matrices. Those numbers are called weights. Precision means how many bits (binary digits) are used to store each number. Most models are trained and stored in FP16 or BF16 — 16-bit floating point, 16 bits per weight.

The idea: shrink the numbers, not the math

Post-training quantization (PTQ) takes a model that is already fully trained and converts its weights to a lower-precision format — usually INT8, 8-bit integers — without retraining it. No gradient updates. It just repacks numbers that already exist. INT8 storage is exactly half the size of FP16 storage, weight for weight.

Why this is the right lever

Tuesday proved single-token decoding is memory-bandwidth-bound: the GPU's compute cores sit mostly idle, waiting for weights to travel from HBM (High Bandwidth Memory — the GPU's large but relatively slow main memory) into SRAM (the tiny, very fast memory next to the compute cores) over a wire of fixed bandwidth (bytes/second). Time per token ≈ total weight bytes ÷ HBM bandwidth. You cannot change the physical bandwidth of that wire. But you can change the numerator — make the weights take fewer bytes. Store each weight in 8 bits instead of 16, and you halve the bytes crossing the bus per token. Since decoding is bandwidth-bound, that translates almost directly into roughly 2x more tokens/second — with no change to the silicon at all.

The catch quantization has to solve

Naive INT8 on large transformers (over about 6 billion parameters) was known to badly hurt accuracy. The reason: a small number of extreme-magnitude "outlier" values per layer blow up the rounding error for everything else nearby. Dettmers et al.'s LLM.int8() (2022) fixed this with a mixed-precision trick — keep the rare outlier dimensions in FP16, quantize everything else to INT8 — and showed no measurable accuracy loss even at 175-billion-parameter scale.

⚠️
Scope for today: we only cover the premise — shrink bytes to beat the bandwidth wall. The outlier-detection math and mixed-precision decomposition are Week 8 Monday's topic.
📚
Official sources (optional): LLM.int8() paper (arXiv:2208.07339) · bitsandbytes GitHub
2 · INTUITIONThe cook, the cart, and the freezer✓

Picture a single overworked line cook (the GPU's compute core) who must fetch every ingredient from a walk-in freezer at the back of the kitchen (HBM) before touching it. The freezer is a fixed 30-second walk away, no matter what — that walk time is the fixed bandwidth, and the cook cannot run there faster.

🧊➡️🚶
FP16 = 2 kg containers

Every ingredient container weighs 2 kg. The cart can only hold so many kg per trip, so most of the shift is spent walking back and forth, not cooking.

📦📦
INT8 = half-weight containers

Switch to smaller, half-weight containers. The same cart now carries twice as many ingredients per trip — half as many walks for the same meal.

In one line: the cooking (matrix-multiply compute) was never the bottleneck — the walking (memory transfer) was. Shrink what's carried, and the walking time shrinks almost proportionally.

⚠️
Where the analogy breaks: repackaging delicate ingredients into smaller containers can damage a few of them — this is the accuracy-degradation problem from naive quantization, where a few "outlier" items don't survive being squeezed down. That's exactly why LLM.int8() keeps a handful of fragile ingredients (outlier features) in their original full-size packaging (FP16) while shrinking everything else. It also breaks down because real quantization pays a small extra "unpacking" compute cost to convert INT8 back into a usable format for math — there's no clean cart-and-freezer equivalent for that.

4 · HOW & WHYHow the numbers are shrunk, and why it matters✓

The rules

  • Pick a scale per weight row: scale = max(abs(weight_row)) / 127 (signed INT8 range is -128 to 127).
  • Quantize: q_i = round(w_i / scale) for every weight — this int8 array is what actually gets stored and moved.
  • Dequantize when the math needs a real number back: w_hat_i = q_i * scale — an approximation of the original weight, not an exact copy.
  • This is post-training: no retraining, no gradient updates. It operates purely on weights that are already trained — a fast, cheap lever compared to changing the architecture.
✅
scale = max(abs(w)) / 127; q = round(w / scale); w_hat = q * scale
Store q (int8 array) and scale (one float) instead of the original FP16 row. That pair is the compressed representation that crosses the memory bus.

Why it's a free speed win

  • Half the bytes, nearly double the tokens/sec — decoding is bandwidth-bound, so halving bytes moved per token halves time per token.
  • No architecture change — same model, same weights (approximately), just packed smaller.
  • The catch: outliers — one huge value in a row inflates the shared scale, crushing resolution for every small value nearby. This is exactly the failure LLM.int8() targets by keeping outlier dimensions in FP16.
🔗
Causal chain: Tuesday's roofline (memory-bound decode) → the only lever is bytes moved → INT8 halves stored bytes per weight → roughly 2x tokens/sec, provided outlier values are handled separately (Week 8).
