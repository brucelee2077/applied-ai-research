Module 5b · Represent · Day 1

Images as Patches

A transformer reads a list — like the words in a sentence. But a photo is a grid of pixels, not a list. So how does a transformer ever look at a picture? Today you learn the one simple trick: cut the image into small squares, unroll each square into a row of numbers, and line them up. The photo becomes a sequence — exactly the food a transformer likes to eat.

🎯 By the end, you'll be able to: split an image into fixed-size square patches, flatten each patch into a vector, and explain why this turns a picture into a sequence of tokens a transformer can read.
1 · WHAT IS ITTurning a picture into a list of tokens✓
🧭
What this assumes: arrays and shapes from M1, and the transformer block you built in M5a. You know a transformer reads a sequence of vectors. Today you learn how to turn an image into that sequence. No computer-vision background needed — this starts from zero.

The problem: transformers read lists, images are grids

A transformer reads a sequence of tokens. Each token is one list of numbers. The model never sees "an image" directly — it only knows how to walk down a list of vectors, one by one.

An image is not a list. It is a grid. A small color photo of size 32×32 has 32 rows and 32 columns of pixels, and each pixel holds 3 numbers — how much red, green, and blue it has. So the image has shape (32, 32, 3). A grid does not fit into something built for lists. You need to reshape it.

The trick: cut into patches, then flatten each one

A patch is a small square cut from the image — say a 4×4 block of pixels. Cut a 32×32 image into 4×4 squares and you get an 8×8 grid of patches, because 32 ÷ 4 = 8. That is 64 patches in total.

Each patch holds 4×4×3 = 48 numbers (4 pixels wide, 4 pixels tall, 3 color channels). Now flatten each patch: unroll its 48 numbers into one flat row. Each patch is now a vector of length 48 — one token. Line up all 64, and the image is a sequence of 64 tokens.

📦
One 32×32×3 image  →  cut into 64 squares of 4×4×3  →  flatten each  →  a sequence of 64 vectors, each length 48.
This is exactly what a sentence looks like to a language model: a list of vectors. The picture just became "a sentence made of patches."

Why patches, and not one pixel per token?

You could treat every single pixel as a token. But a 32×32 image has 1024 pixels, and attention cost grows fast with the number of tokens. Patches shrink 1024 pixels down to 64 tokens — far cheaper — while each token still carries a whole little region of the image, not just one dot. You will feel exactly why the count matters in M5a's attention math. Keep going 👇

2 · INTUITIONCutting a photo into a grid of stickers✓

Imagine you have one big photo. You take scissors and cut it into a neat grid of small square stickers, all the same size. Then you peel each sticker off and lay them out in a row on your desk, left to right, top to bottom. The photo is now a line of stickers instead of one big picture.

✂️🖼️
cutting = patchify

Slicing the photo into equal squares is exactly cutting the image into 4×4 patches. Same size every time, no overlaps, nothing left over.

🏷️➡️🔢
one sticker = one token

Peel a sticker off and flatten it into a row of numbers. That row is one token — the same kind of thing a transformer reads for one word.

In one line: patchify cuts the photo into equal stickers and lays them in a row, so a grid becomes a sequence the transformer already knows how to read.

⚠️
Where the analogy breaks: real stickers on a desk still show you the picture, so your eyes know where each one belongs. A flattened patch is just a row of numbers — the transformer has no idea a patch came from the top-left corner or the bottom-right. That lost "where" is a problem you fix tomorrow, on Day 2, with position information.

4 · MECHANISM & WHYThe patch math, in three small steps✓

Step 1 — in words

Take an image of size H×W×C (height, width, color channels). Pick a patch size P. Slide a P×P window across the image with no overlap. Count how many windows fit across and down — that is your number of patches. Each window's pixels get flattened into one vector. Stack all the vectors into a list.

Step 2 — the formula, every symbol labeled

🧮
num_patches = (H / P) × (W / P)
patch_dim = P × P × C
# output shape after patchify: (num_patches, patch_dim)
  • H = image height in pixels · W = image width in pixels
  • C = number of color channels (3 for red, green, blue)
  • P = patch size (one side of the square, in pixels)
  • num_patches = how many tokens you end up with · patch_dim = numbers inside each token

Step 3 — a worked example with small numbers

Use a CIFAR-10 image: H = 32, W = 32, C = 3, and pick P = 4.

  • num_patches = (32 / 4) × (32 / 4) = 8 × 8 = 64 tokens.
  • patch_dim = 4 × 4 × 3 = 48 numbers per token.
  • Output shape: (64, 48) — a sequence of 64 vectors, each length 48. That is your image as tokens.

⚠️ The one rule that bites people

  • The patch size must divide the image size exactly. Always check H % P == 0 and W % P == 0. With P = 4 and H = 32, 32 % 4 = 0, so it fits. A patch size like 5 gives 32 % 5 = 2 leftover pixels with nowhere to go — a common shape bug.
  • Color channels ride along inside the patch. The ×C in patch_dim is easy to forget. A 4×4 patch is not 16 numbers — it is 4×4×3 = 48, because each pixel carries 3 color values.
🔗
Why this matters: this single reshape is the whole bridge between vision and transformers. Once the image is a (64, 48) sequence, every transformer tool you built in M5a works on it unchanged. Tomorrow you turn these raw patch vectors into proper learned embeddings.
