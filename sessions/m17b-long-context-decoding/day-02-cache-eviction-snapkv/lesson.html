Long-Context Decoding · Week 16 · Day 2

Cache Eviction(SnapKV)

Long prompts make the KV cache huge — sometimes bigger than the model itself. SnapKV shrinks it, without any training, by peeking at a small slice of the prompt to guess which earlier tokens actually matter, then throwing the rest away. Today: how that peek-and-evict trick works, and why it's not the same fix as GQA/MQA.

🎯
By the end, you'll be able to: explain why the KV cache grows linearly and hurts decode latency, walk through SnapKV's vote → pool → top-k → gather pipeline line by line, explain why 1D pooling matters, and tell SnapKV apart from GQA/MQA and from decode-time eviction schemes.
1What is the KV cache, and what does "eviction" mean?What is it
🧭
What this assumes: Monday's lesson on GQA/MQA (sharing K/V heads to shrink the cache). No prior knowledge of eviction needed.

The problem: re-reading everything, every single step

When a transformer generates text one token at a time, it must look back at every earlier token to decide what comes next. To avoid recomputing each earlier token's Key and Value vectors (the two things attention needs to "look back"), the model stores them the first time it computes them. This storage is called the KV cache.

The KV cache's size is:

🧮
cache size = 2 × num_layers × num_kv_heads × head_dim × seq_len × bytes_per_element
The 2 is for K and V. Every other factor is fixed by the model — except seq_len, which grows with how much text you feed in.

That last factor is the problem. Feed the model 100,000+ tokens of context, and the cache can become many times larger than the model's own weights. And on every single decode step, the chip must read the entire cache from GPU memory (HBM) before it can produce the next token. Reading data, not doing math, becomes the bottleneck — this is why decoding is called memory-bandwidth bound, a bottleneck formalized in Pope et al.'s inference-scaling analysis (linked below).

The idea: throw away tokens you don't need

Cache eviction means deciding, at some point, "we don't need every token's K/V anymore — keep only some of them, and delete the rest." You trade a small amount of retrieval accuracy for a large amount of memory and speed. SnapKV is one specific, training-free way to decide what to keep.

Wait — didn't Monday's GQA/MQA already fix this?

GQA and MQA shrink the cache by sharing K/V heads across multiple query heads (e.g. 32 query heads but only 8 or even 1 K/V heads) — a fixed structural shrink, baked in at training time, applied uniformly to every token. SnapKV attacks a different axis: it drops specific token positions that turn out not to matter, and it does this after training, at inference time, on top of whatever head-sharing scheme the model already uses. The two techniques stack.

The discovery behind SnapKV

The SnapKV paper noticed something useful: for a given prompt, each attention head tends to keep attending to roughly the same set of "important" earlier tokens across every later generation step — the pattern barely shifts. And that pattern is already visible near the end of the prompt itself, before generation even starts. So the model can "peek" at a small slice of the prompt to predict what the rest of generation will need.

New words for today

  • Prefill: the one-time forward pass over the whole input prompt. Compute-bound, highly parallel.
  • Decode: generating tokens one at a time afterward. Memory-bandwidth bound, sequential. SnapKV acts right at the boundary — end of prefill, before decode starts.
  • Observation window (L_obs): the last L_obs tokens of the prompt (paper default: 16). These are real prompt tokens — often the user's actual question, since instructions are usually placed last.
  • Prefix (L_prefix): everything in the prompt before the observation window. Eviction decisions are made about this region only.

4Voting, pooling, per-head eviction — and the catchHow & why

The rules

  • Voting: take the queries from the observation window, compute their attention weights against every prefix key (a normal attention pass, already computed during prefill — no extra model call), and sum those weights over the observation-window queries. That gives one importance score ("vote") per prefix position, per head.
  • 1D pooling: before ranking, run a 1D max-pool (kernel size, paper default 5) over the vote scores along the sequence axis. This spreads a high vote to its neighbors, so the survivors come in clusters — contiguous chunks — instead of scattered single tokens.
  • Top-k selection: keep only the k = floor(p × L_prefix) highest-scoring prefix positions, where p is a compression ratio you choose (e.g. keep 10% of the prefix).
  • Per-head, not global: this vote-and-select runs independently for every attention head. Different heads track different things — one might track syntax, another a name mentioned once — so the surviving cache is not one shared subsequence; each head keeps its own different subset.
✅
Naive top-k without pooling tends to pick isolated spiky tokens, breaking up phrases the model needs intact. Pooling first means the kept tokens form readable clusters.
🪜
Math Ladder — SnapKV's vote-and-keep budget
1 · In words: score each prefix token by how much the last few prompt tokens attended to it, smooth the scores into clusters, then keep a fixed fraction.
2 · The formula: vote[j] = Σ_{q∈obs} attn(q, j); pooled = maxpool1d(vote, kernel); keep the k = ⌊p · L_prefix⌋ highest, per head — p = compression ratio, L_prefix = prompt length before the observation window.
3 · Tiny numbers: L_prefix = 10,000, p = 0.1 → keep k = 1,000 prefix tokens + the observation window; the cache for the prompt shrinks ~10×.
4 · Sanity check: the kept count is exactly k (plus the always-kept window) regardless of prompt length, so cache is bounded; and kernel=1 (no pooling) must select a different, spikier index set than kernel=5 — if they match, pooling isn't doing anything.

GQA/MQA vs. SnapKV — same bottleneck, different axis

TechniqueReduces cache byDecided at
GQA / MQAsharing K/V heads across query heads (fixed factor, every token)training time
SnapKVdropping specific prefix token positions (content-dependent)inference time, end of prefill

They stack: SnapKV can run on top of a model that already uses GQA or MQA.

The catch: SnapKV only touches the prompt

⚠️
SnapKV's eviction happens once, at the end of prefill, based only on the prompt. It does not re-evaluate as new tokens get generated. So it bounds the prompt's contribution to the cache — but every newly generated token's own K/V still gets appended during decode, growing the cache regardless, unless you add a separate decode-time eviction policy (e.g. sliding-window or H2O).
🔗
Causal chain: long prompt → huge KV cache → memory-bandwidth-bound decode (Pope et al.) → GQA/MQA shrinks it structurally, per-token → SnapKV shrinks it further, per-position, using attention patterns already computed during prefill → smaller cache, faster decode, same prompt understanding (mostly).

The staff lens — one silent failure, one trade-off

SnapKV throws prompt tokens away for good, and the danger is that the throwing-away never announces itself — the model just answers a little worse.

⚠️
Failure mode (silent): evicting a token you needed later. The vote is cast at the end of prefill using only the observation-window queries. A prompt fact that no window query happened to attend to — a date, a name, one clause buried in a contract — gets a low vote and is dropped from the cache forever. Later in the generation the model needs it, but the K/V is gone, so it quietly makes something up. No exception, no warning: the output is fluent and just wrong. A senior engineer catches this in code review by refusing to trust perplexity alone and instead gating any eviction ratio on a retrieval-style check (needle-in-a-haystack across many needle positions), because average-quality metrics hide these rare-but-critical misses.
⚖️
Trade-off: compression ratio vs. recall safety. A smaller kept budget k = floor(p × L_prefix) means less cache, faster decode, more concurrent requests — but every token you drop is a fact the model can no longer see. Push p down and you win throughput while slowly losing answers that depend on obscure prompt details. Choosing that ratio — and whether some heads or some token spans (system prompt, tool schemas) are exempt from eviction entirely — is the design-review decision, not a knob to set by feel.
🎤
Say this in an interview: "SnapKV is training-free prompt-cache eviction: at the end of prefill, the last few prompt tokens vote (sum of their attention) on which prefix positions matter, 1D max-pooling clusters the votes so kept tokens stay contiguous, and a top-k keeps ⌊p·L_prefix⌋ per head. It attacks a different axis than GQA/MQA — token positions at inference, not shared heads at training — so the two stack. The nuance is what it can't do and can't warn about: it decides once from the prompt, so a fact no window query attended to is evicted forever and the model quietly confabulates — which is why I gate the compression ratio on a needle-in-a-haystack retrieval test, not on average perplexity."
