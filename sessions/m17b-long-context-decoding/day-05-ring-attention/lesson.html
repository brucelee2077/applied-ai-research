Long-Context Decoding · Week 16 · Day 5

Ring AttentionAttention Across a Ring of Devices

Every trick so far in Phase 4 assumed the whole sequence fits on one chip's memory. What happens when it doesn't — when someone wants a million tokens of context, far more than any single GPU's HBM can hold? Ring Attention answers this by splitting the sequence across many devices arranged in a ring, and passing key/value blocks around that ring while overlapping the passing with the computing, so no device ever needs to hold the whole sequence at once.

🎯
By the end, you'll be able to: explain why quadratic attention memory blocks long context even with FlashAttention-style kernels, trace the exact blockwise online-softmax + ring-rotation algorithm step by step, compute and compare the memory footprint of vanilla vs. blockwise vs. ring attention by hand, and simulate the ring rotation in code to prove it reproduces full attention exactly.
1What is Ring Attention, and why does it exist?What is it
🧭
What this assumes: Weeks 13–15 — you've seen the roofline model, FlashAttention's IO-awareness, and why decoding is bandwidth-bound. No prior multi-device or distributed-systems knowledge needed — we define every term as it appears.

The problem: attention memory grows with the square of sequence length

Self-attention computes a score between every pair of tokens in a sequence. For a sequence of length s, that means an attention matrix with s × s entries. Double the sequence length and the attention matrix quadruples. This is the well-known quadratic memory problem: memory for the naive attention matrix grows as O(s²), while everything else in a transformer (embeddings, feedforward layers) grows only as O(s).

FlashAttention (Week 13) already fixed the worst part of this: it never materializes the full s × s matrix in slow memory, instead streaming small blocks through fast on-chip SRAM. That's IO-awareness — reordering the computation so the expensive part is moving data between memory tiers, not the arithmetic itself, and minimizing that data movement. But FlashAttention still assumes the query, key, and value tensors for the whole sequence fit somewhere in one device's HBM (the accelerator's main memory) at once, even if never all in SRAM simultaneously. When someone asks for a context of a million tokens, the K and V tensors alone can be far larger than any single chip's HBM, no matter how cleverly you stream them within that one chip.

The insight that unlocks the whole trick

If one device's memory is the hard limit, the fix is to stop trying to fit the sequence on one device. Split the sequence into N contiguous blocks and hand one block to each of N devices. Each device only ever holds a 1/N slice of the queries, keys, and values. But attention needs every query to see every key and value in the sequence — so each device's slice of keys and values has to visit every other device eventually.

Ring Attention arranges the N devices in a logical ring (device 0 talks to device 1, device 1 to device 2, ..., device N-1 back to device 0) and rotates key/value blocks around that ring one step at a time. At each step, every device computes partial attention between its fixed query block and whichever key/value block has currently rotated into its hands, using the same blockwise online softmax trick FlashAttention uses to combine partial results without ever seeing the full row at once. Critically, while a device computes on the current block, it simultaneously sends its old block to its neighbor and receives the next block — the communication and the computation overlap, so the data transfer is (ideally) hidden entirely behind useful work instead of adding extra wall-clock time.

How this connects to what you've already studied

This is the same physics as the rest of Phase 4, one level up the memory hierarchy. FlashAttention overlaps HBM-to-SRAM traffic with compute inside one chip. Ring Attention overlaps chip-to-chip network traffic with compute across many chips. Quantization and GQA/MQA shrink how much data needs to move; Ring Attention instead spreads the data across more devices and hides the movement behind computation. Same bottleneck — memory bandwidth, now at the interconnect level — attacked with the same core idea: never wait for data you could have been computing with.

So what's today's catch?

The catch is bookkeeping: each device only ever sees one key/value block at a time, but the softmax denominator needs a sum over the entire row of scores before any single score can be normalized. Getting this right without ever materializing the full row is exactly the blockwise online-softmax mechanism you'll trace step by step today.

2A study circle passing notes around the tableIntuition

Picture a study circle of students sitting in a ring, each holding their own question (their query) that they need answered by checking it against everyone's notes (everyone's key/value pairs) in the room. No single student is allowed to hold everyone's notes at once — their desk (device memory) is too small.

🗒️➡️🙋
One student holds all notes

This is the old way: cram every note onto one desk. Works for a small room, but the desk (HBM) runs out of space the moment the room (context) gets big enough.

🔄🪑🔄
Pass notes around the ring

Instead, each student keeps their own notes and passes them to their neighbor on a fixed rhythm. Everyone updates their running answer to their own question a little more each time a new stack of notes reaches them — and while they read the current stack, the next stack is already being handed over.

In one line: nobody ever holds the whole room's notes; the notes circulate, and reading the current batch happens at the same time as receiving the next one.

直觉 / Intuition: 一圈同学各拿自己的问题，笔记按固定节奏一份份传下去；读手上这份的同时，下一份已经在递过来——转 N 圈，人人都看过了全部笔记。In systems terms: each device holds only O(block) of K/V at a time, so context scales with device count, not per-chip HBM, and the ring transfer overlaps with compute.

⚠️
Where the analogy breaks: a student "updating their running answer a little more" sounds approximate, like a rough draft that improves over time — but the math is exact. The online softmax running totals are algebraically identical to computing the full softmax at the end; nothing is approximated. Also, real students can get confused about how much of the answer they've seen so far — the online-softmax bookkeeping (a running max and a running sum) removes that ambiguity completely and always gives the exact same answer as if all notes had been read at once.

4The exact ring rotation rule, and why it mattersHow & why

The rules

  • Split a sequence of length s across N devices into blocks of size c = s/N. Device i permanently holds query block Q_i, and starts by holding key/value block (K_i, V_i).
  • Each device keeps a running max score m_i and a running softmax denominator l_i for its query block — the same two running statistics FlashAttention's online softmax uses, just now updated once per ring step instead of once per SRAM tile.
  • At each of the N ring steps: every device computes attention scores between its fixed Q_i and whichever (K_j, V_j) block currently sits in its local buffer, updates m_i, l_i, and its running weighted output sum using the online-softmax merge rule — while simultaneously sending its current (K_j, V_j) block to the next device in the ring and receiving the next block from the previous device.
  • After exactly N steps, every device's query block has attended to every key/value block in the sequence exactly once, and its running statistics are finalized into the exact softmax output — no approximation, no block ever skipped or double-counted.
  • The communication (sending/receiving one block) and the computation (attention on the current block) are scheduled to overlap: as long as one block's worth of compute takes at least as long as one block's worth of network transfer, the ring's added wall-clock cost is close to zero.
✅
m_i ← max(m_i, m_new); l_i ← l_i · exp(m_i_old − m_i) + l_new · exp(m_new − m_i)
"Keep a running maximum score and a running (rescaled) sum so far. Every time a new block of keys/values arrives, fold its contribution into the running totals using the same rescale-and-merge trick as FlashAttention." This is what lets each device see only one block at a time yet still produce the exact answer.
🪜
Math Ladder — per-device memory vs sequence length
1 · In words: split the sequence into N blocks, give one to each device, and rotate K/V around the ring — so a device only ever stores one block's worth of K/V, no matter how long the whole sequence is.
2 · The formula: block size c = s/N; per-device K/V memory ≈ O(c) = O(s/N) (one block), vs vanilla O(s²) and single-device Flash O(s); total context = N · c. Ring finishes in exactly N steps.
3 · Tiny numbers: s = 1M tokens, N = 8 devices → each holds c = 125k tokens of K/V, not 1M; add devices and c shrinks, so context scales with N, not per-chip HBM.
4 · Sanity check: after N steps every query block has met every K/V block exactly once (no skip, no double-count), and the online-softmax result is bit-for-bit the single-device answer — if it isn't, a running-total rescale was skipped.

Why it's a superpower

  • Memory per device stays flat as sequence length grows — each device only ever holds O(c) of key/value data (one block) plus its own fixed query block, instead of O(s) or O(s²). Context length can now scale with the number of devices, not with any single device's memory.
  • No approximation, no extra overhead when overlap works — the paper's central claim is that Ring Attention reproduces full attention exactly, and when compute-per-block ≥ communication-per-block, the ring communication is fully hidden, so there's no extra wall-clock cost versus a hypothetical single giant device.
  • Composable with earlier Phase 4 material — each device's local attention computation over its current block is exactly a FlashAttention-style kernel; Ring Attention is "FlashAttention's blockwise loop, spread across a network instead of just SRAM tiles."
🔗
Causal chain: attention memory grows quadratically with sequence length → FlashAttention hides the HBM-to-SRAM version of this cost inside one chip but still needs the sequence to fit in one chip's HBM → splitting the sequence across a ring of devices removes that per-chip limit → online softmax lets each device fold in one key/value block at a time without ever seeing the full row → overlapping the ring rotation with compute hides the extra communication, so near-infinite context becomes a matter of adding more devices, not more memory per chip.

The staff lens — one silent failure, one trade-off

Ring Attention claims to give the exact full-attention answer, and the two things that quietly threaten that are the running-max rescale and the overlap assumption behind its speed.

⚠️
Failure mode (silent): forgetting to rescale the running totals when the max jumps. Online softmax keeps a running max m_i, a running denominator l_i, and a running output O_i. When a newly arrived block contains a larger score than any seen so far, m_i increases, and both the old l_i and the old O_i must be multiplied by exp(m_old − m_new) before the new block is folded in. Skip that rescale and nothing crashes — the shapes are right, the loop finishes, and the output looks like a normal attention result. It is just wrong: earlier blocks are weighted incorrectly, so the attention output silently deviates from true softmax, worst on the blocks that arrive first. A senior engineer catches this in code review by testing the ring output against a plain single-device attention on a short sequence and asserting they match to floating-point tolerance — a missing rescale fails that check immediately.
⚖️
Trade-off: block size (device count) vs. hidden communication. The ring only runs "for free" when the time to compute attention on one block is at least the time to send one block to the next device. Splitting a sequence across more devices makes each block smaller, which shrinks compute-per-block faster than it shrinks the transfer, until the network transfer no longer hides behind useful work and the ring becomes communication-bound. Choosing how many devices to spread a given context across — enough to fit the memory, not so many that communication stalls compute — is the design-review decision, and it depends on your interconnect bandwidth, not just the sequence length.
🎤
Say this in an interview: "Ring Attention scales context past one chip's HBM: split the sequence into N blocks across N devices in a ring, each device keeps its fixed query block and rotates K/V blocks around the ring, folding each into a running online-softmax (max + rescaled sum). After N steps every query has attended to every key/value — exactly, no approximation — while each device only ever holds O(s/N) of K/V, so context scales with device count. The transfer overlaps with compute, so it's ~free while compute-per-block ≥ transfer-per-block. Two things bite: skipping the running-total rescale when the max jumps silently corrupts the output (I test it matches single-device attention to tolerance), and too many devices makes blocks so small the ring goes communication-bound."

7Simulate a ring of devices and prove it's exactProduce

Today's task (from the curriculum): understand how sequence lengths exceeding hardware limits are accommodated by passing attention states in a ring architecture across multiple GPUs. The concrete, checkable artifact is a small multi-process (or simulated multi-device) Ring Attention implementation in JAX that demonstrates the mechanism end-to-end on toy data.

Acceptance criteria

  • A from-scratch JAX implementation of blockwise online-softmax attention, plus a ring rotation step using jax.lax.ppermute (or a pmap/shard_map-simulated multi-device ring on JAX's CPU device mesh, since a single machine may not have multiple physical GPUs).
  • A correctness test asserting that Ring Attention's output for a full sequence — split into N blocks and run through N simulated devices in a ring — is numerically identical (within float tolerance, e.g. jnp.allclose(..., atol=1e-5)) to plain full-materialization softmax attention over the same Q, K, V on a single device. Check at least one non-trivial case: sequence length 512, split into 4 blocks of 128, hidden dim 64.
  • A benchmark script that reproduces demo (1)'s memory-formula comparison numerically: compute and print vanilla (2·b·h·s²), blockwise-parallel-transformer/BPT (2·b·s·h), and Ring Attention (6·b·c·h) byte counts for a small sweep of s (e.g. 1k, 10k, 100k, 1M tokens) at fixed b, h, c, showing Ring Attention's per-device memory staying flat while the others grow.
  • Runs end-to-end on CPU-simulated devices (jax.devices() count ≥ 2, e.g. via XLA_FLAGS=--xla_force_host_platform_device_count=4) and exits 0.
⚠️
Common misunderstanding: Ring Attention does not approximate attention to save memory — unlike sparse or low-rank attention variants, every query still attends to every key and value exactly, just spread across devices and time steps. The memory savings come purely from never needing the whole sequence's keys/values on one device at once, not from computing less. Also watch the online-softmax rescaling in step 7–8 of the walkthrough: forgetting to rescale the old running sum/output by exp(m_i - m_new) before adding the new block's contribution is the single most common bug — it silently produces the wrong normalization instead of crashing.
