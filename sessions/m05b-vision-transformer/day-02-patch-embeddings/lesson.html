Patch Embeddings

Yesterday you cut a picture into 64 flat patches. But raw pixel rows are clumsy, and the model has no idea which patch came from the top-left and which from the corner. Today you fix both: give each patch a proper learned ID card (an embedding), add one special "summary" token, and tag every token with its position so the model knows where it sat in the grid.

🎯
By the end, you'll be able to: project each patch into a learned embedding, prepend a learnable class token, and add position embeddings — and explain why each of the three steps is needed.
1Three things you add before the transformerWhat is it
🧭
What this assumes: Day 1 (an image is now a (64, 48) sequence of patch tokens), and the idea of a learned linear layer from M5a. Today you dress up those raw patches so the transformer can use them well.

Problem: raw patch rows are not ready

After Day 1 each patch is a row of 48 raw pixel numbers. Two things are missing. First, the transformer wants every token to live in the same fixed size, called the embedding dimension — often bigger than 48, like 128. Second, raw pixel values are not learned features; the model should choose how to represent a patch, not just eat pixels. Both are solved by one step.

Step one: the patch embedding (a learned ID card)

A linear layer multiplies each 48-length patch by a shared weight matrix, turning it into a longer, learned vector of size 128. This is the patch embedding. Think of it as giving each patch a proper ID card the model designed itself, instead of a raw pixel dump.

Step two: the class token (a summary slot)

A plain ViT adds one extra learnable vector called the class token and glues it to the front of the sequence. It belongs to no patch. Its job is to be a "summary" slot: as the transformer runs, it soaks up information from every patch, and at the very end the model reads only this token to decide the image's class.

Step three: position embeddings (where each patch sat)

Attention treats the sequence like a bag — it does not know a patch's place in the grid. A position embedding is a learned table with one row per slot. You add the matching row to each token, so the model knows which patch was top-left and which was in the corner. Keep going 👇

2Numbering each sticker and giving it an ID cardIntuition

Yesterday you cut a photo into a row of stickers. But the stickers are loose and plain. Today you tidy them up. You give each sticker a printed ID card that describes it in the model's own words. You add one blank "notes" card at the very front for later. And you stamp a seat number on every card so you never lose track of where each sticker came from.

🪪
ID card = patch embedding

A learned linear layer turns each patch's raw pixels into a proper ID card — a longer, learned vector the model chose how to write.

📝🔢
notes card + seat number

The blank card at the front is the class token — it fills with notes as the model reads. The seat number is the position embedding — it says which slot each card sits in.

In one line: patch embedding gives each patch a learned ID card, the class token adds a summary slot, and position embeddings stamp a seat number so order is not lost.

⚠️
Where the analogy breaks: a real seat number is fixed by the room, but the position embedding is learned — the model figures out for itself what each seat number should mean during training. It is not a plain 1, 2, 3 counter; it is a table of numbers that gets tuned like every other weight.

4The three steps, with shapes and a worked exampleMechanism & why

Step 1 — in words

Take the (64, 48) patches from Day 1. Multiply every patch by one shared weight matrix to lift it to size 128 — that is the patch embedding. Glue one learnable class-token vector to the front, making 65 tokens. Then add a learned position table, one row per token, so shape stays but each token now carries its place. The result feeds the transformer.

Step 2 — the formula, every symbol labeled

🧮
embed = patches @ W # (64,48) @ (48,128) = (64,128)
seq = concat(cls, embed) # (1,128) in front → (65,128)
x = seq + pos # pos table (65,128), added elementwise
  • patches = the (64, 48) flattened patches from Day 1
  • W = the learned patch-embedding weight matrix, shape (48, 128)
  • cls = the learnable class token, shape (1, 128) · pos = the position table, shape (65, 128)
  • x = the final token sequence, shape (65, 128), ready for the transformer

Step 3 — a worked example with small numbers

Say embedding dimension = 128 and you have 64 patches.

  • embed: (64, 48) @ (48, 128) = (64, 128) — 64 tokens, now length 128.
  • seq: prepend the class token → (65, 128). The count jumped from 64 to 65.
  • x: add the (65, 128) position table elementwise → still (65, 128), but each token now knows its slot.

⚠️ Gotchas

  • The position table needs num_patches + 1 rows, not num_patches. The +1 is the class token's own seat. Sizing it to 64 instead of 65 is a classic off-by-one shape bug.
  • One shared W for all patches. The same (48, 128) matrix embeds every patch — the model learns one good way to read a patch, not 64 separate ways.
  • The class token starts as noise. It carries no image information at the start. Attention is what fills it, over the transformer blocks you run tomorrow.
🔗
Why this matters: after these three steps the image is a clean (65, 128) sequence — same shape a text transformer expects. Tomorrow you push it through the exact transformer block from M5a, and attention starts mixing patches together.

The staff lens — one silent failure, one trade-off

The three steps all produce the right shape, so the one that can break your model without changing any shape is the position embedding.

⚠️
Failure mode (silent): position embeddings that carry no position. Attention treats the sequence as an unordered bag, so the position table is the only thing telling the model where each patch sat. If that table is initialized to all zeros and accidentally frozen (requires_grad=False), or every row is initialized identically, the add seq + pos still runs and the shape stays (65, 128) — but every token gets the same (or no) position signal. The model trains, the loss drops, nothing errors; it has simply become order-blind and cannot tell a top-left patch from a corner one, so it plateaus below what it should reach. A senior engineer catches this in code review by confirming pos_emb is a learnable parameter with distinct per-row values, not a constant or a frozen tensor.
⚖️
Trade-off: learned position embeddings lock in one input size. A learned table has exactly num_patches + 1 rows, so it only works for the image size and patch count it was trained on. You gain a flexible, data-tuned notion of position; you pay by making the model brittle to a different resolution — feed a bigger image and you have no row for the extra patches. Whether to use a learned table or an interpolatable/relative scheme is the design-review decision when you expect varying input sizes.
