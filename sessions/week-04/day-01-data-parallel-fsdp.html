Phase 1 · Week 4 · Day 1 (Mon)

Data Parallelism & FSDP
Replicate vs Shard

Your model fits on one device — barely. Now you have 8 devices and a big batch. Do you put a full copy of the model on each one (simple, memory-heavy), or split the model across them so no device holds the whole thing? Today: Data Parallel vs Fully Sharded Data Parallel (FSDP / ZeRO-3).

🎯 By the end, you'll be able to: explain what Data Parallel replicates and splits, describe how FSDP shards params + gradients + optimizer state, compute the per-device memory for each, and name the trade-off (memory saved vs. extra communication).
1 · WHAT IS ITWhat is Data Parallel, and what is FSDP?✓
🧭
What this assumes: you know a model has parameters (weights), and that training also stores gradients and optimizer state (Week 2, Day 5: memory ≈ 16N bytes per parameter for Adam training). You've seen "sharding" — splitting one array across devices (Week 2, Day 3). No prior FSDP experience needed.

The setup: you have many devices

Training is faster when many devices work together. The oldest, simplest way to use them is Data Parallel (DP): give every device the same full model, split the batch of data across the devices, let each device compute gradients on its slice of data, then combine the gradients so every copy stays identical.

The step that keeps the copies in sync is an all-reduce: every device sums its gradient with all the others so they all end up with the same total gradient. After that, every copy applies the same update and stays a mirror of the rest.

The problem with Data Parallel: wasted memory

Every device holds a full copy of everything — the weights, the gradients, and the optimizer state. From Week 2, training with Adam costs about 16N bytes for a model with N parameters. With Data Parallel, each device pays that full 16N. Eight devices store the same 16N eight times. That is a lot of duplicate memory.

The answer: FSDP (a.k.a. ZeRO stage 3)

FSDP stands for Fully Sharded Data Parallel. It is the same idea as ZeRO-3 (Zero Redundancy Optimizer, stage 3). Instead of every device keeping a full copy, FSDP shards — splits — the parameters, the gradients, and the optimizer state across the devices. No single device holds the whole model at rest.

📦
When a layer is needed for its forward or backward step, FSDP does a just-in-time all-gather: the devices temporarily pull together that one layer's full parameters, use them, then discard them and move on.
So the full weights of any one layer exist only for a moment, only where they are needed right now.

So what's the catch?

FSDP saves huge amounts of memory, but it is not free. Because each layer's parameters must be gathered on demand every step, FSDP does more communication than plain Data Parallel. That is the whole trade you'll study today: memory saved vs. extra communication.

📚
Official docs (optional): ZeRO: Memory Optimizations (paper) · JAX Scaling Book — Training
2 · INTUITIONOne cookbook each, or one shared cookbook?✓

Picture a kitchen with many chefs cooking the same big dinner. The "cookbook" is the model — all its recipes (parameters). How do the chefs share it?

📚📚📚
Data Parallel = each chef owns the whole cookbook

Every chef has a full personal copy of every recipe. Simple: nobody waits on anyone. But the kitchen stores the same thick cookbook once per chef — huge waste of shelf space (memory).

📄➡️📄
FSDP = one cookbook, split into pages

The cookbook is torn into pages and shared out. When a dish is being cooked, the chefs pass around just the one page it needs, use it, then set it down. No chef ever holds the whole book — far less shelf space.

In one line: Data Parallel replicates the whole model on every device; FSDP splits the model into shards and gathers just the piece it needs, right when it needs it.

⚠️
Where the analogy breaks: passing pages around costs time. Every "gather one page" is real network communication between devices. FSDP trades saved memory for this extra passing-around — that's the cost you accept.

4 · HOW & WHYThe rules of DP and FSDP, and why FSDP wins on memory✓

Data Parallel — the rules

  • Replicate the model: every device holds a full copy of weights, gradients, and optimizer state — the full 16N bytes each.
  • Split the batch: the global batch is cut into equal slices, one per device. Each device runs forward and backward on its own slice of data.
  • all-reduce the gradients: after backward, the devices sum their gradients together so every copy sees the same total. Then every copy applies the identical update and stays a mirror.

FSDP (ZeRO-3) — the rules

  • Shard three things: parameters, gradients, and optimizer state are each split across the devices. At rest, one device holds only its shard — roughly 16N / num_devices.
  • all-gather just-in-time: right before a layer's forward (and again for its backward), the devices gather that one layer's full parameters, use them, then discard the gathered copy.
  • reduce-scatter the gradients: after a layer's backward, each device keeps only its shard of the gradient, so nothing full lingers.
✅
Per-device static memory: DP ≈ 16N  vs  FSDP ≈ 16N / num_devices (plus one transient gathered layer).
For 8 devices: DP holds all 16N on each; FSDP holds about 2N on each. The full weights of a single layer flash into existence only while that layer runs.

Why FSDP matters — and what it costs

  • Fits bigger models — dividing the static memory by the device count lets you train models that would never fit under plain DP.
  • Same math, same result — FSDP computes the exact same update as DP; only the storage layout changed.
  • Costs more communication — every layer needs a fresh all-gather each step, on top of the gradient reduce. That network traffic is the price for the saved memory.
🔗
Causal chain: training needs 16N per parameter (Week 2) → DP duplicates that on every device → FSDP shards params + grads + optimizer state → per-device memory drops by ~num_devices → the extra all-gathers are the cost you pay.

Acceptance criteria

  • Inputs: number of parameters N and num_devices (e.g. N = 1e9, num_devices = 8).
