1What are argparse and subprocess, and why do you need them today?What is it
🧭
What this assumes: you built yesterday's IsoFLOPs matrix (Day 4) — a table of (flop_budget, target_N, actual_N, config, D_tokens) rows — and you have a working single-run training script from earlier in the capstone. No prior argparse or subprocess experience needed.

The problem: one script, twenty-five runs

Yesterday's matrix has 20–25+ rows. Each row is a different model size and token budget that needs its own training run. Today's new tool is not a training technique — it's the plumbing (the wiring that connects pieces and makes them run smoothly) that makes many training runs manageable without you manually babysitting each one.

Without today's tools, you'd have two bad options:

  • Hand-edit the script for every run — open train.py, change the constants at the top, save, run, repeat 25 times. Slow, and one typo silently ruins a run.
  • Babysit one run at a time — start a run, watch it finish, start the next. With 25 runs this could take days even though your hardware could run several at once.

The answer: two Python standard-library tools

argparse is Python's built-in tool for turning a script into a configurable command-line program. Instead of hand-editing constants, you declare named flags once — --d-model, --n-layers, --flop-budget, --run-id — and the same file becomes a reusable template: python train.py --d-model 256 --n-layers 4 --run-id c3_n2.

subprocess is Python's built-in tool for launching and controlling other programs from a parent Python script. Here, one process (a completely separate running copy of the Python interpreter, with its own memory — not a thread, not a function call) is one training run. A launcher script reads yesterday's matrix and starts one process per row, without waiting for each one to finish before starting the next.

📦
subprocess.Popen([...])  →  starts a new process and returns immediately, so many runs can be in flight at once.
This is different from subprocess.run(...), which blocks (waits) until that one command finishes — fine for a single run, useless for launching dozens in parallel.

So what's today's catch?

Launching is the easy part. The hard part is knowing what happened afterward: which runs finished, which crashed, and where each checkpoint landed. That's why today also covers monitoring — checking on processes without blocking, and writing the results to a file you can check without staring at a terminal.

⚠️
Where the analogy breaks: real line cooks improvise and recover from small mistakes. A subprocess does exactly what its command list says and nothing more — if a flag is misspelled or a folder doesn't exist, it fails identically and silently every time. Your monitoring script has to be the one that notices a "burnt dish" (a nonzero exit code); it can't assume no news is good news.

4The rules of argparse and subprocess, and why they matterHow & why

The rules

  • argparse.ArgumentParser() creates a parser — an object that knows what flags your script accepts. parser.add_argument("--d-model", type=int, required=True, help="...") declares one flag: its name, type, whether it's required, and a help message.
  • parser.parse_args() reads sys.argv (the list of words typed after the script name on the command line) and returns a namespace object with one attribute per flag — args.d_model, args.run_id, and so on.
  • subprocess.Popen(cmd) ("process open") starts cmd (a list of strings, like ["python", "train.py", "--d-model", "256"]) as a brand-new OS process and returns a handle immediately — it does not wait.
  • proc.poll() checks on that handle without blocking: returns None if the process is still running, or an integer exit code once it has finished. proc.wait() is the blocking version — it pauses your script until that one process finishes.
✅
subprocess.run(cmd) blocks until cmd finishes — fine for one run.
subprocess.Popen(cmd) returns immediately — required if you want many runs in flight at once.
Calling run() in a loop launches runs one at a time, which defeats the entire point of parallel launching.

Why it's worth its own lesson

  • One script, many runs — argparse turns train.py into a template. No more hand-editing constants and re-saving 25 times, one silent typo away from a wasted run.
  • Parallelism without threads — subprocess launches real OS processes, so several training runs can use separate CPU cores or accelerators at once, capped by however many you actually have.
  • Exit codes are the only ground truth — poll() only tells you a process exited, not that it exited correctly. You must check proc.returncode: 0 means success, anything else (including negative values on Unix, meaning the process was killed by a signal) means failure — and it must show up in your status.json, pointing at that run's log file.
⚠️
Gotcha: if you don't give each subprocess its own log file, output from many concurrent runs interleaves into unreadable garbage on your terminal. Worse, if you set stdout=subprocess.PIPE instead of a file and never read from proc.stdout, a run that produces enough output can fill the OS pipe buffer and deadlock — the child blocks waiting for someone to drain the pipe, and your monitor loop never gets there because it's busy polling other runs. Always redirect each subprocess's stdout/stderr to its own file, never to PIPE, when you're not actively reading it.
🔗
Causal chain: yesterday's IsoFLOPs matrix (Day 4) gives 20–25+ rows to train → argparse turns one script into a template any row can drive → subprocess.Popen launches many rows in parallel under a concurrency cap → a poll-based monitor loop classifies each finished run as success or failure → a clean table of (N, D, final_loss) feeds tomorrow's scipy.optimize.curve_fit scaling-law fit.

The staff lens — one silent failure, one trade-off

⚠️
Failure mode (silent): "no news is good news." A monitor loop that only records runs it saw finish will quietly omit a run that crashed early (nonzero exit) or was killed by the OS (OOM, negative return code) — the launcher moves on, the matrix comes back with 21 of 25 cells, and the missing four look like they were never planned. Nothing errors. In code review, a senior engineer checks that proc.returncode is asserted for every launched row and that failures are written to status.json pointing at the log — a run absent from the results table is a bug, not an accident.
⚖️
Trade-off: concurrency vs. contention. A higher parallel-launch cap finishes the sweep sooner, but oversubscribing cores/GPU memory makes every run slower (or triggers OOM kills), so the sweep can finish later and with holes. The right cap is roughly the resources you actually have, not the number of rows — a design-review number to set deliberately, not a default of "launch them all."
🎤
Say this in an interview: "I turn the training script into an argparse template, then a launcher reads the IsoFLOP matrix and starts one subprocess.Popen per row under a concurrency cap, polling with poll() so it never blocks. The nuance is that poll() returning non-None only means exited, not succeeded — I assert returncode == 0 per run and log failures, because a run silently missing from the results table corrupts the scaling-law fit downstream."

7Build the launcher and monitor for your IsoFLOPs matrixProduce

Today's task (from the curriculum): build launch_matrix.py plus an argparse-ified train.py that can launch, monitor, checkpoint, and retry the full IsoFLOPs matrix from Day 4 — no manual babysitting.

Acceptance criteria

  • train.py accepts at minimum --d-model, --n-layers, --n-heads, --d-ff, --flop-budget, --run-id, --checkpoint-dir, --seed via argparse.ArgumentParser, with required=True on every matrix-derived flag and clear help= text on each.
  • train.py writes a checkpoint to --checkpoint-dir on completion (or periodically) and a metadata.json recording final loss, wall-clock seconds, and exit status.
  • train.py supports --resume: if a checkpoint exists at --checkpoint-dir, it loads and continues rather than restarting.
  • launch_matrix.py reads the CSV/JSON matrix from Day 4's script, builds one argv list per row, and launches runs via subprocess.Popen with per-run stdout/stderr redirected to logs/<run_id>.log.
  • launch_matrix.py enforces a MAX_PARALLEL concurrency cap (a named constant, not hardcoded inline) and never exceeds it.
  • A monitoring loop polls all in-flight processes on an interval (proc.poll()), classifies each finished run as success (exit 0) or failure (nonzero), and writes a running status.json with counts of launched/running/succeeded/failed and their run_ids.
  • A --retry-failed mode in launch_matrix.py re-reads status.json, filters to failed run_ids, and re-launches only those.
  • Proof of correctness: a smoke test run with a cut-down matrix (3 rows, ~50 steps each) completes end-to-end — launch, monitor, checkpoint, status.json — before running the full matrix.
  • Done looks like: the full matrix (5+ FLOP budgets × 4–5 N values, 20–25+ runs) launched via launch_matrix.py, status.json shows every run as succeeded or explicitly failed (none stuck running at script exit), and each succeeded run_id has both a checkpoint file and metadata.json under checkpoints/<run_id>/ — the exact table scipy.optimize.curve_fit will consume next.
