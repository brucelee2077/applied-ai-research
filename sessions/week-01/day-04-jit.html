Compilation

Your JAX code already runs. But each math step is dispatched from Python one at a time — that leaves the GPU/TPU waiting. Wrap your function once with jax.jit(f) and JAX compiles it into one fast, fused program. Today: how compilation works and why the first call is the slow one.

🎯 By the end, you'll be able to: compile a function with jax.jit, explain the trace-then-compile-then-cache flow, time an honest speedup with block_until_ready(), and jit yesterday's MLP forward pass.
1 · WHAT IS ITWhat is a compiler, and what is jax.jit?✓
🧭
What this assumes: basic Python/NumPy and Days 1–3. You can write a JAX function over arrays. No prior compiler knowledge needed.

First, three words

Let's define the words we'll use, because everything today rests on them.

  • A compiler is a program that takes your code and turns it into a faster, lower-level version before it runs. Instead of reading your code line by line every time (like Python does), it prepares one optimized program once, then runs that.
  • To trace a function means to run it once with fake stand-in inputs that only carry shape and type (not real numbers), and write down every operation it performs. The result is a recording of the math — not the answer.
  • To fuse operations means to merge many small steps into one bigger step. Instead of "add, then multiply, then sum" as three separate trips to the hardware, fusion does them in a single pass, so the data is touched once.

The problem: Python dispatches one op at a time

When you call jnp.tanh(x @ x.T).sum(), Python hands each operation to the accelerator (GPU/TPU) one at a time: first the matmul, then tanh, then the sum. Between each step, control comes back to Python. For big models with many small ops, all that back-and-forth wastes time, and the hardware sits idle waiting for the next instruction.

The answer: jax.jit

jax.jit ("jit" means just-in-time compilation) wraps your function and hands it to XLA — JAX's compiler (the name stands for Accelerated Linear Algebra). Here is what happens:

  1. First call: JAX traces your function on abstract inputs (shapes and dtypes only) to record the operations.
  2. XLA compiles that recording into one fused, optimized program for your hardware.
  3. JAX caches that compiled program, keyed by the input shape + dtype.
  4. Later calls with the same shape/dtype skip tracing and compiling entirely — they reuse the cached program. That's the big speedup.
📦
f_jit = jax.jit(f)  →  f_jit(x) runs the compiled program.
The first f_jit(x) pays a one-time cost (trace + compile). Every call after that is fast.

Why this is safe (a callback to Days 1–3)

Tracing works only because JAX functions are pure: arrays are immutable and randomness uses explicit keys (Days 1–2). A pure function has no hidden state, so XLA can safely reorder and fuse its operations without changing the result. That purity is exactly what makes jit possible.

2 · INTUITIONA chef learning a recipe by heart✓

Imagine a chef making a dish for the very first time. They fumble a bit: chop, check the recipe, find the pan, re-read the next step. It's slow because they figure out the order as they go.

👨‍🍳📖
first cook = trace + compile

The first time, the chef works out the best order of steps and memorizes the routine. This planning is a one-time cost — the first plate takes the longest.

👨‍🍳⚡
every cook after = cached fast run

Now the chef knows the routine by heart. Each new plate comes out fast and smooth — no pausing to check the recipe. That's the cached compiled program.

In one line: the first call to a jitted function is slow because JAX is "learning the recipe" (tracing and compiling); every call after runs the memorized, optimized version at full speed.

⚠️
Where the analogy breaks: the chef can improvise if the dish changes slightly. XLA cannot. If the input shape or dtype changes, it's a brand-new "recipe" and JAX has to trace and compile again from scratch.

4 · HOW & WHYThe rules of jit, and why it matters✓

The rules

  • jax.jit(f) returns a new function. The first call traces and compiles (slow, one time); later calls reuse the cached compiled program (fast).
  • The cache is keyed by input shape + dtype. Same shapes → reuse. A new shape or dtype → a fresh trace and compile (a "recompile").
  • Inside a jitted function, values are traced as abstract shapes, not real numbers. So Python print(x) runs at trace time only — you see it once (during compilation), not on every call.
  • Compilation is deferred. Timing is honest only if you force the result to finish with block_until_ready(), because JAX runs work asynchronously and returns before it's done.
✅
f_jit = jax.jit(f); f_jit(x).block_until_ready()
"Compile on this first call and wait for it to finish." Now time the next calls — those are the real, compiled speed.

Two gotchas to avoid

  • No Python side effects inside jit. Things like print, appending to a list, or writing to a global happen only at trace time — not on every call. Do not rely on them for per-call behavior.
  • No Python if/for on traced values. At trace time there's no real number to branch on. If your control flow depends on the values inside an array, use JAX's own control flow: jax.lax.cond (for branches) and jax.lax.scan (for loops).

Why it's a superpower

  • Fused, optimized code — XLA merges many small ops into one program, so the hardware is touched once and stays busy. Big speedups, especially for models with many small operations.
  • Pay the cost once — trace and compile happen a single time; then every call is fast for that shape.
  • Composable — jit stacks with grad (gradients) and vmap (batching, Day 3). E.g. jit(vmap(grad(loss))) compiles a fast, batched, per-example gradient.
🔗
Causal chain: pure functions (Days 1–2) → JAX can trace them safely → XLA fuses and compiles the trace → cache by shape/dtype → the first call is slow, every later call is fast.
