1 · WHAT IS ITWhat is a Vision Transformer?✓
🧭
What this assumes: Days 1–5 (immutability, PRNG keys, vmap, jit, Flax/Optax). You should already be comfortable writing a small Flax module and training it with Optax. No prior transformer or computer-vision experience needed — this section starts from zero on that part.

The problem: transformers read sequences, images are grids

A normal Transformer (the architecture behind most modern language models) reads a sequence of tokens — think of a token as one "unit" the model looks at, like one word in a sentence. It never looks at "an image" natively — it only knows how to process a list of vectors, one after another.

An image is not a list. It's a grid: a CIFAR-10 image is 32×32 pixels, each pixel with 3 color numbers (red, green, blue), so shape (32, 32, 3). So how do we feed a grid into something built for lists?

The answer: cut the image into patches, treat each patch as a token

A patch is a small square cut out of the image — for example a 4×4 pixel square. Cut a 32×32 image into 4×4 patches and you get an 8×8 grid of patches, which is 64 patches total. Each patch has 4×4×3 = 48 numbers in it (4 pixels wide, 4 pixels tall, 3 color channels). Flatten each patch — unroll its 48 numbers into one long list — and now that patch is just a vector of length 48. That vector is one "token," exactly the kind of thing a Transformer already knows how to read.

📦
One 32×32×3 image  →  cut into 64 patches of 4×4×3  →  flatten each  →  a sequence of 64 vectors, each length 48.
This is exactly what a sentence looks like to a language model: a sequence of vectors. The image just became "a sentence made of patches."

Two extra ingredients: the [class] token and positional embeddings

Once you have 64 patch tokens, a plain ViT (Vision Transformer) adds two more things before running the Transformer:

  • A learnable [class] token. This is one extra vector, not tied to any patch, that gets prepended (glued to the front) of the sequence. After the whole model runs, this token's final output is what gets used to decide the image's class. Think of it as a dedicated "note-taking" slot that gathers information from every patch.
  • Positional embeddings. Attention (the mechanism inside a Transformer block) treats the sequence as a bag — it does not know which patch came from the top-left vs. the bottom-right of the image. Positional embeddings are extra learned numbers added to each token that encode where that patch sat in the grid, so the model can still use position when it's useful.

So what's today's catch?

There's no new JAX mechanic to learn today — you already have vmap, jit, and Flax/Optax from Days 2–5. The catch is scale and integration: wiring five days of pieces into one real, trainable model, and knowing how to tell if it actually works before you spend hours training it on the full dataset.

2 · INTUITIONA comic book cut into panels✓

Imagine cutting a comic book page into numbered panels, then letting each panel "look at" every other panel to figure out the full story — the same trick attention uses for words in a sentence.

Each small square panel becomes one "token." Cutting the page into panels is exactly like cutting the image into 4×4 patches.

🔍🔗
attention = "who does this refer to"

To understand panel 5, you might glance back at panel 2 and panel 8. Attention lets every patch look at every other patch the same way, to build context about the whole image.

In one line: a ViT cuts the image into patches (panels), turns each into a token, and lets attention connect them the same way it connects words in a sentence.

⚠️
Where the analogy breaks: comic panels have a fixed reading order — top-left to bottom-right. ViT patches don't. Attention lets any patch look at any other patch regardless of position. Position is only an extra hint (the positional embedding) added on top — not a built-in reading order.

4 · HOW & WHYHow the pieces snap together, and the gotchas✓

The full pipeline, in order

  • Patchify: cut (32,32,3) into 64 patches of 4×4×3=48 numbers each → (64, 48).
  • Linear projection: a Dense layer maps each 48-length patch vector into the model's embedding dimension (say 128) → (64, 128).
  • Prepend [class] token: concatenate one learnable vector of shape (1, 128) in front → (65, 128).
  • Add positional embeddings: a learned table of shape (65, 128) — one row per position, including the class token — added elementwise. Shape stays (65, 128).
  • N Transformer encoder blocks (LayerNorm → attention → residual → LayerNorm → MLP → residual): shape stays (65, 128) the whole way through. These blocks only mix information between tokens — they don't change the sequence length or embedding size.
  • Take token 0 (the class token's final state) → (128,). Everything else is thrown away at this point.
  • Linear head: a final Dense(10) maps (128,) → (10,) — one logit per CIFAR-10 class.
✅
logits = nn.Dense(10)(x[:, 0])
"Take only the class token's row, then run it through one more Dense layer to get 10 class scores." Nothing else in the sequence feeds the final prediction directly — only through what attention wrote into the class token.

⚠️ Gotchas

  • Patch size must evenly divide the image. 32×32 with patch size 4 gives exactly 8×8=64 patches. A patch size like 5 does not divide 32 evenly — you'd get leftover pixels with nowhere to go. Always check image_size % patch_size == 0.
  • The positional embedding table must be sized num_patches + 1, not just num_patches — the +1 is for the class token's own position slot. Forgetting the +1 is a classic off-by-one shape bug here.
  • Everything is still pure functions with explicit params — same purity theme from Day 1. A Flax module's __call__ doesn't hide any mutable state; params (cls_token, pos_emb, every Dense layer's weights) are just values threaded through explicitly, exactly like Day 1's immutable arrays.

7 · PRODUCEBuild, overfit, and train a from-scratch ViT✓

Today's task is a two-part artifact — the weekend capstone. Part A (Saturday) proves your model's plumbing is correct. Part B (Sunday) proves it can actually learn.

Part A — overfit a single batch (correctness proof)

File: experiments/week01_jax/vit_overfit_batch.py

  • Build a from-scratch Flax ViT: patchify → PatchEmbed (Dense projection + learnable cls token + pos embedding table) → a small stack of Transformer encoder blocks → Dense(10) head on the class token.
  • Take ONE batch of 8–16 CIFAR-10 images and train on only that batch, repeatedly, for a few hundred steps.
  • Print the loss curve (step, loss) as you go.
  • Acceptance: final loss < 0.05 within a few hundred steps on that one batch. Random-guess loss on 10 classes is ln(10) ≈ 2.3 — dropping from there to near zero proves gradients flow correctly through the entire model, end to end.

Part B — train on the full CIFAR-10 train split (real learning)

File: experiments/week01_jax/vit_train_full.py

  • Reuse the same ViT architecture from Part A.
  • Train on the full CIFAR-10 training set (not one batch) to convergence.
  • Report held-out (test set) accuracy at the end.

Plus — document the architecture

File: experiments/week01_jax/WEEK1_ARCHITECTURE.md

  • Document the functional state-passing design: where do params and opt_state actually live? (Hint: nowhere inside the model or optimizer object — they're values you pass in and get new values back.)
  • Explain how jit, vmap, and grad compose around pure functions in this codebase.
  • Tie it back explicitly to Days 1–5: immutability (Day 1) is why params are safe to pass around; PRNG keys (Day 2) are how every random init and dropout mask is reproducible; vmap (Day 3) is how one image's forward pass becomes a batch; jit (Day 4) is what makes training fast; Flax/Optax (Day 5) is what supplies the params/opt_state containers that this whole model and its optimizer sit inside.
