Transformer Math · Week 3 · Day 3

The KV CacheWhy Decoding Gets Cheaper

A language model writes text one token at a time. Each new token has to look back at every token before it. Do that naively and you redo the same work over and over. The KV cache is the trick that stops the waste — and it also becomes the biggest memory cost in long-context serving. Today: what it stores, why it saves work, and what it costs.

🎯
By the end, you'll be able to: explain what a KV cache stores, why it turns O(n²) recompute into O(n), compute its memory size for a 7B-style model, and say why decoding becomes memory-bandwidth-bound.
1What is the KV cache, and why does it exist?What is it
🧭
What this assumes: you know that a transformer has attention — for each token, the model builds three vectors: a Query (Q), a Key (K), and a Value (V) — and that a token "attends" by comparing its Q against every earlier token's K, then mixing the matching V vectors. That was Day 2. No prior KV-cache knowledge needed.

First, what is autoregressive decoding?

When a model writes text, it does not produce the whole answer at once. It produces one token at a time. (A token is a small chunk of text — roughly a word or piece of a word.) It writes a token, adds it to the end of what it has so far, then writes the next one, using everything written before as context. This one-at-a-time, "each new token depends on all previous tokens" process is called autoregressive decoding.

The problem: the same work, over and over

Here is the catch. To write the next token, attention needs the K and V vectors of every token so far. Those K and V vectors only depend on the tokens that already exist — they do not change when you add a new token.

But the naive way recomputes them anyway. At step 1 you compute K,V for 1 token. At step 2, for 2 tokens. At step 3, for 3 tokens. By the time you have written n tokens, you have recomputed the early tokens' K,V about n times. The total work grows like O(n²) — most of it repeated work you already did.

The answer: cache K and V

The fix is simple: store the past Keys and Values so you never recompute them. This store is the KV cache. After each step you compute K,V for only the one new token and append them to the cache. The next step reads all the old K,V straight from the cache. Work per step becomes roughly constant, so total work drops from O(n²) to O(n).

📦
The KV cache = the stored Keys and Values of all tokens written so far.
Each decode step: compute Q, K, V for the new token → append its K,V to the cache → attend using the new Q against the whole cache. No recompute of old tokens.

So what's today's catch?

The cache is not free. You are trading compute for memory. Its size is 2 × n_layers × n_heads × head_dim × seq_len × batch × bytes_per_value (the 2 is for K and V). That memory grows with the sequence length, and for long context it becomes the real bottleneck — the thing that limits how many requests fit on a chip. We'll size it exactly in the walkthrough.

😕
为什么这里容易卡住 · Why this trips people up: 很多人把 KV cache 当成「省一点计算」就翻篇了，没意识到它才是长上下文里真正吃显存、决定能同时服务多少用户的东西。In plain terms: people frame the KV cache as a compute optimization and stop there — they miss that at long context it becomes the dominant memory cost, and it (not the model weights) is what decides how many requests fit on one chip.

2Writing a story, one word at a timeIntuition

Imagine you are writing a story, and a rule says: before you write each new word, you must reconsider every word you have written so far. The choice matters — how you do this decides whether the task is quick or painful.

📖🔁
no cache = re-read the whole story

Each new word, you read the entire story again from the beginning. Word 100 means re-reading 99 words; word 1000 means re-reading 999. The reading piles up as O(n²) — mostly re-reading what you already read.

📝➕
KV cache = keep notes as you go

Instead, you keep a note card for each word you write (its K and V). For a new word you only read your Q against the notes and add one new card. No re-reading — the work per word stays small, so the total is O(n).

In one line: the KV cache is the stack of note cards — you keep the past Keys and Values so each new token only computes its own K,V and appends them, instead of recomputing everything.

直觉 / Intuition: KV cache 就像你边读书边做笔记 — 读过的内容不必每次都从头重读一遍。The technical point is that we cache each past token's Key and Value once, so every later decode step reads them from the cache instead of recomputing them — turning O(n²) work into O(n).

⚠️
Where the analogy breaks: the note cards are not free. Every token adds cards to every layer and every attention head. The pile of cards (the cache memory) grows and grows with the story length — and for very long stories, the pile itself becomes the thing you run out of room for.

4How the cache works, and what it costsHow & why

The rules

  • The cache stores past Keys and Values only — one K and one V per past token, in every layer and every attention head. It does not store Queries (a Q is used once, for its own step, then thrown away).
  • Each decode step: compute Q, K, V for the one new token → append its K,V to the cache → attend the new Q against the whole cache. Old tokens are never recomputed.
  • This turns per-step work from "recompute all n tokens" into "compute 1 token, read n from cache." Total decode work drops from O(n²) to O(n).
  • The price is memory. The cache size is 2 × n_layers × n_heads × head_dim × seq_len × batch × bytes, and it grows linearly with every token you decode.
✅
cache_bytes = 2 · n_layers · n_heads · head_dim · seq_len · batch · bytes_per_value
The leading 2 counts both K and V. Everything else is "how many numbers per token" times "how many tokens" times "how many bytes each."
🪜
Math Ladder — KV-cache size
1 · In words: the cache holds one K and one V per past token, in every layer and every KV head — so its size is "numbers per token" × "tokens" × "bytes each."
2 · The formula: cache_bytes = 2 · L · H · d · s · b · bytes — 2 = K and V; L = layers; H = KV heads; d = head_dim; s = seq_len (tokens so far); b = batch; bytes = bytes per value (2 for fp16).
3 · Tiny numbers: 7B-style (L=32, H=32, d=128) → per token = 2·32·32·128 = 262,144 values. At s=8192, b=1, fp16: 262144 × 8192 × 2 ≈ 4.29e9 bytes ≈ 4.3 GB — for ONE request.
4 · Sanity check: it's linear in s, so halving context halves the cache (≈0.54 GB at s=1024). If doubling context doesn't roughly double your cache, recheck the head count — GQA/MQA share KV heads, so use the KV-group count, not the query-head count.

Why it matters

  • Compute saved — without the cache, long generations are dominated by re-doing K,V for the whole prefix at every single step. The cache removes that waste entirely.
  • Memory becomes the limit — for long context the cache can reach several gigabytes per request. It, not the model weights, often decides how many requests fit on one chip.
  • Decode is memory-bandwidth-bound — each step does little math but must read the entire growing cache from memory. The chip spends its time moving the cache, not computing. This ties straight back to the roofline model from Week 2: low arithmetic intensity, so you are limited by bandwidth, not FLOPs.
🔗
Causal chain: autoregressive decoding needs every past token's K,V → recomputing is O(n²) waste → cache the K,V so each step is O(n) → but the cache grows with length → decode becomes memory-bandwidth-bound (the roofline story).

The staff lens — one silent failure, one trade-off

The cache is the trick that makes decoding fast, and the resource that quietly decides how many users you can serve. A staff engineer knows both.

⚠️
Failure mode (silent): sizing batch capacity from model weights alone. The KV cache grows linearly with seq_len × batch and, at long context, can exceed the weights themselves. A server that comfortably fits N concurrent requests at short context will OOM at long context — with GPU compute utilization still low, so nothing looks busy; it just runs out of HBM. A senior engineer budgets HBM as weights + peak KV cache, not weights alone.
⚖️
Trade-off: compute saved for memory spent. The cache buys O(n²) → O(n) compute at the price of O(n) memory that becomes the serving bottleneck. You can trade some of it back: shrink the cache with GQA / MQA (fewer KV heads), quantize the cached K,V to fewer bits, or evict old tokens — each spends a little quality or complexity for more batch headroom. In a design review, KV-cache memory (not FLOPs) is usually what decides requests-per-chip.
🎤
Say this in an interview: "The KV cache stores every past token's Key and Value once, so autoregressive decode reuses them instead of recomputing — turning O(n²) work into O(n). The price is memory: 2·L·H·d·s·b·bytes, linear in sequence length; a 7B model at 8k context needs ~4.3 GB per request. The nuance: that makes decode memory-bandwidth-bound, not compute-bound — the roofline story — so KV memory, not FLOPs, usually decides requests-per-chip, and GQA/MQA exist to shrink it."
