Repository CleansingCI, README, Reproducibility

Four weeks of the Addition Transformer Crucible left you with scattered notebooks, scripts, and run logs. Today isn't new ML — it's reproducibility engineering: turning that mess into a clean, single-command repo using .github/workflows and a real README, before Phase 4 begins.

🎯
By the end, you'll be able to: modularize a monolithic notebook into single-responsibility Python files, write a GitHub Actions smoke-test workflow that catches breakage on every push, and write a README whose "Reproduce" section actually works from a clean checkout.
1What is "repository cleansing," and why does it need tools?What is it
🧭
What this assumes: you've written JAX/Flax/Optax code across Weeks 9–12 (data generation, a dense transformer, an MoE upgrade, scaling-law fits) and you use `git` and GitHub. No prior CI or packaging experience needed.

The problem: four weeks of scattered scripts

You did not sit down once and design a clean research pipeline. You ran urgent experiments, week after week, and the code grew the way most research code grows: a notebook here, a tweaked copy of that notebook there, a plotting cell pasted in wherever a run finished. That is completely normal — it is also now a liability.

Two things are missing, and both have names:

  • GitHub Actions — GitHub's built-in continuous integration (CI) system. You drop a YAML file in .github/workflows/ and tell GitHub's servers: "every time code changes, spin up a fresh machine, check out the repo, and run these commands." Without it, nobody — including future you — finds out a training script silently broke until the day you actually need it.
  • README documentation — the file GitHub renders automatically on your repo's homepage. Without a real one, a reader (including future you) has no way to know what the empirical claim is or how to reproduce it.

The answer: modularize, document, automate

Today has three linked moves. First, modularize: split whatever grew organically (data generation, model, training loop, plotting, all mixed in one notebook) into importable, single-job Python files — data.py, model.py, train.py, and so on. Second, write a README that states the exact one-command reproduction recipe. Third, add a GitHub Actions smoke test: a tiny, fast run (say 20 training steps) that proves the code still imports and still trains, on every push, without needing a GPU or TPU.

📦
A smoke test is not the real experiment. It is a scaled-down version of your real training run — same code path, tiny config — whose only job is to catch "I refactored this and it silently broke" within two minutes, instead of three weeks later.

So what's today's catch?

The catch is not technical difficulty — it's discipline. It is tempting to write a beautiful README and never actually test it. We will build the habit of testing the reproduce steps from a genuinely clean checkout, because that is the only way to know they are true.

Think of the last four weeks as a busy chemistry lab bench during a series of urgent experiments. Reagent bottles are unlabeled. Scratch notes about "which run used which formula" sit on loose paper. The one working setup exists only because you happen to remember which three knobs to turn, in which order — nobody else, not even future-you in six months, could walk in and reproduce the discovery.

Label every bottle

Modularizing the scripts into named files with one job each — data.py, model.py, train.py — is labeling the reagent bottles so anyone can find the right one.

📋🔬
Write the protocol sheet

The README is the official lab protocol: a new grad student could follow it start to finish without ever asking you a question.

In one line: "Repository Cleansing" is the end-of-project lab cleanup — label the bottles (modules), write the protocol sheet (README), and install a tripwire alarm (CI) that rings the moment something breaks.

⚠️
Where the analogy breaks down: a chemistry lab cleanup doesn't literally re-run the whole experiment to prove it's reproducible. A good research-repo cleanup does exactly that — the "tripwire alarm" (CI) doesn't just sit there and detect breakage passively. It actively re-executes a scaled-down version of your real training run on every single change. That's a stronger, more automatic guarantee than any physical checklist can give you.

4The rules of a cleansed repo, and why it mattersHow & why

The rules

  • One file, one job. data.py generates data. model.py defines the dense transformer. moe_model.py defines the MoE upgrade, sharing scaffolding with model.py rather than copy-pasting it. train.py runs the Optax loop. sweep.py orchestrates many runs. scaling_law.py fits the Chinchilla-style curve.
  • Config objects, not magic numbers. train(config: TrainConfig) reads hyperparameters from a config file (configs/smoke.yaml, configs/scaling_sweep.yaml), so nothing is hardcoded inside the function.
  • CI reuses the real code path. The smoke test does not test a fake mini-pipeline — it calls the exact same train() function as the full sweep, just with a tiny config (d_model=32, max_steps=20). That is what makes a green check mean something.
  • The README's "Reproduce" section is a contract. It names the exact commands, the expected output file path, and the expected runtime — not just a description of what the project does.
✅
python -m src.train --config configs/smoke.yaml --max_steps 20
This is the entire trick: run the real training function, just tiny and fast, so CI can prove "it still works" in under two minutes on CPU.

Why it's worth doing before Phase 4

  • Future-you can't ask past-you questions. Six months from now, only the README and the code answer questions — not your memory of which cell to run first.
  • CI catches silent breakage immediately. A refactor that breaks an import or a shape mismatch turns red on the very next push, not three weeks later when you need the real scaling-law runs.
  • Modular code is testable code. You cannot unit-test a 40-cell notebook. You can absolutely unit-test generate_addition_batch() in two lines of pytest.
🔗
Causal chain: four weeks of urgent experiments (Weeks 9–12) → code grows organically in notebooks → without cleanup, nobody (including future-you) can reproduce the result → modularize + README + CI → a repo Phase 4 (custom kernels, ThunderKittens) can build on with confidence.

7Cleanse the Phase 3 repo into one reproducible pipelineProduce

Today's task is not new experiment code — it's turning everything you built in Weeks 9–12 into a repository someone else (or future-you) could clone and reproduce with one command.

Acceptance criteria

  • sessions/m14b-capstone-moe/day-05-repository-cleansing/src/{data.py, model.py, moe_model.py, train.py, sweep.py, scaling_law.py} exist, each importable standalone — e.g. python -c "from src.model import AdditionTransformer" succeeds with no notebook context needed.
  • sessions/m14b-capstone-moe/day-05-repository-cleansing/tests/ contains at least 3 passing pytest tests (data shape test, model forward-pass shape test, training-loss-decreases smoke test); pytest tests/ -q exits 0.
  • .github/workflows/smoke_test.yml exists and, when pushed, shows a green check in the GitHub Actions tab on the remote.
  • sessions/m14b-capstone-moe/day-05-repository-cleansing/README.md covers: what the project is, the empirical claim (dense vs. MoE Chinchilla-style scaling exponents from your own runs), install steps, and one copy-pasteable "Reproduce" command sequence with expected output path and runtime.
  • Acceptance test: from a fresh clone (or git clean -xdf scratch checkout), running only the README's commands regenerates the scaling-law plot with no manual notebook editing, no undocumented environment variables, and no crashes.
  • sessions/m14b-capstone-moe/day-05-repository-cleansing/EXPERIMENT_LOG.md (or PROGRESS.md) has a final dated entry marking the cleanup complete, linking the README and CI badge.
⚠️
The most common failure mode: a beautiful "Reproduce" section that was never actually tested from a clean checkout — it references a renamed config file, assumes an environment variable you forgot you set locally, or quietly depends on a cached dataset sitting on your disk that a fresh clone won't have. Always do the final test in a genuinely clean environment: a fresh git clone into a scratch directory, or at minimum git clean -xdf plus a fresh virtualenv — running nothing but the README's own instructions.

Repository Cleansing checklist for sessions/m14b-capstone-moe/day-05-repository-cleansing/:

1. Inventory every notebook, script, and results file from Weeks 9-12 (data gen, dense model, MoE upgrade, scaling-law fits).
2. Decide module boundaries: data.py, model.py, moe_model.py, train.py, sweep.py, scaling_law.py, run.py.
3. Create sessions/m14b-capstone-moe/day-05-repository-cleansing/{src,tests,configs,results,reports}/.
4. Extract the synthetic addition-sequence generator into src/data.py with a typed signature and docstring stating shapes.
5. Extract the dense Flax transformer into src/model.py as a standalone nn.Module, removing hidden notebook-global state.
6. Extract the MoE upgrade into src/moe_model.py, sharing the base transformer via composition, not copy-paste.
7. Extract the Optax training loop into src/train.py as train(config) -> TrainState, Metrics.
8. Extract sweep orchestration into src/sweep.py: calls train() across a grid of model sizes/token budgets, saves each run to results/.
9. Extract Chinchilla-style curve-fitting into src/scaling_law.py: returns fitted alpha, beta (and N_c, D_c) plus a plot.
10. Write configs/smoke.yaml (tiny, fast) and configs/scaling_sweep.yaml (the real sweep) so no magic numbers stay hardcoded.
11. Write run.py or python -m src. CLI entry points for the full pipeline, no notebook clicking required.
12. Write pytest tests: data shape test, model/moe forward-pass shape test, loss-decreases-over-N-steps smoke test.
13. Delete or archive dead code, abandoned branches, stale results, and now-duplicated notebook cells.
14. Write .github/workflows/smoke_test.yml: checkout, setup-python, pip install, python -m src.train --config configs/smoke.yaml --max_steps 20, pytest tests/ -q.
15. Push, confirm the Actions tab shows green; deliberately break an import once to confirm it goes red, then revert.
16. Write the comprehensive README.md: description, empirical claim, install, exact reproduce command sequence with expected output path and runtime.
17. Add a results/reports section to the README with your own fitted scaling-law numbers and plot (not placeholders).
18. Final clean-checkout test: fresh clone into a scratch dir, run only the README's reproduce command, confirm zero manual intervention.
19. Update PROGRESS.md/EXPERIMENT_LOG.md marking the cleanup complete, linking the README and CI badge.
20. Add a CI status badge to the top of the README pointing at the smoke_test.yml workflow.

After finishing, write one line in sessions/m14b-capstone-moe/day-05-repository-cleansing/log.md: what would have broken if you had written the README's "Reproduce" section without testing it from a clean checkout?
