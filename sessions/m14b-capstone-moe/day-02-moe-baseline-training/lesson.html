1What is a Mixture-of-Experts layer, and why does it need a new JAX primitive?What is it
🧭
What this assumes: you have a working dense addition-transformer from earlier Phase 3 weeks, with a normal feed-forward block. No prior MoE experience needed.

Part 1 — the ML idea: routing instead of one shared FFN

In your dense transformer, every token passes through the same feed-forward network (FFN) — one set of weights, used by every token, every time.

A Mixture-of-Experts (MoE) layer replaces that single FFN with E separate FFNs, called experts (say E=8), plus a tiny extra network called the router (or gate). For each token, the router looks at that token's hidden vector and outputs one score per expert. You take the top-1 highest-scoring expert and send the token only to that expert's FFN.

Every token still gets processed by exactly one FFN's worth of compute — same FLOPs per token as the dense model. But the model now has E times as many FFN parameters to draw from, because different tokens can specialize into different experts. This is the "sparse" part of "sparsely-activated model": parameters scale with E, compute per token does not.

Part 2 — the JAX problem: batch sizes nobody knows in advance

Naively, MoE dispatch means: for each token, drop it into its expert's bucket, run a batched matmul per expert, then put the results back in order. The catch: bucket sizes are different every batch — that's what ragged means, not a fixed rectangular shape — and they depend on the data, not on anything known when the program is compiled.

JAX/XLA programs are normally compiled for fixed shapes. A naive fix either (a) pads every expert's bucket up to some worst-case size — wasting compute and memory, and silently dropping tokens that overflow — or (b) loops over experts in Python, which is slow and stops the compiler from fusing the work into one operation.

jax.lax.ragged_dot(lhs, rhs, group_sizes) solves this directly. lhs is your token matrix, shape (m, k) — tokens already sorted so expert 0's tokens come first, then expert 1's, and so on. rhs is the stacked expert weights, shape (g, k, n). group_sizes is a length-g vector telling the kernel exactly how many of the m rows belong to each expert (they must sum to m). One fused, hardware-efficient grouped matmul, no padding, no Python loop.

Part 3 — why "check the router is even" is today's real task

Nothing in the architecture forces even routing. Left alone, routers famously collapse: a couple of experts get most tokens, so they get more gradient signal, so they get better, so the router sends them even more tokens — a rich-get-richer loop. Meanwhile other experts starve. The Switch Transformer paper (linked below) fixed this with a differentiable auxiliary load-balancing loss plus a hard expert capacity cutoff. Today's task is to run the baseline and check, from the actual training run, that this machinery works — not just assume it does because the paper says so.

📚
Official sources (optional): Switch Transformers: Scaling to Trillion Parameter Models with Simple and Efficient Sparsity · jax.lax.ragged_dot API · jax.lax.ragged_dot_general API
2An ER with specialist doctors instead of one generalistIntuition

Think of a hospital emergency room. One setup has a single general-practice doctor who sees every patient. Another has several specialist doctors plus a triage nurse who decides who sees whom.

🩺
dense FFN = one generalist doctor

Every patient (token) sees the same doctor (FFN). Consistent, but the doctor can't be deeply specialized in everything.

🏥
MoE = specialists + a triage nurse

The nurse (router) looks at each patient and sends them to the best-suited specialist (expert). Each patient still sees only one doctor — same "doctor-minutes" per patient — but the hospital as a whole holds far more expertise.

In one line: the router picks one expert per token; every token costs the same compute as before, but the model has many more specialized FFNs to draw from.

ragged_dot is the hospital's scheduling system: instead of walking each patient down the hall to their doctor one at a time (a slow, one-by-one Python loop over experts), it sorts the whole morning's patients by assigned specialist, writes down how many patients each specialist got (group_sizes), and processes each specialist's whole block in one efficient batch.

⚠️
Where the analogy breaks: a real triage nurse has common sense — she'd never send 90% of patients to one doctor, because people would complain. A router has no such instinct. If you don't explicitly penalize imbalance with a loss term, it will happily send most tokens to one or two experts, because that's whatever minimizes the loss it can see. There's no built-in fairness; you have to engineer it in.

4The rules of MoE routing, and why balance mattersHow & why

The rules

  • The router is one Dense(num_experts) layer. It takes a token's hidden vector and outputs one logit per expert, shape (..., E).
  • Softmax turns those logits into routing probabilities P, shape (..., E). Switch Transformer's top-1 rule: expert_id = argmax(P, axis=-1) — send the token only to its single best-scoring expert.
  • Expert capacity caps how many tokens one expert can accept per batch: capacity = capacity_factor * (tokens_per_batch / num_experts). Tokens beyond capacity for an overloaded expert are dropped — they skip the FFN and pass through only the residual connection.
  • The auxiliary load-balancing loss is what actually teaches the router to spread tokens out: L_aux = E * sum_i(f_i * P_i), where f_i is the hard fraction of tokens routed to expert i (from counting — not differentiable) and P_i is the router's average softmax probability for expert i (differentiable). Pairing them lets gradient flow into the router even though the actual routing decision (argmax) is discrete.
✅
lax.ragged_dot(sorted_tokens, W1_all, group_sizes)
One fused grouped matmul computes the first FFN projection for every token in the batch, using whichever expert each token was routed to — no Python loop over experts, no padding to a worst-case capacity.

Why balance is not automatic

  • Rich-get-richer collapse — if a couple of experts get slightly more tokens early on, they get more gradient signal, get better, and the router sends them even more tokens. Left unchecked, other experts starve.
  • Same compute, more capacity — the whole point of MoE is E× more FFN parameters at the same per-token FLOPs. That benefit disappears if only 2 of 8 experts are ever used — you paid for 8 but are only running 2.
  • The auxiliary loss is what prevents this — without it, nothing in the architecture stops collapse. The capacity cutoff plus L_aux together give the router both a hard limit and a gradient-based incentive to spread load.
🔗
Causal chain: dense FFN (same weights for every token) → replace with E experts + a router → router's argmax is discrete, so pair it with a differentiable proxy (L_aux) → ragged_dot executes the resulting variable-sized groups as one fused matmul → check f_i empirically to confirm the incentive actually worked.

The staff lens — one silent failure, one trade-off

A baseline run is about proving the router is healthy — so the dangerous bugs here are the ones that leave shapes and loss looking fine while the numbers underneath are wrong.

⚠️
Failure mode (silent): tokens and group_sizes fall out of sync. lax.ragged_dot(sorted_tokens, W1_all, group_sizes) assumes the token rows are sorted so the first group_sizes[0] rows belong to expert 0, the next group_sizes[1] to expert 1, and so on. If the sort that groups tokens by expert and the group_sizes vector are computed from slightly different routing arrays — for example one includes dropped tokens and the other does not — the shapes still match and the matmul still returns a full-size output with no error. But some tokens get multiplied by the wrong expert's weights, so the loss curve looks plausible while the model learns from scrambled routing. A senior engineer catches this in code review by asserting group_sizes.sum() == number_of_rows_fed_to_ragged_dot and by checking that the token-sort permutation and the group counts come from the exact same routing decision.
⚖️
Trade-off: ragged_dot's fused speed vs. the padded loop's simplicity. A padded, per-expert dense matmul in a Python loop is easy to read and easy to debug — but it wastes FLOPs on padding rows and stops XLA from fusing the experts into one kernel. ragged_dot does the whole grouped matmul as a single fused primitive with no padding, which is why it is faster and lighter, but the payment is that you now own the token-sorting and group_sizes bookkeeping, and a mistake there fails silently instead of loudly. Choosing between them is a design-review decision: use the simple padded loop while you are still validating correctness, then move to ragged_dot once the routing is trusted and speed matters.

7Run the MoE baseline and prove the router is balancedProduce

Today's task (from the curriculum): build the MoE FFN block with jax.lax.ragged_dot, wire it into the addition-transformer in place of the dense FFN, run a ~10M-parameter baseline, and check — from real logged data, not assumption — that tokens spread roughly evenly across experts.

⚠️
The trap: a low or falling L_aux is not proof of balance. L_aux is a soft proxy built from router probabilities P_i; the hard routing decision (argmax) can still be lopsided even while L_aux looks fine — especially early in training. You must inspect the actual per-expert token counts (group_sizes / f_i), aggregated over a trailing window of many steps, not a single batch.

Acceptance criteria

  • Training script runs end-to-end with no NaNs/crashes; total parameter count is verified at ~10M (printed and logged).
  • f_i is logged for every expert at every logging interval across the full run — not just the final step.
  • No expert has f_i == 0 for an extended trailing window (no dead experts), and no expert's f_i is wildly above 1/num_experts for an extended trailing window (no collapsed expert). The report states the actual thresholds used.
  • L_aux is logged alongside f_i, with a written comment on whether it trended down as balance improved (or why not, if it didn't).
  • A plot (bar or line chart, per expert over steps) exists showing the routing distribution visually, not just as raw numbers in a log.
