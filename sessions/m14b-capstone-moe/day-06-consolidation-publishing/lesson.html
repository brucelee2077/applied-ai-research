Quick recap: what each piece already is

Pallas is a JAX sublanguage for hand-writing a GPU/TPU kernel instead of letting XLA auto-generate one. You write a function that runs once per "grid cell," and Pallas hands you Refs — mutable pointers into fast on-chip memory (SRAM/VMEM) — instead of the slow, large off-chip memory (HBM/DRAM). You control the block size: how big a tile of the input each grid cell chews on.

The MoE (Mixture of Experts) kernel routes each token to one of many expert sub-networks, each doing an up-projection (D→F) then a down-projection (F→D). Naively that's two matmuls with an intermediate activation written to HBM in between. Fusing them means one kernel does both matmuls back-to-back while the intermediate tensor never leaves SRAM. jax.lax.ragged_dot is JAX's built-in primitive for this kind of variable-group-size matmul — the baseline your hand-written kernel needs to beat.

ThunderKittens (TK) is a CUDA C++ DSL (a mini language embedded in C++ via templates) from Stanford's Hazy Research lab. Its bet: GPUs are collections of tensor cores efficient at one thing — multiplying 16×16 tiles. TK gives you three layers matching three levels of GPU hardware, including a Load-Store-Compute-Finish template: some warps fetch the next tile while others compute on the current one, so memory and compute overlap. TMA (Tensor Memory Accelerator) is dedicated Hopper/Blackwell hardware that moves tiles from HBM to SRAM asynchronously, computing addresses itself so compute cores never pause for address arithmetic.

Linear attention reformulates softmax(QK^T)V to avoid materializing the full N×N attention matrix — O(N) instead of O(N²) in sequence length N. It's the case study TK's paper uses to show a 14× speedup over the strongest prior baseline.

What "publish quality" adds on top of "it works"

Today's new discipline, not new algorithm: rerun both kernels' benchmarks and record exact numbers (not "it felt faster"), write out the correctness proof for each, document every non-obvious line of code with a one-line "why" comment, and push a clean commit history to GitHub.

2The garage workshop, and the display caseIntuition

Think of the last six weeks as building two working prototypes in a garage workshop: a fused MoE gearbox and a hand-tuned engine (the TK kernel).

🔧🚗
Garage prototype = Weeks 13-14

The engine runs. You've proven on the dyno that it's faster than the stock part. But the wiring is exposed, nothing has labels, and only you know why you routed a wire the way you did.

🏆📋
Display case = Weeks 17-18

You build the enclosure, label every wire, write the spec sheet with actual dyno numbers (not "feels torquier"), and put it in a case with a sign saying exactly what it does and why it beats the stock part.

In one line: a mechanic — an interviewer, or future-you in six months — should be able to open the case, read the labels, and rebuild your engine from the documentation alone, without you in the room.

⚠️
Where the analogy breaks: a physical engine's performance is easy to eyeball on a dyno. A kernel's performance can quietly regress if you change GPU, batch size, or compiler version. So "documented" for code must include the exact benchmark harness and hardware/software versions used, not just a number frozen in a report.

4The bar for "publish quality," and why it mattersHow & why

The rules

  • Correctness proof, not a vibe check. State what the unfused reference computes, state what the fused kernel computes per block, argue they're algebraically identical modulo floating-point summation order, then back it with an empirical max(abs(fused_out - ref_out)) test across multiple seeds and tile configs — committed as a real test file, e.g. test_moe_kernel_correctness.py.
  • Environment pinning first. Record JAX version, CUDA/TPU driver version, GPU/TPU model, and Pallas/TK commit hashes in an ENVIRONMENT.md before rerunning any benchmark — a number without this is not reproducible.
  • Real measured numbers, not estimates. Time with jax.block_until_ready() around the timed region, at least 20 repeated trials per config, across at least 4 values of F (two below D, two above D) for the Pallas sweep.
  • Line-level "why" comments. Every non-obvious line — BlockSpec/index_map logic, manual masking for ragged expert boundaries, every warp-specialization and TMA boundary in the CUDA code — gets a one-line comment naming the pattern.
✅
max(abs(fused_out - ref_out)) < 1e-3 in bf16, across 5 seeds and 3 tile-size configs
"The fused kernel's output matches the unfused reference within a stated, justified tolerance — tested, not eyeballed." This is the shape every correctness claim in the report should take.

Why it's a superpower

  • Reproducibility survives you. A pinned environment plus a README with setup/run/expected-output means the headline number can be regenerated by someone who has never met you.
  • Ties speedup back to first principles. The SRAM/FLOP-utilization argument connects the observed speedup to the Roofline model from Phase 2 — a claim an interviewer can push on and you can defend with math, not intuition.
  • Commit history is documentation. One commit per kernel-file finalization (not one giant "final polish" commit) lets the history itself show the refinement process.
🔗
Causal chain: working kernel (Weeks 13-14) → pin the environment → rerun benchmarks with real numbers → prove correctness empirically → annotate every non-obvious line → clean commit history → cold-read test passes → publishable systems artifact.

Today's task (from the curriculum): route this through Claude Code — this is a code/kernel-refinement and benchmarking task, not a new visualization or paper summary.

Acceptance criteria

  • Both kernels build/run cleanly from a fresh clone using only the README instructions (cold-read test).
  • Correctness tests for both kernels exist as committed files and pass, with the numerical tolerance stated and justified in writing.
  • Benchmark results include actual measured numbers (not estimates) for at least 4 F/D configurations (Pallas) and at least one head-to-head vs. PyTorch baseline (TK), with hardware/software versions attached.
  • Every non-trivial line of the Pallas BlockSpec/index_map logic and every warp-specialization/TMA usage in the TK CUDA code has a one-line explanatory comment.
  • Git history shows incremental, labeled commits (not one "final polish" commit) and is pushed to GitHub.
