Mathematical Discovery
(FunSearch)

Some math and algorithm problems have a clear scoreboard — you can score any answer — but nobody knows the best one. FunSearch pairs a code-writing language model with a trusted program checker in a loop, and lets them discover results humans never had. Today: how that loop works, and why it later found new routing algorithms too.

🎯 By the end, you'll be able to: explain the FunSearch generate→verify→store loop, say why it searches over programs not answers, why a hallucinating model is still safe, and why the whole thing needs a trustworthy automated evaluator to work at all.
1 · WHAT IS ITWhat is FunSearch, and what problem does it solve?✓
🧭
What this assumes: you know what a computer program (a function) is, and that a neural network can write text. No prior knowledge of FunSearch, evolution, or math research needed. Start here.

The problem: a clear scoreboard, an unknown best answer

Some questions in math and algorithms have a clear scoreboard — a way to measure how good any proposed answer is — but nobody knows the best answer. One famous example is the cap set problem: it asks for the largest set of points in a grid such that no three of them lie in a line. You can instantly count the size of any candidate set you are handed, so scoring is easy. But for years, the biggest possible set was an open question nobody had solved.

FunSearch attacks exactly this kind of question: easy to score, hard to find.

What FunSearch is

FunSearch stands for "Function Search." It is a method published by Google DeepMind in the journal Nature in 2023. Its key idea: instead of searching for the answer directly, it searches over computer programs (functions) that generate the answer. Here are the four pieces — each word defined before it is used:

  • A large language model (LLM) is a neural network trained to predict text. Here it is a code-writing model that, given a Python function, proposes a new version of it. It is the source of creative ideas — but it is unreliable and often wrong.
  • An evaluator is a fixed, human-written program that runs a candidate function and returns a numeric score (for example, "this cap set has 512 points"). It never uses an LLM. It is deterministic and trusted — the same input always gives the same score.
  • A program database stores the best-scoring programs found so far. It is split into separate groups (called islands) to keep the ideas diverse.
  • An evolutionary loop repeats forever: (1) pick a few good programs from the database, (2) put them in a prompt and ask the LLM to write a better one, (3) run the evaluator to score the new program, (4) if it is valid and good, store it back.

The key trick

The LLM does not output the raw answer (a giant set of points). It outputs a small priority function — short code that decides, one step at a time, which element to add next. A tiny, readable program can build a huge, record-breaking object. And because the evaluator checks every single program, the LLM's frequent mistakes and made-up "hallucinations" get filtered out automatically. Only correct, high-scoring code survives. That is why FunSearch could produce verifiably new mathematics — a better cap-set bound and better online bin-packing rules, both checkable by hand or machine. The same loop later discovered new routing algorithms for real computer systems.

2 · INTUITIONA suggestion box with a robotic testing rig✓

Imagine a company facing a hard operations problem: "route the delivery trucks so we burn less fuel." They run a giant suggestion box.

🧑‍💼✍️
Interns = the LLM

Fast and creative, but unreliable. They scribble many rule-of-thumb ideas on cards — some brilliant, many nonsense. They never learn; they just keep writing.

🤖📏
The testing rig = the evaluator

A robot takes each card, runs its rule against last month's real delivery data, and stamps a fuel number on it. It is honest and never fooled.

🗄️
The filing cabinet = the database

Keeps only the best cards, sorted into several drawers (islands) so no single style takes over. The good stuff piles up on top.

🔁
Each morning = the loop

Managers hand interns the best cards and say "beat these." Do this a million times and the cabinet fills with rules better than any expert wrote.

In one line: unreliable creators + a trusted robotic scorer + a cabinet of winners, spun in a loop — and every kept rule is provably real, because the rig tested it, not because an intern claimed it.

⚠️
Where the analogy breaks: real interns learn overnight and get smarter. The LLM here never updates its weights — it is frozen. All the "learning" lives in which cards you feed it and in the growing cabinet, not in the intern's brain. Also, the rig only measures the one number it was built to measure — if your true goal is subtly different, a rule can win the score and still lose the real problem.

4 · HOW & WHYThe rules of FunSearch, and why it works✓

The rules

  • Search programs, not answers. The LLM writes a small priority function; a fixed greedy builder turns that function into the actual object (the set, the packing). A few lines of code can generate a record-breaking answer.
  • The evaluator is the only judge. It re-runs every program from scratch and returns a real score. If a program crashes, times out, or breaks the rules, it gets a score of −infinity and is thrown away. The LLM's claims about its own output are ignored.
  • The database keeps islands. Programs are split into several isolated groups. Each island keeps its best programs on top. This diversity stops the search from collapsing onto one idea too early.
  • The loop never trains the model. The LLM's weights are frozen. Improvement comes only from feeding it better example programs over time.
✅
Generate → Verify → Store.
Sample best programs → prompt the LLM → it writes a new program → the evaluator scores it → if valid and good, store it back in an island. Repeat millions of times; the best score climbs.

Why it works

  • Unreliable creativity becomes safe. The LLM can hallucinate freely because a wrong program simply scores badly and is dropped. You get the model's ideas without trusting its mistakes.
  • Every result is verifiable. The kept programs are re-scored by trusted code, so a new record is real mathematics, not a story the model told.
  • It generalizes far beyond math. The exact same loop later discovered new online bin-packing heuristics, and in the follow-on ADRS work, new load-balancing and scheduling (routing) algorithms for real systems.
⚠️
The one requirement: you must have a cheap, trustworthy automated evaluator. A subtly wrong evaluator (measuring the wrong quantity, or awarding points for invalid answers) makes the search "succeed" loudly while producing garbage — the loop optimizes exactly what you measure. A flawed verifier is far more dangerous here than a flawed LLM.
🔗
Causal chain: a scorable-but-hard problem → an LLM proposes program mutations → a trusted evaluator filters every one → an islands database keeps diverse winners → the loop, spun millions of times, climbs past the human best → the same loop finds new systems routing algorithms.

7 · PRODUCEBuild a FunSearch-style mini-loop that discovers a heuristic✓

Today's task: build a small, runnable FunSearch-style loop that rediscovers a known heuristic on a toy problem (online bin-packing or small cap-set), plus a short writeup of how DeepMind paired an LLM with an automated evaluator to discover novel routing/heuristic algorithms.

Acceptance criteria

  • python funsearch_mini.py --iters 2000 runs end-to-end and prints an iteration / best-score table that is monotonically non-decreasing in best score.
  • Final best score strictly beats the seed/baseline heuristic, printed side by side (e.g. baseline first-fit vs the discovered rule).
  • Every invalid or crashing candidate is caught and scored −inf, never stored (a unit test asserts a deliberately broken candidate gets −inf and is absent from the database).
  • The database keeps ≥2 islands; a test asserts the island count and that each island holds its top-k by score.
  • If the local genAI bridge is unreachable, the script prints a clear "bridge down, using stub mutator" line and still completes (try/except over openai errors).
  • writeup.md (≤1 page) explains the generate→verify→store loop in ground-zero language, names the two DeepMind results (cap set, online bin-packing) plus the ADRS routing follow-on, and cites the Nature paper and arXiv:2510.06189.
  • A tiny score-vs-iteration line chart is saved as a PNG.
