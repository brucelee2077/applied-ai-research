Phase 5 · Week 20 · Day 3

Evolutionary Prompts
EvoPrompt, AlphaEvolve, AdaEvolve

You already know a genetic algorithm keeps a population of candidates and breeds the best ones. But text and code break the classic breeding moves — you can't splice two sentences or flip a random character in a program and expect it to still make sense. Today's fix: let an LLM be the crossover and mutation operator.

🎯 By the end, you'll be able to: explain how EvoPrompt turns an LLM into a genetic operator over prompts, trace the AlphaEvolve loop that does the same for code, spot reward hacking when a fitness function gets gamed, and build a tiny evolutionary prompt optimizer yourself.
1 · WHAT IS ITWhat is an LLM-driven evolutionary search?✓
🧭
What this assumes: nothing about evolutionary algorithms. You just need to know what an LLM is (it takes text in, produces text out). No prior genetic-algorithm experience needed.

Start from what a genetic algorithm already does

A genetic algorithm (GA) is a search method copied from biology. You keep a population — a set of candidate solutions. Each candidate gets a fitness score, a number saying how good it is. Then you repeat, generation after generation: select the best candidates, crossover (mix two good candidates into one new one), mutate (randomly tweak a candidate to explore nearby ideas), and evaluate the new candidates, dropping the weakest to keep the population size fixed.

The problem: text and code don't survive naive breeding

Classic crossover and mutation are built for fixed-length number lists — swap two array slices, flip a bit. That works fine when your "genome" is numbers. But if your candidate is a prompt (a sentence) or code (a program), cutting two prompts at a random point and splicing them together usually gives you a broken sentence. Randomly flipping characters in code usually gives you something that won't even compile. Naive crossover and mutation on text or code almost always produce garbage.

The fix: let an LLM be the crossover and mutation operator

Instead of splicing text mechanically, you hand the LLM the parent candidates inside a meta-prompt — an instruction that says, in effect, "here are two good prompts and their scores; write one new prompt that combines their strengths," or "here is one candidate; write a variant that explores a different idea." Because the LLM understands language and code, its output is almost always well-formed, often genuinely good — not gibberish. This is EvoPrompt's core idea, and AlphaEvolve and AdaEvolve apply the same idea to code.

📦
Classic GA: crossover/mutation = splice two arrays or flip a bit.
LLM-driven GA: crossover/mutation = ask the LLM to combine or vary the candidates.
Same loop structure (select → breed → evaluate → repeat). The LLM just replaces the "how do I make a new candidate" step with something that actually understands the genome.

Two terms you need before we go further

  • Fitness function / evaluator: a fully automatic, executable scorer. It takes one candidate and returns a number — dev-set accuracy for a prompt, or benchmark latency for a scheduler. It must be automatic, no human in the loop, because the search runs thousands of candidates.
  • Reward hacking: the single biggest risk here. If your evaluator has a blind spot, the search — because it is relentlessly optimizing for the score — will find and exploit that blind spot instead of solving the real problem. We'll see a concrete example in the playground.

So what's today's catch?

A high fitness score is not proof of a good candidate. It only proves the candidate is good at the thing your evaluator measured. That gap is exactly why, later in this curriculum's arc, evolved code gets checked by formal verification (TLA+) before anyone trusts it in production.

2 · INTUITIONA professional recipe test kitchen✓

Think of a professional test kitchen, not a home cook. A chef wants the best possible dish, so the kitchen runs many variations in parallel and lets a tasting panel score each one on a fixed rubric.

🥣✂️🥣
Naive crossover = cut-and-paste lines

Take line 3 from recipe A, line 7 from recipe B. This usually makes a nonsense recipe — like adding baking soda to a stir-fry. This is what happens when you splice raw text or code.

👨‍🍳✨
LLM crossover = ask the sous chef

Hand both recipes to a skilled sous chef: "these two scored well for different reasons — combine what worked from each into one coherent new recipe." The sous chef understands why each recipe worked, so the result is coherent, not garbage.

In one line: the tasting panel's rubric score is the fitness function; the sous chef is the LLM acting as crossover/mutation operator; many rounds of tasting-and-remixing is the evolutionary loop.

⚠️
Where the analogy breaks: a human tasting panel has real judgment — it can catch "this technically follows the rubric but tastes wrong." An automatic evaluator in real code/prompt search usually can't do that. It only measures exactly what you coded it to measure, so the search can find a dish that scores perfectly by gaming the rubric (say, oversalting specifically because the rubric only checks "is salt present") rather than being genuinely good. That gap is reward hacking, and it's why real systems need a second, independent check.

4 · HOW & WHYThe rules of the loop, and why it matters✓

The rules

  • The candidate is whatever you're searching over — a prompt string in EvoPrompt, or a code diff in AlphaEvolve/AdaEvolve.
  • The fitness function must be fully automatic: dev-set accuracy for a prompt, benchmark latency/throughput for a scheduler, test-pass rate for code. No human in the loop, because you'll score thousands of candidates.
  • Selection keeps the fittest candidates as parents; crossover and mutation are both done by an LLM meta-prompt, not by mechanical splicing.
  • AlphaEvolve adds a program/prompt database: every (candidate, score) pair ever tried gets fed back into future meta-prompts, so the LLM can see "here's what has and hasn't worked."
  • AdaEvolve adds an adaptive controller: it tracks an accumulated improvement signal per sub-population and reallocates compute away from stagnated populations toward promising ones, instead of using a fixed schedule.
✅
meta-prompt("Here are prompt P1 (71.2%) and P2 (74.5%). Write ONE new prompt combining their strengths.")
The LLM reads both parents and their scores, and produces a new candidate — this is the "crossover" step, done by language understanding instead of string splicing.

Why it's a big deal

  • Well-formed offspring almost every time — because the LLM understands the genome (language or code), its mutations and crossovers are coherent, not gibberish.
  • Finds things humans wouldn't try — AlphaEvolve found a data-center scheduling heuristic now used in Google's production Borg system, and a 4×4 complex matrix-multiplication algorithm beating Strassen's 1969 result, after 56 years unbeaten.
  • Composable with memory — the program database means the search gets smarter over generations, not just luckier.
🔗
Causal chain: classic GA (select → crossover → mutate → evaluate) → text/code breaks naive crossover/mutation → replace those two operators with an LLM meta-prompt call → EvoPrompt (prompts) and AlphaEvolve/AdaEvolve (code) → but the fitness score is still just a proxy, so reward hacking is always possible → next line of defense: formal verification (TLA+), later in this arc.

7 · PRODUCEBuild a minimal LLM-driven evolutionary prompt optimizer✓

Today's task (from the curriculum): build the mechanics of connecting an LLM with a genetic algorithm — using it to mutate and cross-breed candidate prompts across generations, with an automatic evaluator scoring each one.

Acceptance criteria

  • evolve.py runs end-to-end for at least 5 generations with no manual intervention, printing each generation's population scores and a running best-so-far.
  • The best-so-far dev-set score at generation 5 is strictly higher than the best score in generation 0 — evidence the loop actually improves fitness, not just churns.
  • reward_hacking_check.py reports the held-out score for the final best prompt alongside its dev-set score, and results.md states the gap between the two explicitly.
  • results.md contains the full generation-by-generation log table and a one-paragraph conclusion connecting the observed gap (or lack of gap) back to reward hacking.
