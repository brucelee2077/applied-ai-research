Phase 4 · Week 13 · Day 4 (Thu)

The FlashAttention Paradigm
Tiling & Online Softmax

Wednesday you learned one specific hardware bug — bank conflicts from bad striding. Today is bigger: the single idea that made every modern long-context transformer possible. Standard attention writes a giant N×N matrix to slow memory and reads it back three times. FlashAttention never writes that matrix at all. Same math, same output, radically less memory traffic.

🎯 By the end, you'll be able to: explain why standard attention's O(N²) memory is a bandwidth problem — not a compute problem — describe how tiling avoids ever materializing the full score matrix, and trace the online-softmax rescaling trick that makes tiling numerically correct.
1 · WHAT IS ITWhat is FlashAttention, and why does it exist?✓
🧭
What this assumes: you know how attention works mathematically — softmax(QK^T/√d)V — and Mon–Wed's Pallas/kernel basics (writing a kernel body, HBM vs. SRAM, why memory trips cost more than math). No prior FlashAttention knowledge needed — that's today's new concept.

The problem: attention has to look at every pair of tokens

Attention compares every token in a sequence to every other token. For a sequence of length N, that means computing an N × N grid of numbers — the attention score matrix, usually called S. If N is 1,024 tokens, S has about a million entries. If N is 100,000 tokens (a long document), S has 10 billion entries. This grid grows with the square of the sequence length — double the text, quadruple the grid.

Here is the twist: on modern GPUs, the actual multiplications needed to fill that grid are not the bottleneck. The bottleneck is moving that grid in and out of memory. A GPU has a huge, slow memory called HBM (High-Bandwidth Memory — think of it as the GPU's "hard drive," tens of gigabytes, but slow to reach) and a tiny, fast memory called SRAM (the GPU's "desk," only tens of megabytes, but roughly 10-20x faster to read and write). The standard way of computing attention writes the entire N × N matrix S out to HBM, reads it all back to run softmax, writes the softmax result P back to HBM, then reads P and V back in again for the final multiply. That is a lot of slow round trips for a matrix that is only ever used once and then thrown away.

The answer: never write the big matrix at all

FlashAttention is an algorithm — and a hand-written GPU kernel — that computes the exact same attention output as the standard formula, but never materializes the full N × N matrix in HBM. It does this by being IO-aware: instead of designing for fewest math operations, it is designed for fewest trips to slow memory. It works on small chunks ("tiles") of the sequence at a time, keeping each chunk in fast SRAM long enough to finish all the math on it, and only ever writing the small final output back to HBM.

📦
flash_attention(Q, K, V)  →  same output as softmax(Q @ K.T / sqrt(d)) @ V, computed tile by tile.
Think of reading a huge spreadsheet a few rows at a time instead of loading the entire file into a tiny notepad app that keeps crashing — you get the same final answer, just without ever holding the whole thing in memory at once.

So what's today's catch?

Softmax is a problem for chunking, because the normal softmax formula needs to see every value in a row before it can produce any output for that row — you divide by the sum of all of them. If you only have one small tile of the row in SRAM at a time, how do you compute softmax correctly without ever seeing the whole row at once? That puzzle — solved by something called online softmax — is the one new idea for today. Two smaller pieces, tiling and online softmax, combine into one paradigm.

📚
Official papers (optional, cited exactly as published): FlashAttention (2205.14135) · flash-attention GitHub repo · FlashAttention-2 (2307.08691)
2 · INTUITIONGrading a giant stack of exams with a tiny desk✓

Picture grading a huge stack of exam papers, but your desk (SRAM) is tiny and the filing cabinet (HBM) across the room is slow to walk to.

📚➡️🗄️
standard attention = grade one page, refile, repeat

You grade one page, walk it to the cabinet, walk back for the next page, walk that one back too. You visit the cabinet constantly. The grading itself is fast — the walking is what eats your afternoon.

📚🖊️✅
FlashAttention = carry a stack, grade it all at your desk, walk once

You carry a small stack of pages to your desk, grade all of them without getting up, keep a running tally as you go, and only walk to the cabinet once you have the final tally for that group. Same grades, far fewer trips.

In one line: the grades (attention output) come out identical either way; FlashAttention just reorganizes when you walk to the slow cabinet so you do it far less often.

⚠️
Where the analogy breaks: a human grader can glance at the whole stack before starting to guess the "curve" (softmax normalizer). FlashAttention's trick is that it does not get to peek ahead — it has to keep correcting its running tally as new pages arrive, without ever seeing the full stack at once. That correction step is today's real new idea (online softmax), and no exam-grading analogy fully captures the arithmetic of it.

4 · HOW & WHYThe rules of tiling and online softmax, and why they matter✓

The rules

  • Split Q into row blocks of size Br, and K/V into row blocks of size Bc. Loop over K/V blocks in the outer loop, and Q blocks in the inner loop (Algorithm 1 in the paper). Each (Q block, K/V block) pair is small enough to fit together in SRAM.
  • For each pair, compute the small tile of scores S_ij = Q_i @ K_j.T, entirely in SRAM — this tile never touches HBM.
  • Because you haven't seen every K/V block yet, you cannot know the true softmax normalizer (the max and the sum over the whole row) when you process the first tile. Online softmax fixes this: for every query row i, keep a running max m_i and running sum l_i, updated after every new tile.
  • Every time a new tile pushes the running max m_i higher, the output accumulated so far was computed against the old (too-small) max — so it must be rescaled before adding the new tile's contribution. This rescale step is what makes the tiled computation mathematically exact, not an approximation.
✅
m_new = max(m_old, rowmax(S_ij))
l_new = exp(m_old - m_new) * l_old + rowsum(exp(S_ij - m_new))
O_new = exp(m_old - m_new) * O_old + exp(S_ij - m_new) @ V_j
Every quantity carries an exp(m_old - m_new) correction factor — this is the rescaling that keeps a partial result exact even though the true max wasn't known when it was first computed.

Why it matters

  • It is exact, not approximate. FlashAttention computes bit-for-bit (up to floating point rounding) the same output as standard attention — this is not a sparse or low-rank shortcut, it is a different execution order for the identical math.
  • Memory traffic drops from quadratic to (roughly) linear in practice. Standard attention needs Θ(Nd + N²) HBM accesses. FlashAttention needs Θ(N²d²/M), where M is the SRAM size — for typical d and M, this is a large constant-factor reduction, and the paper proves it is asymptotically optimal for the achievable range of M (Theorem 2).
  • Fewer HBM trips means real wall-clock speedup — not because of clever math shortcuts, but because the GPU spends less time waiting on slow memory and more time doing useful work.
🔗
Causal chain: attention needs an N×N score matrix → standard attention writes/reads that matrix to slow HBM 3+ times → tiling keeps each small piece in fast SRAM instead → but softmax needs the whole row's sum first → online softmax's running-max rescale trick removes that requirement → exact output, far less HBM traffic.

7 · PRODUCEBuild tiled FlashAttention forward from scratch, validate against naive✓

Today's task (from the curriculum): implement tiled FlashAttention forward with online softmax from scratch, validate it exactly against a naive reference, and measure the HBM-traffic reduction Theorem 2 predicts.

Acceptance criteria

  • naive_attention(Q, K, V) materializes the full N×N score matrix and computes standard softmax(QK^T/√d)V.
  • flash_attention_forward(Q, K, V, block_size_q, block_size_kv) follows Algorithm 1 exactly: outer loop over K/V blocks, inner loop over Q blocks, maintaining running (m, l) statistics per query row and rescaling the output accumulator on every update — implemented with explicit Python loops over blocks (no jax.nn.softmax shortcut on the full matrix), so the tiling structure is visible in the code.
  • For at least 3 random (N, d) shape combinations (e.g. N=128, d=64; N=512, d=32; N=1000 — not divisible by block size, to test the ragged last-block edge case), np.allclose(flash_attention_forward(...), naive_attention(...), atol=1e-5) holds.
  • Both implementations count bytes moved to/from a simulated "HBM" (a wrapper class or counter incremented on every block load/store), printed as a table of naive vs. tiled byte counts scaling with N — reproducing the qualitative shape of the paper's 40.3GB vs. 4.4GB gap at N=1024, even if absolute numbers differ due to simulation simplifications.
  • A plot of HBM-traffic bytes vs. sequence length N for both implementations on the same axes (log scale on the y-axis, since naive traffic grows like N² and tiled traffic grows roughly linearly for a fixed block size), saved under the same experiment directory.
  • A short writeup (3–5 sentences) stating the measured speedup/traffic-reduction ratio and connecting it explicitly to Theorem 2's Θ(N²d²/M) bound.
