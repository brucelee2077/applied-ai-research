Phase 4 · Week 13 · Day 1 (Mon)

The Pallas Abstraction
Writing Kernels by Hand

So far, you wrote plain JAX (jnp.dot, jax.nn.softmax) and let XLA — JAX's compiler — decide how to tile arrays and move data. Today you meet Pallas: the escape hatch that lets you take over that job, tile by tile, memory space by memory space.

🎯 By the end, you'll be able to: explain what a Pallas kernel, a grid, a BlockSpec, and a Ref are, say why hand-written kernels like FlashAttention exist at all, and write a tiny no-grid and gridded Pallas kernel yourself.
1 · WHAT IS ITWhat is a kernel, and what is Pallas?✓
🧭
What this assumes: the JAX core (Weeks 1–2) — pure functions, jit, arrays, shapes. No prior kernel-writing experience needed.

The problem: XLA guesses, and sometimes guesses wrong

Every jnp op you've written so far — jnp.dot, jax.nn.softmax, elementwise math — gets handed to XLA, JAX's compiler. XLA decides how to chop your arrays into tiles, where to put each tile in memory, and in what order to run the math. Most of the time XLA's guess is close to optimal, and you never need to think about it.

But sometimes XLA's generic guess is far from optimal for a specific pattern. The most famous example: computing attention. A naive attention implementation builds the full (seq_len, seq_len) attention matrix in slow, off-chip memory, when a smarter tiling could keep almost everything in fast, on-chip memory instead. XLA, working op-by-op, doesn't discover that smarter tiling on its own. A human had to write it by hand — that hand-written kernel is called FlashAttention, and it's one of the most-cited systems papers in modern deep learning.

The answer: Pallas

Pallas is a JAX sub-library that lets you write the tiling and memory-placement decisions yourself, in Python, and still get a compiled, fast kernel out the other end. You write a small function — the kernel body — that describes what happens to one tile of data. Pallas takes care of copying tiles in and out of fast memory and running your kernel body once per tile.

📦
pl.pallas_call(kernel_fn, out_shape=...)(x)  →  runs kernel_fn as a compiled kernel over x, tile by tile.
Same spirit as jax.jit — you still write Python, it still compiles — but now you also say how the data gets tiled and moved, not just what math happens.

So what's today's catch?

You're trading automatic tiling for manual control, so three new vocabulary words show up: a Ref (a handle to a block of memory, not a plain array), a grid (how many tiles you're cutting the problem into), and a BlockSpec (which tile of the full array each grid step should see). We build all three from scratch today, with no grid first, then with one.

2 · INTUITIONA warehouse with a tiny front counter✓

Picture a huge warehouse (that's your array's home in the chip's main memory) and a small counter at the front where a worker can actually pack boxes (that's the chip's tiny, very fast on-chip scratchpad). The worker cannot pack boxes sitting in the warehouse — only boxes brought up to the counter.

🏭
plain JAX = a warehouse manager you never meet

You say "pack every box in this shape" and a manager (XLA) decides, behind the scenes, how many boxes to carry to the counter at once and in what order. Usually a good decision — sometimes not.

📦➡️🛎️
Pallas = you write the worker's instructions

You say exactly: "bring up this many boxes, this shape, pack them like this, put the result back here." You control the counter directly, tile by tile.

In one line: the warehouse is slow but huge off-chip memory; the counter is fast but tiny on-chip memory; a Pallas kernel is your exact instructions for moving boxes between the two and doing work at the counter.

⚠️
Where the analogy breaks: there's no literal "worker" — the same compiled kernel body runs once per tile, and on real hardware many tiles can be processed by many parallel execution units at once, not one at a time by a single worker.

4 · HOW & WHYThe three pieces, and why they matter✓

The three pieces

  • Ref — inside a kernel body, you don't get a plain array. You get a reference to a block of memory (x_ref, o_ref). You read it with x_ref[...] and write the output with o_ref[...] = value. This is why Pallas kernels look a little more like low-level code than normal JAX — you're explicitly reading from and writing to memory, not just returning a value.
  • grid — how many times the kernel body runs, and in what shape. grid=(2,) means "run this kernel body twice," once for grid step 0 and once for grid step 1. With no grid at all, the kernel body runs exactly once, over the whole array.
  • BlockSpec — for each grid step, which slice ("tile") of the full array should be copied in. BlockSpec((4, 128), lambda i: (i, 0)) says: each tile is shape (4, 128), and grid step i gets block index (i, 0) — Pallas multiplies that block index by the block shape to find the actual offset, so step 0 gets rows 0:4 and step 1 gets rows 4:8.
✅
pl.pallas_call(k, grid=(2,), in_specs=[pl.BlockSpec((4,128), lambda i: (i,0))], out_specs=pl.BlockSpec((4,128), lambda i: (i,0)), out_shape=...)
"Run the kernel twice. Each time, hand it a 4×128 tile — step 0 gets tile 0, step 1 gets tile 1 — and write the result to the matching output tile."

Why this is worth learning

  • Memory hierarchy control — the whole point of a hand-written kernel is deciding what stays in fast on-chip memory (VMEM on TPU, roughly analogous to SRAM/shared memory on GPU) versus what has to round-trip through slow, large off-chip memory (HBM). Pallas is where you make that call explicitly.
  • This is how FlashAttention works — it's a Pallas/CUDA kernel that tiles the attention computation so the huge intermediate score matrix never fully exists in slow memory, only tile by tile in fast memory. You'll build toward that understanding across this week.
  • It's still just JAX — no new language, no separate compiler toolchain to install. The same jax.jit, jax.vmap, and autodiff machinery you already know can wrap around a Pallas kernel.
🔗
Causal chain: XLA tiles generically (Weeks 1–2) → some patterns need a specific, hand-picked tiling → Pallas lets you write that tiling directly as a kernel body plus a grid plus BlockSpecs → this week builds toward reading and reasoning about real production kernels like FlashAttention.

7 · PRODUCEBuild a no-grid and a gridded Pallas kernel✓

Today's task (from the curriculum): implement the plain-JAX baseline, then both Pallas variants from the walkthrough above, and prove all three agree numerically.

Acceptance criteria

  • Plain-JAX baseline: y_ref = x * 2.0 on a (8, 128) float32 array, timed and printed for comparison.
  • No-grid Pallas kernel: double_kernel(x_ref, o_ref) via pl.pallas_call with no explicit grid; assert jnp.allclose(y_pallas, y_ref).
  • Gridded Pallas kernel: grid=(2,), explicit BlockSpec((4, 128), lambda i: (i, 0)) for both input and output; print pl.program_id(0) for each of the 2 grid steps to prove the kernel body ran twice on different tiles.
  • Print shapes at every stage — full array, per-tile block, grid size — so the tile-vs-full-array distinction is visible in the output.
  • Assert final numerical equivalence between the plain-JAX result and both Pallas variants.
