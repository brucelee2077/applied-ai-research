1 · WHAT IS ITWhat is LLM serving, and why does it need its own field?✓
🧭
What this assumes: the roofline math from earlier this week (compute-bound vs. memory-bound, FLOPs/s, HBM bandwidth). No prior serving-systems experience needed.

The problem: a trained model is not a product yet

Training gives you a big pile of weights that can predict the next word. Serving is the separate engineering job of taking those weights and running them in production so many people at once can chat with the model, cheaply and fast. This is called LLM serving architecture. It is where scaling-law theory meets real chips, real memory limits, and real angry users waiting for a reply.

Term 1 — the KV cache

A transformer generates text one word (token) at a time. Each new token needs to "look back" at every earlier token using attention. Recomputing that look-back from scratch at every step would be wastefully slow. So instead, the model saves each token's key and value vectors — small number lists produced by attention — the first time it computes them, into a buffer called the KV cache. Every later token just reads this cache instead of recomputing it.

🧮
KV cache size = 2 × bytes_per_element × H × K × L × T
H = size of one attention head, K = number of KV heads, L = number of layers, T = tokens cached so far, and the 2 is because you store both keys AND values.

Term 2 — prefill vs. decode

Answering one request has two phases. Prefill reads your whole typed-in prompt at once, in one parallel pass, and fills the KV cache — this reuses the same weights across many tokens, so it is compute-bound (limited by how many FLOPs/second the chip can do). Decode (generation) then produces one new word at a time; each step touches only 1 new token of real work but still has to reload the parameters and the whole KV cache from memory — so decode is memory-bandwidth-bound (limited by how fast data moves from HBM, the chip's fast on-package memory).

Term 3 — memory fragmentation

Different users type prompts of different lengths and get replies of different lengths. A naive server reserves one fixed, worst-case-sized memory block per user — space that mostly goes unused. That wasted, scattered, unusable memory is fragmentation, and since a TPU v5e chip has only 16GB of HBM, fragmentation directly caps how many users you can serve at once.

Today's puzzle: LLaMA 3-70B, real TPU v5e numbers, and the three ideas — PagedAttention, continuous batching, and disaggregated serving — that every modern serving stack (vLLM, JetStream, TensorRT-LLM) is built on.

2 · INTUITIONA hotel booking rooms for conference guests✓

Think of a hotel that books rooms for conference attendees. Every guest stays a different number of nights.

🏨🔒
Naive booking = fragmentation

Every guest gets a room sized for the longest possible stay (30 nights), even if they stay only 3. You "hold" 27 empty nights nobody else can use. The hotel looks full even though most rooms are mostly empty.

🏨🔁
PagedAttention = book night-by-night

Guests get small blocks from a shared pool, released the moment they check out. The hotel's true capacity gets used, not its worst-case capacity.

In one line: continuous batching is the front desk continuously checking guests in and out instead of waiting for a whole tour group to finish; disaggregated serving is having a separate check-in team (prefill — fast, done once) and a separate ongoing-stay team (decode — slow, trickles out over days), because the two jobs need totally different staffing.

⚠️
Where the analogy breaks: hotel rooms don't get more expensive to "read" the longer a guest stays. A KV cache does — every decode step has to reload the entire growing cache from memory, so a long-staying guest doesn't just occupy space, they also slow down every single interaction with them.

4 · HOW & WHYThe rules of the serving roofline, and why they matter✓

The rules

  • Arithmetic intensity of a chip is FLOPs/s ÷ HBM bandwidth. On TPU v5e (bf16): 1.97e14 / 8.2e11 ≈ 240. This number, B_crit, is the batch size where a matmul flips from memory-bound to compute-bound.
  • Prefill batch size (tokens in a prompt) is usually hundreds to thousands — far above 240 — so prefill is almost always compute-bound.
  • Decode batches only as many concurrent users as fit in memory, which is usually far below 240 — so decode is almost always memory-bound.
  • Quantizing weights to int8 halves the bytes you load per parameter, so B_crit halves too (240 → 120) — fewer concurrent users needed to keep the chip's FLOPs unit as busy as its memory unit.
✅
StepTime = (B×KVSize)/BW + max(2×B×Params/FLOPs, ParamSize/BW)
First term: loading the KV cache for every sequence in the batch, every step (always bandwidth-bound). Second term: the bigger of "doing the matmul FLOPs" or "loading the parameters" — whichever the chip actually waits on.

Why it matters

  • KV cache, not parameters, is usually the real memory bottleneck — at long context and high concurrency, the cache can dwarf the model's own weights (we'll see 1.3TB of KV vs. 70GB of weights next).
  • Fragmentation caps your business — HBM is a hard, fixed 16GB-per-chip resource. Wasted padding directly means fewer paying users served per dollar of hardware.
  • The fix composes — PagedAttention (no padding waste) + continuous batching (no idle slots) + disaggregated serving (each phase gets hardware suited to its bottleneck) is the backbone of vLLM, JetStream, and TensorRT-LLM.
🔗
Causal chain: roofline math (compute-bound vs. memory-bound) → decode is memory-bound because FLOPs per token are tiny but the KV cache must reload every step → fragmentation wastes the very memory decode depends on → PagedAttention + continuous batching + disaggregation fix it in production.
