Batching Economics
Roofline vs. the KV Cache

Monday you learned inference splits into prefill and decode. Tuesday you learned decode is bottlenecked by memory bandwidth, not compute. Today: the fix — batching — and the bill that comes with it — the KV cache. Both grow out of the same number: how many bytes the accelerator must move per step.

🎯 By the end, you'll be able to: compute the memory-bound vs. compute-bound step time for any batch size, find the roofline crossover batch size B*, compute KV cache size from first principles, and explain why MQA/GQA exist.
1 · WHAT IS ITWhat is batching, and why does decode need it?✓
🧭
What this assumes: Monday's prefill/decode split and Tuesday's memory wall. You know that decode generates one token at a time and that this is slow. No prior batching-theory experience needed.

Quick recap: the two phases

Prefill is the first step of inference: the model reads your whole prompt at once and is compute-bound — it's basically one big matrix multiply, and the accelerator's math units are kept busy. Decode is every step after that: the model generates one new token per step, feeding the last token back in as input. This is the phase you learned Tuesday is memory-bandwidth-bound: the accelerator spends most of its time waiting, not computing.

Why decode waits on memory

Here is the fact that drives this whole lesson: before the accelerator can do any math for a decode step, it must pull every weight of the model out of HBM (High Bandwidth Memory — the big memory chip sitting next to the compute cores, as opposed to the tiny, much faster on-chip memory) into that fast on-chip memory. It has to do this on every single step, just to produce one token per sequence. Loading all those weights takes far longer than the matrix multiply itself when you're only generating for one sequence — so most of the step's time budget is spent on the memory trip, not the math. This is the memory-bandwidth-bound regime you saw Tuesday.

The answer: batching

Batching means processing several independent requests' tokens through the model in the same forward pass — as one bigger matrix multiply — instead of one request at a time. The trick that makes this powerful: the weights only need to be loaded from HBM once per step, no matter how many sequences you cram into that step. So if you stack B sequences together, you pay the identical weight-loading cost but walk away with B tokens of useful work. This is called amortizing the weight-loading penalty — spreading one fixed cost over more output.

📦
Same weight-load trip, more tokens out the door: batch=1 → 1 token per trip. batch=128 → 128 tokens per the same trip.
This ratio of useful work done per byte loaded has a name: arithmetic intensity. Bigger batches raise it — up to a point. That "up to a point" is today's second half.

The catch: batching is not free

Every sequence in the batch needs its own memory of what it has attended to so far — a KV cache (short for Key/Value cache), which we define fully in the walkthrough. That cache grows with batch size and with how long the conversation gets, and it competes for the exact same HBM the weights live in. Batching helps throughput, but it eats memory. Today you'll compute exactly where the trade-off breaks, using the same roofline idea from Pope et al. (2022) that you met this week.

2 · INTUITIONThe food-truck chef and her sticky notes✓

Picture a food-truck chef whose ingredients are kept in a delivery van parked a block away. Every trip to the van and back takes 5 minutes, no matter what she brings back.

🚶‍♀️🍔
batch=1 = one burger per trip

She walks 5 minutes, cooks one burger in 30 seconds, walks back for the next order. Almost all her time is walking, not cooking — totally wasteful.

🚶‍♀️🍔🍔🍔
batch=20 = a tray per trip

One 5-minute walk, she hauls back a big tray, and cooks 20 burgers from that single haul. Same walk, 20x the burgers — her burgers-per-minute skyrockets.

In one line: the walk is the fixed weight-loading cost; batching means cooking more burgers per trip, spreading that one fixed cost over more useful output.

⚠️
But here's the part the analogy needs to carry: each of those 20 orders has its own sticky note of "modifications so far" (no onions, extra cheese, hold for table 4...) taped to her station, re-read before every flip. Twenty orders means twenty growing sticky notes eating up counter space — and if the orders sit a long time (long conversations), the notes get longer too. Eventually the notes cover so much counter that there's no room left for the ingredient tray. That counter crunch is the KV cache eating into the same memory the weights need. Where the analogy fully breaks: real hardware has a hard capacity wall — there's no asking for a bigger counter mid-shift, so you plan batch size and context length in advance.

4 · HOW & WHYThe roofline rules, and why the KV cache fights back✓

The rules

  • Step time is t_step = max(t_load, t_compute) — whichever is slower sets the pace, and the accelerator idles on the other side.
  • t_load = weight_bytes / HBM_bandwidth is fixed, independent of batch size B — the weights load once per step no matter how many sequences ride along.
  • t_compute = 2 × params × B / peak_FLOPs grows linearly with B — more sequences, more matrix-multiply work.
  • The crossover B* — where t_compute catches up to t_load — is the hardware's own ridge point: peak_FLOPs / HBM_bandwidth. Below it, batching is free throughput; above it, batching costs latency.
✅
B* = weight_bytes × peak_FLOPs / (HBM_bandwidth × 2 × params)
For a 7B bf16 model at 1.2 TB/s / 200 TFLOP/s: B* ≈ 167. Below batch 167, more batching is nearly free. Above it, step time starts climbing again.

Why the KV cache fights back

  • Batching amortizes weight loading — the fixed cost of the walk to the van gets spread over more burgers, exactly as in Section 2.
  • But the KV cache scales with the same batch size — every sequence needs its own Key/Value history, so cache bytes grow linearly with B and with sequence length. It competes for the same HBM as the weights.
  • Pope et al. (2022) show that at realistic batch sizes and context lengths, the KV cache can exceed the model's own weight size — which is why MQA (Shazeer, 2019) and GQA (Ainslie et al., 2023) redesign attention itself to shrink it.
🔗
Causal chain: decode reloads all weights every step (Tuesday's memory wall) → batching amortizes that fixed cost across B sequences (cheap throughput, up to the ridge point B*) → but each of those B sequences needs its own growing KV cache → cache competes with weights for the same HBM → MQA/GQA shrink the cache so you can push B further.
