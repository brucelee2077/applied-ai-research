Anatomy of a Training Loop

A production framework like nanotron does not hide training behind one magic .fit() button. It shows you every step: load a batch, forward, loss, backward, sync gradients across devices, update the weights, and now and then save. Today: trace that loop with the abstractions stripped away.

🎯 By the end, you'll be able to: name the stages of one training step in order, point to exactly where cross-device gradient sync (all-reduce) happens, explain where checkpointing fits, and say why reading code without abstractions is worth the effort.
1 · WHAT IS ITWhat is a training loop, and what does "no abstractions" mean?✓
🧭
What this assumes: you can read Python, and you know that training a model means adjusting its numbers (weights) so its answers get better. From Week 2 you have also seen all-reduce: a collective operation that sums a value across many devices and gives every device the same total. No prior framework-reading experience needed.

What a training loop is

Training a model is repeating one small routine over and over. Each repeat is called a training step. In one step you take a chunk of data, run it through the model, measure how wrong the model was, figure out how to nudge the weights, and nudge them. Do that millions of times and the model learns.

One training step, spelled out, is six stages in a fixed order:

  1. Load + shard a batch — grab a batch (a chunk of examples) and, on many devices, split it so each device holds a slice.
  2. Forward pass — run the batch through the model to get its outputs (the logits, the raw scores before turning them into a prediction).
  3. Compute loss — one number that says how wrong those outputs were.
  4. Backward pass — work out the gradients: for each weight, which direction lowers the loss.
  5. Synchronize gradients — on many devices, all-reduce the gradients so every device agrees on the same average gradient.
  6. Optimizer step — use those gradients to update the weights.

And once in a while — not every step — a seventh action: checkpoint, meaning save the weights to disk so you can resume if something crashes.

What "no abstractions" means, and why read it

A high-level library lets you write model.fit(data) and hides all six stages inside. That is convenient, but you cannot see where the time and money go. A production framework like nanotron (and its tiny teaching cousin picotron) does the opposite on purpose: it writes out every stage as plain code you can read line by line.

Why bother? Because at scale, every stage is a cost you may need to see and control — the forward pass, the gradient sync across devices, the optimizer memory. You cannot tune what a .fit() call hides from you. Reading the loop without abstractions is how you learn where the real work happens.

4 · HOW & WHYThe order of the stages, and why it matters✓

The rules

  • The six stages run in a fixed order: load/shard → forward → loss → backward → sync → update. Each stage needs the output of the one before it.
  • Gradient sync happens between backward and the optimizer step — never before. You must have the gradients before you can all-reduce them, and every device must agree on the averaged gradient before it updates its weights. Sync in the wrong place means devices drift apart.
  • Checkpointing is periodic, not every step. Saving to disk is slow, so you do it every N steps. Its only job is to let you resume after a crash.
  • On a single device you can skip stage 5 (sync) — there is nothing to synchronize. It exists only because training is spread across many devices (Week 2).
✅
grads = backward(loss) → grads = all_reduce(grads) / world_size → optimizer.step(grads)
"Compute local gradients, average them across all devices, then everyone updates with the same averaged gradient." That middle line is the sync.

Why read the loop without abstractions

  • See every cost — at scale the forward pass, the gradient sync, and the optimizer memory each cost real time and money. A .fit() call hides all of it; the open loop shows you where to look.
  • Control every cost — once a stage is visible you can change it: shard differently, overlap sync with compute, or save checkpoints less often.
  • Survive crashes — a long training run will crash. Checkpointing turns a lost week into a lost hour.
🔗
Causal chain: many devices (Week 2) → gradients must be synced with all-reduce → that sync sits between backward and the optimizer step → reading the open loop is how you see and place it correctly.

Acceptance criteria

  • A tiny model (a couple of linear layers is fine) and a loop over a handful of steps.
