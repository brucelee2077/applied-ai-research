1What is this "systems review" weekend, really?What is it
🧭
What this assumes: Weeks 1–8 of JAX (primitives, sharding, rooflines, MoE, profiling). No new JAX syntax today — this is a reading-and-planning day.

Two linked halves

This day has two parts, and you need both before you touch a keyboard.

Half 1 — the listening assignment. "The Peterman Pod" is a podcast that interviews senior engineers about how they actually build systems, as opposed to how systems are described in textbooks. This episode's guest is James Cowling, who was Dropbox's most senior engineer — their principal/staff-level technical leader — and one of the architects of "Magic Pocket," Dropbox's in-house exabyte-scale block storage system, built to stop paying Amazon S3 and store hundreds of petabytes of user files themselves.

An exabyte is 1,000 petabytes — roughly 1 billion gigabytes. At that scale, you cannot treat a hard drive failure as rare. You must assume disks are failing somewhere in your fleet at every moment, and design for that as the normal case, not the exception.

The theme engineers like Cowling return to again and again: most production outages, and most wasted engineering-years, come not from missing features but from unnecessary complexity — abstractions, distributed components, or config flags added "just in case" that nobody ends up needing, but that everybody has to debug forever after. The craft skill being taught is judgment about when complexity is load-bearing (solving a real, present problem) versus speculative (solving a problem you don't have yet, or may never have).

Half 2 — the practical task

You are one week away from starting a 4-week capstone: building an "Addition Transformer" — a transformer language model, written from scratch in JAX (the numerical computing library you've used since Week 1), using Flax (a neural-network layer library on top of JAX — it gives you Dense, Attention, and other building blocks so you don't hand-write every matrix multiply) and Optax (a library of gradient-based optimizers for JAX, e.g. Adam, gradient clipping, learning-rate schedules).

The model's only job is to learn addition from examples like "1 2 3 + 4 5 = 1 6 8" written as digit sequences — no calculator logic, no rules, just next-token prediction learned from millions of synthetic examples. This weekend's job is to get the environment fully working — Python, JAX, Flax, Optax, device access all installed and verified — before Week 9 Monday, so day 1 of the capstone is spent on infrastructure decisions, not pip install errors.

Why pair these two things on the same day?

The Addition Transformer is intentionally the simplest possible transformer project — one task, one tiny vocabulary, no real-world data mess. The temptation for an engineer coming out of 7 weeks of learning about MoE, tensor parallelism, and multi-host sharding is to over-engineer it: add sharding it doesn't need, a tokenizer library it doesn't need, a config system it doesn't need. Cowling's simplicity lens is the antidote — applied right before you'd otherwise reach for it.

2A house with too many roomsIntuition

Imagine two families building a house. Family A builds exactly the rooms they need right now: a kitchen, two bedrooms, one bathroom. Family B builds those rooms too, plus a wine cellar, a home theater, and a guest wing — "just in case" they need them someday.

🛏️🍳
load-bearing rooms

Family A's rooms all get used every day. When a pipe leaks, there are only 4 rooms to check. Every wall is doing real work holding up the roof.

🏰🕸️
speculative wings

Family B's wine cellar sits empty and collects dust — but it still needs a working door, a working light, and a working drain. Every unused room is one more thing that can break at 3am, and one more thing every new person in the house has to learn.

In one line: complexity is only "load-bearing" if it is currently holding up something real. Otherwise it is a room nobody uses that still needs maintenance forever.

⚠️
Where the analogy breaks: in software, unused rooms are worse than in a house. An empty wine cellar just sits there quietly. An unused code path or config flag can still be hit by a bug, a bad input, or a future engineer who assumes it works — and it usually hasn't been tested as carefully as the rooms everyone actually lives in.

4A test for "is this complexity earned?"How & why

The test

  • Is the problem happening right now, to real users or real data? If yes, complexity that solves it is load-bearing. If it's a problem you imagine might happen someday, it's speculative.
  • Would removing this piece break something today? If nobody can point to a current failure it prevents, it's a candidate for deletion, not a candidate for "let's keep it just in case."
  • Does the team maintaining it understand why it's there? Complexity that nobody can explain is a liability even if it was load-bearing once — the original reason may no longer hold.
  • What is the blast radius if it's wrong? At exabyte scale, an assumption like "disks rarely fail" is wrong constantly, so handling failure isn't optional complexity — it's the actual job. That's the opposite case: complexity that looks scary but is genuinely load-bearing.
✅
Rule of thumb from the episode: build the simple version first, and add complexity only when a real, observed problem forces it.
Large-scale storage systems commonly follow this path: start with straightforward multi-copy replication, then move to more storage-efficient erasure coding only once the failure patterns and access patterns at scale are actually understood — not before.

Why it matters

  • Debugging cost compounds — every extra abstraction, service, or flag is one more thing a future engineer (maybe you, at 3am) has to understand before fixing anything.
  • Premature complexity hides real signal — if you add sharding before you have a scaling problem, you can't tell whether a bug is your logic or your sharding.
  • Load-bearing complexity is still worth its cost — Cowling isn't arguing for naive simplicity everywhere; exabyte-scale failure handling is complex because the problem genuinely is complex.
🔗
Causal chain: real scale (exabytes of data, constant disk failure) → real problems (data loss, downtime) → complexity that earns its keep (erasure coding, automated failure handling) → simplicity everywhere else, on purpose.
