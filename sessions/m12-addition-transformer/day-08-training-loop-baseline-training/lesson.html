1What is a training loop, and why does it need Optax?What is it
🧭
What this assumes: Friday's Flax addition-transformer (random-initialized weights) and Wednesday's synthetic data generator. No prior training-loop experience needed.

The problem: a model with random weights does nothing useful

Friday you built the architecture — the shape of the network. But its weights are still random numbers. Right now, if you feed it "12+7=", it outputs garbage. Something has to change those weights so the model's guesses get closer to the truth. That something is the training loop.

The four repeating steps

A training loop repeats four steps, over and over, thousands of times:

  • 1. Forward pass — run the model on a batch of inputs to get predictions.
  • 2. Loss function — a single number that says "how wrong was this". For "predict the next digit" tasks, the standard choice is cross-entropy: it looks at the probability the model gave the correct digit and penalizes low confidence with -log(p_correct).
  • 3. Gradient — using jax.grad, compute the direction and size of the change to every parameter that would reduce the loss.
  • 4. Optimizer update — push every parameter a small step in that direction.

Steps 3 and 4 together are called the optimizer step.

Where Optax comes in

Optax is JAX's gradient-processing library. It is important to get this right: Optax does not hold your model's parameters — it only transforms gradients. Optax represents an optimizer as a GradientTransformation: a pair of pure functions, init (creates optimizer state, like Adam's momentum buffers) and update (takes gradients plus current state, returns new gradients plus new state).

You build a real-world optimizer by chaining transformations with optax.chain(...) — for example, first a gradient clipping step, then Adam. Clipping exists because early in training, or on one unusually hard batch, gradients can spike to huge values and wreck the weights in a single step ("exploding gradients"). A learning-rate schedule is a function from training step to learning rate: small at the very start (warmup), rising to a peak, then decaying — so the model takes careful steps early and fine-tuned steps as it converges.

So what's today's catch?

The catch is that a training loop can run, show a decreasing loss number, and still be silently broken — for example if it's dragged down by trivially-easy padding tokens instead of the actual digits you care about. Today's ritual for catching this: the overfit-10-examples sanity check. If your loop, loss, and gradients are wired correctly, a model with millions of parameters should memorize 10 fixed examples perfectly, driving loss to near-zero within a few hundred steps. If it can't, something is broken — and it's far cheaper to find that bug on 10 examples in 10 seconds than on millions of examples after an hour of training.

2Tuning a guitar stringIntuition

Think of tuning a guitar. You pluck a string (forward pass), hear how far off the pitch is from the target note (loss), and figure out which way and how hard to turn the tuning peg (gradient — direction and magnitude of the fix).

🎸💥
Yanking the peg = exploding gradient

If you're wildly out of tune, a novice yanks the peg too hard and snaps the string. Gradient clipping caps the size of each correction, regardless of how far off the note is.

🎸🎵
Warmup + decay = careful tuning

A careful tuner starts extra gently on a cold instrument, makes bigger turns once it's warmed up, then fine, tiny turns as the pitch gets close — exactly what a warmup-then-decay schedule does to the learning rate.

In one line: the overfit-10-examples check is like tuning to a single, memorized reference note in a silent room first — if you can't even nail that easy case, don't bother tuning the whole orchestra yet.

⚠️
Where the analogy breaks: tuning one string doesn't affect the others, but in a neural network every parameter update is coupled. Gradient clipping operates on the global norm across all parameters simultaneously, not peg-by-peg, precisely because an unclipped spike in one place can indirectly distort everything else through backpropagation.

4The rules of the loop, and why each piece mattersHow & why

The rules

  • Logits and labels. The model's raw output scores (logits) have shape [batch, seq_len, vocab_size]; the true next tokens (labels) have shape [batch, seq_len].
  • Per-token loss. optax.softmax_cross_entropy_with_integer_labels(logits, labels) turns logits into probabilities and returns per-token loss of shape [batch, seq_len].
  • Masked mean, not naive mean. You must build an explicit mask over only the "answer" positions and reduce with jnp.sum(losses * mask) / jnp.sum(mask) — never a plain jnp.mean.
  • Gradients in one pass. jax.value_and_grad(loss_fn) gives you both the scalar loss and the gradient pytree (matching params's structure) together.
  • Clip before scaling. optax.clip_by_global_norm(max_norm) rescales the entire gradient vector (concatenated across all parameters) so its L2 norm never exceeds max_norm, preserving direction while capping magnitude.
✅
tx = optax.chain(optax.clip_by_global_norm(1.0), optax.adam(learning_rate=schedule))
"Cap the global gradient norm at 1.0 first, then let Adam apply its adaptive per-parameter scaling on the already-clipped gradient." Order in chain is the order of application.

Why each piece matters

  • Cross-entropy — a clean, differentiable score of "how wrong". Confident-and-correct → loss near 0; confident-and-wrong → loss explodes toward infinity.
  • Clipping — prevents one rare, hard batch from producing a gradient with global norm 500 and wrecking the weights in a single step.
  • Warmup + cosine decay — small steps while randomly-initialized weights are fragile, a peak learning rate once things stabilize, then a gentle decay as training converges.
  • The overfit-10 check — the cheapest possible test that your loss, mask, and gradients are wired correctly, before you spend an hour training on millions of examples.
🔗
Causal chain: Friday's architecture (random weights) → today's loss function scores the guesses → jax.value_and_grad turns loss into a direction of improvement → the Optax chain (clip then Adam, on a schedule) turns that direction into a safe parameter update → repeated thousands of times → a model that can add.

The staff lens — one silent failure, one trade-off

The loss reduction is one line of code, and it is the line most likely to be quietly wrong. The optimizer chain gives you stability, but not for free.

⚠️
Failure mode (silent): naive mean instead of masked mean. Writing jnp.mean(losses) over the whole [batch, seq_len] loss array is a one-word change from the correct masked reduction, and it runs without any error — the loss is still a scalar, gradients still flow, the curve still goes down. But now the model is graded on the prompt digits and the pad positions, not just the answer it is supposed to produce. It spends most of its gradient learning to copy the input, and answer accuracy stays low while loss looks fine. A senior engineer catches this in code review by insisting the reduction is jnp.sum(losses * mask) / jnp.sum(mask) over answer positions only, and by sanity-checking that a masked and unmasked loss on the same batch give clearly different numbers.
⚖️
Trade-off: gradient clipping trades peak speed for not blowing up. Clipping the global gradient norm to 1.0 guarantees no single hard batch can send a giant gradient through and wreck the weights in one step. The cost is that on the rare batch where a large, honest gradient really was warranted, you have thrown away magnitude and taken a smaller step than the data called for — so clipping can slightly slow convergence in exchange for stability. Whether to clip, and at what norm, is a design-review decision: too tight and you crawl, too loose and one bad batch can undo hours of training.

⚠️
Gotcha: the most common silent failure is averaging the loss over ALL sequence positions (prompt tokens and padding) instead of only the answer digits. Prompt and padding are trivially easy to predict, so the averaged loss looks like it's decreasing nicely — while the real signal for learning arithmetic gets diluted. Always build an explicit loss mask over the answer span, and sanity-check by printing mask.sum() per example.
