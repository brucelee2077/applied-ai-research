1 · WHAT IS ITWhat is a tokenizer, and why does this capstone need a custom one?✓
🧭
What this assumes: Monday's environment setup for the Addition Transformer capstone, and basic Python dicts/lists. No prior tokenizer experience needed.

The problem: neural networks only understand numbers

A neural network cannot read the string "12+45=57". It only multiplies and adds numbers. So before any text reaches the model, something must turn each character into an integer — and turn the model's output integers back into readable text. That "something" is called a tokenizer.

Every tokenizer has two halves:

  • A fixed vocabulary — a lookup table that gives every allowed symbol its own unique integer ID.
  • encode/decode functions that use that table to turn strings into arrays of IDs, and arrays of IDs back into strings.

How general-purpose tokenizers build their vocabulary

Tokenizers you may have heard of — BPE (Byte-Pair Encoding) and SentencePiece — are what "Attention Is All You Need" and the Scaling Book (from Monday/Friday) assume sit in front of a language model. They build their vocabulary statistically: scan a huge pile of text, count which sub-word chunks ("ing", "tion", "the") show up often enough to deserve their own ID. They usually land on 30,000-256,000 vocabulary entries, because English has that much variety.

Why that is the wrong tool today

The Addition Transformer capstone only ever sees strings built from 13 symbols: the digits 0-9, a space, +, and =. Today you do the opposite move from BPE: a strict, closed-vocabulary character tokenizer. You hand-write the vocabulary as a Python dict with exactly 13 entries. Nothing else is representable — no BPE merges, no learned frequencies, no <unk> fallback for a surprise character (there should never be one, since Wednesday's data generator only ever emits these 13 symbols).

📦
General tokenizer: learns ~50,000+ entries from a huge corpus, because it must handle any English text.
Today's tokenizer: exactly 13 hand-written entries, because the data's true alphabet is exactly 13 symbols.

Why this matters for the whole capstone, not just today

This tokenizer is the contract that turns "12+45=57" into a fixed-shape integer array — every later step (Thursday's padding, Friday's model sizing, later scaling-law runs) builds on top of it. Three concrete reasons a tiny vocabulary matters here:

  • Embedding size is wasted space if unused. The embedding table's parameter count is vocab_size × d_model. Unused vocabulary rows are pure overhead sitting inside your ~10M-parameter budget.
  • Clean parameter counts make scaling laws easier to trust. Slack in the vocabulary adds noise to the parameter accounting you need for a clean Chinchilla-style scaling-law fit later.
  • 13 is the information-theoretic optimum here. When the data's true alphabet is 13 symbols, a 13-entry vocabulary compresses it at the best possible ratio — bigger wastes capacity, smaller (e.g. merging digits) would destroy the exact-arithmetic structure the model needs to learn.
📚
Official references (optional): Attention Is All You Need · The Scaling Book — Transformers
2 · INTUITIONA coat-check counter for a chess tournament✓

Think of a tokenizer as a coat-check counter at an event. Visitors hand over items; the counter gives each item a numbered hook and hands it back later.

🏟️🧥
BPE/SentencePiece = convention-center coat-check

It has hooks for coats, hats, umbrellas, skis, bicycles — because it has no idea what visitors will bring. It needs tens of thousands of hooks to cover every possibility.

♟️🎫
today's tokenizer = chess-tournament coat-check

You know, with total certainty, that every visitor brings exactly one of 13 labeled things. So you build exactly 13 hooks — nothing more, nothing less.

In one line: because you know the guest list in advance (digits, space, +, =), you throw out every hook you don't need, and anyone who shows up with something else (a stray * or a letter) simply cannot check it in.

⚠️
Where the analogy breaks: a coat-check just stores physical objects unchanged and hands them back later. A tokenizer's IDs are not neutral storage — the specific integer assigned to each symbol becomes an index into a learned embedding row. Which integer you pick (digit 7 → ID 7 vs. ID 11) has zero effect on model quality, but it matters a lot for your own sanity when debugging print statements later.

4 · HOW & WHYThe rules of the tokenizer contract, and why they matter✓

The rules

  • VOCAB is a Python list (or string) of exactly 13 symbols: "0123456789 +=". Its order fixes every ID forever — stoi and itos must be built from this one source of truth, never redefined separately.
  • stoi (string-to-int) maps each symbol to its index: {ch: i for i, ch in enumerate(VOCAB)}. itos (int-to-string) is the exact inverse: {i: ch for i, ch in enumerate(VOCAB)}.
  • encode(s) looks up every character of s in stoi with direct indexing (stoi[ch], not stoi.get(ch, fallback)), so a character outside the 13 raises KeyError instead of silently mapping to some fallback ID.
  • decode(ids) looks up every integer in itos and joins the characters back into a string. decode(encode(s)) == s must hold for every valid s.
  • vocab_size is a single named constant equal to len(VOCAB) — exactly 13 — so Friday's architecture-sizing script can compute the embedding table shape without re-deriving it.
✅
encode("*") → raises KeyError: '*'
This is a feature, not a bug: a stray character means the data generator (Wednesday) produced something wrong, and you want that to fail loudly right there — not train on silently corrupted data.

Why it's the right design here

  • Fail loud, not quiet — no <unk> token means there is no way to hide a bug. A general tokenizer maps unknown input to <unk> so it never crashes; that is wrong for a closed, fully-specified alphabet like this one.
  • Exact parameter accounting — the embedding table's parameter count is vocab_size × d_model. With vocab_size=13, that line item in your ~10M-parameter budget is tiny and exact, instead of a bigger unknown you'd have to explain away in a scaling-law fit.
  • No padding yet — padding is Thursday's job (a 14th, padding, symbol added on top of this contract). Adding it today would break the "exactly 13" invariant this file is graded on.
