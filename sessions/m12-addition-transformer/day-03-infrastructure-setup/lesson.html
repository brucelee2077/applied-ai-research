1 · WHAT IS ITWhat is a TPU runtime, and why Flax + Optax on top of JAX?✓
🧭
What this assumes: Phases 1–2 — you're comfortable with JAX arrays, grad, vmap, and jit. No prior Flax, Optax, or TPU experience needed.

The problem: four weeks of building need a stable foundation first

Starting today, you build a real transformer from scratch over four weeks — the "Addition Transformer Crucible." But before any of that, two things must be true: you need real accelerator hardware to train on, and you need a pinned, minimal software stack so nothing shifts under you mid-build. Today is entirely about getting both right. No transformer code, no addition data — just power and tools.

Part 1: the Google Colab TPU runtime

Colab is a hosted Jupyter notebook you run in your browser. Its "Runtime type" is normally CPU or GPU. Today you switch it to TPU — Tensor Processing Unit, Google's custom chip built specifically for the matrix multiplications neural networks need. A standard Colab TPU slice (v2-8 or v5e-1) is one physical board that exposes 8 TPU cores as 8 separate JAX devices. The moment the runtime attaches, jax.devices() should list 8 entries instead of 1 CPU device — your proof the hardware swap worked.

Part 2: pure JAX + Flax (Linen) + Optax — and why each layer exists

"Pure JAX stack" means exactly three libraries — no PyTorch, no Keras, no Hugging Face Trainer:

  • JAX — the array + autodiff + compilation library from Phases 1–2. Already familiar. On its own, JAX has no idea what a "layer" or a "model" is — it only knows pure functions and arrays.
  • Flax (Linen API) — a neural network layer library built on top of JAX. It gives you nn.Dense, nn.Module, and a convention for bundling a model's weights into a PyTree (a nested Python structure of dicts/lists whose leaves are JAX arrays), so you never hand-roll every weight matrix. "Linen" is Flax's current stable API generation. You write a model as a class inheriting nn.Module, with the forward pass inside a method decorated @nn.compact.
  • Optax — a gradient-transformation library, also built on JAX. "Update the weights using gradients" is really a small pipeline — clip the gradient, apply weight decay, apply momentum, scale by a schedule — and Optax exists so you don't write that pipeline by hand every project. An Optax optimizer is not a stateful object like torch.optim.Adam. It's a pair of pure functions, init and update, bundled as an optax.GradientTransformation. optax.chain(...) composes several transformations into one.

Why this matters for the whole capstone

Everything for the next four weeks — the transformer, the training loop, the scaling-law sweeps — sits on this exact stack. If the environment is wrong today (mismatched JAX/jaxlib/libtpu versions, or a Flax version that doesn't match your JAX), every later day inherits a silent breakage that's much harder to diagnose once a transformer is also in the mix.

Think of today like moving into a new machine shop. You don't start cutting metal on day one. First you confirm the power line delivers the right voltage, and you unpack and organize your tool chest so every wrench is where you expect it.

🔌
the power line = the TPU runtime

You check the voltage before plugging anything in. Checking jax.devices() shows 8 TPU cores is the same move — confirm the power is real before you build.

🧰
the tool chest = JAX + Flax + Optax

JAX is the raw metal and physics. Flax is the wrench set built to fit that metal (nn.Dense, nn.Module). Optax is the torque wrench that knows exactly how hard to turn each bolt (gradient updates).

In one line: before any building, confirm the power (TPU) is on and the tools (JAX/Flax/Optax) are the right, matching set.

⚠️
Where the analogy breaks: a physical tool chest has no version-compatibility problem — a 2015 wrench fits a 2025 bolt. JAX, jaxlib (JAX's compiled backend), libtpu (the TPU driver), Flax, and Optax are five separately-versioned packages that must agree with each other. A mismatch doesn't throw an obvious "version mismatch" error — it produces a confusing crash that looks like your code is wrong, when really your toolbox is internally incompatible. There's no physical-tools equivalent of that failure mode.

4 · HOW & WHYHow the stack fits together, and why order matters✓

The rules

  • A standard Colab TPU slice (v2-8 or v5e-1) exposes 8 cores as 8 JAX devices. jax.devices() must show 8 TpuDevice entries, and jax.default_backend() must print 'tpu' — not 'cpu'.
  • nn.Module classes hold no weights themselves. Calling model.init(key, x) traces the @nn.compact forward pass once, infers every layer's shape from x, and returns a variables PyTree of actual weight arrays.
  • model.apply(variables, x) runs the forward pass using those weights — this is the pure-function equivalent of calling a trained layer.
  • An Optax transformation is a pair of pure functions: tx.init(params) builds the optimizer state (e.g. Adam's moment estimates); tx.update(grads, opt_state, params) returns new updates and new state. Nothing is a hidden stateful object.
  • optax.chain(a, b, ...) composes transformations in order — e.g. clip gradients first, then apply AdamW — into one new pure-function pair.
✅
optax.chain(optax.clip_by_global_norm(1.0), optax.adamw(3e-4))
"First clip any exploding gradient to norm 1.0, then apply an AdamW step." One composed GradientTransformation, still just init/update.

Why getting this right today matters

  • Everything downstream depends on it — the transformer, the training loop, and the Week 9–12 scaling-law sweeps all assume 8 TPU devices and this exact library trio are already working.
  • Failures are silent and delayed — a version mismatch between jaxlib and libtpu doesn't error on import; it crashes or hangs the first time you touch a TPU device, often days later during a much more complex debugging session.
  • Pure functions, again — Flax's init/apply and Optax's init/update are both pure-function pairs, consistent with the functional style from Phase 1. Nothing here breaks that discipline.

⚠️
Gotcha: the most common failure is a silent version mismatch. Colab's preinstalled jax/jaxlib is tied to a specific libtpu driver version. Running !pip install -U jax — or letting pip install flax silently pull in a newer JAX — can upgrade jax/jaxlib out of sync with the TPU driver already loaded. The symptom isn't an obvious error; it's a confusing crash or hang the first time you touch a TPU device (e.g. during model.init), long after the imports succeeded quietly. Fix: check versions before installing (pip show jax jaxlib flax optax), install Flax/Optax without letting them upgrade JAX, and if you must upgrade JAX, restart the runtime so the TPU backend re-attaches cleanly.
