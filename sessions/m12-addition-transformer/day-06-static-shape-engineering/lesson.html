Static Shape Engineering
Beating Silent Recompilation

Yesterday's synthetic addition generator makes strings of every different length — "12+34=", "1234+5678=". Feed those straight into a jit-ted training step and JAX will silently recompile on nearly every batch. Today: exactly why that happens, and the one-line fix — deterministic padding — that makes it stop.

🎯 By the end, you'll be able to: explain what triggers a JAX recompilation, prove it with a print-inside-jit probe, and pad every training example to one fixed MAX_LEN with a matching attention mask so the whole run compiles exactly once.
1 · WHAT IS ITWhat actually makes jit recompile?✓
🧭
What this assumes: Weeks 1-8 JAX basics (jit, vmap, pytrees) and Wednesday's synthetic addition-string generator. No prior compiler knowledge needed.

The problem: variable-length data meets a compiler that hates variety

Wednesday's generator makes addition problems like "12+34=46" and "9999+1=10000". Those are different lengths — 8 tokens vs. 12 tokens. If you tokenize each string as-is and hand it straight to a jax.jit-ted training step, almost every batch will look "new" to JAX.

jax.jit does not compile your Python function once and reuse it forever. It compiles a specialized executable for one specific input signature — and silently compiles a brand-new executable the moment it sees a signature it hasn't seen before. Today's job is learning exactly what counts as "a new signature," and today's tool is deterministic padding: a preprocessing step that makes every batch share the same signature, so jit only ever compiles once.

Tracing: JAX runs your function with stand-ins, not real numbers

The first time you call a jit-ted function, JAX doesn't run your code with real numbers. It runs it once with abstract stand-ins called Tracer objects, which carry only two things: shape (e.g. (32, 128)) and dtype (e.g. float32). This one pass — a trace — walks every line and records every array operation into a computation graph called a jaxpr (JAX expression).

Plain Python if/for/while still runs for real during tracing, using whatever concrete Python values are around. But branching on a traced value — an actual array element, not a shape — is illegal: JAX cannot resolve that branch and raises a TracerBoolConversionError.

Compilation: XLA turns the jaxpr into a real executable

Once the jaxpr is captured, JAX hands it to XLA (Accelerated Linear Algebra), Google's compiler for linear algebra programs. XLA fuses operators, plans memory layout, folds constants, and produces one compiled binary specialized for the exact shapes and dtypes it saw. That's why jit is fast: pay the trace-and-compile tax once, then every later call reuses the binary at hardware speed.

The cache: one signature, one compiled executable

JAX keeps a cache: abstract input signature → compiled executable. The signature bundles (1) the shape and dtype of every array argument, (2) the value of any argument marked static (a literal baked into the trace, via static_argnums/static_argnames), and (3) the structure of any pytree argument (dict/list/NamedTuple). Same signature next time → instant cache hit, microseconds. New signature → a full recompile, often hundreds of milliseconds to seconds for a transformer-sized graph.

The fix that unblocks the whole capstone: pick one constant MAX_LEN and right-pad every example up to it, so every batch has shape (batch_size, MAX_LEN) for the entire run — one shape, one trace, one compile.

2 · INTUITIONThe machine shop that builds a new die every time✓

Think of jax.jit as a custom machine shop. Bring in a sheet of metal, and the shop machines a press die that fits that exact shape — then stamps it in half a second. Bring the same shape again tomorrow, and it stamps instantly. Bring a different shape, and the shop doesn't adapt the old die — it throws it away and machines a whole new one from scratch, eating another hour.

📐➡️🔁
unpadded batches = a new sheet size every day

Your delivery truck brings a 12x8 sheet, then a 15x9, then a 9x11 — a different addition-string length every batch. The shop spends all its time re-machining dies and never actually stamps at scale.

📐✅
padding = standardize the blank size once

You decide every sheet gets trimmed or backed to one fixed "blank size" before it reaches the shop, with the unused margin marked as scrap-to-ignore. Now the die gets built exactly once, and every delivery after that is a half-second stamp.

In one line: pick one fixed MAX_LEN, pad every example up to it, and the compiler only ever builds its "die" once.

⚠️
Where the analogy breaks: a real die that gets the wrong-sized sheet jams — a hard, visible failure. JAX's recompilation is not a hard failure. Your unpadded training loop still produces the correct numbers; it just spends most of its wall-clock time re-machining dies instead of stamping metal, and nothing in the loss curve tells you that's happening. That silence is exactly why this bug class is dangerous — it can quietly cost you 10-100x throughput with zero errors thrown.

4 · HOW & WHYThe five recompilation triggers, and why padding fixes #1✓

What actually changes the signature

  • 1. Any change in array shape. Today's focus. Length-12 batch, then length-17 batch → different ShapedArray, mandatory recompile, even though the code is identical.
  • 2. Any change in dtype. float32 vs. bfloat16, even Python int vs. float for a scalar, is a different signature.
  • 3. Changing the value of a static argument. static_argnums/static_argnames bakes a literal Python value into the trace. Every distinct static value gets its own compiled executable — a raw, un-bucketed sequence length passed as static recompiles almost every step.
  • 4. Changing donated buffers or other structural jit config (donate_argnums) between calls on what looks like "the same" function.
  • 5. Pytree structure changes. Adding, removing, or reordering dict/list/NamedTuple keys forces a retrace even if every leaf shape is unchanged.
✅
pad(token_ids, max_len=MAX_LEN, pad_id=PAD_ID) → every example becomes shape (MAX_LEN,)
Stack a batch of these and you always get (batch_size, MAX_LEN) — trigger #1 neutralized for the whole run.

Why it matters for the capstone

  • One trace, one compile, thousands of cheap cache hits — instead of paying XLA's optimization passes (hundreds of ms to seconds) on almost every batch.
  • The mask carries the real information — padding fixes the shape, and a same-shaped boolean attention/loss mask (1 = real token, 0 = padding) keeps the model from being graded on or attending to filler.
  • It must be end-to-end — every other shape-determining value derived from sequence length (position ids, mask builders, any static_argnums helper) has to use the fixed MAX_LEN, not a per-example dynamic length, or trigger #3 sneaks back in.
🔗
Causal chain: variable-length addition strings (Wed) → naive tokenize-and-stack gives ragged shapes → jit's cache keys on shape → new shape each batch → recompilation storm → fixed MAX_LEN + padding + mask → one shape forever → Sat's training loop and Weeks 11-12 scaling runs become computationally feasible.

The staff lens — one silent failure, one trade-off

Fixing the shape with padding is the easy half. The dangerous half is the mask that has to travel with it — get that wrong and nothing crashes, the model just quietly learns the wrong thing.

⚠️
Failure mode (silent): padded but unmasked. You right-pad every example to MAX_LEN so compilation is fast, and the code runs perfectly — no shape error, loss goes down, training finishes. But if the loss or attention never applies the pad mask, the model is graded on the filler positions too. It learns to confidently predict the pad token, and your real-token accuracy plateaus below what it should. There is no exception to trace. A senior engineer catches this in code review by checking that the pad mask is threaded all the way into the loss reduction (loss is averaged over real tokens only, not over all MAX_LEN positions), not just built and then dropped.
⚖️
Trade-off: one big MAX_LEN buys stability but burns compute on air. Padding every batch to a single large MAX_LEN gives you one compile forever, but every short example now carries filler positions that still cost forward and backward FLOPs. Set MAX_LEN too high and most of your compute is spent on padding; set it too low and long examples get truncated and silently lose their last digits. The design-review call is where to set that number — or whether to use a few bucketed lengths (a handful of compiles) to cut wasted compute while keeping the cache small.

7 · PRODUCEProve the recompilation storm, then prove the fix✓

Today's task (from the curriculum): implement deterministic padding on top of Wednesday's synthetic addition-string generator, then empirically prove it collapses many compiles into one — not just assert it.

Acceptance criteria

  • pad_batch(examples: list[list[int]], max_len: int, pad_id: int = 0) -> tuple[jnp.ndarray, jnp.ndarray] produces constant-shape output (batch_size, MAX_LEN) regardless of input example lengths — verified over at least 3 examples of different raw lengths.
  • MAX_LEN and PAD_ID are named constants defined in one place, sized for the two-operand addition problem (longest plausible input + output digits, plus margin) — not re-derived ad hoc elsewhere.
  • The returned mask marks pad positions 0/False and real tokens 1/True — hand-checked against at least one example.
  • recompilation_probe.py instruments a toy jax.jit train step with a trace-counter and runs it once on unpadded variable-length batches, once on padded fixed-shape batches, over ~200 batches drawn from the real synthetic distribution.
  • The unpadded path shows >1 compilation event (close to one per distinct length); the padded path shows exactly 1 compilation event, total.
  • results.md reports, side by side: distinct shapes seen, compilation events, and wall-clock time for both paths — with the measured speedup as evidence, not just an assertion.
  • Everything runs end-to-end from a clean shell (python3 recompilation_probe.py), no manual notebook steps.
