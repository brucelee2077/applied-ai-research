Synthetic Data GenerationThe Addition Data Factory

Every remaining day of the Addition Transformer Crucible needs fuel: millions of exact, perfectly-labeled addition problems. Today you build the machine that manufactures them — a fast, vectorized Python/NumPy generator that never runs out and never makes a mistake.

🎯

1What is synthetic data, and why does this capstone need a factory for it?What is it
🧭
What this assumes: Tuesday's 13-symbol tokenizer, and basic Python/NumPy. No prior data-generation experience needed.

The problem: your model needs to see millions of examples

To learn that "127+45=" maps to "172", the Addition Transformer needs to see a huge number of addition problems, each labeled with the exact correct sum. There is no dataset of "addition problems" sitting on the internet in the shape you need — with the digit range you want, the exact length you want, and zero labeling mistakes. So you have to make the data yourself. Data you make with code, instead of collecting from the real world, is called synthetic data.

Why not just write real addition problems by hand?

Because you need millions of them, and a computer can check its own arithmetic perfectly. If you wrote a + b = c for a million pairs by hand, you would make mistakes. But if you write a program that picks random numbers a and b and then computes c = a + b with the same + operator Python already trusts, every single label is guaranteed correct. This is the entire appeal of synthetic data for tasks like arithmetic: the "ground truth" comes for free from the generator itself, with zero human labeling effort and zero labeling error.

Why the generator has to be fast, not just correct

A generator that is correct but slow is still a problem. If you generate one example at a time in a plain Python for loop, calling Python's random number functions one at a time, producing 10 million rows can take minutes to hours. Today's real skill is not "can you produce a correct addition example" — it's "can you produce millions of them by asking NumPy to create whole arrays of random numbers at once," a technique called vectorization. You ask NumPy once for a million random numbers, not a million times for one random number.

📦
Slow way: for i in range(1_000_000): a = random.randint(...) — a million round-trips through the Python interpreter.
Fast way: rng.integers(0, 1000, size=1_000_000) — one call, one array, computed inside NumPy's compiled C code.

Why this matters for the whole capstone, not just today

The generator you build today is the fuel line for everything downstream: Thursday's fixed-length padding needs to know how long your longest example can get, and Friday's model sizing needs to know how much data actually exists before it overfits. Two concrete reasons a careful generator matters here:

  • Duplication silently inflates your training set. If you pick a and b from a small digit range, you can run out of distinct pairs before you run out of rows you asked for — you end up training and "testing" on the same examples without realizing it.
  • A leaky split makes your evaluation numbers a lie. If the same (a, b) pair appears in both your train set and your held-out set, the model can memorize instead of learning the addition algorithm, and your held-out accuracy will look better than the model actually is.

4The rules of a correct, fast generator, and why they matterHow & why

The rules

  • Use numpy.random.Generator (via np.random.default_rng(seed)), not the older global np.random.seed/np.random functions — it gives you a reproducible, explicit random state, the same philosophy as Day 2's PRNG keys.
  • Ask for whole arrays at once: rng.integers(0, 10**max_digits, size=n) draws n random operands in a single call. Never call a random function inside a Python for i in range(n) loop.
  • Compute the label with real addition, in NumPy, on the whole array at once: c = a + b is exact integer arithmetic, elementwise, for every row simultaneously.
  • Build the text field with vectorized string formatting (e.g. np.char operations or a single pandas column assignment), not a Python loop that calls str() row by row.
✅
a = rng.integers(0, 1000, size=n); b = rng.integers(0, 1000, size=n); c = a + b
Three array-level calls produce n perfectly labeled rows — no Python-level loop over individual examples anywhere in the hot path.

Why it's worth doing carefully

  • Throughput compounds — a vectorized generator produces millions of rows per second; a per-row Python loop is typically one to two orders of magnitude slower, because every call pays the Python interpreter's overhead.
  • The uniqueness ceiling is a hard limit, not a suggestion — with max_digits digits per operand, there are only (10^max_digits)^2 distinct (a, b) pairs. Ask for more rows than that and you are guaranteed duplicates, no matter how good your random generator is.
  • Splitting must happen at the pair level — grouping by the distinct (a, b) pair before splitting, not by row, is what prevents the same pair from landing in both train and held-out sets.
🔗
Causal chain: a 13-symbol tokenizer (Day 2) needs training text → that text must be exact and abundant → a vectorized NumPy generator produces it at scale with zero labeling error → a pair-level split keeps evaluation honest for every day that follows.

The staff lens — one silent failure, one trade-off

Synthetic data feels safe because the labels are exact — but the split you draw on top of it is where a quiet, self-flattering bug lives.

⚠️
Failure mode (silent): train/held-out leakage from a row-level split. You generate millions of rows, then split them randomly into train and held-out. Nothing errors, and held-out accuracy looks great — maybe suspiciously great. The problem: with only (10^max_digits)^2 distinct (a, b) pairs, the same pair appears in many rows, and a row-level split drops copies of it into both sets. The model can memorize those pairs and score high on held-out data it effectively already saw, so your accuracy is partly measuring memorization, not generalization. A senior engineer catches this in code review by requiring the split to be done at the unique (a, b) pair level, and by checking that the train and held-out pair sets have zero intersection.
⚖️
Trade-off: cheap infinite data vs. a hard uniqueness ceiling. A vectorized generator gives you effectively unlimited, perfectly-labeled rows for free — but the number of distinct problems is capped at (10^max_digits)^2. Generate far more rows than that and you are just repeating pairs, which inflates memorization risk and wastes compute on duplicates. The design-review call is choosing max_digits and dataset size together: enough digits that the unique-pair space is much larger than what the model sees, so held-out really tests unseen problems.

7Build the addition data factory — generate, verify, splitProduce

Today's task (from the curriculum): write an optimized data generator capable of producing millions of exact addition sequences (e.g. 1 2 3 + 4 5 = 1 6 8), then prove it is correct, fast, and safe to split for training.

Acceptance criteria

  • generate_addition_data.py exposes generate_batch(n, max_digits, seed) -> pd.DataFrame with columns a, b, sum, text, built entirely from vectorized numpy.random.Generator calls — no per-example Python-loop random calls in the hot path.
  • verify_and_benchmark.py generates at least 1,000,000 and 10,000,000 rows, printing wall-clock time and rows/sec for each, and times a naive per-row Python-loop baseline for comparison (the vectorized version must be at least an order of magnitude faster).
  • The same script asserts every text string round-trips — reparse the digits, recompute the sum, compare to the sum column — for a random sample of at least 10,000 rows, with a 100% pass rate.
  • It reports n_unique / n_total distinct (a, b) pairs and warns if duplication exceeds a threshold given max_digits (recall Section 4: the ceiling is (10^max_digits)^2 pairs).
  • train_holdout_split.py splits at the distinct-(a, b)-pair level — not the row level — into train/held-out sets, saving both as .parquet under sessions/m12-addition-transformer/day-05-synthetic-data-generation/day3_synthetic_data_gen/data/, with zero shared pairs between the two files.
  • A README.md (or sessions/m12-addition-transformer/day-05-synthetic-data-generation/reports/week09_day3_synthetic_data.md) states the throughput numbers achieved, the uniqueness ceiling for the chosen max_digits, and the train/held-out split sizes.
