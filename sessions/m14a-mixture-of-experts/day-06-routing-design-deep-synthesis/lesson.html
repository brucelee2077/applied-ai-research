Module 1 · Represent · Day 3

Routing Design& Deep Synthesis

Every token that hits an MoE (Mixture-of-Experts) layer needs an answer to one question: which expert should handle you? A tiny learned router decides, in one forward pass, and that single decision is why labs can run trillion-parameter models without paying a trillion-parameter compute bill per token. Today: how routing actually works, the ragged-shape problem it creates, and the JAX primitive built to solve it.

🎯
By the end, you'll be able to: trace top-1/top-2 routing from raw logits to a dispatched expert, compute expert-capacity and dropped-token arithmetic by hand, explain why jax.lax.ragged_dot beats one-hot masking, and connect all of it to the inference-economics story you'll write up tomorrow.
1What is MoE routing, and why does it exist?What is it
🧭
What this assumes: you've covered scaling laws and how a transformer's feed-forward network (FFN) works, plus this week's earlier MoE fundamentals days. No prior routing-algorithm experience needed.

The problem: dense models have a hard economic ceiling

A normal ("dense") transformer has one FFN per block, and every token must pass through it. That's simple, but it means every extra parameter you add to the model costs extra compute for every single token, forever. Want a bigger, smarter model? You pay for it on every token you ever generate. Compute cost and model size are welded together.

The answer: a Mixture-of-Experts (MoE) layer

An MoE layer replaces that one dense FFN with N separate, smaller FFNs called experts, plus a small learned router — just a linear layer + softmax. For each token, the router looks at its hidden vector and decides which expert (or experts) should process it. Only the chosen expert(s) run their FFN on that token; the rest sit idle for that token.

📦
This makes the model sparsely activated: total parameter count can be enormous (hundreds of billions to trillions), while the FLOPs spent per token stay close to what a much smaller dense model would spend. MoE decouples "how much the model can know" from "how much compute one token costs."

So what's today's catch?

Routing is the exact algorithm that makes the pick. The router computes softmax(token @ W_router) — a probability over experts — then picks the top-k. Shazeer et al.'s original Sparsely-Gated MoE and GShard used top-2 (two experts per token); Switch Transformer simplified to top-1 and showed it works just as well while halving compute and communication per token. Because different tokens pick different experts, the number of tokens landing on any one expert isn't known ahead of time — this is a ragged (irregularly-shaped) computation problem, and JAX has a specific primitive, jax.lax.ragged_dot, built to handle exactly this. We'll build all of it today.

2The emergency room and the triage nurseIntuition

Picture a big hospital emergency room with 8 specialist doctors on call (the 8 experts), and a triage nurse at the front desk (the router).

🏥➡️👨‍⚕️👩‍⚕️👨‍⚕️👩‍⚕️
dense = every patient sees every doctor

Every patient, no matter their complaint, gets examined by all 8 doctors in sequence. Thorough — but incredibly wasteful, and it gets worse the more doctors you hire.

🩺➡️👨‍⚕️
MoE = the nurse sends you to the right one

The triage nurse looks at each patient for a few seconds and sends them to the 1 or 2 doctors best suited to their case. The hospital can hire many more specialists without making any single visit longer.

In one line: the hospital can grow its total "knowledge capacity" (more specialists) without growing how long any one patient's visit takes, because each patient only occupies 1-2 doctors' time, not all 8.

⚠️
The catch: patients arrive unpredictably. Some doctors get flooded on a busy day (load imbalance) while others sit idle. So the hospital sets a "max patients per doctor per hour" — a capacity limit. Overflow patients for that hour get turned away untreated and sent straight to the exit — that's a dropped token in Switch Transformer terms, passed through via the residual connection instead of being processed.
⚠️
Where the analogy breaks down: real doctors keep learning between patients in ways that generalize. Experts in an MoE are just separately-parameterized weight matrices with no personal judgment — routing is a cold, learned linear-algebra decision made in one forward pass, not triage intuition. And the "capacity limit" isn't a flexible daily call — it's a hard, statically-declared array size fixed before the model even runs, because JAX needs shapes known at compile time.

4The rules of routing, and why ragged_dot mattersHow & why

The rules

  • The router is one linear layer: logits = tokens @ W_router, shape (T, N) for T tokens and N experts. softmax turns it into a probability distribution per token.
  • Top-1 (Switch Transformer) picks argmax — one expert per token, half the compute/communication of top-2. Top-2 (GShard, original Sparsely-Gated MoE) picks the two best experts and combines their outputs, weighted by router probability.
  • Because the number of tokens landing on each expert is data-dependent (not known at compile time), a plain per-expert matmul can't express "give expert 3 only its 91 tokens." This is the ragged-shape problem.
  • jax.lax.ragged_dot(lhs, rhs, group_sizes) solves it: sort tokens into contiguous per-expert groups first, then one fused batched matmul multiplies each contiguous slice of rows against its own expert's weight matrix — no padding, no waste.
✅
ragged_dot(sorted_tokens, expert_weights, group_sizes)
"Multiply each contiguous group of tokens by its own expert's weights." Beats one-hot masking, which builds a dense (N, T, D) tensor that's mostly zeros.

Why it's the crux of MoE economics

  • Constant compute per token — top-1/top-2 routing means active FLOPs per token stay roughly fixed even as total parameters (and total expert count) grow.
  • Not free — the model still needs enough memory to hold all experts resident, since any token could route to any expert. MoE saves compute, not total memory footprint.
  • Load imbalance is real — routing isn't perfectly uniform, so capacity buffers and a load-balancing loss are both required in practice, not optional extras.
🔗
Causal chain: dense FFN forces every token through every parameter → cost scales with total size → MoE splits the FFN into experts + a router → routing creates a ragged per-expert workload → ragged_dot executes that ragged workload efficiently → total knowledge capacity grows while per-token active compute stays roughly flat.

The staff lens — one silent failure, one trade-off

Routing turns a clean matmul into a sort-then-multiply pipeline. That extra bookkeeping is where a quiet correctness bug hides, and the primitive that makes it fast is also what you trade for.

⚠️
Failure mode (silent): group_sizes out of sync with the sorted tokens. ragged_dot trusts you: it multiplies the first group_sizes[0] rows by expert 0's weights, the next group_sizes[1] rows by expert 1's, and so on. If the token sort and the group_sizes vector disagree — an off-by-one boundary, a stale count from a previous step, or tokens not actually contiguous by expert — the op still runs with valid shapes and returns a full-size result. It just multiplies some tokens by the wrong expert's weights. No error, no shape mismatch; the model simply learns from scrambled routing and quietly underperforms. In code review a senior engineer checks that sum(group_sizes) equals the token count and asserts the sort order and the group boundaries are produced together from the same routing decision, not computed twice.
⚖️
Trade-off: ragged_dot saves memory but adds a data-dependent sort. The one-hot-mask alternative is simple and shape-static, but it builds a dense (N, T, D) tensor that is mostly zeros — wasting memory and FLOPs on experts a token never visits. ragged_dot avoids that waste by working on contiguous per-expert groups, but it needs the tokens sorted into those groups first, which is a data-dependent gather/scatter that itself costs time and can be awkward to fuse. In a design review the choice is masking's simplicity and predictable shapes versus ragged_dot's memory and compute savings at the price of a sort step and more bookkeeping.
