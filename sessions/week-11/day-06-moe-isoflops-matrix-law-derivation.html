Quick recap: the machine you already built

An IsoFlops matrix is a grid of training runs. You pick a fixed compute budget C (measured in FLOPs, floating-point operations), and for that one budget you train several model sizes N. Because C ≈ 6·N·D (compute ≈ 6 × parameters × training tokens), a bigger N forces a smaller token count D for the same budget. Plotting final loss against N, for one fixed C, traces a parabola — a U-shape. The bottom of that U is the compute-optimal model size for that budget.

You fit that U-shape with curve_fit (from scipy.optimize): a least-squares solver. You give it a function shape — a parabola — and a set of (N, loss) points, and it returns the best-fit (N*, L_min): the optimal size and the lowest loss for that budget.

Do this for several budgets, collect the (C, N*) pairs, and fit a power law: N*(C) = a·C^alpha and D*(C) = b·C^beta. The exponent tells you how fast the optimal model size (or optimal data size) should grow as compute grows. Chinchilla found beta ≈ 0.5 for dense transformers — optimal tokens grow roughly as the square root of compute.

What's new today: beta_MoE vs. beta_dense

Today's new object is a comparison, not a new formula. A Mixture-of-Experts (MoE) model has many more total parameters than a dense model of the same speed, because most of those parameters (the "experts") sit idle for any given token — a router decides which 1–2 experts handle each token. Only the parameters actually used per token are called active parameters.

The MoE literature (Switch Transformer, GShard) suggests MoE models can be more data-hungry per active parameter than dense models, because each expert only ever sees a slice of the tokens — training an expert well takes more total tokens flowing through the whole model. Today you measure this directly, instead of taking the claim on faith: rerun the exact same IsoFlops matrix on your MoE model, refit the parabolas and power law, and read off beta_moe.

argparse (command-line flag parsing) and subprocess (launching other Python processes) aren't new either — they're the plumbing from Week 10 Thursday that launched dozens of training runs as separate OS processes with different hyperparameters. Today you point that same launcher at your MoE model class instead of the dense one.

2 · INTUITIONThe same oven test, on a smart oven✓

Week 10's dense IsoFlops sweep was like running "how many oven-minutes per cake size" on a normal oven — one heating element, one temperature, bake and measure.

🔥🍰
Normal oven = dense model

One heating element cooks the whole cake. Every part of the batter gets attention from the same element. Simple, predictable energy use.

🔥×8 🍰
Smart oven = MoE model

8 separate heating elements (experts). A router decides which element cooks which part of the batter. Most elements sit idle for most of the batter — but the oven can bake bigger total batches for the same energy bill.

In one line: you rerun your whole grid of budget-vs-size tests on the smart oven, refit the same parabolas and power laws, and ask: does the smart oven need proportionally more batter (data) per cake to reach the same quality, because each of its 8 elements is starved of examples?

⚠️
Where the analogy breaks: real heating elements divide space — each cooks a fixed physical region. MoE experts divide tokens dynamically, per forward pass, via a learned router — the same expert might see wildly different tokens between batches, and which expert fires depends on content, not position. There's also no oven equivalent of load-balancing loss — a training-time correction that forces the router to spread tokens evenly across experts. Ovens don't need that; routers do.

4 · HOW & WHYThe rules of a fair architecture comparison✓

The rules

  • Reuse the exact same FLOP budgets C from the dense sweep. Different budgets would confound the comparison — you wouldn't know whether a difference in beta came from architecture or from testing a different compute range.
  • For MoE, active parameters N means the parameters actually touched in one forward pass — embeddings + attention + router + the 1–2 routed experts — not the total parameter count summed across all experts.
  • Convert each (C, N) pair to a token count using C ≈ 6·N_active·D, using the active parameter count — this is the FLOPs-per-token accounting Chinchilla uses, and it only holds if N means active parameters.
  • Check the router's load-balance metric mid-run. A badly balanced router means some experts are effectively idle — fewer active parameters than intended — which quietly invalidates the loss numbers.
⚠️
The classic mistake: plugging the total sparse parameter count into C ≈ 6·N·D instead of the active count. This makes the MoE model look absurdly compute-efficient (way too little data needed) and produces a beta comparison that reflects a bookkeeping error, not a real architectural difference. Log which parameter count you used at every stage.

Why it matters

  • One pipeline, two architectures — the same train-many / fit-parabolas / fit-power-law machinery you built for dense now generalizes for free; you only changed one flag.
  • Real evidence, not a citation — you measure beta_moe on your own model instead of trusting the Switch Transformer / GShard claim on faith.
  • This is the capstone's central empirical payoff — the Dense-vs-MoE beta comparison is the number that anchors Week 12's final report.
