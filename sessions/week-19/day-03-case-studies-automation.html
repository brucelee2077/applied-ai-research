in Automation

You've learned MoE routing, distributed scheduling, and verifiers. Today the payoff: an AI "evolutionary" loop (ADRS) uses a reliable verifier to search over candidate algorithms — and beats hand-tuned human designs at cloud scheduling, MoE load balancing, and transaction scheduling.

🎯 By the end, you'll be able to: explain the ADRS generate → evaluate → refine loop, walk through three real wins (up to ~50% cheaper scheduling, ~5.0x faster transactions, balanced MoE experts), and name the failure mode that decides whether the whole thing works — the verifier.
1 · WHAT IS ITThree words: algorithm, verifier, ADRS✓
🧭
What this assumes: you know what an AI language model (LLM) is and that computers can run code. No prior systems-research knowledge needed. We define every word before using it.

The whole idea hinges on three words. Let's define them one at a time.

1. Algorithm

Here, an algorithm just means a small piece of decision logic. For example: "when a new job arrives, send it to the region with the lowest predicted cost." Systems researchers spend whole careers hand-tuning these little rules.

2. Verifier

A verifier is a program that takes a candidate rule and answers one question honestly: "how good is it?" It answers by running the rule — either in a real system or in a simulator (a fast software model of the system) — against a fixed workload (a recorded or made-up stream of jobs or requests). The output is a hard number: cost, runtime, or delay.

This matters a lot. The AI never has to "believe" its own idea is good. It measures.

3. ADRS

ADRS stands for AI-Driven Research for Systems. It is the loop the paper names, and it has three phases:

  • Generate — an LLM writes a batch of diverse candidate algorithms as code.
  • Evaluate — the verifier runs each one on the workload and returns a score.
  • Refine — the best candidates are kept and handed back to the LLM to mutate, combine, and improve. Repeat for many rounds.

This is literally evolution over programs: mutation plus selection. The LLM is the source of smart mutations. The verifier is natural selection. The paper runs this with an open-source instance called OpenEvolve.

💡
Why systems research? Unlike "write a good poem," system performance has a reliable, cheap, automatic verifier. No human is needed to grade the answer. That property is exactly what lets the search run for thousands of rounds unattended.

The three case studies you analyze today: multi-region cloud scheduling (up to ~50% cheaper than the human baseline), MoE load balancing (spread tokens evenly across experts so no GPU idles), and transaction scheduling (up to ~5.0x faster than state-of-the-art human designs). Same loop, three different problems.

📚
Official sources (optional): arXiv 2510.06189 · Barbarians at the Gate (SIGOPS) · arXiv 2101.03961 (Switch Transformers)
2 · INTUITIONA kitchen inventing a better recipe✓

Picture a professional kitchen trying to invent a better recipe. Two people run the show.

👨‍🍳
LLM = creative sous-chef

Churns out 50 recipe variations an hour: "more salt," "swap butter for oil," "combine the two best sauces." Endless ideas, no idea which are actually good.

🧑‍⚖️
Verifier = strict food critic

Tastes each dish and gives one honest score out of 100 — every time, no bribes, no fatigue. This is the measurement the whole loop trusts.

Each round, you keep the top-scoring dishes, hand them back to the sous-chef, and say "make these better." After a thousand rounds you often end up with a dish no human chef on staff would have written down — because the search explored combinations humans skip.

The workload is the fixed tasting menu you always test against, so scores are comparable across rounds. Multi-region scheduling, MoE routing, and transaction ordering are just three different "cuisines" — but the same kitchen loop discovers winning recipes in all of them.

⚠️
Where the analogy breaks: a food critic can only taste — it never explains why a dish is good, and it can be fooled if a recipe secretly games the scoring (a dish engineered to hit the critic's sugar-detector without being edible). In ADRS this is the real danger: the AI optimizes exactly the number the verifier reports, so a sloppy verifier produces "great" algorithms that fail in the real world. The critic's integrity, not the chef's creativity, is the bottleneck.

4 · HOW & WHYThe three case studies, and why it works✓

The three wins

  • Multi-region cloud scheduling / load balancing. Decide which datacenter region serves each request, to minimize cost while respecting capacity and latency. The verifier measures total dollar cost on a fixed job stream. ADRS found policies reported up to ~50% cheaper than the human baseline.
  • MoE (Mixture-of-Experts) load balancing. In a Switch-Transformer-style model, each token is routed to one expert (a sub-network). If routing is lopsided, some experts overload and others sit idle, wasting the GPU. Balancing the routing is a scheduling problem ADRS can search. The verifier measures the imbalance factor and throughput.
  • Transaction scheduling. Order concurrent database transactions to maximize throughput without violating correctness (no conflicting writes). The verifier measures throughput and checks serializability. ADRS reported up to ~5.0x runtime improvement over state-of-the-art human designs.
✅
Same loop, three problems. Only two things change per case study: the workload (what job stream you test on) and the verifier (what number counts as "good"). The generate → evaluate → refine engine is identical.

Why systems research admits reliable verifiers

A performance problem reduces to one clean recipe: run the candidate code in a real system or a fast simulator, then read a number (cost, runtime, tail latency). No human judgment is needed, the check is cheap, and it gives the same answer every time. That reliable, automatic verifier is what lets the search run unattended for thousands of iterations — the LLM proposes, the verifier scores, and nobody has to watch.

⚠️
The catch that decides everything. The AI optimizes exactly the number the verifier reports — nothing more. If the verifier is loose (measures throughput but not correctness, or uses a simulator that drifts from production), the loop confidently converges on an algorithm that "wins" by exploiting the gap. That is reward hacking, and it is why the verifier is the objective, not a detail.
🔗
The shifted human role: as AI takes over the algorithm search, the human job moves up a level — to problem formulation (defining the task, the workload, and above all the verifier) and strategic guidance (prompts, constraints, reward shaping). Get the verifier wrong and the AI will happily "win" by cheating it.
