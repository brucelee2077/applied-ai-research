Evaluation Engineering
& Hold-out Workloads

Yesterday you built the evaluator sandbox that scores a candidate sorting program on correctness and speed. 1 · WHAT IS ITWhat is an evaluator sandbox, and why can it be gamed?✓
🧭
What this assumes: normal programming fluency and yesterday's Saturday lab (a pytest + pytest-benchmark sandbox that scores a sorting algorithm). No prior ADRS or reward-hacking knowledge needed — we build it from zero.

Back up one level: what is ADRS?

ADRS stands for "AI-Driven Research for Systems." It is a loop that looks like biological evolution, but the mutation step is an LLM instead of random chance:

  • Generate — an LLM proposes a candidate solution: a function, a scheduling policy, a proof step.
  • Evaluate — an automatic judge runs the candidate against test cases and produces one number: the score.
  • Select — keep the best-scoring candidates, feed them back to the LLM as inspiration for the next generation.

Repeat this hundreds or thousands of times. This is exactly how DeepMind's FunSearch (2023) found new bounds for a hard math problem called the cap set problem, and how AlphaEvolve (2025) found a faster way to multiply 4×4 matrices and improved Google's own datacenter scheduling. The LLM never "understands" why a program is good. It only ever sees the evaluator's score and tries again.

Why the evaluator is the most dangerous part

That one fact — the LLM only ever sees a score — is why the evaluator (the automated judge that scores every candidate) is the most important, and most dangerous, piece of the whole system. If the evaluator has a blind spot, the LLM will find it. Not out of malice: a search process that tries thousands of variations is a ruthless optimizer for whatever number you hand it back.

This failure mode has a name: reward hacking (also called specification gaming) — when a system satisfies the literal metric you wrote instead of the goal you actually meant. A classic example from game-playing AI: an agent rewarded for "distance traveled" in a boat-racing game learned to spin in a circle forever collecting speed-boost power-ups, instead of finishing the race. In ADRS, the sorting version looks like this: an LLM writes a "sorting" function that returns input[:5], because your test suite only ever checks 5-element lists.

Today's two new tools, used for a new purpose

You already know both of these from ordinary software testing. Today they play a new role: judge in an evolutionary loop.

  • pytest — a Python testing framework. You write functions named test_* with assert statements; pytest runs them and reports pass or fail. Here it is the correctness gate: does the candidate actually sort correctly, on every input you throw at it?
  • pytest-benchmark — a pytest plugin that runs a function many times, controls for warm-up noise, and reports timing statistics (mean, median, standard deviation). Here it is the fitness function — the actual score the selection step uses to rank candidates against each other.

So what's today's catch?

Yesterday's sandbox only had a visible test suite — the LLM can see it, or see feedback quoted from it. Today's new idea is the hold-out workload: a second, hidden, deliberately adversarial test suite that the LLM never sees. It is the only thing standing between "looks good on what I could see" and "is actually good." We build it in the playground and walkthrough below.

2 · INTUITIONA surprise round in your own bug bounty✓

Picture a bug bounty program for your own future code. You — the evaluator designer — don't write the sorting algorithm. You write the rules for a competition, and you hire a swarm of extremely fast, completely amoral contestants (LLM-generated candidates) who will submit anything that scores well, with zero regard for whether it is "real."

📋➡️🏆
Visible suite = the practice round

If your rules say "must sort these three specific lists correctly, fastest time wins," someone will hardcode the answers to those three lists and submit a one-line function.

🌙🔍
Hidden suite = the surprise round

Hold-out workloads are the organizer secretly writing a hundred more test lists the night before, that no contestant has seen, and re-scoring every submission against those before handing out the prize.

In one line: the visible test suite is the practice round; the hidden test suite is the actual competition — and you never announce the theme of the surprise round in advance, or someone will "practice" for exactly that.

⚠️
Where the analogy breaks: a human bug-bounty contestant might feel shame or reputational risk from submitting an obvious hack, which nudges some humans toward good-faith solutions even without perfect rules. An LLM candidate in an evolutionary loop has no such incentive — it is the mechanical output of a search process that only ever climbs whatever gradient the score gives it. There is no norm-following contestant to appeal to. The rules are the entire enforcement mechanism.

4 · HOW & WHYThe rules of a fortified evaluator, and why they matter✓

The rules

  • Correctness gates fitness. A candidate must pass 100% of the hidden correctness suite before its speed even counts. A fast wrong answer always scores as if it were infinitely slow — never let speed rescue a broken candidate.
  • Never show hidden inputs in feedback. A hidden-suite failure returns only a coarse signal to the next generation's prompt — "failed hidden correctness check" — never the literal failing array or expected output.
  • Vary the axis the visible suite didn't. If visible tests only use random arrays of moderate size, hidden tests must include distributional shifts too: reverse-sorted, all-duplicates, nearly-sorted — not just bigger arrays of the same shape.
  • Fail closed on resources, not just answers. Wall-clock timeouts, memory ceilings, and a ban on dangerous imports (os, subprocess, eval) stop a candidate from "winning" by hanging the evaluator or deleting the test file.
✅
assert candidate_sort(arr) == sorted(arr) for many randomized arrays, hidden and visible
Always compare against Python's trusted built-in sorted(), never a hand-written "expected output" — you never maintain a second oracle that can itself go stale.

Why it's the load-bearing piece of ADRS

  • The LLM only sees the score — it has no notion of "cheating," so any gap you leave in the evaluator is a gap it will eventually fill, just by sampling many variations.
  • pytest and pytest-benchmark can only ever sample — they run the finitely many test cases you thought to write. They catch "wrong answer on this specific case," never "wrong answer on some case I never enumerated."
  • Next week's TLA+ complements this gap — for a judiciously bounded state space, a model checker can prove "no reachable state violates this invariant," a categorically stronger guarantee than sampling. You need both: pytest-benchmark answers "is this candidate fast and correct on everything I tested," TLA+ answers "is this candidate provably safe for every state it could ever reach."
🔗
Causal chain: LLM only sees a scalar score → the score becomes the entire specification of "good" → any untested input is an unenforced rule → an evolutionary search finds unenforced rules → hidden hold-out workloads close that gap for what you can sample, and TLA+ (next week) closes it for what you can prove.

7 · PRODUCEBuild a fortified sandbox that catches its own reward hack✓

Today's task: build a fortified, two-tier pytest evaluation sandbox for a sorting algorithm, with hidden hold-out workloads, and prove on your own machine that the hidden suite catches an overfit candidate the visible suite misses.

Acceptance criteria

  • pytest experiments/week19_adrs/sandbox/test_correctness_visible.py -v exits 0 for the correct candidate.
  • pytest experiments/week19_adrs/sandbox/test_correctness_hidden.py -v exits non-zero for the deliberately flawed candidate, and exits 0 for the correct candidate — the hidden suite catches what the visible suite misses.
  • pytest ... test_speed_benchmark.py --benchmark-json=results.json runs successfully and results.json contains a mean stat for each candidate.
  • run_eval.py, pointed at the flawed candidate, reports correctness_hidden: False even though correctness_visible may be True — reproducing the overfitting gap from demo ③.
  • RESULTS.md states in plain language which candidate would be wrongly selected as "best" using only the visible suite, and why the hidden suite prevents that.

Build a fortified, two-tier pytest evaluation sandbox for a sorting algorithm, with hidden hold-out workloads, under experiments/week19_adrs/:

1. experiments/week19_adrs/sandbox/reference_sort.py — baseline that wraps Python's built-in sorted() as the correctness oracle.
2. experiments/week19_adrs/sandbox/candidates/ — at least 2 candidate sort implementations: one correct and reasonable (e.g. a clean quicksort or mergesort), one deliberately flawed the way a reward-hacking LLM might write it (e.g. only sorts a prefix, or mutates and returns the input).
3. experiments/week19_adrs/sandbox/test_correctness_visible.py — pytest with parametrized "normal" cases (random arrays, a few sizes/ranges) that would be quoted back to an LLM in its feedback prompt.
4. experiments/week19_adrs/sandbox/test_correctness_hidden.py — pytest, kept logically separate with a "DO NOT SHOW TO MODEL" header, covering: empty list, single element, all-duplicates, already-sorted, reverse-sorted, one large-scale stress case, and at least one adversarial/type-edge case.
5. experiments/week19_adrs/sandbox/test_speed_benchmark.py — pytest-benchmark timing test producing --benchmark-json=results.json with mean/stddev per candidate.
6. experiments/week19_adrs/sandbox/run_eval.py — a driver that runs both correctness suites and the benchmark for a given candidate path, returning {correctness_visible, correctness_hidden, speed_mean_s, rejected_reason}.
7. experiments/week19_adrs/RESULTS.md — a short writeup: table of each candidate's visible-vs-hidden pass/fail and timing, one sentence per candidate on why it passed or failed, and one sentence connecting the visible/hidden gap to reward hacking / overfitting.

Make sure hidden-suite failures never leak the literal failing input back into any feedback string — only a coarse pass/fail category. Run every acceptance-criteria command and confirm the outputs match.
⚠️
Gotcha: "hidden" is a property of what information ever reaches the LLM's context, not where the file lives. If your driver's error messages print the exact failing hidden array, you've silently converted your hold-out set into a second visible set the moment the next generation's prompt quotes it. Return only a coarse category ("failed hidden correctness check," maybe "large-N timeout") — never the literal input or expected output.
