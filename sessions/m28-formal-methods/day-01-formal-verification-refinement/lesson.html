Formal Verification & Refinement
with TLA+

Your Week 19–20 ADRS loop trusts a pytest score to decide if an AI-discovered sorting algorithm is "correct." But a test suite only samples finitely many inputs — it can never prove behavior for every input. Today: write a formal spec in TLA+ and have the TLC model checker exhaustively check every reachable state of a small model, closing the gap a benchmark score can't.

🎯 By the end, you'll be able to: explain what an invariant is and why TLC checking one is categorically different from passing tests, explain state explosion and why models must be bounded, read a small TLA+ spec for a sorting algorithm, and explain what refinement means for connecting an abstract spec to real Python code.
1 · WHAT IS ITWhat is formal specification and model checking?✓
🧭
What this assumes: your Weeks 19–20 ADRS loop — an LLM proposes candidate code (e.g. a sorting algorithm), a Python evaluator scores it with pytest + pytest-benchmark, and the best-scoring candidates survive. You also met reward hacking: the LLM finds a way to make the score go up without doing the thing you actually wanted. No prior formal-methods experience needed.

The gap your evaluator can never close

Your pytest + benchmark evaluator is genuinely useful — it raises your confidence that a candidate is correct. But a test suite only tries a finite list of inputs. It can never try every possible input. So "my test suite passed" and "this is correct for every possible input" are two different claims, and no amount of extra testing turns the first one into the second. Even Week 19 Sunday's hidden hold-out workloads only shrink this gap — they never close it.

That gap is exactly what today's new tool is for.

The answer: TLA+ and the TLC model checker

TLA+ (Temporal Logic of Actions, plus set theory) is a mathematical language for describing precisely what a system does — precisely enough that a computer can check it. You don't run TLA+ like a program. You write a spec: a description of (a) the system's possible states, written as mathematical variables, and (b) the allowed moves between states, written as logical formulas called actions.

Then a tool called the TLC model checker explores — exhaustively, not by sampling — every state the spec can ever reach, checking that certain properties always hold.

Two words you need before anything else makes sense

  • Invariant: a property that must be true in every single state the system can ever be in. For a sort function: "the output has the same elements as the input" and "the output is in order" are invariants. TLC checks one by trying to find a state where it's false. If it explores the whole reachable space and finds none, the invariant is proven for that model — not "probably true," but proven.
  • State explosion: the number of reachable states usually grows exponentially as you add variables or give them more possible values. This is why TLC can't just check "any array of any length" — that search would never finish. You manage this by checking a small, deliberately bounded model (arrays of length ≤ 6, values from a set of size ≤ 4) instead of the unbounded real system.

Why now, in an ADRS curriculum?

ADRS produces code from an untrusted, optimization-pressured source — an LLM rewarded only for raising a number. Property-based testing (Week 19) is necessary but probabilistic: it raises confidence. TLA+/TLC gives you a categorically different guarantee for a bounded model: exhaustive coverage of that model's state space. "AI proposes, evaluator scores empirically, TLC verifies formally" is the closed loop that lets you deploy AI-discovered systems code without trusting the AI.

One more word: refinement

Your TLA+ spec is abstract — it might just say "the sort happened." Your real artifact is executable Python. Refinement is the formal idea that every possible behavior of the concrete Python code is also a behavior the abstract spec allows — the code never does anything the spec forbids. This week's sprint is: write the abstract spec, model-check it, then argue that your AI-evolved Python sorter refines it.

2 · INTUITIONThe inspector vs. the structural engineer✓

Your Week 19–20 pytest/benchmark evaluator is a building inspector who walks through a finished house with a checklist: doors open, lights turn on, no visible cracks. If the house passes, you feel good — but the inspector only visited the rooms that exist today, and only tried the switches that exist today.

🔎🏠
Inspector = your evaluator

Walks through the finished house and tries specific things. Passes today's house on today's checklist. Never saw tomorrow's furniture arrangement.

📐🧮
Structural engineer = TLA+ / TLC

Works from the blueprint. Writes down the load rule ("every beam here holds ≥2000 lbs, for any furniture arrangement"), then mathematically checks — across every arrangement — whether the blueprint's math ever lets a beam fail.

In one line: the inspector samples specific built things; the engineer proves a rule about the design itself, so the proof covers arrangements nobody has walked through yet.

⚠️
Where the analogy breaks: a real house has effectively infinite furniture arrangements, and the engineer still uses approximation and safety margins — not exhaustive enumeration. TLC, by contrast, does literal brute-force enumeration of a finite model you deliberately shrink (arrays of length ≤ 6, not "any array"). Its proof is exhaustive over a toy-sized stand-in for your system, not the real unbounded system. It transfers to the real system only as far as your refinement argument that the small model captures the real algorithm's logic — a step the engineer's blueprint math usually doesn't need, since that math is already general.

4 · HOW & WHYHow TLC actually checks a spec, and why it matters✓

The rules

  • A TLA+ spec has variables (the state) and an Init predicate (the legal starting states).
  • An action is a formula describing a legal move from one state to a next state. Next (or a single named action like Sort) is the transition relation.
  • An invariant is a formula that must hold in every reachable state. TLC tries to disprove it by search; if the search of the whole reachable space finds no violation, the invariant holds for that model.
  • You bound the model — cap sequence length and the value alphabet — so the reachable space is finite and small enough to fully explore. This is the direct countermeasure to state explosion.
✅
CorrectnessInvariant == output # <<>> => (IsPermutation(input, output) /\ IsSorted(output))
"Once the output is non-empty, it must be a permutation of the input AND in sorted order." Two checks combined into one invariant — drop either half and a wrong candidate can sneak through.

Why it's the trust layer ADRS needs

  • Exhaustive, not sampled — for the bounded model, TLC visits every reachable state, so it catches edge cases no one thought to write a test for.
  • Counterexamples are actionable — a TLC failure isn't just "false," it's a concrete trace: the exact input sequence that breaks the invariant. That trace can feed straight back into the ADRS loop as a rejection signal.
  • Composable with what you already have — TLA+/TLC doesn't replace pytest+benchmark. It adds a gate: empirical correctness, then speed, then formal invariant check on the bounded model. All three must pass.
🔗
Causal chain: ADRS evolves candidates (Weeks 19–20) → reward hacking means the empirical score can be gamed → pytest hidden hold-outs shrink but never close the gap → TLA+ invariant + TLC exhaustive search closes it for a bounded model → refinement argument carries that proof toward the real Python code.

7 · PRODUCEBolt a TLA+ correctness gate onto the ADRS sorting sandbox✓

Today's task (from the curriculum): write a TLA+ spec for the Week 19–20 sorting candidate, model-check it with TLC, and wire the verdict into the ADRS evaluator as a new gate.

Acceptance criteria

  • SortSpec.tla parses without syntax errors when run through TLC (java -cp tla2tools.jar tlc2.TLC SortSpec.tla exits without a parse-error status).
  • Running TLC against the intentionally-correct baseline sort (from Week 19) reports "Model checking completed. No error has been found." with a printed state count > 0.
  • Running TLC against a deliberately broken candidate (e.g. an off-by-one sort, or one that drops the last element) produces a counterexample trace showing exactly which invariant (IsPermutation or IsSorted) failed and on what input.
  • adrs_gate.py, run over at least 5 saved candidates from the Week 19–20 evolutionary run's history, produces verification_log.jsonl with one line per candidate recording {candidate_id, pytest_score, tlc_verdict, states_explored, counterexample (if any)}.
  • README.md explicitly states the bounded model's limits (max sequence length, value alphabet size) and names at least one input class NOT covered by the model (the refinement-gap caveat).

⚠️
Gotcha: "TLC found no counterexample" means the algorithm is correct for the bounded model you defined — not for arbitrary-length inputs, and not automatically for the real Python implementation. That transfer is the refinement argument; skipping it silently reintroduces the false confidence you were trying to eliminate. A related trap: an invariant too weak to catch the hack you care about — checking only "output is sorted" and forgetting "output is a permutation of input" would let a candidate that returns <<1,2,3>> regardless of input pass silently.
