Module 6 · Represent · Day 2

Output-SizeArithmetic

Yesterday a filter slid over an image and made a smaller feature map. But how much smaller? If you cannot predict the output size, you cannot stack layers — the shapes will not fit. Today you learn one short formula that tells you the exact width and height coming out of any convolution, once you know the filter size, the step size, and the border padding.

🎯
By the end, you'll be able to: use the formula out = floor((W − K + 2P)/S) + 1 to compute a convolution's output size, and say what kernel size (K), stride (S), and padding (P) each change.
1One formula for the output sizeWhat is it
🧭
What this assumes: Day 1 — you know a filter slides over the image and makes a smaller feature map. Today we count exactly how much smaller.

Why size matters

To stack layers, the shape coming out of one layer must match what the next layer expects. If you guess wrong, the network breaks with a shape error. So you need to predict the output size before you run anything.

The three knobs

Three settings decide the output size of a convolution:

  • Kernel size (K) — how wide the filter is. A bigger filter eats more border, so the output is smaller.
  • Stride (S) — how far the filter jumps each step. Bigger steps mean fewer stops, so a smaller output.
  • Padding (P) — extra zeros added around the border so the filter can reach the edge pixels. More padding means a bigger output.

The formula

For an input of width W, the output width is:

🧮
out = floor( (W − K + 2P) / S ) + 1

floor just means round down to a whole number — you cannot make half a filter stop. Height uses the exact same formula. Keep going 👇

😕
为什么这里容易卡住 · Why this trips people up: 公式里有四个字母 (W, K, S, P)，很多人死记硬背，一旦题目换了设置就懵了。In plain terms: people memorize (W−K+2P)/S+1 as a magic string and then freeze when the numbers change, because they never connected it to the simple act of counting how many times the filter can stop. Once you see it as counting stops, the formula stops being scary.
2Counting flashlight stops across the rowIntuition
🔦
How many stops fit?

Picture the flashlight from Day 1. It covers 3 pixels at once (K = 3). You want to know how many stops it can make across the row. That count of stops is the output width — one output number per stop.

👣
Step size changes the count

If you step 1 pixel at a time (S = 1) you get many stops. If you jump 2 at a time (S = 2) you get about half as many. Padding adds fake pixels at the ends so the flashlight can start right at the edge.

In one line: the output size is just "how many times can the filter stop as it walks across", and the formula is the tidy way to count that.

直觉 / Intuition: 别背公式，先想"探照灯能停几次"——停几次，输出就多宽。In code terms: it is the length of the loop for start in range(0, W+2P-K+1, S) — the output width is exactly how many valid start positions that loop visits, which is why +1 counts the very first stop.

Think of a 5-pixel row and a 3-wide filter, stepping 1 at a time. The filter can start at position 1, 2, or 3 — then it would hang off the edge. That is 3 stops, so the output is 3 wide. The formula gives the same 3 without you drawing it.

⚠️
Where the analogy breaks: a real flashlight can stop anywhere. A filter can only stop where a whole patch still fits inside the (padded) image. That "must fit fully" rule is exactly why we round down with floor.

4The formula, built and worked outMechanism & why

Step 1 — in plain words

Add padding to both ends of the row, so the usable width becomes W + 2P. A filter of width K covers K of those pixels. Slide it forward S pixels at a time and count how many full positions fit. Add 1 because the very first position also counts as a stop.

Step 2 — the formula, symbol by symbol

🧮
out = floor( (W − K + 2P) / S ) + 1
  • W = input width (or height).
  • K = kernel size — the filter's width.
  • P = padding — zeros added to each side (so 2P total, one on each end).
  • S = stride — how far the filter jumps each step.
  • floor = round down; the last partial stop does not count.
  • + 1 = counts the very first position.

Step 3 — a worked example

Take an input width W = 7, filter K = 3, stride S = 2, padding P = 1:

🔢
step 1: W − K + 2P = 7 − 3 + 2×1 = 6
step 2: 6 / S = 6 / 2 = 3
step 3: floor(3) = 3
step 4: + 1 = 4

out = 4 # a 7-wide input becomes 4-wide

So a 7×7 image, run through this convolution, comes out 4×4. Change one knob and the answer changes: with stride 1 and the same padding, the output would stay 7×7.

🪜
Math Ladder — convolution output size
1 · In words: pad the ends, see how many whole filter-stops fit as you step by S, and add one for the first stop.
2 · The formula: out = ⌊(W − K + 2P)/S⌋ + 1 — W = input width; K = kernel size; P = padding per side; S = stride; ⌊·⌋ = floor (the last partial stop is dropped).
3 · Tiny numbers: W=7, K=3, S=2, P=1 → ⌊(7−3+2)/2⌋+1 = ⌊6/2⌋+1 = 4.
4 · Sanity check: set K=1, S=1, P=0 and you must get out = W (a 1×1 filter changes nothing); set P=(K−1)/2, S=1 ("same" padding) and out = W too. If your formula ever returns a number larger than W+2P, it is wrong.

Why the parts are there

  • Without −K: the filter would run off the edge; subtracting K keeps every stop fully inside.
  • Without +2P: edge pixels get looked at less often, and the image shrinks fast; padding fixes both.
  • Without dividing by S: you would count every pixel as a stop; dividing by stride counts only the jumps you actually take.
🔗
The big picture: real networks use this on every layer to keep shapes lined up. Pooling uses the very same formula (K = 2, S = 2 halves the size). Knowing it means you can design a CNN on paper before writing a line of code.

The staff lens — one silent failure, one trade-off

The floor in this formula is where the quiet bug lives, and the stride knob is a genuine design choice, not a free win.

⚠️
Failure mode (silent): the floor throws away edge pixels with no warning. When (W − K + 2P) does not divide evenly by the stride S, floor rounds down and the filter simply never visits the last strip of the input. Say W = 10, K = 3, P = 0, S = 2: you get floor(7/2)+1 = 4, and the rightmost column of pixels is silently dropped. Nothing crashes — the tensor shape is still valid — you just quietly lost information from the edge of every image. A senior engineer, in code review, checks whether (W − K + 2P) is a clean multiple of S and adds padding when it is not, so no input strip goes unseen.
⚖️
Trade-off: a bigger stride saves compute but discards detail. Raising S shrinks the output, which means fewer positions to compute and less memory — a real speed-up. But every step you skip is spatial detail you never look at again, and downstream layers can never recover it. Choosing the stride (and how much to downsample overall) is a design-review decision: you are trading feature-map resolution and small-object sensitivity for speed and memory.
🎤
Say this in an interview: "Output size is ⌊(W−K+2P)/S⌋+1 — it just counts how many times a K-wide filter can stop as it steps by S across a W+2P-wide padded input. Stride shrinks it fastest, padding grows it back; 'same' padding is P=(K−1)/2 at stride 1. The nuance is the floor: when (W−K+2P) isn't a clean multiple of S, the last input strip is silently dropped — no crash, just lost edge pixels — so I check divisibility or add padding before trusting a downsampling layer."
