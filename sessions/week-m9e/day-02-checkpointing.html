Module 9e · Scale · Day 2

Saving the Whole
Game, Not the Score

A frontier run lasts a month. Machines crash — that is certain, not possible. So every so often you must save the run's full state to disk, and when a crash happens you reload and continue. But a save that only keeps the model weights is a trap: the run will restart wrong. Today you learn the four things a checkpoint must store, why leaving out any one silently breaks the resume, and how to save fast without freezing training.

🎯 By the end, you'll be able to: list the four parts a checkpoint must save (weights, optimizer state, RNG state, dataloader position), explain why each one matters, and say what async and sharded checkpointing do to make saving fast.
1 · WHAT IS ITA save file that stores everything✓
🧭
What this assumes: from Day 1 you know a run is many chips acting as one machine, and from earlier modules you know a model learns by updating its numbers each step. Today: how do you save that whole living machine so a crash does not throw the month away?

The month-long run always crashes

A frontier run takes weeks. Over weeks, some machine will fail — a chip dies, a host reboots, the power blips. This is normal, not rare. So you save the run's state to disk every so often. That save is a checkpoint. After a crash you reload the last checkpoint and keep going.

The trap: saving only the weights

It is tempting to save only the model weights — the learned numbers. But that is like saving only your score in a video game and losing everything else. Reload it and the run keeps going, but it goes wrong. A good checkpoint must save four things.

The four things a checkpoint must save

  • Model weights — the learned numbers. Without these you have learned nothing.
  • Optimizer state — the extra numbers the optimizer keeps, like the running averages (momentum) that smooth each update. Drop these and the next updates are jerky.
  • RNG state — the RNG state, the position of the random-number machine. Drop it and randomness restarts from a different place.
  • Dataloader position — how far through the data you were. The dataloader position says which example comes next. Drop it and you re-feed data the model already saw.

Save fast, without freezing training

Saving a giant model takes time. Two tricks keep it cheap: async checkpointing writes in the background so training does not stop, and sharded checkpointing lets every chip save its own slice at once. Keep going 👇

2 · INTUITIONA save file that stores every detail✓
🎮
A real save file

In a good video game, the save file keeps everything: your level, your items, where you stand, which doors are open, even the weather. Reload it and the world is exactly as you left it. You continue as if nothing happened.

📝
Saving only the score

Now imagine a save that keeps only your score. Reload, and you have the right number of points — but you are back at the start, no items, wrong place. The game "continues", but it is not the game you were playing. It is a different run wearing your score.

In one line: the model weights are your score. The optimizer state, RNG state, and dataloader position are your items, your location, and how far you had walked. A checkpoint must save all four, or the reload starts a different run.

Saving in the background while you keep playing is async checkpointing. Letting each part of the world save its own piece at once is sharded checkpointing — many small saves happening together instead of one giant slow one.

⚠️
Where the analogy breaks: a game save is small and one machine writes it. A frontier checkpoint can be terabytes spread across thousands of chips, so it must be written by all of them at once and in the background — a plain "pause and save" would waste huge amounts of run time.

4 · MECHANISM & WHYWhy sharded saving is so much faster✓

Step 1 — in plain words

Writing to disk has a speed, in bytes per second. If one chip gathers the whole model and writes it alone, the time is the total size divided by one chip's write speed. If every chip writes only its own slice at the same time, the time is just one slice divided by that same write speed. Many hands, much faster.

Step 2 — the formula

🧮
one writer: time = total_size / write_speed
sharded (N chips): time = (total_size / N) / write_speed
# total_size = full checkpoint size in bytes
# N = number of chips saving in parallel
# write_speed = bytes per second per chip

Symbols: total_size = the full checkpoint size. N = how many chips write at once. write_speed = one chip's disk speed. Sharded saving divides the work by N.

Step 3 — a worked example

Say the checkpoint is 800 gigabytes, one chip writes at 1 gigabyte per second, and there are 400 chips.

🔢
one writer: 800 GB / 1 GB/s = 800 s # over 13 minutes
sharded 400: (800 GB / 400) / 1 GB/s = 2 s # each writes 2 GB

sharded is 400× faster

One writer would freeze the run for 13 minutes. Sharded, each chip writes only its 2 gigabyte slice at once, so the whole save takes about 2 seconds. Add async — writing in the background — and training barely pauses at all.

Why leaving out any part breaks the resume

  • No optimizer state: the momentum averages reset to zero, so the first steps after resume lurch and the loss can spike.
  • No RNG state: random choices (like dropout) restart from a different place, so the continued run drifts away from the one that never stopped.
  • No dataloader position: the run re-feeds data it already saw, or skips data, quietly changing what the model learns.
🔗
The big picture: a checkpoint saves the whole living run, and saving fast means sharded (each chip its slice) plus async (in the background). Tomorrow you learn why even a perfect four-part save must line up exactly on resume — bit-for-bit — or it silently corrupts a scaling experiment.
