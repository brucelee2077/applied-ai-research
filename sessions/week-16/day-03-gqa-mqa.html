Phase 4 · Week 16 · Day 3 (Wed)

GQA & MQA
Sharing Key/Value Heads

Monday and Tuesday shrank the KV cache after training — by picking which tokens to keep. Today's fix happens before training even starts: change the architecture itself so fewer Key/Value heads exist in the first place. Fewer heads to store means a smaller cache on every single request, forever, for free.

🎯 By the end, you'll be able to: explain why only the K/V heads (not the Q heads) need to shrink, walk through the exact head-grouping math for MHA, GQA, and MQA, convert an MHA checkpoint into a GQA one by mean-pooling, and compute the resulting parameter and KV-cache reduction by hand.
1 · WHAT IS ITWhat are Q/K/V "heads", and what does "sharing" them mean?✓
🧭
What this assumes: Monday's KV cache size formula and Tuesday's SnapKV eviction (both attack the same memory-bandwidth bottleneck). No prior knowledge of GQA/MQA needed.

A quick reminder: what a "head" is

In multi-head attention, the model does not compute attention once. It splits the work into several parallel heads — think of each head as its own small attention calculation, looking at the input from a different angle (one head might track grammar, another might track "who is talking to whom"). Each head has its own three learned projection matrices: one that produces Queries (Q — "what am I looking for?"), one that produces Keys (K — "what do I contain?"), and one that produces Values (V — "what do I actually offer if picked?"). A model with, say, 32 heads has 32 separate Q projections, 32 separate K projections, and 32 separate V projections.

The problem: every head's K and V get cached, and cache is what's expensive

Recall Monday's formula: the KV cache stores one K vector and one V vector per head, per layer, per token. If a model has 32 heads and 32 layers, every single token you feed in or generate adds 32 × 32 × 2 new vectors to the cache. The number of heads is a direct multiplier on cache size — and it was fixed the moment the model finished training. Nothing you do at inference time (like SnapKV) can change how many heads exist.

The idea: what if most heads didn't need their own K and V?

Multi-Query Attention (MQA) and Grouped-Query Attention (GQA) both ask the same question: does every query head really need its own private Key and Value projection? Their answer is no. Multiple query heads can share one K/V head between them — each query head still computes its own attention scores and its own output, but several query heads read from the same stored K and V vectors instead of each keeping a separate copy.

📦
MQA (Shazeer, 2019): all query heads share one single K/V head. GQA (Ainslie et al., 2023): query heads are split into a handful of groups; heads within a group share one K/V head, but different groups have different K/V heads.
Only the number of K/V heads shrinks. The number of Query heads never changes — queries are never cached, so shrinking them wouldn't save any memory.

So what's today's catch?

Fewer distinct K/V heads means each shared head has to serve more query heads at once, which is a real capacity trade-off — pushed too far (all the way to MQA), quality can dip. GQA exists specifically as the middle ground between MHA's full quality and MQA's full compression. We'll see exactly how much quality you keep, and how the paper converts an existing trained MHA model into a GQA one without retraining from scratch.

📚
Official papers (optional): Shazeer, Fast Transformer Decoding: One Write-Head is All You Need (arXiv:1911.02150) · Ainslie et al., GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints (arXiv:2305.13245)
2 · INTUITIONOne shared reference shelf, many readers✓

Picture a small research team. Each researcher (a query head) is investigating something slightly different, and each writes their own personal questions on their own notepad. The question is: does every researcher need their own private copy of the reference library, or can they share one?

📚📚📚📚
MHA = everyone has their own library

Each of the 32 researchers keeps a full private copy of the reference shelf (their own K/V). Nobody waits on anyone else, but you're storing 32 copies of nearly the same shelves.

📚
MQA/GQA = shared shelves, private questions

Instead, a handful of shared reference shelves exist (the K/V heads). Several researchers each walk up to the same shelf, but each still asks their own personal question (their own Q) and gets their own personal answer back. One shelf, many independent readers.

In one line: queries stay personal and never shrink; only the shared reference shelves (K/V heads) shrink — from one shelf per researcher (MHA), down to a handful of shared shelves (GQA), down to a single shared shelf (MQA).

⚠️
Where the analogy breaks: real shared library shelves don't change what's written on them depending on who's reading. But GQA's shared K/V head is produced by mean-pooling the original per-head content, not simply "the same shelf as before" — the content of the shared shelf is itself a blend, an average, of what used to be several different shelves. If those original shelves held very different things, blending them can lose some of that specificity.

4 · HOW & WHYThe exact grouping rule, and why it matters✓

The rules

  • Let num_heads be the number of query heads (unchanged always) and num_groups be the number of distinct K/V heads you choose to keep.
  • Query heads are partitioned into num_groups equal-sized groups of num_heads / num_groups heads each. Every query head in a group attends using that group's single shared K and single shared V.
  • MHA is the special case num_groups = num_heads (every head is its own group of 1 — nothing is shared, this is the identity case).
  • MQA is the special case num_groups = 1 (one giant group — every query head shares the same single K/V head).
  • GQA is anything in between, e.g. num_groups = 8 out of num_heads = 32: 8 shared K/V heads, each serving 4 query heads.
✅
cache_size = 2 × num_layers × num_kv_heads × head_dim × seq_len × bytes_per_element
Same formula from Monday — but now num_kv_heads (= num_groups) is a free architectural knob instead of always equaling num_heads. Shrinking it shrinks the whole cache proportionally, at every context length, for every request.

Converting an existing MHA checkpoint into GQA (the practical trick)

You do not have to train a GQA model from a random start. The GQA paper's key contribution is a way to convert an already-trained MHA checkpoint: for each new group, take the mean (average) of the original K projection weights for every head that falls into that group, and do the same for V. Query and output projection weights are copied through completely unchanged.

✅
W_K_group[g] = mean(W_K_head[h] for h in group g)
Averaging, not picking one and discarding the rest — this keeps the converted model's behavior close to the original before any further training, because the mean is the single point that minimizes squared distance to all the original heads it replaces.

After this mean-pooling step, the paper does a short additional training run — "uptraining" — using only about 5% of the original training compute, to let the model adjust to its new, smaller K/V structure. The mean-pooling is what makes that uptraining fast: it starts the model very close to correct, instead of from scratch.

Why it's a superpower

  • Fixed at training time, paid back on every request — unlike SnapKV (content-dependent, decided per-prompt), GQA's saving is architectural. Every request, regardless of content, gets the smaller cache automatically.
  • A tunable dial, not all-or-nothing — num_groups lets you choose a point between MHA's full quality and MQA's full compression, matching the paper's finding that GQA-8 on a converted T5-XXL model nearly matches MHA quality while running close to MQA speed.
  • Stacks with everything else this week — a GQA model still benefits from SnapKV (fewer token positions) and from quantization (fewer bytes per element) on top of its already-smaller num_kv_heads.
⚠️
Common misunderstanding: GQA/MQA do not reduce the number of query heads, and they do not change the attention computation's parallelism across heads — every query head still produces its own separate output. The only thing that shrinks is how many distinct K and V projections exist and get cached.
🔗
Causal chain: KV cache size scales with num_kv_heads (Monday) → most of those heads' K/V content is redundant across heads that attend similarly → group query heads and share one K/V per group (GQA/MQA) → fewer distinct K/V heads to store, fixed at training time → smaller cache at every context length, with SnapKV (Tuesday) able to shrink it further on top.

7 · PRODUCEPerform GQA checkpoint surgery and measure the reduction✓

Today's task (from the curriculum): analyze how GQA physically changes the parameter structure of the model to reduce the KV footprint during the initial training phase — by actually performing the checkpoint surgery on a toy MHA block and measuring the exact before/after numbers.

Acceptance criteria

  • A toy MHA attention block in JAX (or plain JAX with explicit weight dicts) with configurable d_model, num_heads, head_dim.
  • A pure function mha_to_gqa(params, num_groups) that mean-pools W_K and W_V from [d_model, num_heads, head_dim] down to [d_model, num_groups, head_dim], leaving W_Q untouched.
  • Printed/asserted exact parameter-count reduction (before/after shapes and total element counts) for num_groups=1 (MQA), num_groups=8 (GQA-8), and num_groups=num_heads (identity/MHA).
  • Projected KV cache bytes for a stated (num_layers, seq_len, dtype) config, for each of the three settings above, matching hand-computed values within rounding.
  • A unit test asserting: correct output shapes; num_groups=num_heads returns weights numerically identical to the original (mean-pool of a group of 1 is a no-op); num_groups=1 produces a single merged head equal to the mean of all original heads; and something that fails loudly if the wrong axis gets pooled or if W_Q is accidentally modified.
  • No GPU/TPU required — this is about parameter structure, not measuring real decoding latency.
