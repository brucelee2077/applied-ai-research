Phase 4 · Week 16 · Day 1 (Mon)

Decoding Innovations
The KV Cache Problem

In Phase 1 we learned that generating tokens is limited by how fast we stream the model's weights from memory. Today we meet a second memory hog that takes over once the text gets long: the KV cache. We'll prove exactly why it grows without bound past 100k tokens — and set up the whole week as engineering answers to "how do we stop it eating the GPU?"

🎯 By the end, you'll be able to: explain what the KV cache stores and why, write the exact size formula 2 · n_layers · n_kv_heads · head_dim · seq_len · dtype, prove one 100k-token sequence exceeds a single 80GB card, and name which Week-16 trick attacks each factor.
1 · WHAT IS ITWhat is the KV cache, and why does it exist?✓
🧭
What this assumes: you know a transformer reads text and predicts the next word, and you have seen the word "attention." No prior knowledge of caching, HBM, or MHA needed — we define every term the first time it appears.

How a transformer writes text: one token at a time

A transformer is the model behind tools like ChatGPT. A token is a small chunk of text — roughly a word or part of a word. The model writes by predicting one token, adding it to the text, then predicting the next. To pick token number N, its attention step needs to look back at every earlier token 1 through N-1.

What attention looks back at: Keys and Values

For each token, the model computes two small lists of numbers. The Key (K) vector is "what I can be matched against." The Value (V) vector is "what I contribute if I get matched." Both are just simple linear projections (a matrix multiply) of the token's internal state. When the model writes a new token, it compares that token's Query against every earlier token's Key, then mixes together the matching Values.

The waste, and the fix: store K and V once

Here is the problem. To write each new token, the model needs the K and V of all earlier tokens. If it recomputed them every step, the work would grow like N² — a huge waste. So instead it computes each token's K and V once and saves them. That saved table is the KV cache: a big array holding the K and V of every token seen so far. It lives on HBM (high-bandwidth memory — the roughly 80 GB of very fast RAM sitting right next to the GPU chip).

Two phases, and the growing problem

  • Prefill — the one-shot pass over your input prompt that fills the cache.
  • Decode — the per-token loop that reads the whole cache and appends one new (K, V) row.

The catch: the cache grows linearly with the number of tokens and never shrinks. Its exact size in bytes is:

📦
bytes = 2 × n_layers × n_kv_heads × head_dim × seq_len × dtype_bytes
The 2 is for K and V. n_kv_heads is how many separate K/V "heads" each layer keeps. In classic Multi-Head Attention (MHA) that equals the full head count — which is what makes the cache enormous. The rest of Week 16 attacks each factor: MQA/GQA shrink n_kv_heads, SnapKV shrinks seq_len, quantization shrinks dtype_bytes.
📚
Official references (optional): Scaling Book — Inference · Efficiently Scaling Transformer Inference · MQA (Shazeer 2019) · GQA (Ainslie 2023) · SnapKV
2 · INTUITIONThe courtroom stenographer's growing binder✓

Picture a courtroom. Every time someone speaks a new sentence (a new token), the judge wants to re-scan the entire transcript so far before responding.

📄🔁📄
Recompute = ask everyone to repeat

Without notes, the court would ask every earlier speaker to repeat their whole line, every single sentence. That is recomputing K and V from scratch each step — enormous wasted effort.

📚➕📄
KV cache = a growing binder

The stenographer typed each line once and keeps it in a binder (the cache). The judge just reads the binder. Fast — but the binder never gets thinner. After a 3-day trial it is thousands of pages.

In one line: the KV cache saves you from re-deriving the past every step, but it keeps growing, and dragging the whole binder to the judge and back for every new sentence becomes the slow part — not the thinking.

⚠️
Where the analogy breaks: one stenographer keeps a single binder. The KV cache also multiplies by layers and heads — more like keeping 80 separate binders (one per layer), each with 8-to-64 parallel columns. The paper mountain is far bigger and far more parallel than a single transcript.

4 · HOW & WHYThe size formula, and why decode is memory-bound✓

The formula, factor by factor

  • 2 — one Key tensor and one Value tensor per token.
  • n_layers — every layer keeps its own full cache. A 70B model has ~80 layers.
  • n_kv_heads — how many separate K/V heads each layer stores. In MHA this equals the query-head count (e.g. 64); GQA/MQA cut it down (e.g. 8).
  • head_dim — the width of each head's K and V vector (e.g. 128).
  • seq_len — the number of tokens so far. This is what grows during decode and never shrinks.
  • dtype_bytes — bytes per number: 2 for fp16, 1 for fp8. Quantization shrinks this.
✅
bytes = 2 × n_layers × n_kv_heads × head_dim × seq_len × dtype
Every trick this week just clamps ONE of these factors: GQA/MQA → n_kv_heads, SnapKV → seq_len, quantization → dtype.

Why decode is memory-bandwidth-bound (not compute-bound)

  • Prefill processes the whole prompt in parallel — lots of math, compute-heavy.
  • Decode generates just one token per step, but to do it must stream the full model weights plus the entire growing cache from HBM. Tiny math, huge data movement.
  • On an H100 (~3.35 TB/s bandwidth), moving ~170 GB of weights + cache per step sets a floor near 51 ms/token — the compute units sit idle, waiting on memory.
⚠️
The #1 real mistake: using query-head count in the formula when the model uses GQA/MQA. Llama-3-70B has 64 query heads but only 8 KV heads — plug in 64 and you overestimate the cache 8×. Also: the cache is per sequence, so serving 32 concurrent requests multiplies the whole number by 32. Always state the dtype too.
🔗
Causal chain: attention needs every past K/V → cache them to avoid O(N²) recompute → cache grows linearly with tokens × layers × heads → past ~30–53k tokens it rivals then exceeds the whole model on one card → the bottleneck migrates from weights to cache. That is the problem Week 16 solves.
