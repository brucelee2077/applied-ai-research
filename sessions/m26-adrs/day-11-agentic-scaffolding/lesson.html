1What is agentic scaffolding, and why does ADRS need it?What is it
🧭
What this assumes: Week 19's ADRS concept (prompt generator → solution generator → evaluator → storage → selector) and this week's EvoPrompt/RuleFlow ideas. No prior scaffolding or agent-loop experience needed.

The problem: an LLM API call is not a system

Up to now you've studied the idea of ADRS (AI-Driven Research for Systems) and the research results behind it — FunSearch, AlphaEvolve, EvoPrompt. All of them depend on running a generate→evaluate→select loop thousands of times, unattended, for hours. A single call to an LLM API is not that. It is one request, one response, done.

Today's new concept is agentic scaffolding: the ordinary, non-ML software layer of code that wraps a raw LLM API call into something that can run in a loop, all night, without a human babysitting it.

Three new terms, defined now

  • Orchestration — the control-flow code that decides, every iteration: which past solutions to show the LLM next, when to call the API, when to call the evaluator, when to write results to storage, and when to stop.
  • Context window management — an LLM's context window is the fixed budget of tokens it can read in one call. As solution history grows every generation, you must decide what to keep, summarize, or drop so the prompt never exceeds that budget.
  • Reliable output parsing — the code that deterministically extracts a runnable candidate from an LLM's unstructured text reply (which may have stray prose, a missing code fence, or broken syntax), with a defined fallback when it fails.

Why this exists

The LLM is the "creative" part of an ADRS system. The scaffolding is the unglamorous part that keeps a stochastic, occasionally-broken text generator from crashing an experiment that is supposed to run all night — the same kind of retries, timeouts, and malformed-input handling you'd want in any long-running production service. Karpathy's autoresearch repo is studied today because it is a small, readable reference implementation of exactly this scaffolding, without a research paper's abstraction layered on top.

2The overnight contractor and the intake clerkIntuition

Think of the LLM as a brilliant but slightly unreliable remote contractor. You hire them to redesign a machine part, one revision at a time, overnight, while you sleep. You cannot supervise every revision live.

📋
Orchestration = the clipboard process

Before bed, you set up a system that decides which of the contractor's last few drafts to show them next, so they build on the good ones and don't repeat mistakes.

📠
Context window = the fax machine

You only fax the most relevant 3 pages of history, not the entire ten-year archive — the fax machine jams if you feed it too much at once.

🏭
Output parsing = the loading-dock clerk

A strict intake clerk rejects anything that isn't a properly labeled, physically valid part before it ever reaches the test rig — no vague sketches, no unlabeled boxes get through untested.

🌙
All three together = the overnight system

None of them is the "creative" work. All three exist so the creative work can run unattended for hours without crashing.

In one line: the LLM proposes; the scaffolding decides what it sees, keeps that input a manageable size, and refuses to pass along anything broken.

⚠️
Where the analogy breaks: a human contractor understands vague instructions and asks for clarification when confused. An LLM does not stop to ask — it will confidently return a plausible-looking but broken or truncated answer. The scaffolding must assume malformed output happens routinely, not as a rare exception.

4The three layers, and why they matterHow & why

The rules

  • Orchestration is a selection policy over storage, not "send everything." Each generation it picks which past candidates go into the next prompt (e.g. best 2 plus a random weak one, so the model sees what not to do).
  • Context window management means every generation you decide what to keep, summarize, or drop — for example only the top-K scoring candidates plus a short natural-language summary of failed attempts, instead of the full text of every past generation.
  • Reliable output parsing is a strict, deny-by-default gate: extract the code block, run ast.parse() or compile() on it before ever executing it, check the schema if you asked for JSON, and always have a defined fallback for failure.
  • All three run inside a driver loop with defined stopping conditions — max iterations, a time budget, or convergence — checked at the top of every iteration.
✅
parse_llm_output(raw_text) → Candidate | ParseFailure
"Extract the fenced code block, syntax-check it, and return either a valid candidate or a structured failure — never raise, never silently execute unchecked text."

Why it's load-bearing, not optional

  • Unattended duration — FunSearch, AlphaEvolve, and EvoPrompt all depend on running generate→evaluate→select thousands of times, for hours, with no one watching.
  • The LLM is stochastic — it will confidently return truncated, malformed, or subtly wrong output as a routine event, not an edge case.
  • Boring by design — this is the same discipline (retries, timeouts, malformed-input handling, resource limits) you'd want in any long-running production service. The scaffolding has no ML in it at all.
🔗
Causal chain: ADRS concept (Week 19) → research results show the loop works at scale (FunSearch/AlphaEvolve/EvoPrompt) → running that loop unattended requires orchestration + context management + reliable parsing → Saturday's script can only survive 12 hours because this layer exists.
⚠️
The most consequential mistake: treating parsing as an afterthought ("just wrap the exec in a try/except") instead of a strict, deny-by-default gate. A too-permissive parser can let syntactically-valid-but-semantically-wrong code (e.g. code that special-cases the test inputs — reward hacking, same risk flagged Week 19 Friday, now surfacing at the engineering layer) reach the evaluator and get selected as a "winner." The fix: parse strictly, execute only inside a resource-and-time-limited subprocess (never in-process exec), and always fail closed — a broken candidate is discarded, never silently stored as "score 0 but valid."

The staff lens — one silent failure, one trade-off

Context management keeps the prompt small enough to run for hours — but the same trimming that prevents a crash can quietly throw away the one thing the search depends on.

⚠️
Failure mode (silent): context trimming evicts the champion. A prompt that grows forever eventually crashes (the loud failure) — so you summarize or keep only the top-K past candidates. The quiet danger is the trimming policy dropping the current best program, or dropping all the diverse-but-lower-scoring parents, so the LLM stops seeing what it should build on. The loop keeps running with no error; the score just quietly plateaus or drifts back down as the model regenerates ideas it had already surpassed. A senior engineer catches this in code review by checking that the context policy always retains the best-so-far candidate (and some diversity) no matter how it summarizes the rest, and by logging what got evicted each generation to confirm the champion never silently leaves the prompt.
⚖️
Trade-off: prompt richness vs. token budget and cost. Feeding the LLM more history — every past candidate, its score, and its feedback — gives it more to learn from and usually better offspring, but it burns tokens fast, costs more per call, and eventually overflows the fixed context window. Aggressively summarizing keeps every call cheap and safe from overflow but risks starving the model of the signal it needs. In a design review this is the explicit knob for a long unattended run: how much history to keep verbatim, how much to compress into a short natural-language summary, and what you promise never to drop (the champion).
