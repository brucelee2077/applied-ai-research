Module 1 · Represent · Day 3

Data Engineering AutomationThe RuleFlow Framework

Yesterday an LLM found a clever rewrite for one Pandas cell. Today: what happens if you never want to pay for that LLM call again. RuleFlow turns a one-off LLM discovery into a reusable, LLM-free rule that fires forever, for free.

🎯
By the end, you'll be able to: explain the discovery/bridge/deployment split, trace RuleFlow's 3-stage pipeline (SnippetGen → RuleGen → CodeGen), say which stages call an LLM and which don't, and explain why the "low yield, high reuse" observation is what makes the whole system worth building.
1What is the discovery/bridge/deployment split, and what is RuleFlow?What is it
🧭
What this assumes: you've seen the ADRS/FunSearch/AlphaEvolve idea earlier in Phase 5 — "use an LLM as an optimizer, not as a code-writer" — and you've written basic Pandas code (df.drop(...), df.groupby(...)). No prior RuleFlow experience needed.

The problem: Pandas is convenient but slow, in ways you can't easily see

You've written Pandas code before — df.drop(['name'], axis=1) to remove a column, df.groupby(...) to aggregate, df[cols] to select columns. Pandas is Python's dataframe library — a dataframe is a table of rows and columns, like a spreadsheet. Pandas is easy to write, but many idiomatic ways of writing the "same" operation have wildly different speeds, because Pandas sometimes copies the whole table, or loops in Python instead of using fast vectorized code, when a faster path already exists.

Two earlier camps tried to fix this, and both fall short:

  • Systems-based rewrites (Modin, Dask, cuDF, Polars) — reimplement the Pandas API on a faster backend (parallel, distributed, or GPU). Heavyweight: great for huge data, but the extra overhead often makes everyday exploratory notebook code slower, not faster.
  • Compiler-based rewrites (DIAS, SCIRPy) — apply a small, fixed, hand-written set of "pattern A → faster pattern B" rules. Lightweight and safe, but tiny: DIAS has only 10 rules, because a human has to hand-write every single one.

The naive LLM idea — and why it fails at scale

The obvious next move: point an LLM at each Pandas code cell and ask "rewrite this to be faster." This can work brilliantly on one cell — the RuleFlow paper shows an LLM turning df.drop(['name'], axis=1) (which copies the whole table) into df.pop('name') (which removes a column in place), a 1770x speedup. But doing this every time, for every cell, in every notebook run is a bad system: it costs an LLM call every time, and the measured yield — the fraction of attempts that actually produce something usable — is only about 5.7%. Re-running an unreliable, slow model for a 1-in-20 chance of a real win, forever, does not scale.

The answer: split "discover the trick" from "use the trick"

RuleFlow is a 3-stage framework that separates the expensive, unreliable LLM work from the cheap, reliable deployment work: discovery (find and validate one working rewrite, once, using an LLM), bridge (generalize that one-off rewrite into a reusable rule, using an LLM), and deployment (match and apply that rule to brand-new code, with zero LLM calls, forever). Spend the slow model's budget once per pattern, not once per program.

📦
discovery (SnippetGen, LLM) → bridge (RuleGen, LLM) → deployment (CodeGen, no LLM)
The key twist versus FunSearch/AlphaEvolve's per-problem search loop: RuleFlow amortizes the LLM cost across every future program that matches the rule.

So what's today's catch?

The catch is the correctness gate itself. RuleFlow checks a candidate rewrite by running it on sampled test data, not by mathematically proving it equivalent. That's a real limitation — we'll see exactly how it can quietly go wrong in the playground and quiz.

📚

2The process-improvement team vs. the factory floorIntuition

Think of RuleFlow like a company's process-improvement team versus its day-to-day factory floor.

🔬📋
Improvement team = discovery + bridge

They watch how workers do a task, try new ways, test whether the new way still gives a correct product, time it to prove it's faster — and write the winner up as a standard operating procedure (SOP): "IF part is type X AND machine has attachment Y, THEN use the 3-step method." That SOP is the rewrite rule.

🏭✅
Factory floor = deployment

Workers never call the improvement team again. A fast, dumb, checklist-following supervisor just checks: "does this SOP's condition apply right now?" If yes, use the fast method. If no, fall back to the safe, slow, default method. Checking a checklist is instant.

In one line: pay the experts once to find and write down a rule; let a cheap checklist apply that rule everywhere, forever.

⚠️
Where the analogy breaks: a human SOP is written once and trusted. RuleFlow's rules are re-checked automatically every single time they might apply, because the running program can't be trusted to notice on its own whether today's oddly-shaped data (say, a column full of unexpected missing values) actually fits the SOP. So the system builds in an automatic fallback rather than assuming the SOP always fits.

4The three stages, and why the split worksHow & why

The three stages

  • SnippetGen (discovery, offline, LLM-heavy). An LLM proposes candidate rewrites for a real code cell. Two automated gates check each one: EquivCheck (run original and candidate on the same random test dataframes — do outputs match?) and OptCheck (is it measurably faster, past a threshold?). A third piece, FeedbackGen, is an adversarial agent whose only job is to hunt for counterexample inputs that break the candidate — the same spirit as reward-hacking checks in RL: don't trust a candidate just because it scored well, try to break it first.
  • RuleGen (the "bridge," offline, LLM-heavy). A validated (before, after) pair is specific to one program. Four chained LLM sub-agents lift it into a general rewrite rule: a triple of LHS pattern (what to match), RHS pattern (what to replace it with), and preconditions (runtime checks that guard when the rule is safe).
  • CodeGen (deployment, online, zero LLM calls). Given the accumulated rule library, this is a deterministic compiler pass: it pattern-matches each rule's LHS against new, unseen code, and rewrites a match into if <preconditions>: <fast RHS> else: <original LHS>. No LLM runs at this step — that's the whole point of the split.
✅
LHS: v1 = v1.drop([c1], axis=1) → RHS: v1.pop(c1), precondition c1 in v1.columns
A rule discovered once on df.drop(['name'], axis=1), then matched against thousands of unrelated notebooks that never saw the original example.

Why the split matters: low yield, high reuse

  • Amortization — the paper's central observation: any single LLM attempt rarely succeeds, but the small set that do succeed tend to be generic patterns, not one-off tricks. Discovered rules collectively fired on 87.13% of held-out test notebooks.
  • Decomposition beats monoliths — RuleGen's 4-agent split (generalize → infer types → construct rule → synthesize preconditions) hits 68% valid rules, versus 18% for one agent doing all four jobs at once.
  • Correctness never regresses — because CodeGen emits a runtime-checked fallback, a rule that doesn't apply just leaves the original code untouched; speed varies, correctness doesn't.
🔗
Causal chain: naive per-program LLM optimization (Day 3's evolutionary-search cousin) → measured yield is too low to run online (~5.7%) → split into offline discovery+bridge (pay once) and online deployment (free forever) → RuleFlow.

The staff lens — one silent failure, one trade-off

"Correctness never regresses" is only true when two things hold — EquivCheck actually caught every case where the rewrite differs, and the precondition guards exactly those cases. When either slips, the fallback protects nothing.

⚠️
Failure mode (silent): a rewrite that only looks equivalent under-samples the cases where it differs. EquivCheck compares the original and candidate on random test dataframes. If those random frames never contain the input that makes the two diverge, the rewrite passes as "equivalent," gets lifted into a rule, and the precondition RuleGen synthesizes guards the wrong thing. The paper's real example: rewriting Pandas .min() as NumPy np.min(...) — Pandas skips missing values (NaN), NumPy does not. On random data with no NaNs they match; the precondition only checks that the column exists, not that it has no NaN; so in production the rule fires on a column with a missing value and silently returns a different, wrong number. No crash, no fallback triggered — the runtime check preserves correctness only when the precondition captures the unsafe case. A senior engineer catches this in code review by asking, of every rule, "under what inputs do original and rewrite differ, and does the precondition actually exclude those?" — and by making EquivCheck sample the edge cases (NaN, empty, duplicates, mixed dtypes), not just moderate random frames.
⚖️
Trade-off: pay-once offline discovery vs. staleness of the rule library. Splitting into expensive offline discovery (SnippetGen + RuleGen) and free online deployment (CodeGen, zero LLM calls) is what makes RuleFlow fast enough to run on every notebook — the whole design buys cheap, deterministic deployment. But you pay for it in freshness: the rule library only knows the patterns discovered in the last offline run, so new APIs, new idioms, and library version changes are invisible until you re-run discovery, and a rule validated against an old Pandas version can quietly become unsafe after an upgrade. In a design review this is the explicit decision — how often to re-run offline discovery and re-validate rules against the current library, trading compute for the library staying correct and current.
