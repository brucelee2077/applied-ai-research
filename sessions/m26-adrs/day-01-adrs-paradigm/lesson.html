Module 1 · Represent · Day 3

The ADRS ParadigmAI-Driven Research for Systems

For four phases, you have used AI to build and speed up models. Today the direction flips: you study AI as the researcher, automatically inventing new systems algorithms — schedulers, load balancers, cache policies — and beating the humans who designed the current best ones. This is the paradigm the whole of Phase 5 sits on top of.

🎯
By the end, you'll be able to: state in your own words why systems performance research is unusually easy for AI to automate, name the two stages of the research process that AI-Driven Research for Systems (ADRS) takes over, and connect at least two real case-study numbers and two named failure modes to that thesis.
1What is ADRS, and why does it exist?What is it
🧭
What this assumes: normal programming fluency and everything through Phase 4 (you know what a scheduler, a load balancer, and an LLM are). No prior ADRS, evolutionary-search, or systems-research knowledge needed — we build it from zero.

Start with the problem, not the tool

Imagine you are a systems researcher. Your job is to invent a better algorithm — say, a smarter way to decide which cloud server should run which job. Traditionally that means: read papers, think of an idea, hand-write the code, run it against real workloads, measure whether it is actually faster, and repeat for months. Most of that cycle is not "having the idea." Most of it is the slow, mechanical loop of try something, measure it, try something else.

Now ask a different question: which parts of that loop could a machine do instead of a human? To answer that, you need to know when a machine can even tell whether an idea worked.

The one fact that makes this possible: a reliable verifier

A verifier is anything that can look at a candidate solution and say, correctly, whether it solved the problem. For most creative or open-ended tasks — write a good essay, design a good user interface — there is no reliable verifier. A machine cannot check "is this essay good?" the way it checks "did this test pass?" That is why AI has been slower to automate those fields.

Systems performance research is different, and this is the whole point of today's paper. If your candidate solution is a scheduling algorithm, you do not need a human to judge whether it is good. You run it — in a real system or a simulator — against a fixed set of workloads, and you measure a number: latency, cost, throughput, makespan. That measurement is the verifier. It is deterministic (run it twice, get the same answer) and reliable (the number is exactly what you care about, not a proxy for it). Runnable code plus a scoreboard is a far easier thing for a machine to use than "is this a good idea," and that gap is why systems research is unusually well-suited to AI-driven automation — not because "AI is good at writing code" in some vague sense, but specifically because the performance metric you already cared about doubles as an automatic, trustworthy judge.

The answer: ADRS

ADRS (AI-Driven Research for Systems) is the name a 2025 UC Berkeley paper gives to this approach: use that reliable verifier to close a loop where an LLM proposes candidate algorithms, an automated evaluator scores them by actually running them, and the best-scoring candidates get fed back to the LLM to inspire the next round. Repeat hundreds of times. The paper's own framing: a typical AI-driven discovery approach is (i) generate a set of diverse solutions, then (ii) verify them and select the best — and systems research is an unusually good fit for that pattern because it naturally has a reliable verifier already built in.

📦
Two of the four stages of ordinary research — Solution (write the code) and Evaluation (measure whether it worked) — are exactly the two stages ADRS automates. Problem selection and writing up the results stay with the human.
Together those two stages account for roughly 40% of a systems researcher's time, based on the paper's own survey of graduate students.

So what's today's catch?

ADRS is not "the AI understands the system." The LLM proposing new code never sees the real reason a solution is good or bad — it only ever sees the score the evaluator hands back. That single fact is the seed of almost every interesting failure mode you will study this week, including reward hacking (Day 5) and the reason a fortified evaluator with hidden hold-out tests matters so much (Day 6). Today, we stay at the level of the big idea: why this works at all, and what the five pieces of the loop are (tomorrow's topic in detail).

2A tireless intern with a stopwatch, not a judgeIntuition

Picture two kinds of homework. One is "write a persuasive essay" — grading it needs a human's judgment, context, and taste. The other is "make this program run faster without breaking it" — grading it needs a stopwatch and a checklist. ADRS only works on homework of the second kind.

✍️❓
Essay grading = no reliable verifier

Two good essays can disagree. A machine grading style or persuasiveness is guessing at a proxy for a human's taste, not measuring the real thing directly.

⏱️✅
Runtime grading = a reliable verifier

Two candidate schedulers either finish the job faster or they don't. You run both, read the stopwatch, and there is no argument about which number is bigger.

In one line: ADRS automates research exactly where "is this solution good?" already has a mechanical, checkable answer — an intern with a stopwatch, not a judge with opinions.

⚠️
Where the analogy breaks: a stopwatch-and-checklist intern still needs someone to write the checklist. If the checklist has a gap — some case it never measures — a tireless enough intern (or an evolutionary search running thousands of variations) will eventually find and exploit that exact gap, not because it is being sneaky, but because it is optimizing precisely what you told it to measure. You will meet this directly as "reward hacking" later this week.

4The shape of the loop, and why it mattersHow & why

The shape of the loop

  • Generate. An LLM (or an ensemble of them) proposes a candidate solution — a function, a scheduling policy, a piece of code that changes system behavior.
  • Evaluate. An automated evaluator runs that candidate against predefined workloads, in a real system or a simulator, and produces a score — a real measured number, not an opinion.
  • Select and repeat. The best-scoring candidates are kept and fed back to the LLM as context for the next round. Hundreds or thousands of rounds later, the search has explored far more variations than a human team could try by hand.
✅
Reliable verifier = a scoring function that is deterministic (same candidate, same score, every run) and faithful (the score is the thing you actually care about — latency, cost, correctness — not a rough stand-in for it).
This is the property systems performance problems have almost for free, because "run it and time it" already is the thing you care about.

Why it matters

  • It changes what's scarce. If a machine can run the generate-evaluate-select loop thousands of times overnight, the bottleneck stops being "how many ideas can a human try" and becomes "how well did the human define the problem and the evaluator."
  • It only works where the metric is trustworthy. The paper's own case studies — Mixture-of-Experts (MoE) load balancing, multi-region cloud job scheduling, transaction scheduling — all share one property: you can run the candidate and get back a real number for free. That is not true of every research problem, which is exactly why the paper spends real effort on where the boundary of "this works well" sits (next section).
  • It reframes the human's job. As the paper argues, once generation and evaluation are automated, human systems researchers increasingly shift toward problem formulation and strategic guidance — deciding what to search for and how to judge it — rather than hand-writing every candidate themselves.
🔗
Causal chain: systems performance problems already have a runnable, measurable metric → that metric is a reliable, deterministic verifier → a reliable verifier lets you automate "generate candidates, then check them" at machine speed → automating that loop is exactly what ADRS names and studies.

The staff lens — one silent failure, one trade-off

A verifier has two jobs — be repeatable and measure the real goal — and the loop only checks the first one for you. That gap is where this whole paradigm quietly breaks.

⚠️
Failure mode (silent): a deterministic-but-unfaithful verifier. "Reliable" means two separate things — deterministic (same candidate, same score) and faithful (the score is the goal you actually care about). It is easy to build a verifier that is perfectly deterministic yet measures the wrong thing — for example it times throughput but never checks the answers are correct. The loop runs clean, the number climbs, and it happily converges on a candidate that "wins" by returning fast garbage. Nothing crashes; the metric just no longer means what you think. In code review a senior engineer asks one question of every scoring function: "if a candidate maxed this number while doing something useless, would the score still look great?" — and if yes, the verifier is unfaithful.
⚖️
Trade-off: cheap automatable metric vs. faithful measurement. The reason this loop runs unattended is that the metric is cheap — "run it and time it" costs nothing and needs no human. But the cheapest metric to measure (raw speed) is rarely the full definition of "good"; adding correctness gates, held-out workloads, and a simulator faithful to production makes every iteration slower and harder to build. In a design review the choice is explicit: a looser, faster verifier lets you search more candidates per hour but widens the gap the search can exploit, while a stricter, slower verifier searches less but is much harder to fool. You are trading iterations for trust.
