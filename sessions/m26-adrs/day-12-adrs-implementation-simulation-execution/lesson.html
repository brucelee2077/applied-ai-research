1What is an LLM API, and what is ADRS?What is it
🧭
What this assumes: you can write and run Python. You saw the ADRS paradigm and FunSearch earlier this week (Days 1–5). No prior experience running an autonomous loop is needed — we build it from zero here.

Start with the words

An LLM API is a way to send text to a large language model over the internet and get text back. You POST a prompt — like "make this Python sort faster" — to a URL (OpenAI's or Anthropic's), and the model returns code as a plain string. You never run the model yourself. You rent it, one call at a time.

ADRS stands for AI-Driven Research for Systems. It is a loop that uses an LLM to invent code, then automatically tests that code, then feeds the best results back to the LLM to inspire the next attempt. It works because for many systems problems — sorting speed, cache eviction, bin packing — checking "is this solution good?" is mechanical: you just run it and time it. So a machine can do the whole research cycle without a human grading each try.

The loop has exactly five components

  1. Prompt Generator — builds the text prompt. It usually pastes in a few of the best programs found so far and says "here are good solutions; write a new, faster one."
  2. Solution Generator — this is the LLM API call. It reads the prompt and returns a new candidate program as a string.
  3. Evaluator — the mechanical judge. It safely runs the candidate on fixed test inputs, checks the output is correct (a broken sort scores zero), and measures fitness — here, speed, e.g. median seconds over many runs. Fitness is just the score you optimize.
  4. Storage — a database of programs keyed by their score. Often split into islands: separate sub-populations that evolve independently, so the search does not collapse onto one idea too early.
  5. Solution Selector — picks which stored programs get shown to the LLM next, usually favoring high scorers but keeping some diversity.

Why we call it "evolutionary"

The word evolutionary means the loop borrows from biology. It keeps a population of programs, mutates them (the LLM edits or rewrites), scores them (fitness), keeps the winners (selection), and repeats over many generations. The sorting sandbox (built in Week 19) is your safe, self-contained test rig: a correct reference sort, a set of test arrays, and a timing harness — so the Evaluator has something concrete and verifiable to run every candidate against.

📦
Two tools you use with the sandbox: pytest-benchmark times a function many times and reports stable statistics (median, min, standard deviation) instead of one noisy number. pandas is a table library you use afterward to load the run log and find the best generation.

2A food truck hunting the fastest fries recipeIntuition

Imagine you run a food truck and you want the fastest possible fries recipe. Every morning you hand your best cook a few of your best recipes and say "beat these." That morning routine is exactly the ADRS loop.

📋➡️👨‍🍳
You + the cook = Prompt Gen + LLM

You are the Prompt Generator: each day you hand over the top three recipes. The cook is the Solution Generator (the LLM) — they scribble a new recipe from those hints. They never taste the result; they only follow the note.

⏱️🍟
The taster with a stopwatch = Evaluator

A stopwatch-holding taster is the Evaluator. They cook the new recipe, first check the fries are actually edible (correctness — a burnt batch scores zero no matter how fast), then time it. The recipe box is Storage; choosing tomorrow's recipes is the Selector.

In one line: hand the best recipes to the cook, time the new one after checking it is edible, keep the winners, repeat every day for a month — and recipes drift from "boil then fry" toward "par-fry, freeze, flash-fry," an optimized method nobody explicitly designed.

⚠️
Where the analogy breaks: real cooks understand why crispy is good and use taste and creativity. The LLM never tastes anything — it only ever sees the number the stopwatch reports. That gap is exactly why the cook might one day hand you fries that are "fast" because they cheat the stopwatch (skip cooking) rather than truly better. That is the reward-hacking risk your Evaluator must guard against.

4The rules of the loop, and why they matterHow & why

The rules

  • Correctness gates speed. The Evaluator first checks the candidate sorts every test array correctly. Only if it passes does the speed measurement count. A wrong program gets fitness = infinity (worst possible) and is discarded.
  • Fitness is a median, not one timing. Score each candidate as the median seconds over many runs (via pytest-benchmark or repeated timeit). One measurement is noisy; a median is stable enough for the Selector to trust.
  • The LLM only sees numbers and code. The feedback fed back into the prompt is the scores plus the code of the best programs — never an explanation of why they are fast. This is the whole reason reward hacking is possible.
  • The loop must survive failure. Wrap the LLM call in try/except with retry and back-off, and checkpoint state to disk so a 12-hour run can resume after one API error, and halt cleanly on the time limit.
✅
if not is_correct(candidate): fitness = float("inf")  then  fitness = median(times)
"Reject anything that sorts wrong; only then does speed decide the winner." The correctness gate always runs first.

Why it matters

  • Verifiable = automatable — because a benchmark can judge a sort with no human, the whole research cycle can run overnight without you in the loop.
  • Diversity beats greed — islands keep several independent sub-populations, so one early good-but-mediocre idea does not dominate and trap the search in a local optimum.
  • Held-out inputs catch cheats — a fast score on the training arrays can be a memorized special-case; re-checking the champion on unseen arrays separates a real discovery from a trick.
🔗
Causal chain: a mechanical benchmark → the Evaluator can judge code automatically → the LLM can mutate freely and be scored → keep winners, feed them back → over many generations fitness improves → re-verify on held-out inputs to confirm it is real.

The staff lens — one silent failure, one trade-off

The Selector trusts the fitness number completely — so if that number is noise, the whole search follows the noise, and nothing ever tells you.

⚠️
Failure mode (silent): ranking candidates by a noisy single timing. A wall-clock timing wobbles run to run because of OS scheduling, CPU caches, and other processes on the machine. If fitness is one timeit call instead of a median over many runs, a genuinely slower algorithm can post a faster number just because it happened to run during a quiet moment. The Selector, which only sees the score, keeps that candidate and breeds from it — so the search chases measurement noise instead of real speedups. It runs cleanly and the "best" score even improves, but it is improving toward whatever times well by luck, not what is actually fast. A senior engineer catches this in code review by checking the fitness is a median (or min) over enough repeated runs — for example via pytest-benchmark — on a quiet machine, and by re-measuring the champion to confirm its win is stable and not a one-off.
⚖️
Trade-off: measurement stability vs. candidates per hour. Timing each candidate N times and taking the median gives a stable score the Selector can trust, but it makes every evaluation roughly N times slower — so you test far fewer candidates in a fixed 12-hour run. Timing once is fast and lets you search more, but the ranking is noisy and can mislead the whole search. In a design review you pick N deliberately: enough repeats that the fitness is stable relative to the speedups you care about, but no more, because every extra repeat is a candidate you did not get to try.

  • Fitness is a median over ≥5 runs, not a single timing.
  • best_algorithm.py beats the seed's median time by a measurable margin, verified on the held-out arrays.
  • The LLM call has try/except with retry/back-off; the loop checkpoints so it can resume, and halts cleanly on the time limit printing the champion + score.
  • writeup.md shows best-fitness-per-generation (a downward curve) aggregated with pandas.

⚠️
The trap: reward hacking through the Evaluator, not the algorithm. If fitness is measured only on a small fixed set of arrays, the LLM will eventually produce code that special-cases or memorizes those exact inputs — scoring a blazing "speed" that vanishes on real input. It is not being sneaky; it is optimizing exactly what you measured. Defenses: (1) always re-verify the champion on a HELD-OUT set it never saw, (2) randomize array contents/sizes each generation, (3) keep the correctness gate strict. Second, mundane trap: timing noise — one time.time() call can rank a worse algorithm faster, so use a median over many runs.
