AI-Driven Research (ADRS) · Week 20 · Day 2

Formal Theorem Proving(AlphaGeometry)

How do you teach a machine to solve Olympiad geometry when there are almost no human proofs to learn from? DeepMind glued a neural guesser to a symbolic prover, then manufactured 100 million practice problems out of thin air. Today: how that loop works.

🎯
By the end, you'll be able to: explain the neuro-symbolic loop (a rule engine that grinds facts + a language model that guesses new points), say exactly what an auxiliary construction is, and describe how synthetic data + traceback creates training labels with zero human demonstrations.
1Theorems, proofs, and the one move machines cannot makeWhat is it
🧭
What this assumes: you have seen a triangle and know what "prove" means in everyday speech. That is all. No geometry-olympiad or AI background needed.

Start with the words

A theorem is a statement in math that is claimed to be true. Example: "if a triangle is isosceles, its two base angles are equal." A proof is a chain of small, justified steps that connects what you are GIVEN (the premises) to what you must SHOW (the goal). Each step must follow a known rule.

Formal theorem proving means writing that chain in a strict, machine-checkable form. Every step is a rule the computer can verify, so there is no hand-waving. If a formal proof says "done," it is really done.

The hard part: sometimes you must ADD to the picture

To find a proof, you sometimes have to draw something that was not there — a new line, a new point, a circle. A human might say "drop a perpendicular from A to BC." This creative addition is called an auxiliary construction (an "aux" for short). There is an infinite number of possible additions, so you cannot just try them all. This is what makes olympiad geometry hard.

AlphaGeometry: neural spark + symbolic grind

AlphaGeometry is a neuro-symbolic system — "neuro" (a neural network) plus "symbolic" (a rule engine) working together. Two parts:

  • A symbolic deduction engine, called DD+AR. It has fixed geometry rules (like "equal angles imply parallel lines"). Given a diagram, it applies every rule it can, again and again, until no new fact appears. That full set of everything provable is the deductive closure. DD ("deductive database") chases geometry rules; AR ("algebraic reasoning") solves equations about angles, lengths, and ratios with linear algebra. It is fast and never wrong — but it is stuck the moment a proof needs a new point, because it cannot invent points.
  • A language model (a Transformer, same family as GPT). Its ONE job: look at a stuck problem and suggest a useful auxiliary construction, written as text like "construct point X such that ...". It supplies the creative spark the engine lacks.

The loop: run DD+AR → if it proves the goal, done → if it gets stuck, ask the language model for an aux construction → add that point to the diagram → run DD+AR again. Repeat until the goal is proven or a step budget runs out.

The deepest trick: manufacturing data from nothing

There are almost no human-written formal geometry proofs to learn from. So DeepMind used synthetic data generation: sample a random diagram, run the engine to its deductive closure, and read off millions of true theorems for free. Then a step called traceback (dependency pruning) keeps, for each theorem, only the premises the proof actually uses. The magic: when a used premise is a point that was NOT in the original givens, that point is exactly a needed auxiliary construction. So the (problem → aux) training pair is generated automatically, with zero human demonstrations. They made about 100 million such proofs this way.

📚
Official sources (optional): Nature paper: Solving olympiad geometry without human demonstrations · DeepMind blog: AlphaGeometry
2A locked escape room, and the hidden keyIntuition

Picture a locked escape room. You have a ring of keys and a set of locks. Two very different teammates are with you.

🔑🚪
Symbolic engine = the literal assistant

Tries every key on the ring in every lock, exhaustively and without mistakes, until no door will open with the keys you have. When a door needs a key that is not on the ring, this teammate is stuck. That is where a normal search dies.

💡🪑
Language model = the creative teammate

Has seen thousands of similar rooms. Says, "I bet there's a hidden key taped under the third chair." That guessed key is the auxiliary construction. Hand it to the literal assistant and they burst through to the exit.

In one line: the engine grinds through everything it can prove; the language model guesses the one creative addition it cannot invent; together they finish.

The training-data trick is like this: instead of watching humans escape rooms (there are almost none recorded), you build millions of random rooms yourself, let the literal assistant fully explore each one, then rewind the tape to see exactly which hidden key would have been needed — and label THAT as the lesson for the creative teammate.

⚠️
Where the analogy breaks: an escape room has one fixed layout, but a geometry problem is an open space where you can add brand-new points anywhere — the set of possible "hidden keys" is infinite, not a handful of hiding spots. Also, the literal assistant here can do algebra (solve equations), which is more than just trying keys.

4The rules of the loop, and why it earns trustHow & why

The rules

  • The symbolic engine (DD+AR) runs to a fixed point: apply every rule, add every new fact, repeat, until nothing new appears. That set is the deductive closure. It is deterministic and provably correct — same input, same facts, every time.
  • If the goal is inside the closure, the proof is done. If not, the closure is finite and does not contain the goal — a new point is needed. The engine cannot invent points, so it stops.
  • The language model is asked for exactly one thing: an auxiliary construction, a text string like "construct D = reflect(A, M)". It does beam search over possible constructions and returns candidates.
  • The proposed point is added to the diagram, and the engine runs again. This alternation continues until the goal is derived or a step/time budget is hit.
✅
Why the proofs are trustworthy: the neural net never verifies anything. Every deduction and the final check are done by the symbolic engine. A wrong guess just wastes a step — it can never produce a false proof.

Why the data trick is the real breakthrough

  • No human proofs needed. Sample random premises → run the engine to closure → harvest millions of true theorems for free. This side-steps the fact that formal geometry proofs barely exist as a dataset.
  • Traceback creates the labels. Prune each proof to the premises it actually uses. Any used point that was NOT in the original givens is, by definition, a needed auxiliary construction — the exact label the language model must learn.
  • Self-improvement. The symbolic half teaches the neural half the one creative move the symbolic half can never invent. Together they solved 25 of 30 recent IMO geometry problems, near a gold medalist.
🔗
Causal chain: no human data → generate random diagrams → engine finds true theorems → traceback isolates the needed aux point → (problem → aux) pairs train the Transformer → the trained Transformer feeds good guesses back into the solving loop.

The staff lens — one silent failure, one trade-off

The symbolic engine guarantees no false proof can ever slip out — but nothing guarantees the training labels that teach the neural half are correct.

⚠️
Failure mode (silent): traceback mislabeling poisons the training data. The proofs stay sound — a wrong guess just wastes a step, it can never produce a false theorem. The quiet danger is one layer back, in data generation. Traceback is supposed to prune each proof to only the points it actually used, so any used point not in the givens becomes the "needed auxiliary construction" label. If that pruning is loose — it keeps a point the proof did not really depend on — you label a non-auxiliary point as a needed construction. The pipeline runs fine and every proof is still valid, but the Transformer now trains on wrong (problem → aux) pairs and slowly learns to propose useless constructions. You see it only as a mysteriously weaker guesser, never as an error. A senior engineer catches this in code review by testing the traceback on proofs with a known minimal dependency set and confirming the pruned set matches exactly — no extra points kept, none dropped.
⚖️
Trade-off: neuro-symbolic soundness vs. a pure neural prover's flexibility. Routing every deduction and the final check through the symbolic engine buys an absolute guarantee — no false proof is possible — but it confines the system to a domain the symbolic engine can express and verify (here, a fixed set of geometry rules), and the whole thing stalls the moment a needed move is one the engine cannot represent. A pure neural prover would generalize to far more kinds of problems, but it can emit confident, wrong "proofs." In a design review this is the core decision: pay in generality to make unsound output structurally impossible, or pay in trust to gain reach.
