Phase 1 · Week 1 · Day 5 (Fri)

Flax & Optax
Neural Nets, Functionally

Raw JAX makes you carry every weight and every optimizer number by hand. It works, but it gets messy fast. Today you meet two libraries that clean it up: Flax defines your layers, and Optax updates them — all while staying pure and functional.

🎯 By the end, you'll be able to: define a network with a Flax nn.Module, get its weights with model.init(key, x), run it with model.apply(params, x), and do one training step with an Optax optimizer.
1 · WHAT IS ITWhat are Flax and Optax, and why do they exist?✓
🧭
What this assumes: basic Python/NumPy and Days 1–2 (JAX is pure: functions don't secretly change anything; you pass state in and get new state out). No prior Flax or Optax experience needed.

The problem: raw JAX makes you carry everything by hand

Because JAX is pure, nothing is hidden. A neural network has parameters (the weights and biases it learns) and an optimizer has its own state (numbers it keeps between steps, like running averages). In raw JAX, you hold all of that yourself — usually in plain Python dictionaries — and thread it through every function call by hand.

That works. But as networks grow, you end up managing a big pile of loose numbers: which weight belongs to which layer, what shape it is, and where the optimizer's bookkeeping lives. It is easy to lose track.

The answer: two small libraries

Flax is a neural-network library for JAX. Its core idea is nn.Module: you describe your layers, and Flax manages their parameters for you — without hiding them. You call model.init(key, x) to create the parameters, and model.apply(params, x) to run the forward pass (compute an output from an input).

Optax is an optimizer library for JAX. An optimizer decides how to change the weights using the gradients. Optax gives you composable optimizers: optax.adam(lr) returns an object with two methods, init and update. You hold the optimizer state, compute gradients with jax.grad, and apply the changes with optax.apply_updates.

📦
The key idea in both: state stays explicit. Flax hands you the parameters; Optax hands you the optimizer state. Nothing mutates behind your back.
This is exactly why they fit JAX: pure functions (Days 1–2) compose cleanly with jit and grad.

So what's today's catch?

The main new thing to learn is the small ritual: init to make state, apply / update to use it, and always taking the returned new state instead of expecting things to change in place. We'll walk through it in the playground.

2 · INTUITIONA loose pile of ingredients vs. a labeled kitchen✓

Imagine you are cooking a big meal. You need to keep track of every ingredient and every tool.

🥕🧂🥚
raw JAX = loose ingredients

Every weight and every optimizer number sits in a pile on the counter. You track it all by hand. It works for a small dish, but for a big meal you start dropping things.

🍳🏷️
Flax + Optax = a labeled kitchen

Each module knows its own parts (Flax holds the weights), and the optimizer keeps its own state in a labeled drawer (Optax). You still see everything — but it is organized and named.

In one line: Flax gives your network a home for its weights, and Optax gives your optimizer a home for its state — without ever hiding either from you.

⚠️
Where the analogy breaks: a real kitchen lets you leave ingredients out and change them in place. Flax and Optax never change anything in place. Each step returns new parameters and new state, and you keep the new ones. That is what "functional" means.

4 · HOW & WHYThe Flax + Optax ritual, and why it matters✓

The Flax side

  • You define a layer or network as an nn.Module. For a single dense layer: model = nn.Dense(8) (8 output features).
  • params = model.init(key, x) creates the parameters. It needs a random key (Day 2) and one example input x so it can figure out the shapes. What comes back is a pytree: a nested dictionary of arrays (a "tree" of parameters).
  • y = model.apply(params, x) runs the forward pass. Notice the params go in as an argument — the model does not hold them secretly.

The Optax side

  • tx = optax.adam(1e-3) makes an optimizer with learning rate 1e-3. It has two methods: init and update.
  • opt_state = tx.init(params) creates the optimizer's own state (its running numbers).
  • updates, opt_state = tx.update(grads, opt_state) turns raw gradients into the actual changes to apply, and returns fresh state.
  • params = optax.apply_updates(params, updates) adds the changes to your parameters, giving new params.
✅
One training step, in order: grads = jax.grad(loss_fn)(params) → updates, opt_state = tx.update(grads, opt_state) → params = optax.apply_updates(params, updates)
Every arrow returns something new that you keep. Nothing changes in place.

Why keep params and state explicit?

  • Purity — because state is passed in and out, these functions stay pure. That is what lets them compose with jit (compile) and grad (gradients) from earlier days.
  • No hidden mutation — you always know exactly what your weights are. No surprises from something changing behind your back.
  • Composable optimizers — Optax transforms are like building blocks. You can chain gradient clipping, weight decay, and Adam into one optimizer with optax.chain(...).
🔗
Causal chain: JAX is pure (Days 1–2) → params and optimizer state must be explicit → Flax hands you a params pytree and Optax hands you opt_state → the whole training step is pure → it composes with jit and grad.

The staff lens — one silent failure, one trade-off

Explicit params and optimizer state give you purity, but the very fact that state is passed in and out by hand is what lets one dropped return value quietly break training.

⚠️
Failure mode (silent): dropping the returned opt_state. tx.update(grads, opt_state) returns two things: the updates and a fresh opt_state. If you only keep the updates — updates, _ = tx.update(...), or you feed the same old opt_state into every step — the optimizer's running memory never advances. For Adam that means the momentum and variance estimates reset each step, so Adam quietly degrades toward plain SGD. Training still runs and loss still drops a bit, so nothing errors; it just converges worse than it should. A senior engineer checks in code review that both the new params and the new opt_state are captured and threaded into the next step.
⚖️
Trade-off: explicit state threading for purity and composability. A framework that hid params and optimizer state inside the model would be shorter to write — no passing things in and out. Flax and Optax make you carry both by hand, which is more boilerplate and one more thing to thread correctly. In exchange the whole training step stays a pure function, so it composes cleanly with jit, grad, and vmap, and you always know exactly what your weights are. The design-review question: is the extra threading worth a training step you can compile and reason about with zero hidden state? At scale, yes.
