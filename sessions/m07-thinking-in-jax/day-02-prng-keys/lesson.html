Thinking in JAX · Week 1 · Day 2

JAX RandomnessExplicit Keys

In NumPy you just call np.random.normal() and numbers appear. In JAX you must carry around a "key" and pass it in by hand. Today: why JAX makes randomness explicit — and how to use it.

🎯
By the end, you'll be able to: create a random key, explain why reusing a key is a trap, split a key for fresh randomness, and use keys to initialize a tiny neural network.
1How does randomness work in JAX?What is it
🧭
What this assumes: basic Python/NumPy and Day 1 (immutability). If you've used np.random, you already know the thing JAX changes. No JAX randomness experience needed.

First, what is a PRNG?

Computers can't make truly random numbers. A PRNG (pseudo-random number generator) is a deterministic algorithm that, starting from a seed (a starting number), produces a long stream of numbers that look random. Same seed → same stream, every time.

How NumPy does it: a hidden global generator

In NumPy there's one hidden generator shared across your whole program. Each call to np.random.normal() quietly advances its internal state, so you get a new number every time. Convenient — but that state is hidden mutable state, the exact thing JAX avoids (remember Day 1: JAX wants pure functions, no hidden side effects).

How JAX does it: you hold the key

JAX makes randomness explicit. You create a key (a tiny array) from a seed, then pass it into every random call:

📦
key = jax.random.PRNGKey(0)  →  jax.random.normal(key, (3,))
The same key always returns the same numbers. There is no hidden state — the key is the state, and you carry it yourself. (Newer JAX also writes this as jax.random.key(0).)

So what's today's catch?

Because the key fully determines the output, reusing the same key gives you the same numbers again — a subtle trap. To get fresh, independent randomness you must split the key into new keys. That's the whole skill for today.

📚
Official docs (optional, for after): JAX PRNG design note · jax.random API
😕
为什么这里容易卡住 · Why this trips people up: NumPy 里 np.random.normal() 直接给你数字，JAX 却要你手里攥着一个 key 到处传，感觉很啰嗦。In plain terms: people treat the key as annoying boilerplate and quietly reuse the same one — not realizing that the key is the randomness, so reusing it hands you the identical "random" numbers with no warning.
2A key is a ticket that decides your dice rollsIntuition

Picture a random draw as a sealed ticket. The ticket fully decides which "random" numbers you'll get when you cash it in.

🎲
NumPy = dice on the table

One shared pair of dice sits on the table. Everyone rolls them, and they keep moving. You don't manage them — but the state is shared and hidden.

🎫
JAX = you hold the ticket

You hold a ticket (the key). Same ticket → same numbers, on any machine. Want a different draw? You don't re-cash the same ticket — you split it into new tickets.

In one line: NumPy hides and auto-advances the randomness; JAX hands it to you as a key, and you split keys to move forward.

直觉 / Intuition: key 就像一张"决定了骰子点数的票" — 同一张票永远开出同样的点数。The technical point is that the key fully determines the draw, so to get fresh, independent randomness you must split the key rather than call twice with the same one.

⚠️
Where the analogy breaks: tickets aren't "used up," and splitting is fully deterministic — splitting the same key always yields the same new keys. Nothing is actually random about the bookkeeping.

4The three calls you need, and why JAX bothersHow & why

The whole API for today is three calls

  • key = jax.random.PRNGKey(seed) — make a key from an integer seed.
  • jax.random.normal(key, shape) — draw numbers. (Also uniform, randint, ...) Same key + same shape → same numbers.
  • key, subkey = jax.random.split(key) — turn one key into two fresh, independent keys. Use one now, keep one for next time. split(key, n) gives n keys.
⚠️
The #1 beginner bug: calling random.normal(key) twice with the same key. You get the same numbers, so your "random" draws are secretly identical (correlated). Always split before drawing again.

Why does JAX make you do this?

Two payoffs:

  • Purity — no hidden global state means random functions are pure, so the compiler can safely jit, vmap, and parallelize them (this is Day 1's lesson again).
  • Reproducibility — the same key gives the same numbers on every run and every machine. For ML research, being able to reproduce an experiment exactly is priceless.
🔗
Causal chain: explicit keys → no hidden state → pure & reproducible → safe to compile, batch, and run on many devices deterministically.

The staff lens — one silent failure, one trade-off

Explicit keys buy you purity and reproducibility, but the same "the key is the randomness" rule hides one trap, and it costs you some bookkeeping.

⚠️
Failure mode (silent): correlated randomness from a reused key. Reusing a key does not error — random.normal(key, ...) happily returns numbers. But the same key returns the same numbers. So if you initialize two layers with the same key, both layers start with identical weights; if you draw two "independent" noise samples from one key, they are perfectly correlated. Training still runs, the loss still drops a little, but the model quietly underperforms and results look strange. A senior engineer scans code review for a key that is passed into more than one random call without a split in between.
⚖️
Trade-off: manual key threading for reproducibility. NumPy's hidden global generator is convenient — you never think about state. JAX makes you carry and split keys by hand, which is more code and one more thing to get wrong. In exchange you get exact reproducibility across runs and machines, and randomness that is safe to jit, vmap, and shard across devices. The design-review question: is the extra key-threading worth being able to reproduce any experiment exactly? For research at scale, yes.
🎤
Say this in an interview: "JAX makes randomness explicit — you pass a key into every random call instead of relying on a hidden global generator, so the function stays pure and the run is bit-for-bit reproducible across machines; to advance you split the key. The nuance is the silent failure: reusing a key doesn't error, it returns the same numbers — so two layers initialized from one key get identical weights, and 'independent' noise samples come out perfectly correlated. Training still runs; the model just quietly underperforms."

7Build a tiny neural net's weights with split keysProduce

Today's task (straight from the curriculum): write a small MLP forward pass in raw jax.numpy, with weights initialized from split keys. An MLP (multi-layer perceptron) is just a few matrix multiplies with a nonlinearity between them.

Acceptance criteria

  • Start from one key = random.PRNGKey(0), then split it into one key per layer.
  • Initialize W1, W2 from those separate keys (so layers don't share the same random values).
  • A forward(x) that computes tanh(x @ W1 + b1) @ W2 + b2 and prints the output shape.
  • Run it twice — confirm you get identical output (reproducible).
