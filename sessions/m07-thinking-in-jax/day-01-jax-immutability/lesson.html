Phase 1 · Week 1 · Day 1 (Mon)

JAX Immutability
The Immutable Array

The first thing that trips up almost everyone new to JAX: x[0] = 99 works fine in NumPy, but throws an error in JAX. Today we'll understand exactly why — and why it's actually a feature.

🎯 By the end, you'll be able to: explain in one sentence why JAX arrays can't be edited in place, and write the correct way to "change" one.
1 · WHAT IS ITFirst, what exactly is JAX?✓
🧭
What this assumes: a little Python and NumPy (you know what x = np.array([1,2,3]) and x[0] are). No JAX experience needed — we start from zero.

What is JAX?

JAX is a Python library from Google for high-performance array math. It's best known for two things:

  • It runs your array computations automatically on GPUs/TPUs (an accelerator = a chip built for large-scale math), so they're very fast;
  • It does automatic differentiation (autodiff — the engine behind training neural networks). We won't need this today, so set it aside.

How does it relate to NumPy?

Here's the key idea: JAX ships a module called jax.numpy that is almost a clone of NumPy — mostly the same function names and usage. So almost all of your NumPy intuition carries straight over. By convention you import it and call it jnp:

📦
import jax.numpy as jnp
From now on, read jnp.array(...) as "the JAX version of np.array(...)."

So what's today's catch?

JAX deliberately differs from NumPy in a few places. The first one — and the one newcomers hit most — is this: a JAX array cannot be modified in place. In NumPy, x[0] = 99 is routine. In JAX, that exact line throws an error.

Why would JAX be so awkward on purpose? That's today's puzzle. Keep going 👇

2 · INTUITIONWhiteboard vs. photo: a picture you won't forget✓

Before any code, lock in a mental picture. To mutate means: change the contents of an object in place, without making a new one.

📝
NumPy = whiteboard

Want to change a number? Erase it and write a new one. It's still the same board — only the contents changed. That's mutation (mutable).

📷
JAX = printed photo

Once a photo is printed, you can't edit it. Want something different? Print a new one; the original is untouched (immutable).

In one line: NumPy changes the array in place; JAX leaves the old array untouched and hands you a new one.

⚠️
Where the analogy breaks: a photo is "expensive to reprint," but creating a new JAX array is actually cheap — the compiler optimizes the waste away. The analogy only carries the "can't edit in place" part.

4 · FIX & WHYThe correct way to "change" one — and why JAX is designed this way✓

The fix: .at[ ].set( )

Since you can't write x[0] = 99, JAX gives you a replacement syntax called a functional update:

✅
y = x.at[0].set(99)
Read it as: "based on x, set position 0 to 99, producing a new array y." The original x does not change at all.

Why is JAX this "awkward"?

Because arrays are immutable, every computation in JAX becomes a pure function: the same inputs always give the same output, and it never secretly changes anything outside itself (no side effects).

Pure functions have a huge payoff: JAX's compiler (called XLA — a program that automatically makes your code fast) can safely reorder operations, fuse them together, and split them across many chips to run in parallel. If arrays could be edited in place, the compiler wouldn't dare — it couldn't guarantee that changing one thing won't quietly affect another.

🔗
Remember this causal chain: immutable → pure functions → the compiler can safely optimize → it runs fast on GPUs/TPUs. No purity, no speed.

(jit and vmap, coming later this week, both build on this chain — we'll leave them for now.)

The staff lens — one silent failure, one trade-off

Immutability protects you loudly (it errors on x[0] = 99), but there is one way it can go quietly wrong, and one cost you pay to get its speed.

⚠️
Failure mode (silent): a bug that doesn't announce itself — the dropped update. When you write x.at[0].set(99), JAX builds a new array and returns it. If you forget to catch it — you write x.at[0].set(99) on its own line instead of x = x.at[0].set(99) — the code runs with no error at all. The new array is created and thrown away; x still holds its old values. Nothing crashes; your update just silently vanished, and later math uses stale numbers. A senior engineer scans code review for any .at[...].set(...) whose result is not assigned back to a variable.
⚖️
Trade-off: extra copies for safe optimization. Because JAX cannot edit in place, every "change" conceptually makes a fresh array instead of overwriting one — that is more memory traffic than NumPy's in-place edit. In exchange, the compiler gets the purity guarantee it needs to reorder, fuse, and parallelize the whole computation. The design-review question is: do you want the freedom for XLA to make the whole program fast, or the freedom to hand-tune one in-place edit? For accelerators, the whole-program win is almost always worth the copies — and the compiler often optimizes the extra copy away anyway.
