Module 5 · Train · Day 3

The Mini-Batch Loop
& Overfit-One-Batch

You have a forward pass and a hand-wired backward pass. Now you need to run them over 60,000 images without waiting all day. The trick is the mini-batch: update on a small handful at a time. And before you trust a long training run, there is one quick test that catches almost every wiring bug — try to overfit a single batch.

🎯 By the end, you'll be able to: explain why mini-batch SGD is faster and smoother than using one example or the whole set, and run the overfit-one-batch sanity check to prove your training code works.
1 · WHAT IS ITUpdating on small handfuls, and a fast sanity check✓
🧭
What this assumes: the forward pass (M2), the hand-wired backward pass (Day 2), and the update step W = W − lr·dW from gradient descent (M3 Day 3). Today wraps them in a loop and adds a way to test it.

The choice: how much data per update?

Each weight update needs a gradient. You could compute that gradient from one example, from the whole 60,000, or from a small group in between. A mini-batch is that middle choice — say 32 or 64 images at a time.

Mini-batch SGD

SGD means you take a step after each mini-batch instead of waiting to see everything. Small batches are fast (you update often) and smoother than single examples (averaging a few gradients cancels out some of the random noise).

The one-line bug catcher

Before a long run, take a single small batch and train only on it. Correct code can drive the loss to nearly zero — the model just memorizes those few examples. This is the overfit-one-batch test. If the loss will not drop, your wiring is broken — stop and fix it. Keep going 👇

2 · INTUITIONStudying a handful of flashcards at a time✓
🃏
A handful, not the whole deck

You could study one card, then adjust — but one card is noisy, and you might over-react to it. You could study all 60,000 before adjusting — but that is slow. Grab a handful of, say, 32, get their average lesson, then adjust. Repeat.

🎯
The wiring test

Before a big study session, prove you can learn: take 8 cards and drill only those until you get every one right. If you cannot, your study method is broken — not your effort.

In one line: update on small handfuls to stay fast and steady, and use a single handful you can memorize as a quick test that the whole machine works.

⚠️
Where the analogy breaks: a student who memorizes 8 cards has learned nothing useful, and that is bad. But in the overfit-one-batch test, memorizing is exactly the goal — reaching near-zero loss proves the forward, backward, and update code all connect.

4 · MECHANISM & WHYBatch size, the loop, and why the sanity check works✓

Step 1 — the loop in plain words

Shuffle the data, cut it into batches, and for each batch do the same four steps you already know: forward pass, loss, backward pass, update. When you finish all the batches, that is one epoch. Shuffle and repeat for several epochs.

Step 2 — the numbers

🧮
for epoch in range(num_epochs):
  shuffle(data)
  for X_batch, y_batch in batches(data, size=32):
    probs = forward(X_batch) # M2
    loss = cross_entropy(probs, y_batch) # M3 D1
    grads = backward(...) # Day 2
    W -= lr * grads # M3 D3

Symbols: num_epochs = how many full passes, size=32 = the batch size, lr = the learning rate (step size). The gradient from a batch of 32 is the average of 32 per-example gradients — which is why it is steadier than a single one.

Step 3 — a worked feel for batch size

60,000 images with batch size 32 gives 1,875 updates per epoch. Batch size 1 gives 60,000 tiny, noisy updates — slow and jumpy. Batch size 60,000 (the whole set) gives one very smooth update per epoch — but it barely moves and wastes memory. Sizes like 32–256 sit in the sweet spot: enough averaging to be smooth, enough updates to learn fast.

Why the overfit test is so trusted

A model with thousands of weights has more than enough capacity to memorize a handful of examples. So if you train on 8 examples and the loss cannot reach near zero, the fault is not "hard data" — it is a bug: a wrong transpose in the backward pass, an update with the wrong sign, or a learning rate of zero. This one test catches most training bugs in seconds instead of hours.

🔗
Golden rule: overfit one batch first. Only after the loss hits near zero on that batch do you unleash the full multi-epoch run. Even labs training giant models start every new setup this way.

The staff lens — one silent failure, one trade-off

The loop has one line that looks optional but isn't — and one number, the batch size, that trades speed for smoothness.

⚠️
Failure mode (silent): forgetting to shuffle before batching. This is a bug that doesn't announce itself. If the data is stored in order (all the 0s, then all the 1s, …) and you skip the shuffle(data) line, every batch contains almost one digit. The code runs, the loss even falls, but each update yanks the model toward the current batch's single class, then the next batch yanks it back — it never settles, and test accuracy stays low. Nothing errors. A senior engineer in code review checks that the data is shuffled every epoch before it is cut into batches, and is suspicious of a training loss that jumps around instead of trending down.
⚖️
Trade-off: batch size — speed vs. gradient noise. A small batch (say 8) gives many fast, noisy updates; a large batch (say 4096) gives few, very smooth updates that use the hardware well but move little per step and eat memory. In a design review you pick a size (often 32–256) that balances enough averaging to be stable against enough updates to learn quickly — and you remember that changing the batch size usually means re-tuning the learning rate.
