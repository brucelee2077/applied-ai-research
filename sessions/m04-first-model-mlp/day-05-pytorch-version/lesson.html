What PyTorch is

PyTorch is a library for building and training neural networks. It gives you three things you built by hand this week, ready-made.

The three pieces

  • nn.Module — you define the layers and the forward pass; it holds the weights.
  • autograd — you call loss.backward() and it computes every gradient for you (your whole Day 2, automated).
  • optimizer from torch.optim — optimizer.step() applies the update (your Day 3 update, automated).

The same loop, far shorter

The training loop keeps the exact shape you already know: forward, loss, backward, update. In PyTorch it is three short calls: loss = criterion(model(x), y), loss.backward(), optimizer.step() — plus optimizer.zero_grad() to reset. Keep going 👇

4 · MECHANISM & WHYThe three pieces, and the loop line by line✓

Step 1 — the model, in plain words

You subclass nn.Module. In __init__ you list the layers; in forward you say how data flows through them. PyTorch reads the layers and stores their weights for you — no more writing W1 = np.random.randn(...) by hand.

🧮
class MLP(nn.Module):
  def __init__(self):
    super().__init__()
    self.fc1 = nn.Linear(784, 128) # = W1,b1
    self.fc2 = nn.Linear(128, 10) # = W2,b2
  def forward(self, x):
    x = torch.relu(self.fc1(x)) # = relu(x@W1+b1)
    return self.fc2(x) # logits (no softmax)

Note: no softmax in forward. PyTorch's nn.CrossEntropyLoss folds softmax inside, which is more numerically stable than doing it separately.

Step 2 — the loop, symbol by symbol

🧮
optimizer.zero_grad() # clear old gradients
outputs = model(inputs) # forward pass
loss = criterion(outputs, labels) # cross-entropy
loss.backward() # autograd fills every .grad
optimizer.step() # apply W -= lr * grad

Symbols: criterion = the loss object (nn.CrossEntropyLoss()), optimizer = the update rule (e.g. optim.SGD(model.parameters(), lr=0.01)), .grad = each weight's gradient. loss.backward() replaces your entire hand-wired Day-2 backward pass; optimizer.step() replaces your Day-3 W -= lr*dW.

Step 3 — why zero_grad?

PyTorch adds new gradients onto whatever is already stored. In your NumPy code you computed gradients fresh each batch, so this never came up. In PyTorch you must call optimizer.zero_grad() first, or batch 2's gradient piles on top of batch 1's and the update is wrong. Forgetting it is the most common beginner bug.

The point: the framework did not invent new ideas. It automated the exact three things you built by hand — that is why you learned them first.

The staff lens — one silent failure, one trade-off

PyTorch's convenience hides a piece of state you now have to manage yourself: gradients that quietly add up unless you clear them.

⚠️
Failure mode (silent): forgetting optimizer.zero_grad(). This is a bug that doesn't announce itself. PyTorch adds each new .backward() onto whatever gradient is already stored. In your hand-written NumPy code the gradient was fresh every batch, so this never came up — but in PyTorch, if you skip zero_grad(), batch 2's gradient piles on top of batch 1's, batch 3 on top of that, and the update steps grow far too large. No error prints; the loss just explodes to NaN or refuses to fall. The same class of bug is forgetting model.eval() before evaluation, which leaves dropout on and quietly lowers test accuracy. A senior engineer in code review checks that every training step starts with zero_grad() and that evaluation switches to model.eval().
⚖️
Trade-off: framework convenience vs. hidden state. loss.backward() and optimizer.step() save you from ever hand-wiring a gradient again, which is a huge win. What you pay is that the framework now holds state you cannot see — accumulated .grad buffers, train-vs-eval mode, the autograd graph. In a design review the framework is the obvious choice for anything real, but the team treats "manage the hidden state correctly" (zero_grad, eval, no_grad) as a required checklist, not an afterthought.
