The Backward PassWired by Hand

Yesterday your MLP made a guess. Today you teach it to fix that guess. You will compute the gradient — the "which way to nudge each weight" signal — layer by layer, using the chain rule. You will wire dL/dW for every layer of the 784→128→10 MLP by hand, and then check your work against a slow-but-honest numerical gradient.

🎯
By the end, you'll be able to: walk the gradient backward through a 2-layer MLP with the chain rule, write dL/dW1 and dL/dW2, and verify them against a numerical gradient.
1Computing the fix for every weightWhat is it
🧭
What this assumes: the forward pass h = relu(x@W1+b1), logits = h@W2+b2 (M2), the cross-entropy loss (M3 Day 1), and that a gradient tells you which way to nudge a weight (M3 Day 2). Today we compute those gradients ourselves.

The one question the backward pass answers

For every single weight in the model, ask: "if I nudge you a tiny bit, how much does the loss change?" That answer is the gradient. The backward pass (also called backpropagation) computes all of them in one sweep from the output back to the input.

Why "backward"?

The loss lives at the very end of the forward pass. To know how an early weight affects the loss, you have to trace its effect through every later step. So you start at the loss and walk backward, step by step, carrying the blame with you. That tool for chaining the steps together is the chain rule.

The check that keeps you honest

Hand-wired gradients are easy to get subtly wrong. So you compare them to a numerical gradient — nudge a weight, watch the loss, divide. If the two match, your wiring is correct. Keep going 👇

2Passing the blame down a line of workersIntuition
🏭
An assembly line

Worker 1 hands a part to Worker 2, who hands it to Worker 3, who ships it. The final product is wrong. Someone made a mistake — but who, and how much?

📣
Blame flows backward

The manager tells Worker 3 "you were off by this much". Worker 3 works out how much of that came from the part Worker 2 gave them, and passes that share of blame back. So does Worker 2 to Worker 1.

In one line: each layer takes the blame it received from the layer after it, keeps its own share, and passes the rest further back — that passing-back is the chain rule.

Your forward pass is the assembly line: x → layer 1 → h → layer 2 → logits → loss. The backward pass sends the blame the other way: loss → layer 2 → h → layer 1 → x. At each layer, the blame it holds tells it exactly how to fix its own weights.

⚠️
Where the analogy breaks: real workers each pass blame once, but the same intermediate value (like h) can feed many later steps. The chain rule handles that by adding up all the blame that flows back through it — a worker can be blamed by several people at once.

4The chain rule, wired for our two layersMechanism & why

Step 1 — in plain words

The forward pass is a chain: logits = (relu(x@W1+b1)) @ W2 + b2, then softmax and cross-entropy give the loss. To find how W1 affects the loss, multiply together the small effects along the chain: how the loss depends on the logits, how the logits depend on h, how h depends on W1. That multiplying-along-the-chain is the chain rule.

Step 2 — the formulas, symbol by symbol

A lovely fact makes the start simple: for softmax + cross-entropy, the blame at the output is just predicted probabilities minus the true one-hot label. Everything else falls out of it.

🧮
dlogits = probs − y_true # shape (10,) — the starting blame
dW2 = h.T @ dlogits # (128,1)@(1,10) → (128,10)
db2 = dlogits # (10,)
dh = dlogits @ W2.T # (1,10)@(10,128) → (128,) — blame handed to layer 1
dz1 = dh * (z1 > 0) # ReLU gate: blame passes only where z1 was positive
dW1 = x.T @ dz1 # (784,1)@(1,128) → (784,128)
db1 = dz1 # (128,)

Symbols: probs = softmax output (10 numbers), y_true = one-hot true label, h = the hidden activations, z1 = x@W1+b1 = the pre-ReLU values, W2.T = the transpose of W2. Every d… is "loss's sensitivity to that thing". Notice the pattern: each layer's dW is its input, transposed, times the blame flowing into it.

Step 3 — a worked example (tiny numbers)

Say the true digit is class 0, so y_true = [1, 0, 0, …], and softmax gave probs = [0.7, 0.2, 0.1, …]. Then dlogits = probs − y_true = [-0.3, 0.2, 0.1, …]. The -0.3 on the true class says "push this logit up"; the positives say "push those down". Feed that into dW2 = h.T @ dlogits and you get one gradient number per weight in W2. The ReLU gate (z1 > 0) then zeroes out blame for any hidden unit that was switched off.

Why this is the whole game

Every deep network — including a giant LLM — learns with exactly this backward sweep: start with probs − y_true, then repeat "transpose the input, multiply the blame" through each layer, gating at each nonlinearity. Tomorrow you will run it in a loop over mini-batches.

🔗
The check: a numerical gradient nudges one weight by a tiny ε, measures (loss(W+ε) − loss(W−ε)) / (2ε), and should match your hand-wired dW to several decimal places. If it doesn't, a transpose or a gate is wrong.

The staff lens — one silent failure, one trade-off

A hand-wired backward pass is where wrong gradients hide — the arithmetic still runs, so nothing tells you the math is off.

⚠️
Failure mode (silent): a wrong gradient that still runs. This is a bug that doesn't announce itself. If you write dW2 = dlogits @ h.T instead of h.T @ dlogits, or forget the ReLU gate (z1 > 0), or flip a sign, the shapes can still line up and the code runs with no error. But the gradient points in the wrong direction, so training crawls, wanders, or the loss slowly rises. There is nothing to see in the output. A senior engineer never trusts a hand-wired backward pass without a code-review gradient check: nudge one weight by a tiny ε and confirm (loss(W+ε) − loss(W−ε)) / (2ε) matches your dW to several decimals before running any real training.
⚖️
Trade-off: hand-wiring gradients vs. automatic differentiation. Deriving each dW by hand teaches you exactly how learning works and lets you optimize a specific layer, but it is slow to write and easy to get subtly wrong. A framework's autograd (M5 later) computes gradients for you and is almost never wrong, at the cost of hiding the mechanism. In a design review the call is clear for anything real: use autograd and keep the hand-derivation for understanding and for the rare custom kernel where you must.
