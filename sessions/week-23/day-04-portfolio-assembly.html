1 · WHAT IS ITWhat is a portfolio repo, a README, and a CI badge?✓
🧭
What this assumes: you can use a terminal and you have a GitHub account. No prior knowledge of GitHub Actions, READMEs, or CI needed — we define every word before we use it.

Three new ideas, defined before use

1 · A portfolio repository. A GitHub repository is a folder of your code that lives on GitHub's servers, tracked by git (git is the tool that records every change you make). A portfolio repo is a repository whose main job is not to run in production, but to show your work to a human reader. Its most-read file is the README.md: a Markdown file (plain text with light symbols — # for a heading, - for a bullet, backticks for code) that GitHub turns into a formatted front page. The README is your storefront window: most visitors read it and nothing else.

2 · A profile README. This is a special repository whose name is exactly your username. If your username is octocat, you make a repo literally named octocat. GitHub takes that repo's README.md and pins it to the top of your profile page. It is the one README a recruiter sees before they even open a single project.

3 · GitHub Actions. This is GitHub's built-in automation. You put a YAML file (YAML is a config format that uses indentation and key: value) under .github/workflows/. On events you choose — most often on: push (every time you upload code) — GitHub spins up a fresh, clean virtual machine, runs your listed commands (install, test, lint), and reports pass or fail. The visible payoff is a status badge: a small green build: passing image you embed in the README. That badge says "a clean machine ran my code today and it worked" — far more credible than "trust me, it runs."

Why all this exists

Code that only lives on your laptop is invisible and unverifiable. A portfolio repo makes it findable. A README makes it understandable. A CI badge (CI = Continuous Integration = automatically building and testing on every change) makes it trustworthy. And unlisted videos let you show the running system without a public splash.

🎬
Unlisted (YouTube): anyone with the link can watch, but the video never appears in search and is not listed on your channel. Perfect for linking from a README you control.

4 · HOW & WHYThe rules of a trusted portfolio, and why it works✓

The rules

  • One repo, one front door. All 24 weeks live as folders inside a single repository. Every week is either a folder or is explicitly linked from the README — no orphan weeks.
  • The README sells in 30 seconds. It opens with a one-line title, a "what I built" paragraph, a copy-pasteable Quickstart (clone + install + run one demo), a results table linking each week, and a "Demo videos" section.
  • CI runs on the branch you push. ci.yml triggers on: push to your real branch (often main, not master), then installs deps and runs at least one test or lint step on a clean machine.
  • The badge URL must match the workflow file. The badge Markdown points at your actual workflow so it reflects the latest run — not an old, stale green.

Why it works

  • Findable — one repo means a recruiter never has to hunt across scattered gists or laptops. The profile README points straight at it.
  • Understandable — the README is a storefront window; 80% of visitors read it and nothing else, so it does the selling.
  • Trustworthy — the CI badge is independent, reproducible proof. A clean machine re-earns your credibility on every push, which beats "trust me, it runs."

7 · PRODUCEAssemble the master portfolio repo✓

Today's task: gather all 24 weeks of code into one public-facing repo with a flawless README.md, unlisted YouTube demo links, and a green GitHub Actions CI badge — plus a profile README pointing to it.

⚠️
The classic mistake: adding the build: passing badge Markdown before a working workflow exists. The badge then renders "no status" — or worse, stays green from an old run while main is actually broken because CI only runs on branches you configured. Fix: trigger on: push to the branch you really push (often main, not master), run the exact CI commands locally first (Playground step 2), and confirm with gh run list --limit 1 that the LATEST commit shows "completed success." A green badge that does not match your current HEAD is worse than no badge — it looks like a lie when a reviewer clicks it.

Acceptance criteria

  • README.md renders with a one-line title/tagline, a "What I built" paragraph, a copy-pasteable Quickstart (clone + install + run one demo), a results table linking each week, and a "Demo videos" section.
  • README top shows a GitHub Actions badge whose Markdown URL matches the actual workflow file name, and it reads "passing".
  • .github/workflows/ci.yml exists, triggers on: push, runs at least install + one test/lint step; gh run list --limit 1 shows STATUS "completed success".
  • All 24 weeks appear as folders or are explicitly linked from the README (grep for each week label → 24 hits, none missing).
  • Every demo video is Unlisted on YouTube; each URL opens without a login and is not findable via search.
  • ruff check . exits 0 across the repo; no secrets, keys, large binaries, or copyrighted PDFs committed; .gitignore present.
  • A separate profile README repo (named exactly your username) links to frontier-portfolio as the featured project.
