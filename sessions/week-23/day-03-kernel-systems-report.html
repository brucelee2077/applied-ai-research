Phase 4 · Week 23 · Day 3 (Wed) · Kernel Systems Capstone

Kernel Systems Report
Pallas & the Roofline

A kernel can be "faster" and still leave 90% of the chip idle. Today you learn the two memories on a GPU/TPU, why big chips starve waiting for data, and how to prove a hand-written Pallas kernel wins — with a roofline, byte counts, and a correctness check.

🎯 By the end, you'll be able to: compute a chip's roofline ridge point, classify an op as memory-bound or compute-bound, size a Pallas kernel's tiles against the SRAM budget, and write a systems report where every speedup claim is tied to a number.
1 · WHAT IS ITTwo memories, FLOPs, kernels, Pallas, and the roofline✓
🧭
What this assumes: you can read Python and you know a matrix multiply is lots of multiply-and-add. No hardware or kernel experience needed — we start from the chip.

Start with the hardware: two kinds of memory

A GPU or TPU has two very different memories. HBM (High Bandwidth Memory) is large — tens of gigabytes — but it sits far from the compute units, so reaching it is slow. SRAM (the on-chip scratchpad, called "shared memory" on GPUs) is tiny — tens to hundreds of kilobytes per core — but it is right next to the math units, so it is extremely fast.

The compute units do FLOPs (Floating-Point Operations — the multiply-and-add math). One FLOP is one such operation. A chip is rated in FLOP/s (FLOPs per second).

The key problem: math is way faster than memory

Modern chips do math far faster than they can fetch data. An NVIDIA H100 does about 990 TFLOP/s of bf16 math but only about 3.35 TB/s of HBM bandwidth. That is roughly 295 FLOPs of math budget for every byte you move from HBM. So if an operation reads a lot of data but does little math per byte, the compute units sit idle waiting for memory. We call that memory-bound. If it does lots of math per byte, it is compute-bound.

Arithmetic intensity is the ratio (FLOPs done) / (bytes moved from HBM). It tells you which regime you are in.

Kernels, Pallas, and fusion

A kernel is a single program that runs on the accelerator to compute one operation (a matmul, or attention). By default, frameworks run many small kernels back-to-back, and each one reads its inputs from HBM and writes its outputs back to HBM. That round-trip is the bottleneck for memory-bound work.

Pallas is a JAX extension that lets you write your own kernel in Python/JAX-like code. You decide which tiles (blocks) of data to load into SRAM, do all the math on them there, and only write the final result back to HBM. Doing several math steps in one kernel so intermediate results never touch HBM is called kernel fusion. Pallas runs on both GPU (via Triton / Mosaic-GPU) and TPU (via Mosaic).

FlashAttention is the famous example: it fuses the whole attention computation into one tiled kernel, so the giant N×N score matrix is never written to HBM — exact attention with far fewer reads/writes and 2–4× wall-clock speedups. ThunderKittens is a newer framework showing a few tile-level abstractions can match or beat hand-written kernels.

Roofline: the tool that proves a kernel is good

Plot achieved FLOP/s against arithmetic intensity. There is a sloped memory roof (bandwidth × intensity) and a flat compute roof (peak FLOP/s). Your kernel sits under both. On the sloped roof → bandwidth-limited (fix: move fewer bytes). On the flat roof → you are done. For a MoE (Mixture of Experts — each token is routed to only a few of many expert sub-networks), the naive version wastes bandwidth on gather/scatter and small padded matmuls; a good Pallas kernel keeps expert weights and grouped tokens resident in SRAM, pushing intensity toward the compute roof.

2 · INTUITIONA professional kitchen: the freezer and the counter✓

Picture a busy restaurant kitchen. The walk-in freezer at the back is huge and holds everything — but every trip there costs the chef a long walk. The small counter right next to the stove is tiny and fits only a few ingredients — but the chef can grab from it instantly. The chef's hands are blazing fast.

🚶‍♂️❄️
naive kernel = walk to the freezer for every step

Grab one ingredient, cook one step, walk back to store the half-finished dish, walk again for the next ingredient. The hands are lightning-fast but idle most of the time — this chef is bandwidth-bound.

🍳🗒️
Pallas kernel = plan the trips

Grab a whole tray in one trip, keep it on the counter, do every chopping and cooking step there, then make one trip back with the finished plate. Same food, far fewer walks. FlashAttention never stores the half-finished "score matrix" in the freezer.

The mapping: the freezer is HBM (big, slow, far). The counter is SRAM (tiny, fast, close). The hands are the compute units. FLOP/s is how fast the chef chops and cooks; bandwidth is how fast ingredients arrive from the freezer.

⚠️
Where the analogy breaks: a real chef can improvise and reorder freely, but a kernel author must fit inside a fixed, tiny SRAM budget and a rigid tile schedule decided before cooking starts. Load too big a tray and it does not fit on the counter (SRAM overflow / spills) — which is worse than not planning. The counter size is a hard hardware limit, not a suggestion.

4 · HOW & WHYThe rules of the roofline, and why bytes beat math✓

The rules

  • The ridge point is peak FLOP/s ÷ HBM bandwidth. For an H100: 990e12 ÷ 3.35e12 ≈ 295 FLOP/byte. Below it → memory-bound; above it → compute-bound.
  • Arithmetic intensity = FLOPs done ÷ bytes moved from HBM. Compute it for your op and compare to the ridge point.
  • Attainable FLOP/s = min(peak, bandwidth × intensity). If you land on the sloped memory roof, adding more math does not help — you must move fewer bytes.
  • Tiling loads a block of data into SRAM and reuses it many times. Fusion keeps intermediate results on-chip so they never round-trip to HBM. Both raise intensity.
  • The SRAM budget is a hard cap (e.g. ~228 KB/SM on H100). Your tiles (A + B + accumulator) must sum below it, or the kernel spills back to HBM and gets slower.
✅
Naive MoE gemm: intensity ≈ 12 FLOP/byte → attainable = min(990e12, 3.35e12 × 12) ≈ 40e12 = only ~4% of peak.
A fused Pallas kernel keeps gathered tokens and expert weights in SRAM, cutting HBM bytes ~17× and pushing intensity toward 295 → toward the compute roof.

Why bytes beat math (and the trap)

  • The chip is starving. With ~295 FLOPs of budget per byte, a low-intensity op leaves the compute units idle. Fewer bytes → higher intensity → more of the chip working.
  • Wall-clock time alone lies. A kernel can be "faster" and still leave 90% of the chip idle. Always convert to the roofline: intensity and % of peak FLOP/s.
  • Correctness is non-negotiable. Fused/tiled kernels (online-softmax attention, reduced-precision MoE accumulation) can silently change numerics. A speedup with wrong outputs is worthless — check max-abs-error against the reference.
🔗
Causal chain: two memories with a huge speed gap → most ops are memory-bound → tiling + fusion keep data in SRAM → intensity rises toward the ridge point → the marker climbs the roofline toward peak FLOP/s → the report proves it with byte counts, not adjectives.

7 · PRODUCEWrite the MoE Pallas Kernel systems report✓

Today's task: turn a MoE building block into a hand-tuned Pallas kernel and write a systems report that argues, with numbers, why it beats the reference implementation through better SRAM reuse and higher FLOP utilization. The report must be backed by a small reproducible benchmark (baseline vs Pallas kernel).

Acceptance criteria

  • State target hardware and peak specs (peak FLOP/s, HBM bandwidth) and compute the roofline ridge point.
  • Baseline: measured latency, achieved FLOP/s (% of peak), HBM bytes moved, and arithmetic intensity — with the roofline marker shown as memory-bound.
  • Kernel design: explicit tile shapes (M, K, N) and a SRAM budget calculation in KB proving the tiles fit under the per-SM limit; state what is fused so intermediates stay on-chip.
  • After: same metrics for the Pallas kernel, marker moved toward the compute roof; report the HBM-byte reduction factor and achieved-FLOP/s improvement.
  • A speedup table (baseline vs Pallas) with wall-clock speedup, plus a correctness check (max abs error vs reference below a stated tolerance).
  • Every speedup claim tied to a specific number (byte count or roofline point), not prose. Include the run command(s); save raw output under results/. Include a before/after roofline figure (or clearly-labeled ASCII/table equivalent).
