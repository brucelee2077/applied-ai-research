Memory Economics
Synthesis

This week you met QuIP#, AQLM, and QTIP — three different ways to squeeze a weight down to 2-3 bits. But why is squeezing weights worth the trouble at all? Today you go back to the roofline model from Week 2 and prove, with the same AI = FLOPs / bytes arithmetic, that a single LLM decode step is so starved for memory bandwidth that spending extra compute to unpack tiny codebooks is essentially free.

🎯 By the end, you'll be able to: compute the arithmetic intensity of a decode-step matmul at fp16, int8, and ~2-bit precision, show all three sit deep in the memory-bound region of an H100 roofline, and explain in one sentence why fetching fewer bytes beats fetching uncompressed weights even after paying a dequantization compute tax.
1 · WHAT IS ITWhat is "memory economics", and why does it need its own day?✓
🧭
What this assumes: Week 2's roofline model (arithmetic intensity, ridge point, compute-bound vs. memory-bound) and this week's quantization algorithms (QuIP#, AQLM, QTIP — Days 3-4, shrinking weights to 2-3 bits). No new quantization algorithm today.

The question nobody answered yet

Days 3 and 4 this week showed you how to shrink a weight matrix to 2-3 bits per number — lattice codebooks, additive codebooks, trellises. Every one of those methods costs something: you have to decompress (dequantize) the packed bits back into real numbers before you can multiply them, which burns extra math on top of the matmul itself. Nobody yet asked the economics question: is that trade worth it? You are spending compute to save memory traffic — but only if compute is the thing you have to spare.

Memory economics, as used today, means exactly that trade: on real hardware, is a given operation sitting in a place where extra compute is nearly free and bytes-moved is expensive — or the reverse? If it is the first case, quantization is a strict win. If it is the second, all that codebook cleverness could actually make things slower.

The tool you already own: the roofline model

Week 2 gave you the answer key. Every operation has an arithmetic intensity (AI) — FLOPs done divided by bytes moved to and from memory — and every chip has a ridge point — the AI at which its peak compute and its peak memory bandwidth are equally the bottleneck. Below the ridge point, you are memory-bound: the chip's math units sit mostly idle, waiting on bytes. Above it, you are compute-bound: bytes arrive faster than the chip can chew through them.

🧮
AI = FLOPs / bytes_moved  ·  ridge = peak_FLOP/s / bandwidth
Same formulas as Week 2, Day 1. Today you plug in the numbers for one specific, extremely common operation: a single decode-step matmul, at three different weight precisions.

Today's specific target: one decode step

When an LLM generates text one token at a time (autoregressive decoding), each step multiplies a single activation row against a big weight matrix, say shape [d_model, d_ff]. That matmul does very little math per byte of weight it reads — each weight is read once, used in one multiply-add, and discarded. Compressing the weights doesn't change the FLOPs. It changes the bytes moved, which changes the AI, which — since decode already lives far below the ridge point — barely matters for the "am I memory-bound" verdict, but massively changes how long the memory stall actually takes.

2 · INTUITIONThe delivery truck that only carries a quarter as much✓

Week 2 used a kitchen with a delivery door and a team of chefs. Keep that picture, but change one thing about the deliveries.

🚚📦📦📦📦
fp16 = a full-size delivery truck

Every ingredient (weight) arrives at full size — 16 bits each. The chefs (compute units) are fast, but the door (memory bandwidth) can only let trucks through so quickly, and most trucks are full-size.

🚚📦
2-bit codebook = ¼-size deliveries + one extra chef step

Each delivery is now roughly a quarter the size (2 bits instead of 16 is 8x smaller; codebooks store a bit more overhead, so real gains land near that). One extra chef quickly "unpacks" each delivery into a usable ingredient before cooking — a small, fixed extra task.

In one line: if the door (memory bandwidth), not the chefs (compute), was always the bottleneck, shrinking every delivery and adding one small unpacking step per delivery is a pure win — the door was the limit either way, and now fewer, smaller trucks need to pass through it.

⚠️
Where the analogy breaks: unpacking isn't free — it is a real matmul-adjacent cost (a lookup or small matrix multiply per group of weights). The trade only wins because, in decode, the chefs were already sitting nearly idle. If the chefs were the bottleneck instead (compute-bound regime), adding unpacking work would make things slower, not faster.

4 · HOW & WHYWhy fewer bytes wins even after the dequant tax✓

The math for one decode-step matmul

  • A single-token activation of shape [1, d_model] times a weight of shape [d_model, d_ff] costs FLOPs ≈ 2 · d_model · d_ff (one multiply + one add per weight element).
  • Bytes moved are dominated by the weight matrix itself (the activation row is tiny by comparison): bytes ≈ d_model · d_ff · bytes_per_param.
  • bytes_per_param is 2 for fp16/bf16, 1 for int8, and roughly 0.25 (2 bits) for a QuIP#/AQLM/QTIP-style lattice codebook — an 8x drop from fp16 to 2-bit.
  • Since FLOPs stay fixed and bytes drop, AI = FLOPs / bytes rises as precision shrinks — but for a single decode-step matmul, AI stays far below the ~295 FLOP/byte ridge point at every one of these precisions. All three are memory-bound.
✅
latency_estimate ≈ bytes_moved / bandwidth  (when memory-bound, i.e. AI < ridge)
Because the FLOPs term never becomes the bottleneck here, the memory-bound branch of achievable = min(peak_FLOP/s, AI × bandwidth) is the one that governs latency — and it scales directly with bytes moved. Cut the bytes 8x, and the memory-bound latency estimate drops roughly 8x too.

Where the "dequant tax" fits in

Unpacking a lattice codebook or trellis entry back into real numbers adds a small, roughly fixed amount of extra compute per group of weights — nowhere close to filling the compute headroom that memory-boundedness leaves idle. That headroom is exactly peak_FLOP/s − (achieved memory-bound FLOP/s), and at decode-time AI it is enormous. Spending a sliver of it on dequantization while saving most of the memory traffic is a strictly good trade, as long as you stay memory-bound after adding the dequant FLOPs (you almost always do, by a wide margin).

Why this matters beyond quantization

  • It explains why decode-time quantization "just works" in production — vLLM, TensorRT-LLM, and similar serving stacks ship 4-bit and lower weight formats for exactly this reason: decode is memory-bound, so shrinking bytes shrinks latency almost for free.
  • It tells you when quantization stops helping — large-batch prefill or training matmuls have much higher AI (more reuse per byte) and can sit near or above the ridge point; there, the dequant tax can start to matter and the win shrinks or reverses.
  • It connects three separate weeks into one argument — Week 2's roofline math, Week 14's FlashAttention IO-awareness (also a "bytes moved is the real cost" argument, applied to activations instead of weights), and this week's quantization algorithms are all instances of the same underlying economics.
🔗
Causal chain: decode-step matmul has low AI (little reuse per weight byte) → it sits below the ridge point → it is memory-bound → achievable latency scales with bytes moved, not FLOPs → shrinking bytes (quantization) cuts latency almost directly, as long as the added dequant FLOPs don't push you past the ridge.
