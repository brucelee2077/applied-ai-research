The Cost of Attention

Attention reads every word against every other word. Double the text and you quadruple the work. Here is where long context gets expensive — and the trick that saves it.

Why does long context get so expensive?

You already know the core operation: every token compares itself against every other token. That sounds harmless for ten words. It is brutal for a hundred thousand.

Picture a party where every guest must shake hands with every other guest. With 5 guests that is about 10 handshakes. With 50 guests it is around 1,225. Add a few more people and the handshakes explode — far faster than the guest list grows.

🤝

Guests = tokens

Each token is a guest at the party. The sequence length we call n is the guest count.

💥

Handshakes = pairs

Every pair of tokens must be compared. The pairs grow with the square of the guest count.

🔁

Where it breaks

Real handshakes happen once. Attention redoes all the pairings at every layer of the network.

💡
The shape of the cost

Comparing every token to every other token is an O(n²) operation: the work grows with the square of the sequence length. This single fact drives almost every long-context engineering decision in modern language models.

Two objects, two very different growth rates

Inside an attention layer there are two memory objects that matter. One grows gently. One grows viciously. Telling them apart is the whole game.

📏
The token tensor — shape n × d — grows like O(n)

Each of the n tokens is a vector of length d (the model dimension). Add one token, add one row. Memory grows in a straight line.

🟥
The score matrix — shape n × n — grows like O(n²)

The materialized table of every-token-against-every-token. Add one token and you add a whole new row and a whole new column. Memory grows like the square.

Put real numbers on it. We will use fp16, where every number takes 2 bytes. This is the standard precision for the activations inside a running model.

n × d × 2 bytes Token tensor (fp16). n rows, each of width d, two bytes per number. Linear in n — this is the gentle one.
n × n × 2 bytes Score matrix (fp16). n rows by n columns, two bytes per number. Quadratic in n — this is the one that explodes.
📊
The ratio that tells the story

Divide the two: the score matrix is exactly n ÷ d times bigger than the token tensor. While n is smaller than d, the token tensor dominates. The moment n grows past d, the n × n matrix takes over — and from there it never looks back.

Watch the cost curves cross

This is the picture to keep in your head. Three memory-growth curves on log-log axes: the token tensor (n × d), the score matrix (n × n), and FlashAttention.

⚠️
Drag n and watch the wall appear

Slide n to the right. At first the token-tensor line sits on top. Then the n × n curve crosses above it and shoots past everything else — that crossing point is the long-context wall. Now tick the FlashAttention box: the n × n curve vanishes and a flat O(n) curve takes its place.

The 100×-per-10× rule

Here is the one number an interviewer wants to hear you reach for instantly. It falls straight out of the square.

1
Make the context 10× longer

Go from an 8,000-token prompt to an 80,000-token prompt. That is a 10× increase in n.

2
Attention memory grows ~100×

The n × n score matrix scales with n², and 10² is 100. So the attention memory balloons by roughly one hundred times.

3
Prefill compute grows ~100× too

The prefill pass does ~O(n²·d) FLOPs, so the work to read a 10× longer prompt also rises by about 100×.

💡
Long context is fundamentally a memory problem

The token tensor stays small. The n × n matrix is what you run out of room for first. So when someone asks "why can't this model just take a million tokens?", the honest first answer is not "not enough compute" — it is "not enough memory to hold all the pairwise scores."

FlashAttention: same answer, far less memory

FlashAttention is the trick that softens the wall. It is IO-aware: it organizes the work to avoid the expensive memory traffic, instead of changing the math.

🧮

Compute: unchanged

Still O(n²) FLOPs. The same number of multiply-adds. The exact same output, number for number.

📉

Memory: O(n)

It never builds the full n × n matrix. It walks through it in tiles, keeping only running totals — so attention memory drops to linear.

⚡

Why it is faster too

It keeps each tile inside fast on-chip memory and avoids round trips to slow HBM.

In production you rarely write the attention math by hand. You call one fused function, and the library uses a FlashAttention-backed kernel under the hood when it is available.

CODE 
import torch.nn.functional as F
# Fused, FlashAttention-backed when available. Does NOT materialize the n×n matrix.
out = F.scaled_dot_product_attention(q, k, v, is_causal=True)
PLAIN ENGLISH

Pull in PyTorch's bundle of ready-made neural-network operations and call it F.

A note for the reader: this one call is fused (the whole attention is done in a single optimized step) and uses FlashAttention when the hardware supports it — so it never writes out the full n × n score table.

Run attention on the queries, keys, and values in one go. is_causal=True means each token may only look back at earlier tokens, never ahead. The result out is the new, context-mixed representation — identical to the slow way, just computed without ever holding the giant matrix in memory.

That last line is the FlashAttention curve from the chart. Same output as the slow path, but the memory it uses is the flat O(n) line, not the exploding O(n²) one.

⚠️
Failure mode & the trade-off worth naming

The first wall you hit at scale is an OOM crash from the n × n matrix (and a growing KV cache, which the next module covers). FlashAttention saves memory IO but does not reduce FLOPs — your compute bill is unchanged. If you need to cut compute, that means sparse or sliding-window attention, which lower the work by approximating the result instead of computing every pair exactly.
